## Runtime-detection method

| Option | Description | Selected |
|--------|-------------|----------|
| Env-var / config-dir heuristic | Mirrors GSD's own ingest-docs RUNTIME=claude/codex/opencode pattern | |
| Parent-process name walk | Inspect process tree for ancestor CLI binary | |
| Both, combined for confidence | Env-var first, fall back to process-tree walk | ✓ (initial answer) |

**User's choice (initial):** "Both, combined for confidence"
**Notes:** Mid-discussion, the user (writing in Spanish) flagged that this whole
line of questioning had conflated two different things: install-target
selection (out of scope, existing wizard's job) vs. identifying which CLI is
currently hosting a running skill's process. The user proposed replacing the
assumed env-var/parent-process mechanism with an empirical research pass:
launch codex, opencode, cursor-agent, and claude as subprocesses, run a
diagnostic probe script under each, and observe what signal each actually
leaves available to a spawned child — deriving the real detection mechanism
from that, never assumed a priori. This correction **supersedes** the initial
"Both, combined for confidence" answer.

| Follow-up option | Description | Selected |
|--------|-------------|----------|
| Yes, empirical research first | Research pass with all 4 CLIs determines the real mechanism | ✓ |
| No, keep the already-chosen heuristic | Keep env-var/parent-process as final | |

**User's final choice:** Empirical research pass first, implementation derived from findings.

Also confirmed in the same area: no caching/TTL for `detect_current_runtime()`
(process-lifetime-fixed value, cheap to recompute); and installation
(`tools/install.sh`/`tools/setup.py`) stays explicitly out of scope for this
phase — the only install.sh change remains `--single-branch`.
