## Summary

This phase is three independent, small pieces of work, and the research effort was weighted accordingly: the git-clone flag change and the opencode report are close to done-in-research (their findings are the deliverable content); the runtime-detection function required genuine empirical work (live-spawning codex/opencode/cursor-agent/claude subprocesses per D-02) and turned up a real structural ambiguity in how the requirement's own acceptance text maps onto the actual codebase, which is documented as Open Question 1 below and must be resolved before task-level planning.

The single-branch installer change is real but behaviorally inert: git's own documentation confirms `--depth <n>` already implies `--single-branch` unless `--no-single-branch` is explicitly passed, and `tools/install.sh`'s current primary clone (`git clone --branch "$REPO_BRANCH" --depth 1 "$url" "$INSTALL_DIR"`) already carries `--depth 1` with no override. Adding the literal `--single-branch` flag changes zero fetched-ref behavior; it is worth doing anyway for explicitness (the intent no longer depends on an unstated git default a future contributor could break by adding `--no-single-branch` or dropping `--depth`), but the test the requirement calls for must assert the flag's literal presence in the invoked command line — there is no observable ref-fetch difference to assert instead.

The runtime-detection empirical pass (D-02) succeeded for two of four CLIs via a live spawned subprocess this session: Claude Code sets `CLAUDECODE=1` on every process it hosts (confirmed from this very research session's own environment), and opencode sets `OPENCODE=1`/`OPENCODE_PID=<pid>` on the environment of any subprocess it runs (confirmed by spawning `opencode run "... env > /tmp/probe.env"` live and reading the result back). codex's live probe was blocked by an expired OAuth refresh token on this machine, and cursor-agent's live probe was blocked by exhausted Free-plan quota — both are pre-existing account-state problems, not defects in the research method. For both blocked CLIs, the actual installed binary/bundle was inspected directly (grepping the real shipped `cursor-agent` `index.js` bundle, and consulting the open-source `openai/codex` Rust source on GitHub) and turned up equally concrete signals: cursor-agent's own bundled code spawns every shell/terminal-tool subprocess with `env:{CURSOR_AGENT:"1"}` (verbatim, quoted below), and codex's open-source `exec_env.rs` unconditionally injects `CODEX_VERSION` into every shell tool call via `inject_session_env()`. A secondary, community-documented codex signal (`CODEX_SANDBOX_NETWORK_DISABLED=1`, set whenever the shell tool runs) corroborates this from a different angle. None of these four signals is live-verified end-to-end for codex/cursor-agent in this session — that gap is called out explicitly rather than silently upgraded to VERIFIED.

A second important empirical finding from the same probe: when opencode was spawned as a subprocess of this Claude Code session, its own child environment showed **both** `OPENCODE=1` and the inherited `CLAUDECODE=1` — env vars accumulate through nesting and are never stripped by an intermediate CLI. This is a genuine edge case (an AI CLI shelling out to another AI CLI), not the normal single-hop case ai-kit's skills actually run in, but `detect_current_runtime()`'s implementation should pick one documented, fixed check order for the rare case multiple markers are present, and must never claim more certainty than the check order actually supports.

The opencode UI research (REQ-multi-cli-opencode-ui-research) found that `anomalyco/opencode#5971` ("Plugin API for custom sidebar panels") is open, unimplemented, assigned but with no maintainer commitment or linked PR as of 2026-09-09. A second, closely-related open issue, `anomalyco/opencode#23539` ("Plugin API for custom status bar widgets"), covers the status-bar half of this phase's own scope and should be cross-referenced alongside #5971, not silently omitted — the phase's own goal names both "sidebar/status-bar."

**Primary recommendation:** Ship the `--single-branch` flag as a defensiveness/explicitness change (not a behavioral fix) with a flag-presence test; implement `detect_current_runtime()` using the four env-var signals below with a documented, fixed precedence order and an explicit `[ASSUMED]`/gap note for the two CLIs that could not be live-verified this session; before writing tasks for `native_runtime`, resolve Open Question 1 (does this field attach to `model_catalog.py`'s catalog-entry schema, to `review-spec.toml`'s native-reviewer-entry schema via `config_io.py`, or both) since the two locations are structurally disjoint in the current code and the requirement's own wording assumes a connection between them that does not exist yet; write the opencode report using both #5971 and #23539, recommending "wait for upstream" given neither issue has a shipped implementation.

## Architecture Patterns

### Installer Hardening (`tools/install.sh`)

**Current code, read this session, `[VERIFIED: /var/home/bazzite/git/personal/ai-kit/tools/install.sh:95-134]`:**

```bash
fetch_repo() {
  local url="https://github.com/${REPO_SLUG}.git"
  local tarball="https://github.com/${REPO_SLUG}/archive/refs/heads/${REPO_BRANCH}.tar.gz"
  if [ -d "$INSTALL_DIR/.git" ]; then
    info "updating $INSTALL_DIR"
    git -C "$INSTALL_DIR" pull --ff-only
  elif have git; then
    info "cloning $REPO_SLUG into $INSTALL_DIR"
    git clone --branch "$REPO_BRANCH" --depth 1 "$url" "$INSTALL_DIR"
  elif have curl || have wget; then
    ...tarball fallback, atomic swap...
  else
    die "need git, curl, or wget to fetch the repo"
  fi
}
```

**Critical finding — the change is behavior-neutral for fetched refs.** Per git's own documentation (`git-scm.com/docs/git-clone`, fetched and quoted this session `[CITED: git-scm.com/docs/git-clone]`):

> `--depth`: Create a shallow clone with a history truncated to the specified number of commits. **Implies `--single-branch` unless `--no-single-branch` is given** to fetch the histories near the tips of all branches.

`tools/install.sh`'s clone line passes `--depth 1` and never passes `--no-single-branch`, so it is **already** fetching only `$REPO_BRANCH`'s history today, before this phase's change. This has been true since git 1.9 (2014) — old enough that no realistic install target needs a compatibility fallback. REQ-multi-cli-install-single-branch's acceptance ("only ever fetches the target branch's history... never pulling unrelated refs") is therefore **already true of the current code**; adding the literal `--single-branch` token changes nothing about what gets fetched.

The change is still worth making, for a different reason than "fixing broken behavior": **explicitness over an implicit git default**. A future edit that adds `--no-single-branch` for some unrelated reason, or that drops `--depth 1` (e.g. to support a `--full-history` debug flag) would silently reintroduce all-branch fetching with the current code, and nothing in the file documents that `--depth 1` is *load-bearing* for the single-branch property. An explicit `--single-branch` makes the intent self-documenting and independent of a git default a reader has to know about.

```bash
# Recommended change — one token added to the existing line:
git clone --single-branch --branch "$REPO_BRANCH" --depth 1 "$url" "$INSTALL_DIR"
```

**Test implication:** `tests/test_install.sh` cannot assert a ref-count/branch-count difference (there isn't one to observe — both before and after this change, only one branch's tip is fetched). It must assert the **literal flag string** is present in the invoked `git clone` command line. The file already has exactly the right harness for this at the `--branch` test (`[VERIFIED: /var/home/bazzite/git/personal/ai-kit/tests/test_install.sh:107-152]`, section "4c. `--branch` drives the BOOTSTRAP clone"): a fake `git` script on `PATH` that captures its own argv to a marker file when invoked with `clone`, e.g.:

```bash
# tests/test_install.sh's existing FAKEGIT harness (already reads url/branch out of argv);
# extend the marker-writing loop to also capture whether --single-branch was present, e.g.:
#   case "$1" in
#     --single-branch) sb=1 ;;
#     ...
#   esac
# then assert `[ "$sb" = 1 ]` the same way the existing test asserts $br/$url.
```

Do not add a new, separate fake-git harness — the existing one at lines 111-152 already parses clone argv into a marker file; extend its `case` statement with one more branch rather than duplicating the fixture.

**Important nesting finding, live-verified this session:** when `opencode` was spawned as a subprocess of this Claude-Code-hosted research session, its own child process's environment contained **both** `OPENCODE=1` (opencode's own marker) **and** the inherited `CLAUDECODE=1`/`CLAUDE_CODE_SESSION_ID`/etc. from the grandparent process — env vars propagate downward through subprocess chains and are never stripped by an intermediate CLI. In the normal single-hop case ai-kit's skills actually run in (a user launches exactly one of these four CLIs, which directly spawns the skill's Python subprocess), only one marker will be freshly present. The multi-marker case only arises when one AI CLI shells out to another — confirmed here purely as an artifact of this research session's own probe method, not a documented production workflow. `detect_current_runtime()` should still adopt one fixed, documented check order (e.g. the table order above) for the rare case multiple markers are simultaneously present, and should not claim to resolve "genuinely which one is the immediate parent" beyond what a fixed priority order actually establishes — consistent with the project's core value of never overclaiming certainty.

**Recommended implementation shape** (matching `ai_kit_spec/detection.py`'s existing conventions — `env: dict` injectable for testing, mirroring `resolve_agents_tooling_path(env=None)` `[VERIFIED: skills/ai-kit-spec-review/ai_kit_spec/detection.py:113-125]`):

```python
_RUNTIME_ENV_SIGNALS = (
    ("claude", "CLAUDECODE"),
    ("opencode", "OPENCODE"),
    ("cursor", "CURSOR_AGENT"),
    ("codex", "CODEX_VERSION"),
)


def detect_current_runtime(env: dict | None = None) -> str:
    """Which CLI is hosting THIS process right now (D-01) -- never cached (D-03).
    Checked in a fixed, documented order; returns the first present signal's
    label. Returns "unknown" -- never silently omitted (D-04) -- when none of
    the four signals are present."""
    env = env if env is not None else os.environ
    for label, var in _RUNTIME_ENV_SIGNALS:
        if env.get(var):
            return label
    return "unknown"
```

Note the `native_runtime` **label** for cursor-agent is `"cursor"` (per D-09's valid value set), while both the env var it checks (`CURSOR_AGENT`) and `KNOWN_CLIS`' own binary-name entry (`"cursor-agent"` `[VERIFIED: skills/ai-kit-spec-review/ai_kit_spec/detection.py:13]`: `KNOWN_CLIS = ("claude", "codex", "opencode", "grok", "cursor-agent")`) use the `-agent` suffix — this label/binary-name mismatch is deliberate per D-09 and must be preserved exactly (never normalize `KNOWN_CLIS`'s `"cursor-agent"` entry itself; only the returned `native_runtime` label changes).

**Recommendation for the report (per REQ's own acceptance wording, which explicitly allows "wait for opencode to ship a real sidebar API"):** given two independent open, unimplemented, maintainer-unengaged feature requests and zero present hook surface for UI rendering, the report should recommend **wait for upstream** rather than a hook-based prototype — there is no hook to prototype against today. Re-investigate when either #5971 or #23539 gains a linked PR or a maintainer implementation comment.

| Determining which CLI hosts the current process | A new process-ancestry walker (`/proc/<ppid>/comm`, `ps` parsing) | Env-var presence checks (`_RUNTIME_ENV_SIGNALS` above) | Live-tested this session: Node-based CLIs (opencode, cursor-agent) do not preserve an `exec -a`-renamed argv[0] in `/proc/pid/comm` — Node overwrites it with `node`/`node-MainThread` via its own `prctl` call. A process-tree approach would work for 2 of 4 CLIs and silently misreport the other 2; the env-var approach is uniform. |
| TOML writing for `native_runtime` (if it lands in `review-spec.toml`, per Open Question 1) | A new hand-rolled TOML writer path | `cfg_render_toml`'s existing flat-value serializer (`_toml_value`) plus `_KNOWN_REVIEWER_FIELDS`/`validate_reviewer_fields`'s existing extension pattern | `config_io.py` already has a documented, tested extension point for exactly this shape of change — `purpose`/`is_router`/`fallback_quota` were added this same way (see `validate_reviewer_fields`'s own docstring, "the review-spec.toml-side sibling of model_catalog.validate_catalog_entry"). Do not invent a second validation path. |

**Key insight:** every piece of this phase has an existing, established pattern to extend (env-var reads already exist in `detection.py`; optional-field schema validation already exists twice, once per file, in `model_catalog.py` and `config_io.py`) — the work is additive within those patterns, not new architecture.

## Common Pitfalls

### Pitfall 1: Treating "git already does this" as "the requirement is done"

**What goes wrong:** A planner reads REQ-multi-cli-install-single-branch, sees that `--depth 1` already implies single-branch behavior, and either skips the change entirely or writes a test that tries (and fails) to observe a fetched-ref difference that doesn't exist.
**Why it happens:** The requirement's acceptance criteria are worded as if this is a behavioral fix ("never pulling unrelated refs"), but git's own default already provides that behavior given the existing `--depth 1`.
**How to avoid:** Ship the flag anyway (explicitness/defensiveness value, argued above), and write the test against the **literal command line invoked** (extend the existing FAKEGIT harness), not against observed fetched-ref counts.
**Warning signs:** A test that tries to diff `git ls-remote` output before/after, or that counts refs in `.git/refs/` — there is nothing to observe there.

### Pitfall 2: Silently upgrading a `[CITED]`/binary-inspection finding to `[VERIFIED]`

**What goes wrong:** codex's and cursor-agent's env-var signals were confirmed via the actual installed binary/bundle (not training-data guesses) but **not** via a live spawned subprocess this session (auth/quota blocked both). It would be easy for the executor to treat these as fully live-verified.
**Why it happens:** The evidence trail (grepping a real shipped bundle, reading real open-source Rust source) *feels* as solid as a live probe, and in this case the underlying finding is likely correct — but "likely correct from static inspection" and "observed live" are different confidence tiers.
**How to avoid:** When the plan reaches the task that implements the codex/cursor-agent branches of `detect_current_runtime()`, add a `checkpoint:human-verify` (or equivalent live smoke test) step that actually runs `codex exec`/`cursor-agent -p` with a real, working auth session once one is available on the target machine, before calling those two branches production-confirmed.
**Warning signs:** A completed-phase report that describes all four CLI signals as "confirmed" without distinguishing the two live-tested from the two source-verified.

### Pitfall 3: Assuming `native_runtime` and `cli: None` already share one data structure

**What goes wrong:** REQUIREMENTS.md's acceptance text for REQ-multi-cli-runtime-detection reads as if `model_catalog.py`'s catalog entries already have (or naturally will have) a `cli` field that can be `None`. They do not — see Open Question 1 below. A planner who writes a task assuming this exists will discover the mismatch mid-implementation.
**Why it happens:** AGENTS.md's own Architecture section states "`cli is None` already means 'native candidate'... across `execute_dispatch.py`, `dispatch_injection.py`, `gsd_cross_ai.py`, `adapter.py`" — true, but those four files consume **`review-spec.toml`-derived candidate dicts** (built by `quota.py`'s `resolve_reviewers`/`resolve_ladder_pick`), a structurally different object from `model_catalog.py`'s catalog entries (which are keyed `provider/model_id` and carry a `runtimes: {cli_name: {...}}` dict, never a top-level `cli` key).
**How to avoid:** Resolve Open Question 1 explicitly before task-writing — see below.
**Warning signs:** A task description that says "add `native_runtime` next to the existing `cli: None` check in `model_catalog.py`" — there is no existing `cli: None` check in that file to add it next to (`[VERIFIED: skills/ai-kit-spec-review/ai_kit_spec/model_catalog.py:1-195, full file read]` — `cli` does not appear anywhere in this file's `_FIELD_TYPES`, `_MANDATORY_CATALOG_FIELDS`, `_RUNTIME_FIELD_TYPES`, or `validate_catalog_entry`).

### Open Question 1 (BLOCKING for task-level planning): where does `native_runtime` actually attach?

**What we know:**

- `model_catalog.py`'s catalog-entry schema (`_FIELD_TYPES`, `_MANDATORY_CATALOG_FIELDS`, `_RUNTIME_FIELD_TYPES`) has **no `cli` key anywhere** — entries are keyed `provider/model_id` and carry a `runtimes: {cli_name: {model_id, ctx_window}}` dict (multiple CLIs per entry is the whole point of this shape — see `canonical_key`'s own docstring: "two CLIs naming the same real model differently... always collapse to one key"). `[VERIFIED: skills/ai-kit-spec-review/ai_kit_spec/model_catalog.py:1-195, full file read this session]`
- The **only** place `cli is None` literally appears in this codebase is in `execute_dispatch.py`'s candidate-dict handling (`candidate["cli"]`, checked for `None`) `[VERIFIED: skills/ai-kit-spec-review/ai_kit_spec/execute_dispatch.py:46-52]`, and those candidate dicts are built by `quota.py`'s `resolve_reviewers`/`resolve_ladder_pick` **from `review-spec.toml`'s `[[reviewers]]` entries** — `quota.py` never imports or reads `model_catalog.py` at all (confirmed via grep: no `catalog` token anywhere in `quota.py`). A native (`cli`-omitted) `review-spec.toml` entry is what produces `cli: None` today; `model_catalog.py` entries never participate in this at all.
- `config_io.py` already has the exact extension pattern this would need if `native_runtime` belongs to `review-spec.toml` instead: `_KNOWN_REVIEWER_FIELDS` plus `validate_reviewer_fields` already validates `purpose`/`is_router`/`fallback_quota` as recognized-but-not-mandatory fields, explicitly documented as "the review-spec.toml-side sibling of `model_catalog.validate_catalog_entry`." `[VERIFIED: skills/ai-kit-spec-review/ai_kit_spec/config_io.py:13, 96-117]`

**What's unclear:** Whether the phase intends (a) a schema-only addition to `model_catalog.py` (add the field, validate it, but no code path in this phase actually sets it on a real entry, since no real catalog entry has `cli: None` today), (b) a schema addition to `config_io.py`/`review-spec.toml` instead (matches where `cli: None` actually lives functionally today, but contradicts CONTEXT.md's explicit `model_catalog.py` file pointer), or (c) both — plus a new code path that makes a native review-spec.toml entry also register/synthesize a corresponding `model_catalog.py`-shaped record (a genuinely new mechanism, not described anywhere in CONTEXT.md/REQUIREMENTS.md).
