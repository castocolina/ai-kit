# Phase 1.2: Multi-CLI Runtime Foundation - Context

**Gathered:** 2026-09-07
**Status:** Ready for planning

<domain>
## Phase Boundary

ai-kit's installer and model-catalog tooling are hardened and made runtime-aware
as the project expands beyond Claude Code toward opencode and Codex. Three
independent pieces of work: (1) a single-branch git fetch hardening in
`tools/install.sh`, (2) a `detect_current_runtime()` capability that lets a
running skill (e.g. `ai-kit-spec-config`) know which CLI is currently hosting
it, surfaced as an optional `native_runtime` field on model-catalog entries
with `cli: None`, and (3) a research-only report on opencode's sidebar/status-bar
viability. No code changes for (3); (1) and (2) are implementation work.

</domain>

<decisions>
## Implementation Decisions

### Runtime-detection method (detect_current_runtime)
- **D-01:** `detect_current_runtime()` answers "which CLI is hosting **this
  process right now**" (i.e. which of claude/opencode/codex/cursor-agent
  spawned the current skill's subprocess) — it is NOT about install-target
  selection. Installing ai-kit (which runtime gets the skill symlinks) stays
  the existing wizard's job (`tools/setup.py`) and is explicitly out of scope
  for this phase.
- **D-02:** Before implementing, run an empirical research pass: launch codex,
  opencode, cursor-agent, and claude each as the parent of a subprocess running
  a diagnostic probe script; observe what each leaves available to that spawned
  child (env vars, anything exposed in its own runtime) — never assume the
  detection mechanism a priori. `detect_current_runtime()`'s actual
  implementation is derived from what this research finds, consistent with the
  project's core value of verifying live rather than assuming.
  — **Reversibility:** reversible — a research pass that turns up a different
  signal than expected just changes the detection heuristic's internals, no
  external contract changes.
- **D-03:** No caching/TTL for `detect_current_runtime()`, unlike
  `detect_installed_clis()`/`detect_opencode_models()` (`RUNTIMES_TTL_SECONDS`
  = 30 days). Which CLI hosts a given process is fixed for that process's
  whole lifetime — cheap to recompute, never needs cross-process persistence,
  and caching would only add staleness risk for no benefit.

### "unknown" surfacing
- **D-04:** When `native_runtime` can't be determined, the catalog entry shows
  the explicit literal string `"unknown"` — never silently omitted — matching
  the same undeterminable-value convention Phase 4 (Config Doctor) establishes
  elsewhere in this milestone: never silently pass/omit an inconclusive result.
- **D-05:** `native_runtime` (including an "unknown" value) is purely
  informational. It never blocks or degrades ranking or wizard candidate
  selection — same spirit as `name_declared_purpose`, which exists as a label
  without driving ranking logic.

### opencode UI research depth
- **D-06:** The research report focuses on opencode's side-panel/status-bar
  viability only. It cross-references `anomalyco/opencode#5971` and gives an
  explicit recommendation, per `REQ-multi-cli-opencode-ui-research` — no code
  changes. Codex is explicitly out of focus for this report — mentioned with a
  single "not applicable here" line, not given its own analysis section.
- **D-07:** The installer's current shared-folder-plus-per-skill-symlinks
  pattern (Claude Code only needs its settings pointed at the shared path) is
  confirmed as already how `tools/install.sh` works today. This is NOT a new
  idea to capture or build — no deferred item, no phase-1 task beyond the
  already-scoped `--single-branch` change.

### native_runtime wizard placement
- **D-08:** `ai-kit-spec-config`'s ranked-candidate output labels
  `native_runtime` as an inline annotation next to the native candidate's row
  (e.g. `(running under: claude)`) — matching the existing pattern for
  `name_declared_purpose`/heuristic annotations. No new table column, no
  separate section.

### Amendment (2026-09-08, during Phase 4 discussion)
- **D-09:** `native_runtime`'s valid value set is `claude`/`opencode`/`codex`/`cursor`/`unknown`
  — `cursor` was missing from `REQUIREMENTS.md`'s original wording despite
  D-02 already scoping `cursor-agent` into the empirical subprocess-probe
  research. Caught and corrected during Phase 4's Config Doctor discussion,
  which separately confirmed Cursor is a real, actively-used runtime on this
  machine (`~/.cursor/cli-config.json`, `~/.cursor/hooks.json` both present
  and populated).

### Claude's Discretion
None — every gray area in this phase had an explicit user decision.

<code_context>
## Existing Code Insights

### Reusable Assets
- `tools/install.sh` `fetch_repo()` (lines ~95-120): the primary git-clone path
  is `git clone --branch "$REPO_BRANCH" --depth 1 "$url" "$INSTALL_DIR"` —
  `--single-branch` is a one-line addition here, alongside the untouched
  tarball-fallback and `git pull --ff-only` paths.
- `skills/ai-kit-spec-review/ai_kit_spec/detection.py`: already has
  `KNOWN_CLIS = ("claude", "codex", "opencode", "grok", "cursor-agent")` and
  `detect_installed_clis()` (which CLIs are on PATH) plus
  `RUNTIMES_TTL_SECONDS` caching pattern — `detect_current_runtime()` is a
  new, deliberately uncached sibling function, not a modification of this one
  (per D-03, presence-on-PATH and current-host-identity are different
  questions).
- `skills/ai-kit-spec-review/ai_kit_spec/model_catalog.py`: `_FIELD_TYPES`
  dict is the exact place to add `"native_runtime": str` as a new optional
  field, following the `name_declared_purpose` precedent added in commit
  `359daac` — same shape: optional, type-checked when present, absent is never
  a validation failure, validated against a small closed set of values when
  D-04's "unknown" is included as a legal value.

### Established Patterns
- Optional catalog fields are added to `_FIELD_TYPES` + (when the value has a
  closed vocabulary) a `_VALID_*` set constant + a presence-and-membership
  check in `validate_catalog_entry()` — see `name_declared_purpose` /
  `_VALID_NAME_DECLARED_PURPOSE` for the exact pattern to replicate for
  `native_runtime` (open values: `claude`/`opencode`/`codex`/`unknown`).
- `cli is None` already means "native candidate, executes in-process, never
  subprocess-dispatched" across `execute_dispatch.py`, `dispatch_injection.py`,
  `gsd_cross_ai.py`, `adapter.py` — `native_runtime` is a label that applies
  only to these `cli: None` entries, consistent with existing terminology
  (see also prior memory: "native" must stay host-agnostic wording, not
  Claude/opus-specific).

### Integration Points
- `skills/ai-kit-spec-config/SKILL.md` §"ranked candidate list" (~line 167 on):
  where the wizard builds and prints the ranked-candidate output — this is
  where D-08's inline `native_runtime` annotation gets added.
- `tools/setup.py` (install wizard) is explicitly NOT touched by this phase
  (D-01) — no integration point here despite superficial "runtime" naming
  overlap.

</code_context>

  not from a priori assumption.

  `(running under: claude)` next to the native candidate's row — short, not a
