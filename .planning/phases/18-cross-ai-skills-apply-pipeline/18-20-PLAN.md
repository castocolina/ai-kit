Design notes:
- The approval prompt itself is the agent's job (SKILL.md, 18-21); the CLI prints the block as
  data and runs it only with `--approve`.
- "Changed" keys come from the plan alone, never from the live config: an entry is changed when
  its op is `set` and its `value` differs from its recorded `existing`, or its op is `unset` and
  `existing` is not null. The block apply prints and the block a later `followups` builds
  against the already-applied config are therefore identical (same ids, same argv). A re-run
  after a successful sync lists the same commands; both are idempotent, the effort dry-run
  count shows 0, and the run reports already-current results (SPEC R14 idempotency).
- The effort dry-run is read-only (`effort sync --dry-run`, gsd-core default) and runs while
  building the block, with the project-local gsd-tools when one resolves; when none resolves
  yet (opencode before its installer) the count is `null` and `detail` says `change count
  unavailable until the local install exists`. Tests inject `run_fn`.
- Unverified, stated in the block and the docs: the `--config-dir <project>/<host dir>` value
  (`HOST_DIRS` is used for nothing else) and the opencode local root `<root>/.opencode/gsd-core`
  (inferred from gsd-core's capability registry `localConfigDir: ".opencode"`); Phase 20 runs
  the real opencode installer and settles both.
- No second resolver: followups.py never builds a gsd-core path list of its own (ponytail 2).

  f"--{host}", "--local"]`
- `class FollowupCtx(NamedTuple)`: `plan_path: str`, `inv_path: str`, `project_dir: str`,
  `deps: host.InventoryDeps`. Callers holding apply's `ApplyDeps` build
  `host.InventoryDeps(deps.which_fn, deps.run_fn, deps.env_fn)`, exactly as 18-17's
  `resolve_target` does.

  _err = host.resolve_gsd_core(project_dir, host_name, deps)`; returns `core.tools_path` when
  `core` is not None and `core.scope == "local"`, else None
- `changed_keys(plan) -> list[str]` (pure, sorted): keys of entries whose op is `set` and whose
  `value` differs from `existing`, or whose op is `unset` and whose `existing` is not None
- `effort_sync_argv(node, tools, host, project_dir, apply: bool) -> list[str]` (`[node, tools,
  "effort", "sync", "--apply" | "--dry-run", "--runtime", host, "--config-dir",
  <project>/<HOST_DIRS[host]>, "--project-dir", project_dir]`)
- `effort_dry_run_count(argv, run_fn, env) -> int | None` (`len(json["changes"])`; None on any failure)
- `build_followups(plan: dict, inv: dict, ctx: FollowupCtx) -> dict`: decides from
  `changed_keys(plan)` only and reads no config file; node comes from
  `gsd_catalog.resolve_node_binary(ctx.deps.which_fn)` (none -> no effort sync, with a note
  saying node was not found). Returns `{"required": [FollowUp as dict], "recommended":
  [{"id": "map_codebase", "text": ...}], "notes": [...], "disclosures": [...], "approve_with":
  "followups --plan <p> --inventory <i> --project-dir <d> --approve"}` (paths from `ctx`);
  `notes` always holds `effort sync --config-dir <dir> is inferred from the host layout
  (unverified)` when effort sync is required, and on an opencode host `the local install root
  <root>/.opencode/gsd-core is inferred (unverified until Phase 20)`. Effort sync is required
  when an `effort.*` key changed, the host is in `EFFORT_SYNC_HOSTS`, and either a project-local
  gsd-tools resolves now or the block also holds the installer (which creates one). Otherwise,
  on claude or codex, there is no effort-sync entry and `notes` holds `effort sync not offered:
  no project-local gsd-core for <host> in <project>; effort keys take effect only after a local
  gsd-core install runs its effort sync`.
- `run_followups(block: dict, host_name: str, ctx: FollowupCtx) -> tuple[int, list[dict]]`:
  runs `required` in order through `ctx.deps.run_fn` (installer, then effort sync with
  gsd-tools re-resolved through `local_gsd_tools(ctx.project_dir, host_name, ctx.deps)` after
  the installer; no
  local gsd-tools after the installer -> that step fails with `no project-local gsd-core after
  the installer`); each result `{"id", "argv", "cwd", "returncode", "stdout_tail",
  "stderr_tail"}` (tails at most 2000 chars); a failure stops the sequence, exit 1, and stderr
  prints `ai-kit-gsd-curated-config: <id> failed; run it yourself: <shlex.join(argv)> (cwd
  <cwd>)`

CLI: `followups --plan --inventory --project-dir [--approve]` loads its inputs through
`apply.load_inputs` (digest check, D-42) and builds the block exactly as apply does; without
`--approve` prints the block
JSON and exits 0; with it prints `{"results": [...]}`; exit 0 when nothing is required.
