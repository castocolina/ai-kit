Design notes:
- The approval prompt itself is the agent's job (SKILL.md, 18-21); the CLI prints the block as
  data and runs it only with `--approve`.
- Which follow-ups are required: `followup_ids` maps changed keys to ids. The plan-time keys
  come from the plan alone (`set` whose `value` differs from `existing`, or `unset` with a
  non-null `existing`); apply adds the keys it actually wrote or reconciled, because live drift
  can make apply write a key the plan recorded as unchanged. A later `followups` cannot see
  apply's writes and never reads the live config, so apply's `approve_with` carries the
  required ids as `--require <ids>`; the block apply prints and the block that command builds
  are identical (same ids, same argv). A re-run after a successful sync lists the same
  commands; both are idempotent, the effort dry-run count shows 0, and the run reports
  already-current results (SPEC R14 idempotency).
- Workstreams: apply writes through the workstream-aware `config-set`, but gsd-core 1.16's
  `effort sync` resolves effort from the root `.planning/config.json` (walking up from the
  project) merged with `~/.gsd/defaults.json` and ignores workstreams, for claude and opencode.
  Offering it for a workstream would report a sync of the wrong settings, so it is not offered
  there and the note names the workstream config and the reason.
- The effort dry-run is read-only (`effort sync --dry-run`, gsd-core default) and runs while
  building the block, with the project-local gsd-tools when one resolves; when none resolves
  yet (opencode before its installer) the count is `null` and `detail` says `change count
  unavailable until the local install exists`. Tests inject `run_fn`.
- Unverified, stated in the block and the docs: the `--config-dir <project>/<host dir>` value
  (`HOST_DIRS` is used for nothing else) and the opencode local root `<root>/.opencode/gsd-core`
  (inferred from gsd-core's capability registry `localConfigDir: ".opencode"`); Phase 20 runs
  the real opencode installer and settles both.
- No second resolver: followups.py never builds a gsd-core path list of its own (ponytail 2).

  from `ctx`; `--require` lists the required ids comma-joined in `REQUIRE_IDS` order and is
  left out when nothing is required);

  (unverified)` when effort sync is required, and on an opencode host `the local install root
  <root>/.opencode/gsd-core is inferred (unverified until Phase 20)`. Effort sync is required

  it would sync the root's effort settings, not the ones apply wrote`.

  runs `required` in order through `ctx.deps.run_fn` (installer, then effort sync with
  gsd-tools re-resolved through `local_gsd_tools(ctx.project_dir, host_name, ctx.deps)` after

  <cwd>)`

`build_followups(plan, inv, ctx, followup_ids(<keys in report writes and reconciled>, host))`.
