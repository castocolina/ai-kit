Design notes:
- When `acquire_marker` returns False, apply exits 2 with
  `config_backup.recovery_text(config_backup.read_marker(config), config)` (18-16: the steps
  follow what that apply recorded: committed or not, backup taken or not, runner `change`,
  `add` or none). The marker never auto-heals.
- The runner is part of the transaction. For a planned `change`, `config_backup.snapshot_file`
  copies the pristine runner and `update_marker(runner={path, snapshot, kind})` records it
  before `write_script`; a planned `add` records `snapshot` None. Rollback follows the kind
  `write_script` returned (18-13), never the planned one: a run that diverted to `.new` leaves
  the user's runner alone, and its snapshot is discarded and `runner` cleared in the marker at
  once. `write_script` publishes atomically, so a raise from it means the runner was not
  replaced.
- The failure helper `_rollback(progress, target) -> str | None` is the only caller of
  `restore_backup`. It restores the config only when `progress` says the backup step
  completed (a failure in `create_backup` itself leaves the config untouched) and the runner
  only when `write_script` returned. Every restore runs even if an earlier one raised; any
  `OSError` text is returned as `restore_error`, and then the marker, the backup and the
  snapshot are kept for manual recovery. With no restore error it discards the snapshot,
  clears the marker, and then removes `progress.created_dirs` deepest first with `os.rmdir`,
  which refuses a non-empty dir (anything else living there stays; an `OSError` from it is
  ignored, an empty dir left behind is harmless). `created_dirs` holds every dir this run
  created: the config's dir and each of its missing ancestors when absent before
  `acquire_marker` (which creates them, 18-16), and the runner's dir when absent before
  `write_script` (`cache_write_bytes` creates it). Decision (plan-checker W1): a
  failed apply on a fresh project leaves no `.planning/` behind; a rollback that keeps the
  marker keeps the dirs too.
- Commit point (review cycles 2 and 3): the apply is committed once its last config write
  returned, since D-22 restores only on a failure in steps 4-6. From then on nothing calls
  `_rollback`. `_cleanup_committed(progress, target, report) -> None` runs, in order, each step
  in its own `try` (an `OSError` or `ValueError` becomes a `warnings` entry naming the step and
  the leftover path to delete, and the next step still runs): `update_marker(committed=True)`;
  `verify_skills` (a failing or unparseable `agent-skills` call becomes that agent's
  `{"error": <text>}` entry); `clear_marker` at once when recording `committed` failed;
  `discard_snapshot` and `prune_backups`, only when the marker reads `committed` or is gone
  (once it is gone the snapshot has no purpose left); `clear_marker` if not done yet. When
  recording `committed` and clearing the marker both fail, discard and prune are skipped, so
  the uncommitted-looking marker keeps its snapshot, and the warning reads `the apply
  committed but could not record it in or delete <marker>; <config> and the runner hold the
  applied state: delete <snapshot> if it exists, then <marker>; do not restore the backup`
  (with no recorded snapshot it names only the marker). The next apply's `recovery_text`
  agrees: its `apply --dry-run` check shows only keep rows, so it gives the same steps (18-16).
  A committed run exits 0 with `applied` true whatever cleanup reported.
- `acquire_marker` raising `OSError` (an uncreatable dir, `mkstemp`, or a filesystem without
  `os.link`) ends the run with exit 1 and `error` naming it; apply removes the dirs this run
  created (`created_dirs`, deepest first, as `_rollback` does) and writes nothing else: no
  backup, no config call (review cycle 3; the test is in 18-19).
- The live config is re-read after `config-new-project` and before each family's writes are
  computed; a value already equal to the live one is skipped (this is what makes re-apply a
  no-op).
- Reuse 18-17's helpers: `read_live_config` for every read, `presets.get_dotted` for every
  dotted lookup.
