Design notes:
- When `acquire_marker` returns False, apply exits 2 with `an apply is running or did not
  finish (<marker>); its backup is <backup, or "none: the config did not exist", or "not taken
  yet">; its runner snapshot is <snapshot or "none">; if no apply is running, put the backup
  back over <config> (or delete <config> when the config did not exist), put the snapshot back
  over <runner>, then delete the marker` (fields from `read_marker`; a corrupt marker says it
  is unreadable). The marker never auto-heals.
- The runner is part of the transaction. For a planned `change`, `config_backup.snapshot_file`
  copies the pristine runner and `update_marker(runner={path, snapshot, kind})` records it
  before `write_script`; a planned `add` records `snapshot` None. Rollback follows the kind
  `write_script` returned (18-13), never the planned one: a run that diverted to `.new` leaves
  the user's runner alone, and its snapshot is discarded and `runner` cleared in the marker at
  once. `write_script` publishes atomically, so a raise from it means the runner was not
  replaced.
- The failure helper `_rollback(progress, target) -> str | None` is the only caller of
  `restore_backup`. It restores the config only when `progress` says the backup step
  completed (a failure in `create_backup` itself leaves the config untouched) and the runner
  only when `write_script` returned. Every restore runs even if an earlier one raised; any
  `OSError` text is returned as `restore_error`, and then the marker, the backup and the
  snapshot are kept for manual recovery. With no restore error it discards the snapshot and
  clears the marker.
- The live config is re-read after `config-new-project` and before each family's writes are
  computed; a value already equal to the live one is skipped (this is what makes re-apply a
  no-op).
- Reuse 18-17's helpers: `read_live_config` for every read, `presets.get_dotted` for every
  dotted lookup.
