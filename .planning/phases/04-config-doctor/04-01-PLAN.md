<notes>
## Planner decisions recorded here (not silent)

1. **`config_doctor_checks.py`/`_readers.py` port rather than import
   `tools/setup.py`'s helpers, even though `tools/` -> `tools/` is not a
   layering violation the way `tools/` -> `skills/` is.** `_read_json_checked`
   and its siblings ARE reusable by a plain import — nothing forbids it
   structurally — but `tools/setup.py` is a 2700+-line wizard/install-CLI
   module that itself does argparse parsing, uv re-exec bootstrapping, and a
   dozen other install-specific concerns. Importing it from the "core engine"
   module RESEARCH.md's own Architectural Responsibility Map asks to stay
   import-clean (for Backlog 999.1's future CLI-front-end split) would
   transitively couple a small, portable JSON-reading concern to a large,
   wizard-specific one. Porting the ~15-line 3-state reader shape is cheap and
   matches this codebase's own established precedent (`tools/setup.py`'s own
   `_atomic_write_json` docstring: "Adapted from
   skills/ai-kit-opencode-providers/.../atomic_write.py rather than
   imported").

2. **`read_toml_checked` is a genuinely new function, not a reuse of
   `tools/setup.py::read_toml`.** That function's own docstring states it
   collapses "Missing / empty / malformed" into a single `{}` return — the
   exact conflation Phase 3's review round 1 (F1) found and fixed for JSON via
   `_read_json_checked`. Reusing `read_toml` here would silently reintroduce
   that bug for Codex's `config.toml`, defeating this phase's own
   `04-RESEARCH.md` Common Pitfall 3 (never present a guessed value with more
   certainty than the read actually supports).

3. **Row 1's `apply` field stays `None` in this wave, deliberately, not as a
   permanent stub.** `CheckRow.apply` is part of the schema from the first
   line of `config_doctor_checks.py` (D-01 requires the full record shape up
   front), but no writer exists until Wave 3. Wave 3 MODIFIES this SAME row
   record (not a new parallel one) to add a real Claude-JSON applier — the
   final, post-Wave-3 state has row 1 fully apply-capable, so this is
   tracer-first incremental build-out, not a scope reduction.

4. **`config_doctor_app.py` uses a `DataTable`, not a hand-rendered `Static`
   board like `wizard_app.py`'s Choose/Arrange screens.** D-06 asks for "the
   same visual style," which this plan interprets as the same PALETTE and
   footer-key-bar convention, not a literal re-implementation of
   `wizard_app.py`'s bespoke Static-rendering approach. The Checks Catalog is
   naturally tabular, keyboard-navigable row data — `DataTable` is the
   idiomatic Textual widget for exactly this shape, and it is what makes a
   per-row detail pane (the "pros/cons" content the phase's Specific Ideas
   ask for) straightforward via `RowHighlighted`.

5. **`CheckRow` gains a `reads_section_file: bool = True` field in this
   wave, ahead of any row that needs it `False`.** Wave 1's own single row
   never exercises the `False` path, but defining the field and the
   corresponding `evaluate_row` degrade-logic branch here — rather than
   revising `evaluate_row` a second time in Wave 2 — keeps the
   unreadable-file short-circuit rule internally consistent from the first
   commit. Wave 2 adds the first two rows (`claude-telemetry`,
   `cursor-sandbox-json`) that actually set it `False`. (Addresses cross-AI
   review finding: an earlier draft of the "every row in an unreadable
   section is forced to unknown" rule would have wrongly masked a row whose
   value is fully knowable from `ctx.env` or a separate file.)

6. **`cmd_config_doctor` wraps `run_config_doctor(ctx)` in `stdin_on_tty()`,
   matching `launch_wizard`'s identical wrap.** Without it, `--config-doctor`
   run via `curl | bash` inherits the script pipe as fd 0, and Textual's
   Linux driver — which reads keystrokes from fd 0 directly — cannot be
   driven at all. A PTY test alone cannot catch this omission (a PTY always
   provides a real fd 0), so this task also adds a piped-stdin PTY test
   mirroring `tests/test_wizard_pty.py::TestCurlBashE2E`. (Addresses
   cross-AI review finding, HIGH severity.)
</notes>
