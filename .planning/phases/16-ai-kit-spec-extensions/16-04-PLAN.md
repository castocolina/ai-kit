<objective>
Make `detect-runtimes` enumerate claude with the hybrid source 16 D-04 locks in: hardcoded aliases,
full model ids taken from models.dev's anthropic provider through the model-catalog refresh path,
and a small, dated, clearly labeled fallback list when no catalog data exists — without ever
executing claude.

Purpose: SPEC-02 (claude half). Phase 17 needs claude host models (aliases for tier slots, full ids
for scoring). Claude Code has no list-models command (`claude --help`: `--model` takes an alias or a
full name), so the full ids must come from the catalog.
Output: claude constants, `claude_runtime_fields` and `claude_runtime_is_current` in
`detection.py`, a lazy `catalog_fn` hook on `build_runtimes_snapshot`, a catalog-aware
`detect-runtimes --if-stale` skip test, anthropic-id recording in `fetch-model-catalog` together
with same-fetch materialization of an `anthropic/<id>` catalog entry for every recorded id, an
`anthropic` match hint for claude candidates, tests, and a design-spec erratum describing the
runtimes shapes and the convergence behavior Phase 17 consumes.

Catalog -> runtimes freshness edge (addresses the review cycle 1 HIGH shared by 16-03 and 16-04):
the approved refresh order is `detect-runtimes --if-stale` THEN `fetch-model-catalog --if-stale`
(design spec §3). On the first upgraded run, detection happens before the catalog holds any
anthropic ids, so it writes the dated fallback; the fetch then records the ids; and, without a
dependency edge, the now-fresh, current-schema runtimes.json would make every later
`detect-runtimes --if-stale` skip for up to 30 days, stranding claude on the fallback. Fix chosen
here: runtimes.json's claude portion is DERIVED from model-catalog.json `_meta`, so the catalog is
an input of the runtimes cache. `detect-runtimes --if-stale` therefore also re-detects when the
cached claude entry differs from what the current catalog yields (`claude_runtime_is_current`).
Rejected alternatives: re-stamping `clis.claude` from inside `fetch-model-catalog` (it would
write into its `--runtimes-json` INPUT, which a wizard may have narrowed to a custom path), and
fetching the catalog before detection (catalog discovery needs the runtimes snapshot first). The
tracer test runs the REAL order and ends with `models_source: catalog`.

Catalog materialization (addresses review cycle 2 HIGH "new catalog ids are learned but not
materialized as scored catalog entries"). The freshness edge alone is not enough.
`fetch-model-catalog` builds entries only for the candidates it is given. Those come from the
runtimes snapshot's `models` arrays, which on the first upgraded run hold only the four fallback
ids. The next `fetch-model-catalog --if-stale` then skips models.dev because the fetch-meta sidecar
is fresh. Without a fix, an id outside the fallback would be listed in runtimes.json but stay
`unmatched` until the 30-day catalog TTL ran out. Fix chosen (option a): the fetch that records
the anthropic ids in `_meta` also passes every recorded id the snapshot does not already list to
`build_model_catalog` as an extra claude candidate, gated on `which_fn("claude")` finding claude.
It is not gated on the snapshot, because the `--runtimes-json` input may be a wizard-narrowed
copy that dropped claude while still refreshing the shared fetch-meta sidecar. The ids and their
entries are therefore always written together. After the next `detect-runtimes --if-stale` lists
them, a network-skipping fetch keeps each one through the existing `(cli, model_id)` runtime
recovery (`_find_existing_key_for_runtime`). The extra candidates never enter the printed
`discovered` or `unmatched` lists, so the wizard's narrowed ranking scope does not change.
Rejected alternative (option b, a candidate-set freshness key that forces a second real fetch
when the runtime candidate set changes): it changes `--if-stale`'s documented contract for every
CLI (today it gates only the network calls, and a new opencode model is reported unmatched by
design), it spends an extra network and Artificial Analysis quota call, and it still needs a
second adapter run before the ids can be scored. Supporting fix found while verifying the
premise: on live models.dev (2026-09-24) every anthropic id also appears under 9-21 reseller
providers (e.g. `claude-sonnet-5` under `opencode`, `github-copilot`, `azure` and 17 more).
`match_models_dev` returns no match for an unhinted multi-provider bare id, so no claude id would
become an entry against real data. `build_model_catalog` therefore passes
`_FIRST_PARTY_PROVIDER_BY_CLI.get(cli_name)` (`{"claude": "anthropic"}`) as `provider_hint`.
That value only breaks ties, because a single match still wins regardless of the hint. The
tracer's models.dev fake includes a colliding reseller row.

Malformed models.dev rows (addresses review cycle 3 agreed concern "`_anthropic_model_ids` does
not require each model row to be a dict"). `fetch_models_dev` checks only the JSON transport, not
the row shape. `match_models_dev` spreads the matched row (`{**model, "provider": ...}`), and
`build_model_catalog` calls `.get` on the matched row's `limit` and `cost`. So a `null`, string or
list row, or a row whose `limit`/`cost` is not an object, would raise inside
`fetch-model-catalog` if its id became a materialization candidate. Fix chosen:
`_anthropic_model_ids` keeps only ids whose row is a dict whose `limit` and `cost` (when present)
are dicts too. A skipped row is neither recorded in `_meta` nor materialized. In addition, after
a materializing fetch (claude on PATH), `_meta.anthropic_model_ids` is narrowed to the ids that
really got an `anthropic/<id>` entry with a claude runtime. A well-shaped row whose entry
`validate_catalog_entry` rejects (for example a non-bool `tool_call`) is then reported only in
`rejections` and is never recorded without an entry.

lists. A wizard run that narrows its runtimes snapshot to chosen models is therefore never

`current_candidate_keys(catalog, discovered)`.
