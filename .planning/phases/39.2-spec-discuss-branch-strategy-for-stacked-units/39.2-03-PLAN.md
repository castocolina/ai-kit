<objective>
SPEC R6 (CONTEXT D-01, D-10): after a plain commit on a lower unit, one `fold.py restack` rebases every open unit above it onto the new tip, locally, without a push and without rewriting any unit's own commits. Because every syncing command (`start`, `checkpoint`, `ready`, `hotfix`, `restack`) runs the same `_sync_restacked`, they all gain this; the unit contract says so.

Decisions recorded here:
- `cascade` gains `push=True`; the saved restack state stores `"push"`, and `_publish` pushes only when `consented(repo) and state.get("push", True)`, so `restack --continue` after a pause of a local restack pushes nothing either (orchestrator decision after research).
- Pass order (planner, deviation from the orchestrator's "bottom-up" correction, for correctness; the fixture is the arbiter): the loop restacks the HIGHEST moved pair first. Reason: `git rebase --update-refs --onto <new> <old> <top>` only moves refs that point at commits inside `old..top`. With plain commits on A and on B, a first pass for A replays `a1..C`, which does not hold B's new commit, so B is left behind and its recorded parent tip becomes false. Restacking C onto B's new tip first puts B's new commit inside `a1..C`, so the pass for A then carries B and C together. If the two-moved-units fixture fails with this order, stop and report; never weaken the assertion.
- Reversibility: costly (CONTEXT D-01: `restack` and `sync` are called by `start` and the cascade; undoing it changes an existing command's semantics for every caller). The owner already decided it; no checkpoint.
