SPEC R6 (CONTEXT D-01, D-10): after a plain commit on a lower unit, one `fold.py restack` rebases every open unit above it onto the new tip, in a local pass without a push and without rewriting any unit's own commits. Because every syncing command (`start`, `checkpoint`, `ready`, `hotfix`, `restack`) runs the same `_sync_restacked`, they all gain this; the unit contract says so.

Decisions recorded here:
- Restack options travel inside a copy of `settings` under the key `"restack"` (`{"push": <bool>, "entry": {"tips": {...}, "record": {...}}}`), because `cascade` already has five arguments (pylint max-args 5; review C4). `cascade` keeps its signature and its existing callers (flow_unit.py `_checkpoint` line 314 and `_sync_restacked`); without the key it behaves as today. The saved restack state stores `"push"` and `"entry_record"`; `_publish` pushes only when `consented(repo) and state.get("push", True)`, so `restack --continue` after a pause of a local pass pushes nothing either.
- Pass order inside the lower-unit loop: the HIGHEST moved pair first (planner, deviation from the orchestrator's "bottom-up" correction, for correctness): `git rebase --update-refs --onto <new> <old> <top>` only moves refs that point at commits inside `old..top`, so a first pass for A would replay a range that lacks B's new commit. Order between the loop and the trunk: the lower-unit loop FIRST, then the trunk cascade (review C1; reason in the must_haves). If a fixture fails with these orders, stop and report; never weaken the assertion.
- Abort contract (review C3, SPEC R6 "restores every branch at its starting tip"): the command-entry tips and record are saved once per sync and copied into every pass's state; restoring writes them back.
- Reversibility: costly (CONTEXT D-01: `restack` and `sync` are called by `start` and the cascade; undoing it changes an existing command's semantics for every caller). The owner already decided it; no checkpoint.
