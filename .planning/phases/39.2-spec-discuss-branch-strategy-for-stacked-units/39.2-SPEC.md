# Phase 39.2: Spec-discuss branch strategy for stacked units — Specification

**Created:** 2026-11-23
**Ambiguity score:** 0.18 (gate: ≤ 0.20)
**Requirements:** 10 locked

## Goal

An orchestrator running spec-discuss over a range of phases knows, at every step, which branch holds which phase's documents and
how to return to it: each file is committed on the lowest open unit that owns it, the units above are restacked after the
commit, a read-only where-am-I step and a recipe table replace hand moves of branches and of the stack record, and the fold tool
gains the three behaviours the rule needs.

## Background

Inserted 2026-11-23 by owner decision; source and transcript evidence in
`.planning/todos/pending/2026-11-23-spec-discuss-branch-strategy-after-the-chain.md` (home-mobility, ai-kit and tools-installer
sessions). The owner's request (translated): for each phase spec-discuss creates the branch, which is fine; the problem is that
afterwards the orchestrator does not know how to go back, or assumes each document lives in its own branch, and gets confused
when it plans or implements.

**The owner's decisions (highest priority):**

- 2026-11-23, answers to this phase's question batch: (1) a cross-phase amendment is written on the amended phase's own branch
  and the shared planning files (REQUIREMENTS, ROADMAP, STATE, todos, config, the goal file) on the lowest open unit, the units
  above restacked after each phase step; (2) when GSD's own phase branching conflicts with the unit flow, spec-discuss stops
  with the reason, changes nothing and writes no config; (3) an inserted decimal phase that must sit below open units gets a
  recipe row only (ask the owner, number it after the top); no insert-below command is built.
- Rejected by the owner's design rule: keeping "amend in the later phase's commit" with a carry-down before planning (repeated
  conflicts and stale plans in the 2026-11-19 to 2026-11-20 run), and writing a whole range on one branch (breaks one unit per
  phase and the `discuss:pre` hook).

**Refined by a live fact, confirmed by the owner 2026-11-23:** the owner's answer 2 is applied as "stop when GSD's branch name for the phase
differs from the unit branch the fold flow creates", because ai-kit's own `.planning/config.json` sets
`git.branching_strategy: "phase"` with `phase_branch_template: "gsd/phase-{phase}-{slug}"`, which renders the same names the fold
flow creates (this phase's unit is `gsd/phase-39.2-spec-discuss-branch-strategy-for-stacked-units`); a rule that stops on any
strategy other than `none` would stop ai-kit's own runs. The home-mobility collision came from a branch name that did not match
(`gsd/phase-01-pwa-project-scaffold` against the unit's own name).

## Requirements

1. **One ownership rule decides every write**: `ai-kit-gsd-spec-discuss` SKILL.md states that a file is committed on
   the branch of the lowest open unit that owns it and the units above are restacked after the commit: a phase's own SPEC,
   CONTEXT and DISCUSSION-LOG on its unit; a cross-phase amendment on the amended phase's unit; REQUIREMENTS.md, ROADMAP.md,
   STATE.md, todos, config and the goal file on the lowest open unit; the writes of one phase step are batched into one branch
   switch and one restack.
   - Current: SKILL.md says an amendment goes "in K's commit" (line 237), so on K's branch above J, and the `docs(state)` commit
     and the goal file land on the stack top.
   - Target: the "in K's commit" sentence and the end-of-range paragraph name the owning branch instead.
   - Acceptance: a doc-contract test pins the ownership sentence and fails when the old "in K's commit" wording returns; an
     eval over three phases where the third finds a fact that contradicts the first ends with the amendment committed on the
     first phase's unit, the units above restacked, the amendment visible on all three and no restack conflict.

2. **A read-only where-am-I step runs at setup and before each phase**: it prints the current branch, the stack order
   with each unit's state, and for each phase of the range whether its unit exists and which branch holds its SPEC and CONTEXT;
   it never edits the stack record or moves a branch.
   - Current: no such step; orchestrators read `.git/ai-kit-stack.json` by hand.
   - Target: the step is named in SKILL.md at setup and before each phase, uses the all-units view of requirement 7 and
     `git branch --show-current`.
   - Acceptance: a doc-contract test pins the step and its read-only rule; an eval checks the printed fields (current branch,
     stack order with states, branch holding each phase's documents).

3. **Going to phase J goes through `start` and `guard`**: before any step reads or writes phase J's files, the
   orchestrator runs `fold.py start --phase J` (reuses and checks out an open unit) and `fold.py guard --phase J`; a refusal goes
   to the recipe table of requirement 9, never to a hand move of a branch or an edit of the record; the goal-prompt rails carry
   one line saying the same for planning or executing an earlier phase.
   - Current: SKILL.md and its references never say how to go back to phase J.
   - Target: SKILL.md states the two commands as the only way to switch and the goal-prompt rails carry the line.
   - Acceptance: a doc-contract test pins both commands and the no-hand-move rule; an eval "plan the first phase after the
     chain" reads nothing from the top branch and runs `start` then `guard` first; a goal-prompt rail test pins the line.

4. **The end report states the branch situation**: the end-of-range report names the branch the checkout is left on
   (the lowest phase of the range), the stack order with tips, which branch holds each phase's documents, the goal file's path
   and branch, and every `unit flow off` line.
   - Current: the end report says nothing about branches.
   - Target: SKILL.md lists the five fields in the end report and the ledger.
   - Acceptance: a doc-contract test pins the five fields; an eval over a finished range checks each is printed.

5. **Start-time checks stop with a reason before the first `start`**: spec-discuss stops, moves no branch, edits no
   record and writes no config, when (a) GSD's `git.branching_strategy` is not `none` and the branch name GSD gives the phase
   differs from the unit branch the fold flow creates for it, or (b) HEAD is a branch that is not a recorded unit and holds
   commits the trunk lacks (it shows the commits).
   - Current: neither check exists; in home-mobility GSD's `gsd/phase-01-pwa-project-scaffold` and `start` collided and the
     orchestrator reset the record by hand.
   - Target: both checks run before the first `start` and print their reason.
   - Acceptance: fixture repos, each refused with its reason: strategy `phase` with a template that renders another name,
     strategy `milestone`, and an unrecorded HEAD branch with local commits; strategy `none`, and strategy `phase` whose template
     renders the unit's own name (this repo's case), both proceed; a repo with no `.planning/config.json` or no `git` section
     proceeds; a template that differs from the unit name only by zero padding is refused.

6. **The fold tool restacks the units above after a plain commit on a lower unit**: a new restack path (a flag of
   `fold.py restack` or a step of `checkpoint`; the discuss step names it) rebases the units above onto the lower unit's new tip
   without a fold rewrite and without a push.
   - Current: `fold.py restack` cascades only when the trunk moved (`flow_stack.py:344`); a plain commit on a lower unit leaves
     the units above on the old tip.
   - Target: after a plain commit on unit J, one command restacks every open unit above J locally; a conflict pauses with the
     existing `restack --continue` and `--abort` flow.
   - Acceptance: fixture-repo tests: a plain commit on the bottom of three units leaves all three on one line after the command
     and nothing is pushed; a conflicting commit pauses and `--abort` restores every branch at its starting tip; a non-vacuity
     case shows the old command leaves the units above unmoved; the units end in stack order with each parent an ancestor of
     the next; a unit with no commit of its own stays on the new tip; with no unit above the committed one the command reports
     nothing to do, and a second run after a restack reports nothing to do; fixture units include a decimal phase id; a restack
     started while one is paused is refused with `restack_pending`.

7. **The fold tool offers a read-only all-units view**: one command prints, for every recorded unit, its id, branch,
   parent, state and whether the branch exists, and changes nothing.
   - Current: `show` takes one selector; there is no all-units view.
   - Target: an all-units form of `show` (the discuss step names the flag).
   - Acceptance: a fold test with three units and one deleted branch asserts the printed rows and that the stack record bytes
     are unchanged after the call; with no recorded unit it prints an empty view and exits 0; rows come in stack order and a
     decimal phase id prints verbatim.

8. **`start` names a stale parent unit as its own reason**: when the newest unmerged unit in the record has a deleted
   branch, `start` refuses with a reason that names the stale unit instead of `no_trunk`.
   - Current: `no_trunk: <parent> does not resolve to a commit` (`flow_unit.py:222`), after which spec-discuss turns the unit flow
     off for the phase (tools-installer, phases 27-35).
   - Target: a refusal with its own reason that names the unit and its missing branch; spec-discuss shows it to the owner and
     does not turn the flow off silently.
   - Acceptance: a fixture-repo test asserts the new reason and that a plain `no_trunk` (missing remote) keeps its reason; a
     SKILL.md doc-contract test pins that a stale unit is shown to the owner, not ledgered as `unit flow off`; with no unmerged
     unit in the record `start` behaves as today; the reason names the unit's branch verbatim, including dots and slashes.

9. **A recipe table maps every refusal or symptom to the next step**: a new reference file
   (`skills/ai-kit-gsd-spec-discuss/references/branches.md`) holds one row per refusal or symptom with its action:
   `ref_mismatch`, `wrong_parent`, `plan_not_carried`, `branch_missing`, a stale unit, GSD branching in conflict, an unrecorded
   HEAD branch with local commits, an inserted phase that must sit below open units (ask the owner, number it after the top; no
   insert-below command), and a paused restack; it also holds the where-am-I output shape and the end-report template.
   - Current: no recipe; a refusal ended in hand moves of branches and of the record.
   - Target: the file exists and SKILL.md points to it at the first refusal.
   - Acceptance: a doc-contract test checks every listed reason appears with an action, and the file names no hand edit of
     `.git/ai-kit-stack.json` as an action; every refusal reason that `unit-contract.md` lists appears in the table or in an
   explicit list of reasons that never reach spec-discuss.

10. **The changed SKILL.md files meet the judge bar (JDG-04)**: `ai-kit-gsd-spec-discuss` and `ai-kit-commit-fold` (and any other
    SKILL.md this phase changes) carry new-shape evals and tests and pass the skill-judge loop.
    - Current: neither has an eval or test for the branch rules above.
    - Target: each judged result has no critical or high finding, or grade B or better, and no regression beyond the judge's
      run-to-run variation.
    - Acceptance: the judge record of each changed skill meets the bar of AGENTS.md and `make check-dogfood` validates the
      records.

## Boundaries

**In scope:**
- The spec-discuss SKILL.md rules, the new `references/branches.md`, the evals and doc-contract tests of requirements 1 to 5 and 9.
- Three fold behaviours: restack after a plain lower-unit commit, an all-units view, a named stale parent unit; their tests.
- One goal-prompt rail line (requirement 3).
- The judge loop of the changed skills.

**Out of scope:**
- An insert-below command for decimal phases (owner decision 2026-11-23: recipe row only).
- Setting or changing `git.branching_strategy` by any tool (owner decision: stop and ask).
- Repairing the home-mobility repository (its stack record and `main` are the owner's).
- Moving the fold engine into `ai-kit-project-rules` (Phase 45) and the goal-prompt learned rails (Phase 47.2).
- The run-ledger location (todo 2026-11-20 run ledger in gitignored tmp, same SKILL.md, separate work).
- The superpowers adapter's unit commands and the per-phase PR model; push-consent rules stay as they are.
- Any change to what `checkpoint`, `ready` and `merge-chain` do beyond the restack path of requirement 6.

## Constraints

- Runtime code stays stdlib-only; fold tool edits keep `flow_*.py` conventions and the `FlowError` refusal reasons; every config
  or record write stays atomic and none is added to spec-discuss.
- A restack path never pushes and never rewrites a unit's folded commits; any later push of restacked units still needs the
  existing consent.
- The skills stay portable (Agent Skills standard); the new commands are plain `fold.py` calls any host can run.
- No machine-specific absolute path in skill text, tests or the reference file.
- The branch-name check of requirement 5 reads the name GSD itself reports for the phase; which gsd-tools verb carries it, and
  whether it zero-pads the phase number (the home-mobility branch was padded), is a plan-time check.
