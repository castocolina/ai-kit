- **D-06:** Test gating has one source of truth. `tools/run_unittest_parallel.py` discovers `tests/test_*.py` by default. Two explicit exception sets remain:
  - uv-only modules run in the wizard hook;
  - the two e2e modules run in `make e2e-test`.

  The hooks and the `Makefile` tiers call it with a group flag, so a new module is gated automatically. `tests/test_gate_scope.py` (stdlib only) asserts that every discovered module lands in exactly one group and that every shipped `.py` is selected by the hooks. It has non-vacuity cases built on synthetic file lists. This also fixes today's drift, where `test_run_unittest_parallel` is in no `Makefile` tier.

  > **Amended 2026-10-14 (uz):** unit tests run in parallel, never sequentially. Every `Makefile` test tier (`test-unit`, `test-integration`, `e2e-test`, `arch-test`) runs its modules through `tools/run_unittest_parallel.py`. No tier calls a sequential `python3 -m unittest <list>` (today `Makefile:46-62` does). AGENTS.md's Testing section states this as a rule: run one subprocess per module in parallel through the runner, and add a module by placing it in a runner group, never by appending to a sequential list. A module that cannot run in parallel goes into an explicit, commented exception set, never a silent sequential path. `tests/test_gate_scope.py` asserts that no tier invokes `python3 -m unittest` directly.

  > **Amended 2026-10-14 (uz):** parallelism is never pinned to an explicit core count; it is a share of the available CPUs, capped at 40%. The runner sets `max_workers = min(len(modules), max(1, floor(0.40 * available_cpus)))`. `available_cpus` comes from `os.process_cpu_count()`, falling back to `len(os.sched_getaffinity(0))` and then to `os.cpu_count()`, so it honors affinity and cgroup limits. On uz's 24-thread machine that gives 9 workers. Today's code (`tools/run_unittest_parallel.py:31`) uses every core and must change. An optional environment override may lower the share (for example `AI_KIT_TEST_CPU_SHARE`), but it can never push the share above 40%. No Makefile, hook, plan or doc hardcodes a worker or core number (no `-j 8`, no `max_workers=12`). AGENTS.md's Testing rule states the 40% cap. Unit tests in `tests.test_run_unittest_parallel` pin it with synthetic CPU counts: 24→9, 4→1, 1→1, None→1, an override above the cap is clamped, and the result never exceeds the module count.

- **D-21:** R14: switch only when `--branch` / `AI_KIT_BRANCH` is explicit, since the default `main` does not count. The sequence is `git remote set-branches --add origin B` → `git fetch --depth 1 origin B` → `git switch -C B --track origin/B` (verified on a shallow single-branch clone). A dirty tree, detected with `git status --porcelain`, refuses. `--dry-run` prints the plan with no git mutation, and in bootstrap mode no clone. The fake `git` in `tests/test_install.sh` records every invocation.
  - **Amended 2026-10-15 (RUN-36, code review B-CR-01/B-CR-02/B-WR-01):** the original sequence left a stale refspec after a typo'd or deleted branch, which broke every later `pull --ff-only`. The explicit-branch sequence is now: `git check-ref-format --branch B`; refuse on a dirty tree, a failing `git status` or an `index.lock`; refuse when local B has commits no origin ref has (`rev-list --count refs/heads/B --not --remotes=origin`, checked before the fetch because a `--depth 1` fetch hides older history); `--dry-run` prints the plan and stops here; `ls-remote --exit-code --heads origin B` (refuse when B is not on origin); `remote set-branches --add origin B` only when that refspec is absent; `fetch --depth 1 origin B` then `switch -C B --track origin/B`, removing the refspec this run added if either fails. Without an explicit branch the update is `pull --ff-only origin <current branch>` (refused on a detached HEAD), so a leftover refspec cannot break it. `--dry-run` mutates nothing on every path, including a non-git (tarball) install.
