# Phase 16.1 — independent skill-judge evaluation

**Rubric:** `skill-judge` (8 dimensions, 120 points), applied fresh. The earlier
`16.1-SKILL-JUDGE-*.md` files were self-scored by the editing model; none of their numbers are
reused here.

**Baseline:** each `SKILL.md` at commit `302b50c`. **Current:** `HEAD` of
`gsd/v1.3-curated-config-v2` (clean tree).

**Pass rule (AGENTS.md):** no remaining Critical/Important finding, or a score of at least 96/120;
in both cases with no regression vs the baseline.

**Method:** read baseline and current text in full; ran `--help` for every named subcommand; ran
live checks in temporary directories (no real user config touched): `trust-local --show` with
both `--cwd` forms, `probe-quota` against an untrusted local config, `merge-reports` with
missing, malformed and `Failure` lanes, `apply-execution` against a scratch project, the
project-rules-agents `check`/`remediate` output shape, and the bundled codemod `rename-symbol`
on a two-line fixture.

- **Important (new in 16.1): the exit-2 paragraph is now incomplete and misdirects.** The skill
  says exit 2 means `node` or gsd-core's `gsd-tools.cjs` is missing, "not a bug in this skill".

  At `302b50c` the writes used the skill's own `gsd_write.py` and had no such dependency. The
  resolver also now prefers a project-local gsd-core (D-18), which the skill does not say either.
  **Fix:** list all three exit-2 causes (sibling skill missing, `node` missing, no gsd-core
  found, project-local first), and state in Scope that the skill needs `ai-kit-spec-review`
  installed beside it.
- **Important (pre-existing): the "bare command name" claim is false.** The NEVER rule and the
  `apply-execution` table row say `workflow.cross_ai_command` gets only the bare command name and
  never an absolute path. A live run wrote

  absolute project directory. That is the "moves machines" landmine the rule warns about. The
  cursor binary is also `cursor-agent`, not `cursor`. **Fix:** describe what is actually
  written (a rendered `build_execute_command` template whose binary is resolved through `PATH`
  but whose `--dir`/`--workspace` is the absolute project path), or change the code to match the
  rule.
- Minor: internal planning IDs (`07-CONTEXT.md D-01…D-10`, `D-18`) point at documents that do

The 16.1 change is an improvement: bootstrapping no longer depends on `CLAUDE_PLUGIN_ROOT`, and
the description names `codemod_template.py.txt`. All documented subcommands and flags match
`--help`.

- **Critical (pre-existing): `rename-symbol` creates the false positives the skill promises to
  avoid.** `RenameSymbol.leave_Name` renames every `Name` node with a matching value; it does no
  scope or qualified-name resolution. Live, the skill's own example
  (`rename-symbol --old-name connect --new-name open`) turned `sqlite3.connect(":memory:")` into
  `sqlite3.open(":memory:")`, which breaks the code. The decision table sends "name appears in
  unrelated contexts" to this codemod, which is exactly where it fails. **Fix:** either add a
  NEVER rule plus a table row ("`rename-symbol` is name-only; for names shared with
  stdlib/third-party attributes, restrict `--paths`, or use `QualifiedNameProvider` metadata")
  and replace the `connect` example, or make the transformer scope-aware.
- Minor: "Dry-run on smallest target first" implies a `--dry-run` flag that does not exist. Say
  "run on one file, then `git diff`".
- Minor: the "LibCST missing → silent partial-success" NEVER is inaccurate (the import fails at
  start-up and nothing changes). `uv add --dev libcst` contradicts the pinned
  `"libcst>=1.5,<2"` advice. `--call-value` (add-parameter) is undocumented. The `cp` target
  needs `mkdir -p tools`.
