##### Concerns

1. **HIGH — The new lease source defeats the promised concurrent-writer protection.**  
   Evidence: `.planning/phases/29.1-stacked-phase-branches-chained-prs-and-the-merge-chain-inserted/29.1-02-PLAN.md:102` prescribes leasing against “the remote tip,” while line 96 expects a second clone’s intervening push to cause `stale_lease`. The installed `gh stack submit --help`, checked read-only, explicitly says submission pushes **all active branches atomically** before updating PRs and otherwise auto-detects the remote. This matches `.planning/phases/29.1-stacked-phase-branches-chained-prs-and-the-merge-chain-inserted/29.1-SPEC.md:54`. However, the fake specified at `.planning/phases/29.1-stacked-phase-branches-chained-prs-and-the-merge-chain-inserted/29.1-01-PLAN.md:267` models submission’s PR effects without its push effects. Consequently, the tests can miss duplicate pushes, incorrect remote selection and pushes of other stack branches.

Keep the locked gh-stack backend; remove the duplicate responsibility, not the capability.

3. **HIGH — One invocation can fold several finished plans but push only once.**

This follows the existing loop in `skills/ai-kit-commit-fold/scripts/fold.py:105`, which processes multiple finished plans. Plan 02 then performs one tip comparison, push and counter increment at `.planning/phases/29.1-stacked-phase-branches-chained-prs-and-the-merge-chain-inserted/29.1-02-PLAN.md:102`. - Expose per-checkpoint results from the existing fold loop rather than adding a second loop with different semantics.

#### 29.1-03

##### Summary

The plan addresses the hardest required behavior—restacking, agent resolution, rollback and resumable merging—and appropriately fails closed when project gates are absent. Its main weaknesses are transactional: the rebase is not bounded to the intended old commit range or branch set, rollback restores refs without necessarily restoring the checkout, and successful remote operations are not consistently reconciled into durable local state. Shared-interface omissions also prevent parts of the plan from running independently as scheduled.

##### Strengths

- **Resolution is followed by explicit gates and reporting.** `.planning/phases/29.1-stacked-phase-branches-chained-prs-and-the-merge-chain-inserted/29.1-03-PLAN.md:148` specifies adapter gates, project gates, named failures and a no-project-gates refusal rather than silently treating resolution as verification.
- **Snapshots include remote expectations.** `.planning/phases/29.1-stacked-phase-branches-chained-prs-and-the-merge-chain-inserted/29.1-03-PLAN.md:112` saves local and remote tips before rebasing, providing the necessary foundation for atomic leased publication.
- **[ponytail] Reuses the existing fixture and logging patterns.** The tests can build on `tests/fold_fixtures.py:38` (`run_git`) and `tests/host_fakes.py:73` (`fake_calls`), avoiding another subprocess harness or log format. These support real local-Git behavior without real GitHub writes.

##### Concerns

1. **HIGH — The proposed rebase does not reliably isolate descendants of a rewritten lower unit.**  
   Evidence: `.planning/phases/29.1-stacked-phase-branches-chained-prs-and-the-merge-chain-inserted/29.1-03-PLAN.md:112` uses `git rebase --update-refs <moved-unit-branch>`. After folding, the new lower tip need not be an ancestor of the upper branches: `skills/ai-kit-commit-fold/scripts/fold_engine.py:439` reconstructs commits and line 308 replaces the branch tip. A plain rebase onto the new lower branch can replay old lower-unit commits as well as upper-unit work; patch-equivalence is not a reliable boundary after folding. The installed Git manual’s “Recovering from upstream rebase” section explicitly distinguishes this case and uses the old boundary with `--onto`.  
   **Required outcome:** retain the old lower tip and replay precisely `old-parent..top` onto the new parent, preserving each upper unit’s boundary. Test a lower fold that combines or changes patch boundaries, not merely a tip movement.

2. **HIGH — `--update-refs` can miss required branches and move unrecorded ones.**  
   Evidence: the same command at `.planning/phases/29.1-stacked-phase-branches-chained-prs-and-the-merge-chain-inserted/29.1-03-PLAN.md:112` snapshots only selected stacked-unit refs. Installed Git documentation confirms that `--update-refs` updates branches pointing into the replayed history, but **does not update branches checked out in another worktree**. Thus an upper unit can remain behind, while an unrelated branch in the replayed range can move without being included in restoration. This matters because the record is deliberately shared across worktrees; see `.planning/phases/29.1-stacked-phase-branches-chained-prs-and-the-merge-chain-inserted/29.1-01-PLAN.md:34`.  
   **Required outcome:** establish the complete affected-ref/worktree set before mutation. Safely refuse unsupported occupied branches or constrain updates to the recorded allowed set. Include fixtures for an occupied unit branch and an unrelated branch pointing inside the replay range.

3. **HIGH — Lower-unit rewrites are not wired into the cascade transaction, and successful cascades leave record metadata stale.**  
   Evidence: `.planning/phases/29.1-stacked-phase-branches-chained-prs-and-the-merge-chain-inserted/29.1-03-PLAN.md:112` makes `sync` respond to trunk movement, but does not define detection or invocation for a rewritten lower unit. Meanwhile, `.planning/phases/29.1-stacked-phase-branches-chained-prs-and-the-merge-chain-inserted/29.1-02-PLAN.md:102` folds and pushes that lower branch without handing off its old/new tips. Plan 03’s test at line 104 starts with the lower branch already pushed, which does not prove atomic publication of the rewritten stack. The successful cascade also has no prescribed updates to `parent_tip` and `pushed`; the inherited guard uses `parent_tip` at `.planning/phases/29.1-stacked-phase-branches-chained-prs-and-the-merge-chain-inserted/29.1-01-PLAN.md:208`.  
   **Required outcome:** define the checkpoint→cascade handoff before publishing a lower rewrite, then atomically reconcile the record’s parent and acknowledged-push metadata. Test `restack → guard → unchanged checkpoint → start next unit`, not only immediate ref equality.

4. **HIGH — Ref-only restoration does not fulfill the clean-working-tree guarantee.**  
   Evidence: `.planning/phases/29.1-stacked-phase-branches-chained-prs-and-the-merge-chain-inserted/29.1-03-PLAN.md:112` restores saved refs with `update-ref`, then switches to `branch_before`. After a completed rebase followed by gate or lease failure, the index and files still contain the rebased tree. Updating the currently checked-out branch backwards and switching to that same branch does not establish the saved tree. The existing helper documents this distinction directly in `tests/fold_fixtures.py:82`.
