# Phase 29.1: Stacked phase branches, chained PRs and the merge chain — Specification

**Created:** 2026-11-03
**Ambiguity score:** 0.13 (gate: ≤ 0.20)
**Requirements:** 13 locked

## Goal

Every finished unit of planned work, from any spec-driven system, runs on its own branch stacked on the previous
unmerged unit, is pushed at each finished plan, has one draft PR chained on the previous unit that turns ready when
the unit is verified, and reaches its target branch only through an owner-started bottom-up merge chain with merge
commits, an MVP fast path, or a hotfix that never enters the stack.

## Scope

The branch, push, PR, hotfix and merge-chain flow is **ai-kit's own** and **general**: it serves any project and any
spec-driven system (GSD, superpowers, and later grill-me, spec-kit or others) through one framework-neutral **unit**
contract and one thin adapter per system. superpowers itself governs none of this (it covers brainstorming, plans,
execution and review); GSD's own branching is only an input the GSD adapter works with. ai-kit is the first user;
it runs GSD phases and superpowers plans under the same rules. The fixture tests use one GSD fixture project, one
superpowers fixture project and one synthetic third-system adapter, never ai-kit's own repo. Two requirements are
**ai-kit dogfood**, each with its general counterpart: R11 (ai-kit's GSD config; general counterpart CUR-04,
curated-config writing branch per phase, Phase 44) and R12 (AGENTS.md's ship rule; general counterpart RULE-17, the
end-of-unit playbook, Phase 47).

**Terms used below.**
- **Unit**: one finished piece of planned work that gets one branch and one PR. A GSD phase is one unit; a
  superpowers plan is one unit.
- **Checkpoint**: a point inside a unit where its work is folded (Phase 29) and pushed. Each finished GSD plan is a
  checkpoint of its phase; a superpowers plan has one checkpoint, at its end.
- **Target branch**: a branch units merge into. Configurable per project; the default list is the project's base
  branch (`main` in ai-kit). Others may be a sandbox or staging branch.
- **Trunk**: the target branch a stack is based on.
- **Stacked unit / hotfix unit**: a stacked unit branches off the newest unmerged unit (or the trunk); a hotfix unit
  branches off its target and never joins the stack.

## Background

Live-verified on 2026-11-03 in the ai-kit checkout (scratch copies, scratch HOME, `AI_KIT_REFUSE_REAL_HOME=1`,
local bare remotes only; scripts and notes under the gitignored `tmp/p29.1/` and `tmp/p29/`):

- **GSD's branching.** gsd-core 1.18.0 keys: `git.branching_strategy` (`none|phase|milestone`), `git.base_branch`
  (unset resolves through `origin/HEAD` to `main`), `git.phase_branch_template` (`gsd/phase-{phase}-{slug}`);
  unknown keys are refused by `config-set`. ai-kit today: strategy `none`, base branch unset. With `phase`, the
  branch names are `gsd/phase-29-…`, `gsd/phase-29.1-stacked-phase-branches-chained-prs-and-the-merge-chain-inserted`,
  `gsd/phase-30-…`. `execute-phase.md` `handle_branching` forks a new phase branch off `origin/<base>` (anti-stacking,
  #2916) and reuses an existing local branch as-is. `git.base_branch` is one project-wide key that also drives
  `ship.md`'s `--base`, its commit range and diff, and the protected-branch checks; a phase branch is not protected.
- **GSD worktrees on a stacked branch.** A branch ahead of `origin/HEAD` degrades worktree execution to sequential
  unless `worktree.baseRef` is `"head"` (`.claude/settings.local.json`, `gsd-tools worktree set-baseref`). ai-kit
  already has it; a fresh project does not. A stacked phase branch is always ahead of `origin/HEAD`.
- **superpowers 7.0.0.** `finishing-a-development-branch` offers merge locally, push and open a PR against the base
  branch, or keep. Its push and PR would bypass a stack.
- **gh and gh-stack.** gh 2.101.0 with `github/gh-stack` 0.3.0. `gh stack init` adopts or creates branches, each on
  the previous; `submit --auto` pushes atomically and creates draft PRs unless `--open`; `push` uses per-branch
  `--force-with-lease`, atomic, skipping merged branches; `rebase` pulls the trunk and cascade-rebases; on a conflict
  it pauses (a rebase stays in progress) and `rebase --abort` restores every branch; `merge` is GitHub's
  all-or-nothing stack merge up to a chosen PR, `--merge` for merge commits, `--yes` non-interactive. GitHub repo
  `castocolina/ai-kit`: merge, squash and rebase allowed, auto-delete of merged branches off, default branch `main`;
  a read-only `GET repos/<repo>/stacks` answers `[]`. Creating a stack and the stack merge on GitHub were not run.
- **Plain git.** After the lower unit merges with a merge commit, the upper PR retargeted to `main` shows only its
  own commits and merges cleanly with no rebase. Because squash is never used, `merge-base --is-ancestor <unit>
  <target>` tells reliably whether a unit merged. `git rebase --update-refs <trunk>` from the top branch rebases the
  whole stack in one go; on a conflict `rebase --abort` restores every branch ref and the working tree. A stale
  `--force-with-lease` push is refused. An MVP phase branch fast-forwards into `main`, which is then pushed.
- **Hotfix with an open stack (probed both ways).** A hotfix merged into `main` while a two-unit stack is open: plain
  `rebase --update-refs origin/main` and `gh stack rebase` both move both units onto the new `main` with each unit
  keeping only its own commits; a hotfix that touches a file the lower unit changes conflicts, and abort restores
  both branches unchanged with a clean tree.
- **Health.** `validate health` reads `degraded` (W019) for `.planning/INGEST-CONFLICTS.md`, a v1.2 ingest artifact;
  moved to `.planning/milestones/v1.2-INGEST-CONFLICTS.md` it reads `healthy` with no warnings.
- **Ship rule.** AGENTS.md has no ship rule today; "merge every phase into local main" lives only in session memory.
  ai-kit's install links (`~/.claude/skills/<skill>`, `~/.pi/agent/skills/jev-fast-decision`) point into the main
  checkout, so that checkout must sit on the unit branch's tip when installing.
- **Personal settings.** `.aikit/` is gitignored in ai-kit and holds `review-spec.toml`; Phase 33 (CFG-01) inventories
  every ai-kit setting, the push consent included.
- **Phase 29 (locked).** One folding step and one policy; backup tag `ai-kit-fold/<unit>/<old-short-sha>`, local
  only; FLOW-01 amended so an unmerged pushed branch may be folded again and pushed with `--force-with-lease`.

## Requirements

1. **One neutral unit contract with thin adapters**: The flow knows only units, checkpoints and targets; each spec-driven system reaches it through a thin adapter that maps its own work onto that contract.
   - Current: no unit flow exists; Phase 29's fold step has a GSD side and a superpowers side.
   - Target: one documented unit contract names what an adapter supplies (unit id and kind, stacked or hotfix, target branch, branch name, each checkpoint's commit range and tested tip, the unit-finished and verification-passed signals) and what the flow does at each signal; a GSD adapter (phase = unit, finished plan = checkpoint) and a superpowers adapter (plan = unit, one checkpoint at its end) ship now; superpowers' own merge and PR options are not used for a unit.
   - Acceptance: a synthetic third adapter in a fixture project drives the whole flow (branch, checkpoint push, draft PR, ready, merge chain) with no change to the flow's code; a text test fails when the flow's core code or policy names GSD or superpowers outside the adapters, with a non-vacuity case.
   - Scope: general.

2. **One stack per repository**: A new stacked unit branches off the newest unmerged unit of any kind, or off the trunk when no unit is unmerged.
   - Current: GSD forks every phase branch off `origin/<base>`; nothing stacks.
   - Target: the unit's branch exists on the right parent before the system starts work on it (for GSD, before `handle_branching`, which then reuses it); a unit started after the previous one merged branches off the updated trunk.
   - Acceptance: in the GSD fixture, phase B's branch starts at phase A's tip; a superpowers plan started next starts at B's tip; after A merges, the next unit starts on the trunk; the same holds in the superpowers fixture with plans only.
   - Scope: general.

3. **A push at every checkpoint**: Each checkpoint's folded tip is pushed to its unit branch on the primary remote.
   - Current: nothing pushes; GSD's `ship` pushes once per phase.
   - Target: after the checkpoint's fold, the unit branch is pushed; the first push of a unit is a plain push; a push after a rewrite of that unmerged branch uses `--force-with-lease` with the expected remote tip.
   - Acceptance: in both fixtures, after each checkpoint the bare remote's branch tip equals the local folded tip; a GSD phase with two plans gives two pushes.
   - Scope: general.

4. **One chained draft PR per unit**: Each unit has one PR against the previous unit's branch (or the trunk), opened as a draft at the unit's first push and marked ready when the unit finishes and its verification passes, through gh-stack when installed and plain `gh` otherwise.
   - Current: no PRs are opened; GSD's `ship.md` opens one against `git.base_branch`.
   - Target: the PR's base is the unit's parent branch; it stays a draft until the unit-finished and verification-passed signals; with gh-stack the units form one GitHub stack, with plain `gh` each PR carries `--base <parent>`; a missing or failing gh-stack falls back to plain `gh` with the same bases.
   - Acceptance: with fakes for `gh` and gh-stack recording their calls, both backends give the same base per PR, draft at first push, ready only after verification passes; a unit whose verification fails stays a draft; with gh-stack absent the plain path runs.
   - Scope: general.

5. **Force-push and remote bounds**: Pushes go to the primary remote only; a rewritten branch is pushed only with `--force-with-lease`, and only when it is a unit branch whose PR has not merged.
   - Current: no rule in code.
   - Target: the primary remote is the project's `origin` unless the project names another; target branches and merged unit branches are never force-pushed or rewritten; PRs are opened only when the primary remote is on GitHub, and on another forge the flow pushes and reports that PRs are not supported there.
   - Acceptance: fixtures refuse a forced push to a target branch and to a merged unit branch with a named reason and the remote unchanged; a stale lease is refused with the remote unchanged; a structural test fails on any `--force` without a lease, or any push to a remote other than the primary, in the flow's code, with a non-vacuity case.
   - Scope: general.

6. **Cascade the stack when a lower branch or the trunk moves**: When a lower unmerged unit is rewritten (folded again) or the trunk moves, every unmerged unit above is rebased onto its new parent and the stack is pushed atomically with `--force-with-lease`; a conflict restores every branch and stops.
   - Current: nothing rebases a stack.
   - Target: each upper unit keeps exactly its own commits on the new parent; with gh-stack through its rebase and push, with plain git through one `rebase --update-refs` from the top; on a conflict the flow aborts the rebase itself (gh-stack leaves it paused), every branch and the working tree are back where they were, nothing is pushed, and the report names the unit and the conflicting paths.
   - Acceptance: clean and conflicting fixtures for both backends; after a clean cascade each unit's range holds only its own commits and the remote matches; after a conflict every local and remote branch equals its starting tip and the tree is clean.
   - *Amended 2026-11-03 (29.1 D-07):* owner rule — a rebase conflict is resolved, not only stopped on. An agent resolves each conflicting file keeping both sides' intent, with GSD's planning files merged by content; then the project's gates and tests run on the resolved stack, and only then is it pushed; the report names every resolved file and how it was resolved. The flow restores every branch and stops only when the resolution fails or the gates fail. Acceptance adds: a fixture whose hotfix and lower unit both change `STATE.md` and one code file resolves both, passes the gates, pushes, and lists both files with how each was resolved; a fixture whose resolution leaves a failing test restores every local and remote branch to its starting tip with a clean tree.
   - Scope: general.

7. **A hotfix never enters the stack**: A hotfix unit branches off its target branch, has its own PR to that target (or the MVP fast path), and is never stacked; after it merges into the trunk of an open stack, the stack is cascaded onto the updated trunk (R6).
   - Current: no hotfix path; GSD's `quick` workflow has its own optional branch template.
   - Target: the owner starts a hotfix naming its target from the project's configured target branches; the hotfix branch starts at the target's remote tip; its PR's base is the target; a hotfix into a target that is not the open stack's trunk leaves the stack untouched.
   - Acceptance: a fixture with a three-unit open stack takes a hotfix to `main` that merges first, then the stack cascades onto the new `main` and the merge chain still merges it; a hotfix to a configured `staging` target leaves the stack's branches unchanged; a hotfix naming an unconfigured target is refused with a named reason.
   - *Amended 2026-11-03 (29.1 D-06):* a hotfix may change `.planning/` like any unit; GSD's own STATE, ROADMAP and REQUIREMENTS tracking is not restricted or bypassed, and the conflicts this causes in the cascade are resolved under R6's amended rule.
   - Scope: general.

8. **The owner-started merge chain**: One owner-started command merges every ready PR bottom-up with merge commits, stops at the first draft, failing check or conflict, and a rerun resumes.
   - Current: no merge chain; the owner merges by hand into local `main`.
   - Target: merge commits only, never squash or rebase; an optional argument stops the chain at a lower unit; with gh-stack one stack merge with the merge method up to the last ready PR; with plain `gh` one PR at a time, the next PR retargeted to the trunk before its parent's branch can go; after the run local trunk fast-forwards to the remote trunk even when the checkout sits on a unit branch, and each merged unit's local backup tags (`ai-kit-fold/<unit>/…`) are deleted; the report names what merged and where it stopped.
   - Acceptance: with a fake forge, a three-unit stack whose middle PR is a draft merges only the bottom unit and stops naming the draft; a rerun after it turns ready merges the rest; no fake call uses squash or rebase; local trunk equals the remote trunk afterwards; merged units' backup tags are gone and unmerged units' tags remain.
   - Scope: general.

9. **The MVP fast path**: When the unit's MVP mode is on and nothing unmerged sits below it, the unit branch fast-forwards into its target, and the target is pushed after each checkpoint, with no PR and no review step; otherwise the flow refuses with a named reason and stays on the PR path.
   - Current: no MVP path in any flow.
   - Target: the MVP signal comes from the adapter (for GSD, `phase.mvp-mode` active); a target that moved so the fast-forward is impossible refuses with a named reason and never makes a merge commit.
   - Acceptance: a main-only fixture in MVP mode ends each checkpoint with the remote target equal to the unit tip and no PR call; an MVP unit above an unmerged unit is refused and opens a draft PR instead; a diverged target is refused with the target unchanged.
   - Scope: general.

10. **One-time push consent per project**: Pushes, PRs and hotfix PRs need the owner's consent once per project, recorded in the personal, gitignored ai-kit settings until revoked.
    - Current: no consent record exists.
    - Target: the first push asks once; a revoke command removes the record; with no consent the flow still commits and folds locally, skips every push and PR, and lists them; the first run after consent pushes what was skipped; the record is written only to a file git ignores in that project.
    - Acceptance: with no record, a fixture checkpoint makes no remote call and its report lists the skipped push; after consent the next checkpoint pushes the backlog; after revoke the next checkpoint skips again; with the settings file not ignored the record is refused with a named reason.
    - Scope: general.

11. **ai-kit's GSD config runs the flow**: ai-kit's `.planning/config.json` reads branch per phase, set through the project's `gsd-tools`, and the planning health check is clean.
    - Current: `git.branching_strategy` is `none`; `validate health` is degraded (W019, `INGEST-CONFLICTS.md`).
    - Target: `git.branching_strategy` is `phase`, written with `gsd-tools config-set`; the keys the flow relies on are the live-verified ones; `INGEST-CONFLICTS.md` is archived to `.planning/milestones/v1.2-INGEST-CONFLICTS.md`; the clean health check stays checked by the live-project check, never by a test that reads `.planning/`.
    - Acceptance: `gsd-tools config-get git.branching_strategy` prints `phase`; `gsd-tools validate health` reads `healthy` with no warnings; the live-project check fails when health degrades.
    - Scope: ai-kit dogfood; general counterpart CUR-04 (Phase 44).

12. **AGENTS.md states how a finished unit ships**: AGENTS.md's Workflow section states the ship rule and a doc-contract test pins its steps.
    - Current: no ship rule in AGENTS.md; the old "merge every phase into local main" lives in session memory only.
    - Target: the rule says gates green on the unit branch, an installer dry run and the new hooks against a scratch HOME, then the main checkout on the unit branch's tip for the install and a live re-check, and local `main` moves only when the stacked PRs merge; it replaces the old rule.

## Constraints

- Runtime scripts stay stdlib-only under system python3; outside tools are `git`, plus `gh` and gh-stack only when
  present.
- No test calls a real `gh`, gh-stack or GitHub, and no test reads the repo's `.planning/` (Phase 28); fixtures use
  temporary repos with local bare remotes and fakes that record calls.
- No `reset --hard`, `git clean -f`, `checkout .` or `restore .`; a cascade that fails leaves every branch where it
  started.
- Merge commits only; nothing squashes or rebase-merges a PR.
- Target branches and merged unit branches are never rewritten or force-pushed; every force-push carries a lease.
- No absolute machine path in source, tests or fixtures; no key or token is printed or logged.
