## Summary

I reviewed the unit-flow core (`flow_git`, `flow_record`, `flow_unit`, `flow_pr`, `flow_mvp`,
`flow_stack`, `flow_merge`), the `fold.py` and `fold_adapters.py` wiring, the GSD capability
(`ai-kit-fold.cjs`, `capability.json`), `tools/check_dogfood.py`, `tools/flow_live_check.py`, the
skill and reference text, and the test fakes. The scope is `git diff c3a73b3..HEAD`.

The lease and push choke point is well shaped: one argv builder, recorded-sha leases, and target and
merged-branch bounds. The weak spots are the steps around it.

- After a successful push, the record is written only once the follow-up `gh` call succeeds. A
  `gh` failure leaves the record behind the remote, and every later command then refuses with
  `stale_lease` (CR-01).
- The PR number is parsed from stdout and stderr joined together, so any `gh` warning loses it
  (CR-02).
- `merge-chain --until` with an unknown id merges the whole ready stack (CR-03).
- Reusing a unit whose local branch was deleted recreates it at the parent tip. The next leased
  push then rewinds the remote branch (CR-04).
- The merge chain was tested only against a fake forge, which does not model GitHub's
  `StatusContext` checks, `SKIPPED`/`NEUTRAL` conclusions, the async `mergeable: UNKNOWN` state,
  or merge queues. The owner-attended live run (FLOW-11) has not been done. Several merge-chain
  findings (WR-02, WR-03, WR-04) come from that gap.

One finding was proven with a scratch git probe (`tmp/phase29.1-close/update_refs_probe.sh`).
`git rebase --update-refs` does not move an empty unit at the old boundary, yet the flow records
that unit's parent tip as moved (WR-06). The other findings come from reading the code.

I checked the executor gaps the orchestrator named; each is filed below. Short answers:

- **gh-stack cascade:** the docs do not claim it (IN-10).
- **`reset --soft` in plan 04:** no shipped code or doc tells anyone to reset (IN-11).
- **`restack_needed` and `trunk_moved`:** confirmed dead. Nothing raises them, and four codes
  that the code does raise are missing from the docs (IN-06).
- **Untested edge lines:** each one, with the cheap test that would cover it, is in WR-15.

## Critical Issues

### CR-01: A successful push followed by a failing `gh` call leaves the record stale and wedges the unit on `stale_lease`

**File:** `skills/ai-kit-commit-fold/scripts/flow_unit.py:49-54`, `flow_unit.py:273-283`, `flow_unit.py:230-232`
**Severity:** high
**Issue:** `catch_up` pushes, sets `entry["pushed"] = pending` in memory, then calls
`flow_pr.open_draft`. `write_record` runs only after that call. `open_draft` raises `pr_failed`
whenever `gh` exits non-zero: gh missing (`run_gh` returns 127), gh signed out, a network error,
or "a pull request for branch … already exists". `_publish` has the same shape: it pushes at
line 273, then calls `ensure_pr`/`open_draft` or `update_pr`, and `_checkpoint` writes the record
only at line 232.

When the `gh` step raises, the record on disk still holds the old `pushed` sha while the remote is
at the new tip. The next command leases on the old sha (`--force-with-lease=refs/heads/B:<old>`),
git rejects it with "stale info", and the flow refuses `stale_lease`. Every later
checkpoint, start or ready does the same, and SKILL.md tells the agent "Show the owner; never
force". The only recovery is a hand edit of `ai-kit-stack.json`.

A single transient failure of `gh pr edit` after a push is enough. `catch_up` also skips
`ensure_pr`'s graceful "gh not found / not signed in" handling (see WR-11).
**Fix:** persist the push before any forge call, and degrade the PR step:
```python
flow_git.push(repo, settings, record, [(unit.branch, entry["pushed"], None)])
entry["pushed"], entry["pending"] = new_tip, None
write_record(repo, record)          # the remote moved; record it now
try:
    ... ensure_pr / update_pr ...
except FlowError as exc:            # PR trouble never un-records a push
    notes.append(f"PR step failed: {exc.reason}: {exc.detail}")
```
Apply the same order in `catch_up`, and call `ensure_pr` there instead of `open_draft`. Add a test
in `tests/test_flow_checkpoint.py` that makes the fake `gh pr edit` fail once, then runs a second
checkpoint and asserts it does not refuse `stale_lease`.

### CR-02: The PR number is parsed from stdout plus stderr, so any `gh` warning records `pr: None`

**File:** `skills/ai-kit-commit-fold/scripts/flow_pr.py:30`, `flow_pr.py:83-84`
**Severity:** high
**Issue:** `run_gh` returns `stdout + stderr`, and `open_draft` takes
`text.strip().rsplit("/", 1)[-1]`. `gh pr create` writes warnings to stderr; for example, it
prints `Warning: N uncommitted changes` whenever `git status --porcelain` is non-empty, and
untracked files count. The text then ends `…/pull/12\nWarning: 1 uncommitted change`, `isdigit()`
fails, and `entry["pr"]` becomes `None` even though the PR exists.

The next checkpoint sees `pr is None` and runs `gh pr create` again. That fails with "already
exists", the flow raises `pr_failed` after the push, and CR-01 wedges the unit. `ready` on a
`pr: None` unit marks it ready without touching any PR (WR-13). The fake `gh`
(`tests/forge_fakes.py:161`) prints only the URL, so no test can catch this. This repo's own
checkout usually has untracked files, so the fault is likely to show up on the first live run.
**Fix:** parse stdout only, with an anchored pattern:
```python
_PR_URL = re.compile(r"/pull/(\d+)\s*$", re.MULTILINE)
proc = subprocess.run([...], capture_output=True, check=False)
match = _PR_URL.search(proc.stdout.decode("utf-8", "replace"))
return int(match.group(1)) if match else None
```
A cheaper alternative is to follow the create with `gh pr view <branch> --json number`. Make the
fake `gh` write a warning to stderr on `create` so the test pins the behaviour.

### CR-03: `merge-chain --until <typo>` merges every ready PR in the stack

**File:** `skills/ai-kit-commit-fold/scripts/flow_merge.py:216-246`; `fold.py` (merge-chain parser)
**Severity:** high
**Issue:** `--until` is never checked against the record. `_chain` breaks only when
`until == entry["id"]`. An id that is misspelled, already merged or belongs to a hotfix never
matches, so the loop merges every ready PR to the trunk. These are irreversible remote merges
beyond what the owner asked for, made by the one command SKILL.md lets run only "when the owner
asks". `_stack_chain` has the same hole (line 194).
**Fix:** refuse before the lock, any `_view` call or any merge:
```python
if until is not None and until not in {e["id"] for e in unmerged}:
    raise FlowError("bad_value", f"--until {until} is not an unmerged stacked unit")
```
Add a test in `tests/test_flow_stack.py`: `--until nope` refuses `bad_value`, and the fake log
shows no `pr merge` call.

### CR-04: `start` on a recorded unit whose local branch is gone recreates it at `parent_tip`, and the next leased push rewinds the remote branch

**File:** `skills/ai-kit-commit-fold/scripts/flow_unit.py:170-174`, `flow_unit.py:84-87`, `flow_unit.py:271-276`
**Severity:** high (data loss on the remote)
**Issue:** For an existing entry, `_start` calls `_check_parent`, which returns early when the
branch does not resolve (lines 74-75). It then calls `_switch(repo, branch, existing["parent_tip"])`,
which creates the branch at the parent tip. The unit's real commits are on the remote at
`entry["pushed"]`, but the local branch now has none of them.

The next `checkpoint` finds nothing to fold. `_publish` sees `new_tip (= parent_tip) != pushed`
and pushes with `--force-with-lease=refs/heads/B:<pushed>`. The remote is still at `pushed`, so
the lease holds and the remote branch is rewound to the parent tip. The PR loses every commit.
The trigger is a local `git branch -D` of a pushed unit, a common clean-up.
**Fix:** in `_start` (and `_switch`), recreate a missing branch from `entry["pushed"]` (or
`entry["pending"]`) when one is set; otherwise refuse `wrong_parent` or a new `branch_missing`.
`_publish` should also refuse a push whose new tip is not a descendant of `entry["pushed"]`,
unless a fold or cascade recorded that rewrite in this run.

## Warnings

### WR-01: `merge-chain` merges and retargets PRs without push consent

**File:** `skills/ai-kit-commit-fold/scripts/flow_merge.py:271-283`, `flow_merge.py:99-104`, `flow_merge.py:138`
**Severity:** medium
**Issue:** SKILL.md:96, unit-contract.md:122 and the README say that pushes and PRs need push
consent. `cmd_merge_chain` never checks it. Without consent, `_fetch` is skipped, `gh pr merge`
and `gh pr edit --base` still run, and then `_retire` → `delete_remote` refuses `no_consent` with
the detail "nothing was pushed". By then the PR is already merged on GitHub and recorded merged
locally.
**Fix:** at the top of `cmd_merge_chain`, `if not consented(repo): raise FlowError("no_consent", ...)`.

### WR-02: The check-state logic misreads GitHub status contexts and skipped or neutral check runs

**File:** `skills/ai-kit-commit-fold/scripts/flow_merge.py:77-85`
**Severity:** medium
**Issue:** `statusCheckRollup` mixes `CheckRun` entries (`status`, `conclusion`) with
`StatusContext` entries (`state`, no `conclusion`). A commit status always yields
`conclusion == ""` here, so the chain reports "check pending" forever. `SKIPPED` and `NEUTRAL`
conclusions, common for conditional workflow jobs, are reported as "check failing". This fails
safe, since it stops rather than merges, but it blocks real repositories. The fake only emits
`{"conclusion": ...}` (`tests/forge_fakes.py:192`).
**Fix:** read `conclusion or state`. Treat `SUCCESS`, `SKIPPED` and `NEUTRAL` as passed, and
`PENDING`, `QUEUED`, `IN_PROGRESS`, `EXPECTED` or an empty value as pending. Add fake entries of
both shapes.

### WR-03: `mergeable: UNKNOWN` after a retarget is reported as "conflict"

**File:** `skills/ai-kit-commit-fold/scripts/flow_merge.py:94-95`, `flow_merge.py:228-243`
**Severity:** medium
**Issue:** GitHub computes mergeability asynchronously. Right after `_retarget` changes the next
PR's base, `gh pr view --json mergeable` usually returns `UNKNOWN`. `_stop_reason` treats
anything but `MERGEABLE` as "conflict", so on a real forge the chain will usually stop after the
first merge and give the wrong reason. The fake always answers `MERGEABLE`.
**Fix:** report `UNKNOWN` as its own reason ("mergeability pending"). Re-view a bounded number
of times (for example three times, 2 s apart) before stopping, and keep "conflict" for
`CONFLICTING`.

### WR-04: A unit is recorded merged and its remote branch deleted without checking that GitHub merged it

**File:** `skills/ai-kit-commit-fold/scripts/flow_merge.py:234-244`, `flow_merge.py:198-210`
**Severity:** medium (unverified against a live forge)
**Issue:** After `gh pr merge` exits 0 (or `gh stack merge` in `_stack_chain`, which marks the
whole ready prefix merged), the unit is set `merged` and `_retire` deletes its remote branch. On
a repository with a merge queue, or anywhere the call queues instead of merging, the PR is not
merged yet. Deleting its head branch closes the PR. The local branch survives only because of the
`is_ancestor` check at line 152.
**Fix:** after `_fetch`, require `flow_git.merged_on_remote(...)` (or `gh pr view --json state`
returning `MERGED`) before `_retire`. Otherwise stop with `stopped at <id>: merge not confirmed`.

### WR-05: The stale-lock takeover in `chain_lock` races

**File:** `skills/ai-kit-commit-fold/scripts/flow_merge.py:47-67`
**Severity:** medium
**Issue:** There are two windows.
1. Between `os.open(O_CREAT|O_EXCL)` and `handle.write(pid)`, the file is empty. A second run
   reads `held = 0`, treats the lock as dead, unlinks it and takes it, so both runs hold the lock.
2. Two runs that both see a dead pid both `unlink`. The second unlink can remove the lock the
   first run just created.

This is the plan's "R8 concurrency" line.
**Fix:** use `fcntl.flock(fd, LOCK_EX | LOCK_NB)` on a persistent lock file (stdlib, released
automatically when the holder dies; the pid is written only for the report). A smaller fix: write
the pid to a temp file and `os.link()` it into place atomically, and treat an empty or unreadable
lock as held, not dead.

### WR-06: A cascade records a moved parent tip for an empty unit at the boundary that `--update-refs` did not move (proven)

**File:** `skills/ai-kit-commit-fold/scripts/flow_stack.py:214-221`, `flow_stack.py:237-244`
**Severity:** medium
**Issue:** `git rebase --update-refs --onto NEW OLD TOP` moves only refs that point into
`OLD..TOP`. A unit with no commits of its own sits exactly at `OLD` and is left in place. The
probe `tmp/phase29.1-close/update_refs_probe.sh` confirms this: `unitA` stays at `old` while
`unitB` lands on `new`. `_rebased` still assigns that unit `parent_tip = new`. On the next
command, `_check_parent` asks `is_ancestor(new, old)`, which is false, and the unit refuses
`wrong_parent` for good; the skill text forbids moving it by hand.

This happens when two units are started back to back and the trunk moves, or when a refold
cascades over an empty unit above the moved one.
**Fix:** in `_rebased`, move a unit whose tip still equals `old` to `new` with
`update-ref refs/heads/<b> <new> <old>`, inside the saved-tips restore set. Alternatively, keep
its `parent_tip` at its actual tip. Add the probe's shape as a test in `tests/test_flow_stack.py`.

### WR-07: `checkpoint --phase` and `checkpoint --plan` fold whatever branch HEAD is on, not the unit's branch

**File:** `skills/ai-kit-commit-fold/scripts/fold.py` (`_phase_step`, `_plan_step`); `fold_adapters.py:238`, `fold_adapters.py:299`
**Severity:** medium
**Issue:** `_checkpoint_step` (`--unit`/`--unit-id`) refuses `ref_mismatch` unless the checkpoint
ref is the unit branch. The `--phase` and `--plan` steps build the checkpoint from `_current(repo)`,
which is HEAD's branch. If HEAD is on another branch, such as the unit above or a trunk checkout,
that branch is folded. `_cascade_if_moved` then compares the unit's own, unchanged tip, and
`_publish` pushes the unit branch unchanged. The unit stack is rewritten on the wrong branch.
**Fix:** one guard in `flow_unit._checkpoint`, before `args.fold_step`:
`if flow_git.head_branch(repo) != unit.branch: raise FlowError("ref_mismatch", ...)`.

### WR-08: A `FoldError` from `superpowers_checkpoint` escapes the flow as a traceback

**File:** `skills/ai-kit-commit-fold/scripts/fold.py` (`_plan_step`); `flow_unit.py:147-153`
**Severity:** medium
**Issue:** `superpowers_checkpoint` raises `FoldError` (detached HEAD, a `--base` that does not
resolve, a `git_error` from merge-base; `fold_adapters.py:86-93`, `302-307`). `_plan_step` calls
it outside `fold_engine.fold`'s own catch, and `flow_unit._run` catches only `FlowError`. The
command crashes with a Python traceback instead of a rendered `refused <reason>` report, which
breaks the report contract the adapters parse.
**Fix:** wrap the call in `_plan_step` with `except FoldError as exc: raise FlowError(exc.reason, exc.detail) from exc`,
or catch `FoldError` next to `FlowError` in `flow_unit._run`.

### WR-09: The resolution check rejects valid files and crashes on a delete resolution, and a rejection discards the agent's work

**File:** `skills/ai-kit-commit-fold/scripts/flow_stack.py:356-366`, `flow_stack.py:433-438`
**Severity:** medium
**Issue:**
1. Any line that is exactly `=======` counts as a conflict marker. That is a valid setext or RST
   underline for a 7-character heading, such as "Install" or "Example". `bad_resolution` then
   runs `_abort_and_restore`, which discards the whole resolution.
2. A modify/delete conflict resolved by deleting the file makes `open()` raise
   `FileNotFoundError`. That is not a `FlowError`, so the crash leaves the rebase paused with no
   report.
**Fix:** flag `=======` only when a `<<<<<<<` line appears before it in the same file. Skip
paths
that no longer exist (stage the deletion with `git rm --cached -q`). On `bad_resolution`, keep the
rebase paused and refuse, so the agent can fix the files and re-run `--continue`; leave
aborting to an explicit `--abort`.

### WR-10: A gate command that is not installed crashes mid-restack

**File:** `skills/ai-kit-commit-fold/scripts/flow_stack.py:409-423`
**Severity:** medium
**Issue:** `subprocess.run(argv, ...)` on a gate whose binary is missing raises
`FileNotFoundError`, an uncaught traceback. The top unit is left checked out, the restack file
stays, and every later command refuses `restack_pending`. Gates come from settings typed by the
owner, so a typo is plausible.
**Fix:** catch `OSError` per gate, report it as `<label> fail (not found)`, and take the same
`_abort_and_restore` path as a non-zero exit.

### WR-11: `catch_up` bypasses `ensure_pr` and the MVP path

**File:** `skills/ai-kit-commit-fold/scripts/flow_unit.py:42-56`
**Severity:** medium
**Issue:** `catch_up` pushes the pending tip to the unit branch and calls `open_draft` directly.
This has two effects:
1. gh missing or signed out refuses the whole `start`/`checkpoint`/`ready` (feeding CR-01),
   where the normal path reports "no PR opened".
2. An MVP unit checkpointed without consent is caught up as a normal unit: it gets a draft PR,
   and its target is never fast-forwarded. This contradicts unit-contract.md:103-105 ("No PR is
   opened").
**Fix:** route `catch_up` through the same publish helper as `_checkpoint` (MVP branch,
`ensure_pr`, persisting the record before the forge call).

### WR-12: A parent merged outside the chain leaves the child PR on the old base, and `merge-chain` then refuses `base_mismatch` forever

**File:** `skills/ai-kit-commit-fold/scripts/flow_stack.py:330-335`; `flow_merge.py:219-224`
**Severity:** medium
**Issue:** `_sync_restacked` records an externally merged unit as merged but never retargets the
PR above it. `base_of` now says the child's base is the trunk, so `_chain` expects the trunk and
the PR's real base (the merged parent's branch) fails the check before any merge. GitHub
retargets automatically only when the parent's head branch is deleted. Nothing here deletes it,
because `_retire` runs only inside the chain.
**Fix:** when a sync records a unit merged (with consent), run `flow_pr._plain_bases` for the
units above it, or let `merge-chain` retarget a PR whose base is a recorded-merged unit instead
of refusing.

### WR-13: `ready` on a unit with no PR number reports done, and `merge-chain` later runs `gh pr view None`

**File:** `skills/ai-kit-commit-fold/scripts/flow_unit.py:315-320`; `flow_merge.py:70-74`, `flow_merge.py:219-220`, `flow_merge.py:258`
**Severity:** medium (known gap, plan 03 "No-PR units")
**Issue:** With `entry["pr"] is None` (non-GitHub remote, gh missing at first push, or CR-02),
`_ready` sets `state = "ready"` and returns `done` without saying that no PR exists.
`merge-chain` then passes `str(None)` to `gh pr view` and refuses `pr_failed` with gh's text,
not a named reason.
**Fix:** `_ready` should add the line "no PR to mark ready". `_chain` and `_hotfix` should refuse
`no_pr` naming the unit before any `_view`. Add `no_pr` to unit-contract.md.

### WR-14: The docs say a refusal changes nothing and that the PR opens against the target; neither is always true

**File:** `skills/ai-kit-commit-fold/SKILL.md:80`, `references/unit-contract.md:153`, `references/unit-contract.md:99-100`
**Severity:** medium
**Issue:** "A refused flow command changed nothing" and "`1`: refused; nothing was changed" are
false in several cases:
- `catch_up` pushes and then the command refuses.
- A cascade refuses `conflict` with a paused rebase.
- `merge-chain` refuses after merging earlier PRs.
- A fold rewrites the branch and then `_publish` refuses (`mvp_diverged`, `pr_failed`).

Agents follow this sentence, and the project rule forbids presenting results with more certainty
than verified. Separately, unit-contract.md:100 says the first push "opens a draft PR against the
unit's target", but `base_of` (`flow_pr.py:54-62`) uses the parent unit's branch while that
parent is unmerged.
**Fix:** reword to "a refusal stops the command; steps before it (catch-up pushes, a fold, earlier
merges) stay done and are listed in the report". Also state the base rule as `base_of` implements
it.

### WR-15: Untested edge lines from plans 01-03 (assessment of the named executor gaps)

**File:** tests (`tests/test_flow_stack.py`, `tests/test_flow_checkpoint.py`, `tests/forge_fakes.py`)
**Severity:** medium overall (each is a real gap; two hide real defects found above)
**Issue and cheap test for each:**
- **Lock takeover:** a real gap, and the code is racy (WR-05). Cheap: `chain_lock(repo, pid_alive=lambda _p: False)`
  with a pre-written lock file holding a pid, asserting entry and clean-up. The seam already
  exists, so this is a unit test in `tests/test_flow_stack.py`.
- **R8 concurrency:** a real gap. A true two-process race is not cheap, but an empty lock file
  (the WR-05 window) asserted to refuse `chain_locked` is a cheap test once the fix lands.
- **No `--squash`/`--rebase`:** the structural rule `check_flow_merge_method` (`tests/test_arch.py:950`)
  covers the source text. For behaviour, the cheap test asserts that every `pr merge` entry in the
  fake log has `--merge`, inside the existing bottom-up merge test (`test_flow_stack.py:496`).
  Acceptable as recorded.
- **Staging hotfix:** a real gap. Cheap: `settings set --target main --target staging`, `hotfix
  --target staging`, then assert every stacked branch tip and the record's stacked entries are
  unchanged (`test_flow_stack.py`).
- **No-PR-number refusal:** a real defect, not only a gap (WR-13). Cheap after the fix: write a
  record with `pr: null` and assert `merge-chain` refuses `no_pr` with no `gh` call.
- **`ready` on a superpowers plan:** a real gap. Cheap in `tests/test_flow_checkpoint.py`:
  `start --plan`, `checkpoint --plan --final`, `ready --plan`, then assert the fake PR is not a
  draft. Note that `signals` are `(None, None)` for `--plan`, so `not_verified` can never fire
  there. Readiness rests wholly on the caller (`fold-step.md`); document that.
- **`gh stack --help` probe:** partly covered. The live-check fixture installs a `STACK_PROBE`
  wrapper (`tests/test_flow_contract.py:1056`, `:1094`), so the probe runs at integration level.
  There is still no unit test of `flow_pr.backend` itself. Cheap: patch `flow_pr.run_gh` to
  return `(0, "")` for `stack --help` and `(1, ...)` otherwise, and assert `gh-stack` versus `gh`
  with `AI_KIT_FLOW_PR_BACKEND` unset.
- **The fakes do not model the forge behaviours behind CR-02, WR-02, WR-03 and WR-04** (stderr
  warnings, `StatusContext`, `UNKNOWN` mergeability, queued merges). Add opt-in fake switches.
