**Gathered:** 2026-11-03 (interactive, standard discuss mode `--analyze --all --batch`, after 29.1-SPEC.md; best over easy, DESIGN-01)
**Status:** Ready for planning

<domain>
## Phase Boundary

ai-kit's own, framework-neutral unit flow: every unit of planned work (a GSD phase, a superpowers plan, later any
other system through a thin adapter) gets a branch stacked on the newest unmerged unit at its first planning commit,
a fold and push at each checkpoint, one chained draft PR that turns ready after verification, and reaches its
target only through the owner-started merge chain, the MVP fast path or a hotfix that never enters the stack. The
fold itself and the jev ladder are Phase 29.
</domain>

<decisions>
## Implementation Decisions

### Where the flow lives and when a unit starts

- **D-01: A unit's branch is created at the unit's first planning commit (spec, discuss or plan), on the stack
  top.** Each PR then carries the whole unit: spec, decisions, plans and code; main moves only through merges.
  - Live: gsd-core 1.18.0's `execute-phase.md` declares `execute:pre` but dispatches no hook before
    `handle_branching`, which forks a new branch off `origin/<base>` and reuses an existing one as-is; planning
    workflows commit on the checked-out branch; `discuss:pre` and `plan:pre` are dispatched; spec-phase has no hook
    point, so `ai-kit-gsd-spec-discuss` calls the start command itself before its first commit.
  - A wave-1 guard (`execute:wave:pre`) refuses when the phase branch's parent is not the recorded one (SPEC R2
    edge).
  - Owner choice (recommended). — **Reversibility:** costly — every adapter's start point and the spec-discuss
    skill depend on it.
- **D-02: `ai-kit-commit-fold` grows into the unit-flow engine.** One stdlib script with the commands `start`,
  `checkpoint` (fold, then push), `ready`, `hotfix`, `restack`, `merge-chain` and `consent` (grant, revoke,
  status); the unit contract and its adapter guide sit in the skill's `references/` beside the folding policy. It
  moves into `ai-kit-project-rules` in Phase 45 with the fold (RULE-27). Owner choice (recommended).
- **D-03: GSD adapter: `git.base_branch` stays unset; the flow pre-creates the phase branch; a `ship:pre` gate
  points GSD's ship step to the flow; the adapter sets `worktree.baseRef` to `head` through `gsd-tools worktree
  set-baseref` when worktrees are on.** Checkpoint at `execute:wave:post` with Phase 29 D-02's fold; ready at
  `verify:post` (D-11, D-13). The Phase 29 D-02 spike also proves the `discuss:pre`, `plan:pre`, `ship:pre` and
  `verify:post` hooks; if a hook form cannot run the command, planning returns to the owner (Phase 29 D-02 rule).
  - Live: `git.base_branch` drives ship's `--base`, its commit range and diff and the protected checks; a branch
    ahead of `origin/HEAD` degrades worktrees to sequential unless `worktree.baseRef` is `head` (ai-kit already has
    it in the gitignored `.claude/settings.local.json`).
  - Owner choice (recommended).
  - *Amendment after cross-AI review (2026-11-04):* the installed gsd-core workflows do not dispatch three of the
    hook points named above, so the capability registers only the points that run, and the rest are flow commands
    the commit-fold SKILL text tells the orchestrator to run. Real hooks: a `discuss:pre` step `ai-kit-fold start`
    (`discuss-phase.md:296-301` applies every active entry; `references/loop-hook-dispatch.md:45-56` runs
    `ref.command`), the `execute:wave:post` step `ai-kit-fold checkpoint` (`execute-phase.md:984-995`), and a blocking
    `ship:pre` gate (`ship.md:118-204` evaluates gates and halts) that always refuses GSD's own ship (`not_ready`
    until `ready` has run, then `ship_redirect` to `fold.py merge-chain`). Not hooks: `plan:pre` (its step contract
    has only `ref.skill`/`ref.agent` arms, `plan-phase.md:510-515`, and its contribution roles are researcher,
    planner and checker, `bin/lib/loop-host-contract.cjs`, enforced at `bin/lib/capability-validator.cjs:3125-3133`)
    becomes `gsd-tools ai-kit-fold start --phase N` before plan-phase when discuss was skipped;
    `execute:wave:pre` (dispatches contributions and steps only, never a gate, `execute-phase.md:616-626`) becomes
    the guard inside `fold.py checkpoint` and `start` plus `gsd-tools ai-kit-fold guard --phase N` before
    execute-phase; `verify:post` (dispatched before the verifier writes `VERIFICATION.md`,
    `execute-phase/steps/verify-phase-goal.md:38-48`) becomes `gsd-tools ai-kit-fold ready --phase N` after the
    verifier reports passed. The owner instruction for this replanning pass overrides this decision's "return to the
    owner" clause for this case. The D-01 wave-1 guard line above is enforced the same way. D-01 gap for
    superpowers: its planning skills are a third-party plugin with no hook point ai-kit owns, so a superpowers unit
    starts at `ai-kit-spec-execute-superpowers` Step 1, after its planning commits; the adapter guide states it.
- **D-04: The stack record lives inside `.git/`** (one per clone, never committed): unit id, kind (stacked or
  hotfix), target, branch, parent, PR number, state. When gh-stack is used the flow keeps gh-stack's own record
  (`.git/gh-stack`) in step through `gh stack init`/`add` adoption. Owner choice (recommended).
  Amended 2026-11-05 (live-verified, gh-stack 0.3.0): the flow adopts through `gh stack link` alone, with the
  PR URLs bottom to top once two units exist (`link` needs two arguments). `gh stack init` is not called: it
  checks out the top branch and a second run exits 5 "already part of a stack".
- **D-05: One gitignored `.aikit/` file holds the consent record, the target branches and the primary remote.**
  When `.aikit/` is not ignored, the consent ask offers to add it to `.git/info/exclude`; declined means refused
  (SPEC R10). Written atomically. Phase 33 (CFG-01) inventories it and migrates it. Owner choice (recommended).

### Hotfixes, planning files and conflicts

- **D-06: A hotfix may change `.planning/` like any unit** (SPEC R7 amended). GSD's own STATE, ROADMAP and
  REQUIREMENTS tracking is never restricted, redirected or bypassed by a follow-up record step; each stacked unit
  reads the state of the branch below it, because it branches from it. Owner decision against the recommended
  option: "If they are stacked they should be able to know the state of the previous branch, and if a conflict comes
  up you just resolve it. I don't want GSD to break later because we tried to change its flow for tracking state,
  roadmap, etc."
- **D-07: A rebase conflict is resolved, not only stopped on** (SPEC R6 amended, FLOW-11 amended, roadmap
  criterion 9 amended; edge row added).
  - An agent (a subagent where the host has one) resolves each conflicting file keeping both sides' intent; GSD's
    planning files are merged by content (both sides' entries kept, then `gsd-tools validate health` runs as one of
    the gates for a GSD project).
  - Then the project's gates and tests run on the resolved stack; only then is it pushed, atomically with leases.
  - The report names every resolved file and how (both sides kept, one side chosen and why), at its real certainty.
  - The flow restores every branch and stops only when the resolution fails (a conflict marker left, a change
    outside the conflicting files) or a gate fails.
  - Live: plain `git rebase --update-refs` pauses on a conflict and `--continue` resumes; `gh stack rebase` pauses
    (rebase in progress) and takes `--continue`, and its `--abort` restores every branch (probe
    `tmp/p29.1/probe_hotfix.sh`).
  - Owner decision against the recommended option.
- **D-08: A hotfix is started by the flow's `hotfix` command, which creates the branch at the target's remote tip;
  any work on that branch is the unit** (a GSD quick task, a superpowers plan or plain commits); the flow does the
  PR or MVP step to the target. Owner choice (recommended).
- **D-09: Every flow command fetches first and restacks when the trunk has commits from outside the stack (a
  hotfix); `restack` also runs it on demand.** Merges made by the merge chain never trigger a restack: merge commits
  leave the upper PRs clean (probe `tmp/p29.1/probe_chain.sh`). Owner choice (recommended).

### The merge chain and ready

- **D-10: Any failing or pending check stops the merge chain; after a merge, the merged unit's remote and local
  branches are deleted once the PR above is retargeted.** ai-kit has no CI today (no `.github/workflows`), so only
  drafts and conflicts stop it here. Owner choice (recommended).
- **D-11: In ai-kit, a PR turns ready after GSD's verification passes and after the ship rule's install and live
  re-check from the unit tip** (SPEC R12's steps run before `ready`). Generally, ready follows the adapter's
  verification-passed signal (D-13). Owner choice (recommended).

### Provisional, own reasoning (not objected by the owner)

- **D-12: The superpowers adapter lives in `ai-kit-spec-execute-superpowers`**: it runs `start` and the final
  `checkpoint`, then `ready` after the final review, and never uses the finishing step's merge or PR options; a
  superpowers plan run inline without that skill follows the same commands from the skill's text.
- **D-13: Verification signals:** GSD — `VERIFICATION.md` `status: passed`, at `verify:post`; superpowers — the
  final code review passes; the synthetic adapter calls `ready` explicitly.
- **D-14: Draft PR titles and bodies are generated from the unit** (name, goal, checkpoints done) and updated at
  each checkpoint.
- **D-15: A lock under `.git/` stops two merge-chain runs at once** (SPEC R8 added edge row).
- **D-16: Tests fake `git push`, `gh` and gh-stack through the shared fake helper from Phase 28** (D-04 there),
  on temporary repos with local bare remotes; no test calls a real `gh`, gh-stack or GitHub.
- **D-17: SKILL.md files under the judge bar (JDG-04):** `ai-kit-commit-fold` (grown, D-02),
  `ai-kit-spec-execute-superpowers` (D-12) and `ai-kit-gsd-spec-discuss` (calls `start`, D-01).

  Blocks: this phase's verification.
