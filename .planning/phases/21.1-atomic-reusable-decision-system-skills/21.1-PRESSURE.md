## Method

The arms are **in-session subagents** (the general-purpose agent, sonnet) started by the
orchestrator — not `claude -p`. 5 reps per scenario per arm, and each rep's final message is
saved verbatim as `pressure/<arm>-<scenario>-<rep>.md` (for `none`, `current` and `green`:
5 scenarios x 3 arms x 5 reps = 75 files, plus 20 for the S2r and S4r redesign).

Weaker than the plan's original design, stated plainly (D-23):

- No `claude -p`, because a run writes session state under the real Claude config dir, and
  pointing `CLAUDE_CONFIG_DIR` at a scratch dir loses the login — so the control cannot be a
  fresh CLI process here.
- A subagent can still see globally installed skills, so the `none` arm is *told* not to load
  any skill instead of being prevented from doing so. The `none` arm is therefore an
  approximation of "no skill at all".
- Every arm prompt ends with: "Describe exactly what you would do and the commands you would
  run; do not run any command." So no arm spends a real call, dials a remote endpoint, or
  writes to a user config file.

A scenario whose `none` arm does not show the expected failure is redesigned before GREEN (plan
Task 1 Step 2). S2 and S4 showed no failure, so both were redesigned once (S2r, S4r below) and
re-run in both arms; the original rows stay as measured.

- **S1, omission:** keep the state-bleed fact with its measured number next to the one-call-per-item rule.
- **S3 and S4r, conditional:** state the consent rule's conditions outright. A set key, the ladder's
  next rung, and a relayed or standing instruction are not consent for an off-machine backend;
  a loopback backend needs none. Add rationalization rows for "the key is set", "the ladder says
  TypeSafe next" and "the user said use Jev today".

- **S5, shape:** the backend table names `typesafe` (direct, needs its key) and `opencode` (Zen)
  as different routes. A missing key means the `typesafe` backend is unavailable, and switching to
  `opencode` is the user's call.

Micro-test method (orchestrator, 2026-10-23): nine of the eleven sentences are exercised by a pressure
scenario, so their control is that scenario's RED `none` arm and their green arm is the GREEN run
(no extra runs). The two sentences no scenario covers got new prompts: M1 (`unsupported_feature`
and `disabled`) and M2 (an `ok` answer used as a merge gate), 5 `none` + 5 `green` reps each
(`pressure/{none,green}-M{1,2}-<rep>.md`). The delete rule assumes a valid control. Controls that
pass only by citing this repo's AGENTS.md or memory ("Jev is advisory, verify first", "never
claim more certainty than verified") are contaminated (D-23): the skill ships to hosts without
those rules, so their sentences stay. Ladder: Laya chose "delete all five" (0.76); the
orchestrator overrode it for the three contaminated sentences and deleted the two clean ones.
