# Phase 21.1: Atomic reusable decision-system skills — Specification

**Created:** 2026-10-18
**Ambiguity score:** 0.14 (gate: ≤ 0.20)
**Requirements:** 11 locked (R4, R6, R8, R11 amended 2026-10-18 by 21.1-CONTEXT)

## Goal

ai-kit ships the System One decision system as repo skills under `skills/`:
- the shared Jev client `skills/jev-fast-decision/`, with three backends (Laya, TypeSafe,
  OpenCode Zen) behind one backend table, and the low-confidence escalation implemented once;
- `decide.py` as a thin caller of that client.

Both are installed for claude, opencode and pi, and every advisory answer is logged.

  review rounds, 2026-10-15 Jev 1.14 addendum) has not been executed. It targets the global,

## Requirements

1. **Client skill in the repo**: `skills/jev-fast-decision/` holds the System One client as the plan specifies, with the `main` todos' corrections and the live skill's 2026-10-15 "Required reading" section.
   - Current: Only the global, unversioned live skill exists. The plan's code exists only in `main`'s scratchpad.
   - Target: The repo skill has `SKILL.md`, `reference.md`, `backends/{laya,typesafe,opencode}.md` and `scripts/jev_review.py`. The script carries the plan's backend table, `--probe`, `JEV_BACKEND` selection, per-backend dispatch (Laya one request per item), `needs_fallback`, the `GSD_PATH_JEV` kill switch and the eval cases. Each correction from the 2026-10-11 todo has its own test: every Laya error-taxonomy row, a 2-decimal answer summing to 0.99 accepted, and a Zen 429 budget error treated as unavailable.
   - Acceptance: Each correction has a named unittest, and `make test-unit` runs it green. `SKILL.md` contains the Jev 1.14 "Required reading" links.

2. **Backend seam**: A backend is added or removed by editing only its table row, its adapter and its `backends/<name>.md`.
   - Current: The live client has a single env-configured endpoint. `decide.py` hard-codes two backends.
   - Target: Selection, dispatch, escalation, the probe, the answer log and `decide.py` read the backend table. None of them names a specific backend outside it.
   - Acceptance: One test registers a stub fourth backend through the table alone and sees it probed, selected in auto order and dispatched. A second test deletes the `opencode` row and still gets green probe/screen results with no other edit.

3. **Escalation implemented once**: The client's auto mode runs the ladder: local first, one item per call; low-confidence or errored items go to the next usable consented remote backend in one batch; items still low come back to the caller marked `needs_fallback`.
   - Current: `decide.py` sequences Laya → TypeSafe itself. The plan's auto mode falls through on errors only.
   - Target: The escalation order and its rules live only in the client. An explicit `JEV_BACKEND` never escalates or falls back to another backend.
   - Acceptance: A stub test with low Laya answers on items 1 and 3 sends exactly items 1 and 3 to the remote backend in one request. With `JEV_BACKEND=laya` and the same answers, no remote request is made and items 1 and 3 carry `needs_fallback: true`.

4. **Thin ladder caller**: `decide.py` delegates every backend call to the client and keeps only what is its own: item validation (summaries only), the consent record, `detect`, `--second-opinion` and its result shape.
   - Current: `decide.py` has its own backend URLs, model ids and sequencing.
   - Target: `decide.py` holds no endpoint URL, no model id and no backend order. Its result keeps the per-item `laya`/`typesafe`/`decided_by` fields the spec-discuss logs use, generalized to the backends the table names. `--second-opinion` sends every valid item to the remote rung only.
   - Acceptance: `rg -n 'typesafe\.ai|jev-1\.|laya-rl-agent' skills/ai-kit-gsd-spec-discuss/scripts/decide.py` finds nothing. The existing `tests.test_ai_kit_gsd_spec_discuss` cases, updated to the new seams, pass. One test proves `--second-opinion` makes no Laya call.
   - *Amended 2026-10-18 (21.1 D-06):* the persisted consent record (24 D-10, same file and semantics) moves into the client skill, so `decide.py` keeps validation, `detect`, `--second-opinion` and the result shape, and delegates `consent grant|revoke|show` to the client.

5. **Model-id policy**: A remote backend requests its configured alias (default `jev-latest`, overridable per backend by env to pin a version). It accepts any response `model` matching `jev-<version>`, and every answer carries the model that answered.
   - Current: Exact match against `jev-1.13.0`, so a moved alias breaks the TypeSafe rung.
   - Target: Responses from `jev-1.13.0`, `jev-1.14.0` and a future `jev-1.15.2` are accepted. A non-`jev-` model is `invalid_response`. The answering model appears in the result and in the answer log.
   - Acceptance: Stub tests: `jev-1.14.0` is accepted with `model` recorded; `gpt-4o` gives `invalid_response`; a pinned id is sent in the request body when its env override is set.

6. **Consent gate**: The client's per-session `JEV_ALLOW_REMOTE=1` gate (plan Global Constraints) is the only enforcement point for remote backends. `decide.py` sets it in its child's environment only when the persisted consent record for that backend's endpoint host exists.
   - Current: `decide.py` enforces its own persisted record. The live client has no consent gate.
   - Target: Without the record, `decide.py` never contacts a remote backend and reports `consent_required_for_remote`. With it, the child env carries the flag for that run only. The parent environment is never modified.
   - Acceptance: Stub tests: no record → zero remote requests; record for host A with the endpoint moved to host B → zero remote requests; record present → the remote request is made. `consent revoke` → the next run makes zero remote requests.
   - *Amended 2026-10-18 (21.1 D-06, D-07):* the client owns the per-user record and satisfies its gate from either a session value or a matching record. The gate value is `1` (all remotes, as in the plan) or a comma list of backend names; a record for one remote never enables another (a TypeSafe-only record never reaches opencode on fallthrough).

7. **Every answer logged**: Every answer the client returns, from any caller, appends one record to a local per-user JSONL answer log under ai-kit's XDG state dir. Callers keep their own logs as well.
   - Current: Only the spec-discuss DISCUSSION-LOG records answers. Other callers keep nothing.
   - Target: One JSON line per answered item: timestamp, caller label, item id, type, `instructions`, backend, answering model, choice or score, winning probability, `needs_fallback`, `request_sha256`. Never a key, `context`/`state` text, criteria descriptions or image data. Each append is a single write of one line. A logging failure never changes the answer or the exit code.
   - Acceptance: A test runs three items and finds three lines with exactly those fields. A test with an unwritable log dir still returns `status: ok`. A test asserts that a fake key value never appears in the log file.

8. **Installed for claude, opencode and pi**: ai-kit setup links `jev-fast-decision` into `~/.claude/skills/` (claude and opencode) and `${PI_CODING_AGENT_DIR:-~/.pi/agent}/skills/` (pi), and uninstall removes both links. Codex and cursor get a recorded status: linked, or a documented gap.
   - Current: Links go to `~/.claude/skills/` only. pi never sees ai-kit skills. The live global copy is a real directory.
   - Target: Both links come from one skills selection, with no link under `~/.agents/skills/`, so opencode never sees the name twice. A real directory or a foreign symlink at a link path is never removed silently. Setup offers to move it to a timestamped backup and link the repo copy, only after an explicit wizard confirmation or an explicit headless flag. Otherwise it warns and leaves it.
   - Acceptance: e2e tests under a temporary `HOME` check four things. Install creates both links. Uninstall removes both and leaves foreign entries. A pre-existing real directory survives install without the flag and is moved to `*.bak-<timestamp>` with it. `~/.agents/skills/jev-fast-decision` is never created.
   - *Amended 2026-10-18 (21.1 D-15):* the backup goes to an ai-kit backups dir under the XDG state dir (`ai-kit/backups/<root>/<name>.bak-<timestamp>`), never beside the original: a sibling copy still holds a `SKILL.md` with the same name, and pi discovers skills recursively and keeps the first name it finds.

9. **Hook-ready probe**: `jev_review.py --probe` reports usable and unusable backends as JSON without sending question content. It finishes within 3 seconds when every backend is unreachable, so the later phases' hooks can call it.
   - Current: The live client has no probe. `decide.py detect` checks TCP only.
   - Target: `--probe` works with the kill switch off. It never prints a key and uses a bounded connect timeout per backend.
   - Acceptance: A test with Laya on a closed port and no remote key exits 0 within 3 s with `status: unavailable` and per-backend reasons. A test asserts that no request body was sent.

10. **Jev 1.14 capability matrix**: `reference.md` carries a dated matrix of `score`, `box`, a single image, several images compared, long context and multi-question batching against `typesafe`/`opencode`/`laya`. Each cell is `verified-live`, `documented`, `unsupported` or `unverified`, with its source. The client and `decide.py` accept a feature on a backend only when its cell is `verified-live` or `documented`.
    - Current: No matrix. `decide.py` rejects `score`, and nothing handles images or `box`.
    - Target: `score` is accepted end to end (client and `decide.py` item types). A request for an `unverified`/`unsupported` feature on the selected backend is rejected with `unsupported_feature` before any network call. Every cell carries a source and a date.
    - Acceptance: A `score` item passes through `decide.py ladder` against a stub. An image item aimed at a backend whose cell is not `verified-live`/`documented` returns `unsupported_feature` with zero requests. The matrix has no empty cell.

11. **Advisory skill contract**: Every new or materially changed `SKILL.md` (the client, plus `ai-kit-gsd-spec-discuss` where it now defers to the client) keeps the advisory, "reason it yourself" contract and passes the `skill-judge` loop.
    - Current: The live client's `SKILL.md` is 154 lines and has never been judged as an ai-kit skill.
    - Target: The descriptions start with "Use when", and each body is under 500 words. Each answer's handling is a recipe: `needs_fallback` → decide it yourself; `consent_required_for_remote` → ask, then retry. The writing-skills RED/GREEN pressure scenarios of plan Tasks 1, 6 and 7 are run.
    - Acceptance: Both judges (native in-session and the pi lane) score ≥ 96/120 with no remaining Critical finding and no regression against the baseline. The scores are recorded in the phase dir.
   - *Amended 2026-10-18 (21.1 D-22):* the 500-word body cap and the "Use when" description apply to the new client skill. `ai-kit-gsd-spec-discuss` (1,748 words, layout set by 24 D-14) is judged on its changed sections without the cap.

## Constraints

- Runtime scripts are stdlib-only, run with `python3 -B` outside any venv. Tests are stdlib
  `unittest` with an in-process `http.server` stub, wired into `make test`. No network, no
  real config dirs, no real keys.
- Never print or log a key. A key is only ever sent to its own backend's URL. A loopback
  check applies to Laya (plan Global Constraints).
- Config and state writes are atomic (`mkstemp` + `os.replace`). The answer log is
  append-only.
- The plan's paths remap from `~/.claude/skills/jev-fast-decision/` to
  `skills/jev-fast-decision/`, and its `diff -ru` checkpoints become logical commits. Its
  `claude -p` pressure scenarios run under a scratch config, never the real one.
- The skill name `jev-fast-decision` is kept so `global:jev-fast-decision` in
  `.planning/config.json` and `decide.py`'s lookup keep resolving.
- Plan Tasks 5–8 need Laya healthy on 127.0.0.1:8010. TypeSafe live checks need a key and
  consent. The Zen backend is built and stub-tested; live use waits for budget.
