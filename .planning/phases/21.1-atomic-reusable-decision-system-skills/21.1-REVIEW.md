I reviewed the new client (`jev_review.py`, read in full), `eval_cases.py`, the thin `decide.py`, the installer changes in `setup.py`/`wizard_app.py`, the judge validator and the new tests. The installer work is careful and well tested. The client has two blocking defects:

## Critical Issues

### CR-01: Remote rows reject every real `jev-<version>` response as `invalid_response`

**Fix status:** fixed (1b7798b)

**File:** `skills/jev-fast-decision/scripts/jev_review.py:839`, `:862` (also `tests/test_jev_fast_decision.py` stubs `typesafe-1`/`opencode-1` throughout)
**Issue:** The typesafe row's `response_model` is `typesafe-[a-z0-9_.-]+` and the opencode row's is `opencode-[a-z0-9_.-]+`. Other sources disagree:
- SPEC R5 and its acceptance criteria, plan 21.1-01 (lines 51, 381) and RESEARCH (lines 176, 220) all say the remote rows accept `jev-<version>` (`jev-1.13.0`, `jev-1.14.0`, `jev-1.15.2`, `jev-1.14.0-preview`).
- The v3 reference used the prefix `jev-`.
- RESEARCH cites TypeSafe docs saying the response `model` is the versioned id that answered.

I confirmed this with a stub answering `model: "jev-1.14.0"` on the typesafe row: `status: unavailable, errors: {"a": "invalid_response"}`. The one bug SPEC R5 was written to fix (a moving alias breaks the TypeSafe rung) is therefore now worse: every TypeSafe and Zen answer fails, whatever the version.

The tests hide this. They stub invented `typesafe-1`/`opencode-1` ids, and the R5 acceptance tests (accept `jev-1.14.0` and `jev-1.15.2`; reject `jevx-1`, `gpt-4o` and a missing model) do not exist. `backends/typesafe.md:15` and `backends/opencode.md:15` repeat the wrong patterns.
**Fix:**
```python
_JEV_RESPONSE = re.compile(r"jev-[0-9]+(?:\.[0-9]+)*(?:-[A-Za-z0-9.]+)?")
# typesafe and opencode rows:
"response_model": _JEV_RESPONSE,
```
Then add the `model_policy` tests from plan 21.1-01 line 381. Change the remote stubs to `jev-1.13.0`/`jev-1.14.0` and fix both backend docs.

### CR-02: Laya questions (with `context`) go to `http_proxy`, so off-machine sends happen without consent

**Fix status:** fixed (1b7798b)

**File:** `skills/jev-fast-decision/scripts/jev_review.py:222` (`_exchange`'s `build_opener`); `skills/ai-kit-gsd-spec-discuss/scripts/decide.py:258-266` (`child_env` passes proxy variables through)
**Issue:** `urllib.request.build_opener()` adds a default `ProxyHandler` that reads `http_proxy`/`https_proxy` from the environment. `proxy_bypass('127.0.0.1:8010')` is `False` unless `no_proxy` lists it. I confirmed this with a loopback listener set as `http_proxy`: `jev_review.py --probe` sent `GET http://127.0.0.1:8010/health` to the proxy. A screen POST takes the same path. So the full `state`, including every item's `context`, goes to whatever host the proxy is, with no consent check, because Laya is a local row.

This breaks the SPEC Constraint "a loopback check applies to Laya" and the MUST-NOT "no question to a remote backend without the consent gate". The `_is_loopback` URL check gives false assurance, since the transport ignores it. The tests run under `clear=True` envs, so they never see a proxy.
**Fix:** Never use an env proxy for a loopback row. The simplest version disables proxies for every exchange:
```python
yield urllib.request.build_opener(urllib.request.ProxyHandler({}), NoRedirect(),
                                  _RecordingHTTPHandler(sockets),
                                  _RecordingHTTPSHandler(sockets))
```
If remote rows must honour a corporate proxy, pass `ProxyHandler({})` only when `not row["remote"]`. Add a test that sets `http_proxy` to a loopback listener and asserts it receives zero bytes.

## Warnings

### WR-01: A final remote error throws away the local answer; a TypeSafe 402 never reaches the next remote

**Fix status:** fixed: requires human verification (1b7798b) — ladder logic change

**File:** `skills/jev-fast-decision/scripts/jev_review.py:1465-1467`, `:1755-1756`; `tests/test_jev_fast_decision.py:866`
**Issue:** `_post` can end with action `next_model` (no next id), `caller_error` or `deadline`. `_fold_rung` marks every action except `escalate` as final in `run.failed`, even when the item already holds a low Laya answer in `run.tentative`. That item then never reaches the promotion loop in `_ladder`. Stub result for a low Laya answer followed by a TypeSafe 402: `status: unavailable`, `errors: {"a": "http_402"}`, `answers: []`. But `_log_run` writes the Laya answer to the answer log, so the log and the result disagree.

The same loss happens when the remote request hits the deadline mid-flight. The not-started path (`:1541`) deliberately keeps tentative answers, so the two deadline paths behave differently.

There is a second problem. A remote billing or budget signal (TypeSafe 402, or Zen 429 on its last id) is final, so a consented opencode row after TypeSafe is never tried. 401/403 does escalate. The test `test_model_policy_typesafe_single_id_402_escalates` asserts the opposite of its name.
**Fix:** In `_post`, turn an exhausted `next_model` into `escalate`, as is already done for an exhausted `retry`. In `_fold_rung`, never fail an item that has a `run.tentative` entry: record the error in `last_error` and let the end-of-ladder loop promote the tentative answer. Rename or fix the test.

### WR-02: Top-level `backend`/`model` name the first rung, not the one that answered; `eval_cases.py` records that wrong value

**Fix status:** fixed: requires human verification (1b7798b) — top-level backend/model are null when answers come from different rungs

**File:** `skills/jev-fast-decision/scripts/jev_review.py:1492-1493`; `skills/jev-fast-decision/scripts/eval_cases.py:224`
**Issue:** `_finalize` sets `run.backend`/`run.model` the first time any rung answers, and a tentative low Laya answer counts. Stub result: an item escalated from Laya to TypeSafe has top-level `backend: laya, model: laya-rl-agent`, but `answers.a.backend == "typesafe"`. `eval_cases.py` labels each case with `result["backend"]`, so any auto-mode eval that escalates mixes remote tops into the Laya calibration set. That is exactly what `--calibrate` then rewrites.
**Fix:** In `eval_cases.py`, use `answer["backend"]`. In `_result`, either drop the top-level `backend`/`model` or compute them from the final answers (for example, a single value only when all answers share one backend).

### WR-03: A deeply nested JSON response escapes as an uncaught `RecursionError` (traceback, non-zero exit)

**Fix status:** fixed (1b7798b)

**File:** `skills/jev-fast-decision/scripts/jev_review.py:1409`, `:1447`; `skills/ai-kit-gsd-spec-discuss/scripts/decide.py:471`
**Issue:** `json.loads(data)` on a response under the 1 MiB cap made of `[` characters raises `RecursionError`. I confirmed it: a stub body `b"[" * 200000` made `screen()` raise `RecursionError`. `_post` catches only `OSError, ValueError, HTTPException`. This breaks the "never a traceback / always exit 0" contract: any misbehaving or hostile endpoint crashes the client. The same file already catches `RecursionError` for stdin and the consent file. `decide.py main` has the same gap for its own stdin.
**Fix:** In `_send`, wrap `json.loads` so that `RecursionError` is re-raised as `ValueError("invalid_response")`. In `decide.py`, catch `(ValueError, RecursionError)`.

### WR-04: Remote URLs are not scheme-checked, and consent is bound to the hostname only, so a bearer key can travel over plain HTTP

**Fix status:** partially fixed (1b7798b) — https required for remote rows (loopback http kept for stubs); consent binding to scheme+port not changed (outside the orchestrator's ruling)

**File:** `skills/jev-fast-decision/scripts/jev_review.py:678-685`, `:734-742`, `:1016-1032`
**Issue:** `JEV_TYPESAFE_URL`/`JEV_OPENCODE_URL` accept any scheme. `record_consent` compares only `urlsplit(endpoint).hostname`. A saved grant for `api.typesafe.ai` is therefore satisfied by `http://api.typesafe.ai:8080/...`, and `_send`/`_bearer_probe` send `Authorization: Bearer <key>` in cleartext. Any other scheme `build_opener` supports (`ftp:`, `file:`) is also reachable under a session `JEV_ALLOW_REMOTE=1`. This goes against "a key is only ever sent to its own backend's URL".
**Fix:** For remote rows, require `https`, unless the host is loopback (which the stubs need), with a `insecure_url` reason. Bind the consent record to scheme + host + port (`urlsplit(...).netloc` plus scheme), and treat older host-only records as no consent.

### WR-05: Key sources drift from locked D-07, and the Zen key file skips the 0600 rule

**Fix status:** fixed (1b7798b)

**File:** `skills/jev-fast-decision/scripts/jev_review.py:56`, `:688-695`, `:745-760`
**Issue:**
- D-07 (locked) and plan 21.1-01:384 give TypeSafe's key order as `TYPESAFE_API_KEY`, `JEV_API_KEY`, `JEV_API_KEY_FILE`, then `${XDG_CONFIG_HOME}/ai-kit/secrets.env`. The pre-phase `decide.py` read the last three (`git show 3d8a83a:...decide.py:125-138`). The client reads only `TYPESAFE_API_KEY` and `${XDG_STATE_HOME}/typesafe/api_key`. A user whose key lived in `secrets.env` or `JEV_API_KEY` now silently gets `missing_api_key`. That is a regression with no amendment recorded. The docstring also cites D-09 instead of D-07.
- The plan also said the Zen key comes from `OPENCODE_API_KEY`, then opencode's `auth.json`. The code reads `OPENCODE_ZEN_API_KEY`, then a hardcoded `~/.pi/agent/keys.json`. That path is pi's directory, not opencode's ("opencode's own file" is wrong), and it ignores `PI_CODING_AGENT_DIR` (setup.py honours it). Unlike `_read_key`, it applies no `_WORLD_READABLE` check.
**Fix:** Either implement the D-07 order (reuse the old `_secrets_env_value` parser), or formally amend D-07/SPEC with the evidence for the new sources. Resolve the Zen file through `PI_CODING_AGENT_DIR`, and run the same `stat` + `_WORLD_READABLE` refusal before `open`.

### WR-06: `decide.py` echoes server-supplied legend text as a score item's `choice`

**Fix status:** fixed (1b7798b)

**File:** `skills/ai-kit-gsd-spec-discuss/scripts/decide.py:332`
**Issue:** For score items, `choice = entry["legend"].get(entry["level"])`. The `legend` is the remote/Laya response's own map; `_check_score_answer` only checks that its values are strings. So an endpoint controls arbitrary, unbounded text that `decide.py` prints to the agent's context and to spec-discuss logs. That undercuts the module's "fixed allowlist" claim and opens a prompt-injection channel from a remote backend.
**Fix:** Map the winning index back to the caller's own criteria: `choice = item["criteria"][int(level)]` (pass `item` into `typed_answer`, or look it up in `fill_columns`). Never print `legend` values.

### WR-07: Remote probes discard the API path; the Zen probe hits `https://opencode.ai/models`

**Fix status:** fixed (1b7798b) — probe sends the bearer to https://opencode.ai/inference/v1/models; `key_check: unverified`

**File:** `skills/jev-fast-decision/scripts/jev_review.py:775` (also `:710`)
**Issue:** `_origin(endpoint, "/models")` keeps only scheme and host. For the Zen default (`https://opencode.ai/inference/systemone/v1/systemone`), the bearer key goes to `https://opencode.ai/models`, a website path rather than an API route. The probe's 200 or non-200 then says nothing about the key: either the row is always `unreachable`, or it is `usable` whatever the key, depending on what the site returns. The probe is the gate that decides whether the row is selected at all. `backends/opencode.md:12` admits the path is undocumented, but the code still trusts it.
**Fix:** Derive the probe from the endpoint's own path prefix (for example, replace the trailing `/systemone` with `/models`), or mark the row's probe `unverified`. In that case, treat it as "key present" only and do not send the bearer to an undocumented path.

### WR-08: `--replace-existing --dry-run` exits 1 and tells the user to re-run with `--replace-existing`

**Fix status:** fixed (9884529)

**File:** `tools/setup.py:3170-3191` (with `backup_and_link` at `:2996`)
**Issue:** Under dry-run, `backup_and_link` prints `would move` but leaves the entry in place. `_headless_link_skills` then counts `skip_real`, prints "re-run with --replace-existing to back it up", and the run exits 1. I confirmed this in a temp HOME: `exit=1`, with that advice printed beside the `would move` line. A dry run of a command that would succeed reports failure.
**Fix:** In dry-run mode, have `backup_and_link` record the paths it would move, and have `_headless_link_skills`/`_headless_sync_pi` skip those paths (or count them as `linked`), so the dry run predicts the real outcome. Add the dry-run case to `test_jev_skill_install_e2e.py`.

### WR-09: The judge-verdict validator accepts duplicate score lines (last one wins)

**Fix status:** fixed (d8b3733)

**File:** `.planning/phases/21.1-atomic-reusable-decision-system-skills/skill-judge/check_verdict.py:71-82`
**Issue:** `dims` is a dict built from `findall`, so a repeated `D3` line silently overwrites the earlier one. `CURRENT`/`CRITICAL`/`IMPORTANT` use `[-1]`. A report with `CRITICAL 2` followed by `CRITICAL 0`, or two `D` rows for one dimension, passes, yet the error text claims "missing or duplicate score/end lines". This is the gate behind the R11 verdict.
**Fix:** Require `len(dim_rows) == 8`, and require exactly one line each for `CURRENT`, `CRITICAL` and `IMPORTANT`; otherwise fail with that reason. Add the duplicate cases to `self_test`.
