Changed by this plan:

- `ai_kit_rules_common.remediation.build_remediation` -- two additive edits in the makefile
  branch, both in Task 3: `auto_apply` becomes a function of the advisory flag's absence, and
  each finding's `issue` is carried forward onto its `remediate` entry. No signature change, no
  change to the returned payload's own two top-level keys, no key removed from an entry, and no
  existing entry key's value changed. `id` is NOT rewritten -- it stays the finding's identifier
  and is documented as a label rather than a unique key.

Finding-shape contract every new finding must satisfy, because `build_remediation` reads
exactly these fields for makefile-kind findings: an identifying `target` OR `category` key,
`criticality`, `summary`, `recommendation` (non-`None` means it becomes a remediate entry),
`needs_research` (`True` with no recommendation means it becomes a blocked entry), and -- once
Task 3's carry-forward lands -- `issue`, which the builder copies onto the entry verbatim. All
six new checks are structural facts readable from the target repo's own files, so every one of
them sets `needs_research: False` and a non-`None` `recommendation` -- none of them is ever
blocked on research. Every new check also sets its own `issue` value, distinct from every other
check's, because two findings that identify as the same target are told apart by nothing else.

Annotation-key note that is easy to get wrong: `build_remediation` resolves a finding's
identifier as `finding.get("target", finding.get("category"))`. A new finding that wants to say
WHICH tooling category it is about must NOT use the key `category` for that, or the identifier
resolution changes meaning for findings that also carry a `target`. Use a distinct annotation
key and keep `category` reserved for the inherited tooling-category findings that are keyed by
it.
