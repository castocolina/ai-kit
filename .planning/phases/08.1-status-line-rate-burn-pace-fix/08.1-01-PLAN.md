<objective>
Land the already-implemented pace-direction fix for `util_rate_burn_ratio` in
`tools/status-line.py`: the burn-rate ratio feeding the unchanged
`theme.ramps["rate"]` ramp becomes `used_percentage / elapsed_fraction`
instead of `used_percentage / remaining_fraction`.

Purpose: Phase 8 shipped a formula that flares a bucket's color near the end
of a rate-limit window even at low usage. The user observed this live -- 25%
used with roughly half of a 5h window gone rendered orange, when low usage
well into a window is good pacing, not urgency (08.1-CONTEXT.md D-01).

Caveat on that reported example, load-bearing for verification: the EXACT
midpoint is a fixed point of this change. At
`elapsed_fraction = remaining_fraction = 0.5` both the superseded and the
landed formula yield `25 / 0.5 = 50`, and `util_pick_color` picks the first
ceiling the value is STRICTLY below, so 50 reads YELLOW before and after.
The fix bites strictly PAST the midpoint (at `elapsed_fraction = 0.6`:
`25 / 0.4 = 62.5` YELLOW before, `25 / 0.6 = 41.67` GREEN after; at the
ROADMAP 8.1 SC1 example's `elapsed_fraction = 0.8`: `25 / 0.2 = 125`
RED+bold before, `25 / 0.8 = 31.25` GREEN after). The user's "roughly half"
report is consistent with the fix, but only the past-midpoint numbers
demonstrate it -- every acceptance case in this plan uses those, never the
midpoint.

Output: the two-file diff of commit `fc2d8bb` (branch
`fix/8.1-status-line-rate-burn-pace`) landed verbatim on the execution branch,
re-reviewed against 08.1-CONTEXT.md's decisions, its two stale-commentary and
one test-coverage gaps closed, and REQUIREMENTS.md formally amended.
</objective>
