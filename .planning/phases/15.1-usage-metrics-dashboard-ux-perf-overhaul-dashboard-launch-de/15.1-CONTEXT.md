# Phase 15.1: Usage Metrics Dashboard UX/Perf Overhaul - Context

**Gathered:** 2026-09-16
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 15.1 fixes the existing Phase 5 usage-metrics dashboard (`skills/ai-kit-usage-metrics/ai_kit_usage_metrics/dashboard.py`) — a single locally-generated static HTML file with embedded refined data, no server, no build step (D-09 from Phase 5, unchanged by this phase). It does not change the raw-capture or refinement-pipeline architecture except where a genuine data bug (date, family, price, session-grouping) requires a refiner/decomposer fix. Scope: (1) client-side rendering performance so the browser stops freezing on the real embedded dataset, (2) a Material-inspired visual redesign via the newly-installed `frontend-design` skill + Material Web Components, (3) filter/column redesign (runtime, subfamily, unified date range, wrapped command with detail dialog), (4) fixing 5 concrete data-correctness bugs found live against the real refined store (4 dashboard-visible + 1 refiner-completeness bug for opencode/codex, D-19), (5) adding 3 charts, (6) filter bar sitting spatially beside the charts row and the whole page actually using available desktop viewport width rather than rendering at a fixed small size (D-20/D-21, added after live Wave-1 human-check feedback), and (7) 2 Wave-1 gap-closure bugs found in the same human-check — invisible unfocused group-by-session checkbox and grouped-mode cells rendering under wrong column headers (D-22/D-23). Auto-opening the dashboard after generation is also in scope.

</domain>

<decisions>
## Implementation Decisions

### Rendering performance
- **D-01:** No prefilter at generation time and no local HTTP server. The full refined dataset keeps being embedded in the static HTML exactly as Phase 5's D-09 decided — that decision stands unchanged. The actual freeze is caused by client-side render/filter cost (the current `renderFlat`/`renderGrouped` in `dashboard.py` rebuild every filtered row into the DOM on every filter/sort event), not by the size of the embedded payload. — **Reversibility:** reversible — a pure rendering-layer change; the embedded-data architecture (D-03/D-09 from Phase 5) is untouched.
- **D-02:** Fix the freeze via client-side virtualization/windowing (render only the rows near the viewport), not by reducing what's embedded.
- **D-03:** An external dependency is acceptable for virtualization — CDN-hosted, not vendored/bundled locally. Loading a `<script src="https://cdn...">` from a page opened via `file://` has no CORS issue (CORS only restricts `fetch`/`XHR` to local resources, not remote `<script>` loading). The user explicitly chose simplicity over keeping the dashboard fully offline-capable. — **Reversibility:** reversible — swapping which CDN library is used, or vendoring it later, doesn't change the data/architecture.

### Visual redesign ("MUI" ask)
- **D-04:** Not React + real MUI (`@mui/material`) — that would require adding a build step (bundler, npm deps) and would break the no-build static-HTML architecture Phase 5's D-09 locked in. Not hand-rolled vanilla CSS either — the user explicitly wants a real design-system-driven result, not ad-hoc styling.
- **D-05:** The `frontend-design` plugin (`claude-plugins-official` marketplace) was installed live during this discussion — `claude plugin install frontend-design@claude-plugins-official`, then the user ran `/reload-skills` and `/reload-plugins` in a local terminal, confirming it is now active as `frontend-design:frontend-design`. **Planning and execution for this phase MUST invoke this skill** to drive the visual redesign — it was not available before this phase and needed to be installed specifically for it.
- **D-06:** Controls/filters/dialogs use **Material Web Components** (`@material/web`, Google's official Material Design 3 web components — framework-agnostic Custom Elements) loaded via `<script type="module" src="https://cdn.../...">`. No official Material data-table component exists, so the actual `<table>` stays hand-styled using the same Material color/typography/elevation tokens, OR a separate grid library if research finds one that combines well (see D-07).
- **D-07:** The concrete data-table/grid library choice is deliberately NOT fixed here — delegated to `frontend-design` + the planner's research step, to avoid locking a library name before evaluating what actually combines well with Material Web Components.
- **D-08:** Theme: default Material palette, with automatic light/dark following `prefers-color-scheme` (OS setting). No custom brand palette.
- **D-09:** Chart library: also delegated to `frontend-design` + planner research, same reasoning as D-07 (not fixed to a specific name like Chart.js here).

### Filters and columns
- **D-10:** Add `runtime` as both a filter and the leftmost table column (currently missing entirely — the filter bar only has family/model/command/date/tokens/price).
- **D-11:** Add a new `subfamily` derived field (second command-level token, e.g. `git commit` → family=`git`, subfamily=`commit`). Extraction reuses `family.py`'s exact wrapper/assignment/leading-flag-skipping logic (`_WRAPPERS`, `_ASSIGNMENT_RE`, leading-flag skip after the family token), then takes the next non-flag token as subfamily — so `git -C /path commit` → subfamily=`commit`, not `-C`. — **Reversibility:** reversible — additive derived column, no schema break (see D-15 on whether this is computed at refine-time or dashboard-render-time).
- **D-12:** Reorder both the filter bar and the table columns to: runtime → model → family → subfamily → command (wrapped, with a popup/dialog for the full text) → exec time → the remaining columns (tokens, price, source_confidence, execution_certain, session).
- **D-13:** Replace the 4 separate date fields (preset/day/start/end) with a single unified "desde/hasta" range control — flight-booking style (one field responsible for the whole range). A single day is expressed by setting start=end. Implementation: a Material Web date-range component if one exists, or two `<input type="date">` elements visually merged into one control.
- **D-14:** The full-command dialog (triggered from the wrapped command column) shows: (1) the full untruncated `command_text`, (2) a copy-to-clipboard button, (3) the decomposer's step breakdown (`step_index`/`step_count`/`operator`) when the row is part of a compound command.

### Data-correctness bugs — fix now, not deferred
- **D-15:** All 4 data bugs found live during this discussion are fixed **in this phase**, not deferred to backlog. The user explicitly weighed "fix now" vs "defer to backlog" and chose fix-now specifically because of the verification guarantee it carries: each bug becomes an explicit success criterion in `15.1-PLAN.md`, independently re-verified in `15.1-VERIFICATION.md` before the phase can close — the same mechanism (Phases 14/15) that caught real gaps executors claimed were fixed but weren't. Deferring would stay visible via `ROADMAP.md` backlog + `/gsd-progress`/`/gsd-audit-milestone`, but carries no verification gate until promoted to an active phase — insufficient given the user's stated concern about work not actually getting done. — **Reversibility:** reversible — a scoping decision about this phase's plan, not an architectural commitment.
- **D-16 (diagnostic starting points for the planner/researcher, not final root causes — investigate with real historical data before fixing):**
  - **`date` column renders empty:** `dashboard.py`'s `_QUERY_COLUMNS` includes `date` and the JS renders `row.date` correctly — the bug is upstream, in how `refiner.py` populates `date` per source, not in `dashboard.py`.
  - **`family` shows "garbage" values:** NOT random — `family.py` deterministically uses `os.path.basename` of the first non-wrapper/non-assignment token as the family for anything outside the curated `cat/grep/find/sed/ls` set. Apparent garbage is likely `control_flow_script`/`unclassified` decomposer entries whose "first token" isn't a real binary — needs live investigation, not a guess.
  - **`price` always renders as 0:** `pricing.py`'s `estimate_price()` returns `(None, "unknown")` on any catalog miss, never `0` — either a `None`→`0` conversion bug somewhere else in the pipeline, or the model catalog genuinely lacks entries for the models actually in use (e.g. Claude Sonnet 5, GPT-5.2). Needs verification against the real catalog file and real captured rows.
  - **Session-group duplicate rows:** `dashboard.py`'s `groupBySession()` dedupes on `session_id + "\0" + turn_id` — duplicates likely mean `turn_id` is missing or inconsistent for some rows; needs investigation into which capture source(s) produce that.
- **D-17:** Auto-open the dashboard after generation, always, at the end of `run`/`dashboard` subcommands (currently `generate()` only writes the file — no `webbrowser.open()` call exists anywhere in `cli.py`). No opt-out flag required — this is a new default behavior.
- **D-19 (added after live investigation, this session — not part of the original discuss-phase discussion):** A 5th data bug, found by querying the real `refined.db` directly while answering a follow-up question about why the dashboard visually appeared dominated by opencode data. Confirmed with hard numbers, not speculation:
  - **`date` is NULL for 100% of opencode's refined rows (17,414 of 17,414) and all of cursor's (41 of 41).** Raw capture for both is live and working (opencode `captured_at` up to 2026-09-14, codex up to 2026-09-16 — telemetry is NOT disabled, contrary to the user's initial suspicion). Because any date-based filter excludes `NULL`-date rows, applying ANY date filter makes opencode's entire dataset silently vanish — this is the same underlying defect as D-16's "date empty" item, now confirmed systemic (all rows, not a handful) rather than sporadic.
  - **Codex is massively under-refined: 36,582 raw captured lines exist (live, most recent `captured_at` 2026-09-16) but only 1,946 rows made it into `refined_commands`, all confined to a narrow 2026-07-25–07-27 window.** This is a genuinely new finding — a refiner-completeness defect specific to codex, distinct from the 4 dashboard-visible symptoms D-16 already named. It was not discoverable from `dashboard.py`'s code alone (what discuss-phase examined); it only surfaced by querying the live `refined.db` directly.
  - **Real runtime distribution (for calibration — contradicts the "everything is opencode" visual impression):** `claude`=35,244 rows, `rtk`=29,437, `opencode`=17,414, `codex`=1,946, `cursor`=41. Claude actually has the most data; the opencode-dominant *impression* is most likely explained by the NULL-date filtering-out behavior above, though the exact visual mechanism (sort order, render-freeze timing) wasn't independently proven — only the NULL-date fact and its date-filter consequence were confirmed with a live query.
  - **User decision:** fold this into Phase 15.1's scope now, same treatment as D-15/D-16 — an explicit success criterion investigated and fixed with independent verification, not deferred. This means the refiner's opencode `date`-population path and the codex-refinement completeness gap are now both in scope for this phase's plan, in addition to the original 4 dashboard-level bugs. — **Reversibility:** reversible — a refiner-logic bugfix + investigation, no schema/architecture change.

### Charts (new, addresses "no charts at all")
- **D-18:** Add 3 charts: (1) tokens/price per day, line or stacked-bar broken down by runtime, (2) family/subfamily distribution, horizontal bar or treemap, (3) runtime distribution, pie/donut.

### Layout and responsiveness (added after Wave-1 human-check feedback, this session)
- **D-20:** The filter bar sits spatially alongside the charts row (side-by-side), not stacked above/below it as a separate full-width block, on viewports wide enough to fit both. **User's exact words:** "The filers needs to be next to the chart." Undocumented in the original discuss-phase/ui-phase output — surfaced only when the user viewed the Wave-1 tracer output live. **Reversibility:** reversible, pure layout/CSS — no data or architecture change. **Routing:** Plan 03 (which already owns the filter bar's full rebuild and D-12's column/filter reordering) absorbs the spatial layout requirement; Plan 05 (which owns the charts row's final 3-panel sizing) must produce a charts-row width that leaves room for the filter bar beside it rather than assuming full-viewport width.
- **D-21:** The dashboard must be genuinely responsive — readable and usable across common desktop viewport widths (the user's concrete complaint: at 1920x1080 full-width the chart renders tiny and fixed-size, and nothing in the page adapts to viewport width at all). No specific breakpoint set or mobile-support requirement was locked — narrow-viewport/mobile support is explicitly NOT required, only that desktop viewport width is actually used (charts/filter bar/table scale or reflow with available width instead of rendering at a fixed small size inside a wide window). **User's exact words:** "all the screen is not responsive at all." Undocumented in the original discuss-phase/ui-phase output. **Reversibility:** reversible, CSS-only. **Routing:** Plan 05 (charts sizing — canvases must scale to their container width rather than a fixed 240x240px) and Plan 03 (filter bar and table container width) both need a responsive-sizing pass; this does not require a new plan or a new UI-SPEC.md research cycle since it's a mechanical CSS-unit fix (percentage/`clamp()`/flex sizing instead of fixed pixels), not a new design-system decision.

### Wave-1 gap-closure fixes (found during human-check, fixed directly — not deferred)
- **D-22:** The `<md-checkbox id="group-by-session">` element (added in Plan 01 Task 2 to prove Material Web Component CDN upgrade, D-06) has no CSS for its unfocused visual weight and is effectively invisible until focused. Fix: give it explicit always-visible styling (border/fill contrast against the surface-variant background) that does not depend on `:focus`. Owned by whichever plan/commit next touches this element (Plan 01's own gap-closure, immediate).
- **D-23:** In grouped-by-session mode, `groupedRowBuilder` emits only 5 `<td>` cells (session_id, count, tokens_input, tokens_output, price) while `<thead>` and the `:nth-child(1..11)` column-width CSS are both fixed for the 11-column flat-mode shape — real data visibly renders under the wrong column headers, with headers 6-11 showing empty cells. This is a correctness bug, not a styling gap: `<thead>` must switch to a grouped-mode-specific header set (or the grouped builder must emit placeholder cells preserving the flat column positions) so headers and cells always agree on column count and meaning. Owned by whichever plan/commit next touches the grouped rendering path (Plan 01's own gap-closure, immediate — Plan 02 must not build on top of this broken path).

### Plan-05 mid-execution addition (found and fixed directly, documented after the fact)
- **D-24:** The date filter gets airline/hotel-booking-style quick-select range presets (`Today` / `Last 7 days` / `Last 30 days` / `This month` / `All time`) as buttons above the existing from/to range inputs, rather than requiring every filter to be set by hand-typing two dates. `Last 30 days` ("month") is the default active preset on initial page load, replacing the prior default of the full unfiltered dataset — the operator's real dataset spans months, and loading unfiltered was itself part of what made first paint feel slow and cluttered. A manual edit to either date input clears the active-preset highlight (no preset looks selected once the filter no longer matches it exactly). Implemented directly in `dashboard.py` (`#date-presets`, `applyDatePreset()`) during Plan 05 execution rather than being scoped in the original discuss-phase/ui-phase output; recorded here after the fact for the record, matching D-20 through D-23's pattern of documenting decisions surfaced by live use rather than upfront planning. **Reversibility:** reversible, additive UI sugar on top of the existing D-13 unified date-range control — no data or architecture change. **Routing:** Plan 05 (owns the date-range control's final polish).

### Post-UAT gap-closure fixes (found via fresh live testing after phase.complete, fixed directly)
- **D-25 (revises D-10/D-11/D-20):** UAT was marked passed on stale evidence — after the phase was reported complete, live Playwright testing of the regenerated dashboard reproduced two real defects the UAT round never actually hit: (1) `md-outlined-select`'s `md-menu` popup closes itself on the very click that opens it, worse in Firefox than Chromium (browser-dependent light-dismiss/focus-retargeting bug tracked upstream against material-web's menu component, not something a fixed attribute workaround was confirmed to resolve) — the user's exact words: *"cada vez que le doy a un picker multiple en el selector se cierra solo"*, confirmed second-hand worse in Firefox: *"¿Por qué en chromium parece comportarse mejor que en firefox?"*; (2) the charts-beside-filters layout D-20 introduced was still explicitly rejected by the user even after that revision shipped: *"sigo viendo esos graficos al mismo nivel de los filtros"*. Fix: the 4 filter `<md-outlined-select>` elements are replaced with native `<select>` (styled to match the outlined-field look; `fillSelect()` now creates plain `<option>` elements) — eliminating the popup-closing bug class entirely rather than chasing a workaround, consistent with D-13's existing precedent of using native `<input type="date">` where the Material component doesn't hold up. `#dashboard-top` changes from a row (charts + filters as siblings) to a column: the filter bar becomes its own full-width row below `<h1>` and above the charts row, restoring a natural "narrow the data, then see the result" reading order and letting each chart panel use roughly 3x its former width. The date-range inputs also get intentional CSS (calendar-icon color-scheme/invert for dark mode, focus-visible outline) since they read as unstyled browser chrome next to the newly-native selects. **Reversibility:** reversible, presentation/component-choice only — no data model or filter-logic change; `readCriteria()`/`clearFilters()`/`applyFilters()` are untouched since a native `<select>`'s `.value` API is identical to `md-outlined-select`'s. **Routing:** applied directly to `dashboard.py` post-hoc (no new plan) since UI-SPEC.md's original D-10/D-11 "Outlined select" row and D-20's "beside charts" phrasing are now superseded by this entry — UI-SPEC.md is not separately amended (CONTEXT.md is the decision record of last resort for this phase per D-20/D-23/D-24's own precedent).
