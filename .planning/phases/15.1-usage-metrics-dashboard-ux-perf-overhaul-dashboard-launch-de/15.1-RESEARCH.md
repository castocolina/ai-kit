## Summary

This phase fixes a working, well-tested (`103/103` passing unit tests) Phase 5
dashboard, not a greenfield build. All research below is grounded in (1) a
full read of the 6 source files this phase modifies (`dashboard.py`,
`refiner.py`, `family.py`, `pricing.py`, `decomposer.py`,
`capture_opencode.py`, `capture_codex.py`, `capture_cursor.py`,
`refined_store.py`, `cli.py`, `paths.py`) and the 3,096-line test suite, and
(2) direct **read-only SQL/Python queries against the user's real local
`refined.db` (84,082 rows) and real raw `codex.jsonl`/`opencode.jsonl`**
(permitted per this phase's own scope — see `additional_context`). This
second step overturned one of D-19's own working hypotheses (the "codex
under-refinement" root cause) and sharpened three of the other four data
bugs into two-sub-cause pairs rather than the single cause D-16 sketched.
Every root-cause claim below is either a direct source-code citation or a
live query result; none are guessed.

**Primary recommendation:** Fix the 5 data bugs first, each independently
(they have independent root causes and independent regression-test
fixtures), before or alongside the UI/perf rework — several of the
visual/UX symptoms the user reported (opencode "dominating" the dashboard,
apparent row duplication, price always looking wrong) are **downstream
consequences** of the date/price/turn_id bugs, not independent rendering
defects. Fixing data first makes the UI rework easier to verify against
real numbers.

### Pattern 1: Pure-function JS block extraction for testing

**What:** `dashboard.py` embeds `filterRows`/`sortRows`/`groupBySession`/
`displayFamily` between literal comment markers
`/* PURE_FUNCTIONS_START */` ... `/* PURE_FUNCTIONS_END */` inside
`_HTML_MID`. The test suite's `_extract_pure_js(html)` helper
(`tests/test_ai_kit_usage_metrics.py:2281-2288`) slices the generated HTML
at those exact marker strings, writes the slice to a `.js` file alongside a
`require()`'d JSON fixture, and executes it under real Node via
`subprocess.run(["node", wrapper], ...)` — see
`test_group_by_session_dedups_turn_tokens` (line 2466) and
`test_shipped_js_canonical_query_via_node` (line 2513).

**When to use:** Any new logic this phase adds that is independently
testable and DOM-free (e.g. a JS-side `subfamilyOf()`/date-range-merge
helper, or virtualization math that computes "which row indices are
visible" without touching `document`) should go INSIDE the marker block so
it inherits this test pattern for free. DOM-manipulation code (row
rendering, MWC component wiring, chart instantiation) stays OUTSIDE the
markers, exactly as `render()`/`renderFlat()`/`renderGrouped()` do today.

**Example (existing, verbatim from `dashboard.py:245-287`):**

### Pattern 2: Atomic write for generated output

**What:** `_atomic_write_text()` (`dashboard.py:434-461`) writes to a
`tempfile.mkstemp()` sibling, `fsync`s, then `os.replace()`s — ported from
`tools/config_doctor_appliers.py`. Preserves the pre-existing file's mode
bits, defaults new files to `0o600`.

**When to use:** Reuse verbatim for the generated `dashboard.html` — do not
write a second, parallel write helper for any new output this phase
produces (there should be none; only `dashboard.html` is generated).

### Anti-Patterns to Avoid

- **`innerHTML` with row-derived data:** the existing test
  `test_no_data_driven_innerhtml_assignment` (line 2498) asserts zero
  `.innerHTML =` assignments matching `row` or a template literal anywhere
  in the shipped `<script>` block AND in `dashboard.py`'s source. This is
  simultaneously an XSS-prevention pattern (command text/family values are
  untrusted-ish local data, rendered via `textContent` today) and a hard
  regression gate. Any new rendering code (virtualized rows, the
  full-command dialog, chart tooltips) MUST continue using `textContent`/
  `element.appendChild`-style DOM construction, never `innerHTML` fed from
  row data.
- **Re-deriving `_QUERY_COLUMNS`/`_INSERT_COLUMNS` independently:**
  `dashboard.py`'s `_QUERY_COLUMNS` (line 12) and `refined_store.py`'s
  `_INSERT_COLUMNS` (line 18) are two hand-maintained tuples that must stay
  column-order-consistent with `_CREATE_TABLE`. Any new column (e.g. a
  schema-level `subfamily`) needs edits in three places
  (`_CREATE_TABLE`, `_INSERT_COLUMNS`/`_INSERT_SQL`'s `ON CONFLICT... SET`
  clause, `_QUERY_COLUMNS`) — missing one produces a silent
  column/value-count mismatch, not a loud error.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Row virtualization / windowing math | A custom "visible row index" scroll-position calculator | `@tanstack/virtual-core`'s `Virtualizer` with `estimateSize: () => 40` (UI-SPEC's fixed 40px dense row height) | Off-by-one scroll bugs and resize-observer edge cases are exactly what this library exists to absorb; UI-SPEC already fixed the row height specifically so `estimateSize` can be a constant |
| Material Design color/typography tokens | Hand-picked hex values / a custom CSS variable scheme | `@material/web`'s `--md-sys-color-*` / `--md-sys-typescale-*` CSS custom properties (already the UI-SPEC's Color/Typography sections) | Automatic light/dark via `prefers-color-scheme` comes free; hand-rolled values would need separate light/dark tables and drift from Material's baseline |
| Date-range picker UI | A custom calendar-popup widget | Two `<input type="date">` elements visually merged (UI-SPEC's confirmed fallback — no MWC date-range component exists, live-verified via jsDelivr directory listing) | UI-SPEC already did the "does a MWC date-range component exist" research and confirmed absence; re-researching this is out of scope |
| Codex `custom_tool_call`/"exec" JS-body argument extraction | A hand-rolled brace-counter or full JS tokenizer | Locate the `tools.exec_command(` (or matching allow-listed `tools.*`) call site with a regex, then feed the position immediately after `tools.exec_command(` into Python's `json.JSONDecoder().raw_decode(text, idx)` (stdlib, handles balanced-brace JSON parsing without hand-rolled counting) | `json.JSONDecoder().raw_decode` is exactly "parse one JSON value starting here, tell me where it ended" — the precise primitive this extraction needs; a hand-rolled counter reinvents it with more bug surface |
| Epoch-ms → ISO date conversion for opencode's `time_created` | String-splitting/manual arithmetic on the millisecond integer | `datetime.fromtimestamp(time_created / 1000, tz=UTC).isoformat()` (stdlib) | The module already uses this exact idiom shape elsewhere (`refiner.py`'s `_parse_ts`, lines 17-24, handles the inverse direction) — stay consistent with the established pattern |

**Key insight:** Every "don't hand-roll" item above already has an
established idiom either in this codebase (`_parse_ts`, `_atomic_write_text`,
the UI-SPEC's own delegated-and-resolved research) or in the stdlib
(`json.JSONDecoder().raw_decode`). This phase's bugfixes are unusually
low-risk for reinventing-the-wheel because the surrounding code already
demonstrates the correct pattern one function away.

## Common Pitfalls

### Pitfall 1: Treating "date empty" as one bug with one fix

**What goes wrong:** A single fix targeting `_row_timestamp()`'s fallback
chain will fix opencode but silently leave cursor's 41 NULL rows unfixed
(or vice versa), and a single regression test asserting "date is populated"
against one fixture won't catch the other runtime's independent defect.

**Why it happens:** The two runtimes have genuinely different root causes.
Opencode: `capture_opencode.py`'s raw envelope
(`_base_envelope`, lines 109-134) never sets a `"timestamp"` key at all —
only `"time_created"` (an epoch-millisecond integer, e.g. `1784667474777`,
confirmed live). The JSON `payload` body for `message`/`part`/`session`
rows also has no `"timestamp"` key (live-verified `payload_keys` for
`message`: `['agent', 'model', 'role', 'summary', 'time']`; for `part`:
`['text', 'type']` — no `"timestamp"` in either). So `refiner.py`'s
`_row_timestamp()` (lines 379-386):
```python
def _row_timestamp(rec: dict):
    value = rec.get("timestamp")
    if value is not None:
        return value
    payload = rec.get("payload")
    if isinstance(payload, dict):
        return payload.get("timestamp")
    return None
```
returns `None` for literally every opencode record — both lookups miss. `[VERIFIED: skills/ai-kit-usage-metrics/ai_kit_usage_metrics/refiner.py:379-386, capture_opencode.py:109-134 — read this session]`

Cursor: `capture_cursor.py`'s `_envelope()` (lines 43-68) **hardcodes**
`"timestamp": None` as a literal value:
```python
    return {
        "raw_ref": f"cursor:{source_file}:{source_line}",
        ...
        "source_confidence": "low",
        "session_id": session_id,
        "timestamp": None,
    }
```
`[VERIFIED: skills/ai-kit-usage-metrics/ai_kit_usage_metrics/capture_cursor.py:56-68 — read this session]` — never populated from anything in the payload, by construction, not by accident of a missing-key lookup.

**How to avoid:** Fix both independently: (1) opencode needs
`_row_timestamp`'s opencode branch to fall back to
`datetime.fromtimestamp(rec["time_created"] / 1000, tz=UTC).isoformat()`
when both existing lookups miss and `rec.get("runtime") == "opencode"` and
`rec.get("time_created")` is not `None`; (2) cursor needs its own
investigation into whether the reverse-engineered transcript JSON actually
contains a usable per-line timestamp anywhere (it is not proven one
exists — see Open Questions). Write two independent regression test
fixtures (one per runtime), matching the existing per-runtime `TestRefiner*`
test class pattern already in the suite.

**Warning signs:** A plan/task description that says "fix the date bug"
singular, with only one test fixture, is under-scoped for this bug.

**Live verification (this session, read-only query against real `refined.db`):**

### Pitfall 2: Conflating "price=0" with "price is None"

**What goes wrong:** A fix that treats every visible `price` value as
suspect will "fix" data that is already correct (opencode's genuinely
zero-cost rows) while leaving the actually-broken rows (claude/codex/rtk,
which show `price=None`, not `0`) unaddressed, because the JS renders
`null` as an **empty string**, not literal `"0"` — `td(row.price)`
(`dashboard.py:342-346`): `cell.textContent = text == null ? "" : String(text)`.

**Why it happens (live-verified, read-only query against real `refined.db`, 84,082 rows):**
```
price_confidence | count
high              | 17414   (== opencode's exact row count)
not_applicable    | 29437   (== rtk's exact row count — by design, rtk has no price concept)
unknown           | 37231   (== claude 35244 + codex 1946 + cursor 41 — exact match)

Of the 17,414 "high"-confidence (opencode) rows:
  price = 0    : 16,366  (94%)
  price > 0    :  1,048  (6%)
```
The 37,231 "unknown" rows (claude/codex/cursor) get `price=None` because
`~/.cache/ai-kit/spec/model-catalog.json` **does not exist on this
machine** (`ls` confirms absence) — `pricing.py:estimate_price()`
(lines 24-26): `if not os.path.isfile(path): return None, "unknown"`. This is
the single largest, most legitimate "price is broken" symptom, and it is a
**data/ops gap** (missing catalog file), not a code bug in `pricing.py`
itself — `estimate_price()` already degrades honestly to `(None, "unknown")`

### Pitfall 3: Assuming `groupBySession`'s dedup key produces duplicate ROWS

**What goes wrong:** Investigating "session-group row duplication" by
looking for a way `groupBySession()` could emit 2 rows for 1 `session_id`
wastes time — it structurally cannot. `order.push(sid)` (`dashboard.py:252`)
only fires the first time a `session_id` is seen; the final `order.map(...)`
(line 277) therefore always emits exactly one output row per distinct
`session_id`, regardless of how many input rows shared it.

**Why it happens:** The real symptom is a **sum/undercounting** bug (via
the `seen[key]` dedup on `session_id + "\0" + turn_id`,
`dashboard.py:258-262`), and separately, a **visual-confusion** issue in the
FLAT (non-grouped) view, where a single compound command's N decomposed
steps legitimately repeat the SAME turn-level `tokens_input`/
`tokens_output`/`price` across N rows (documented, correct behavior per
SKILL.md: "Token/price figures on a compound command are turn-level values
duplicated onto every step of the turn"). Live-verified: one real
session+turn_id pair has 55 step-rows sharing identical token/price values
(a large `&&`-chained compound command) — visually this can read as
"duplicate rows" to someone unfamiliar with the schema, especially
alongside Pitfall 4's family-noise bug making unrelated-looking commands
appear on adjacent rows.

Two real dedup-key weaknesses do exist, confirmed live:
- **rtk**: `turn_id` is `None` for 100% of rtk rows (29,437/29,437,
  `_refine_rtk_record` hardcodes `"turn_id": None`,
  `refiner.py:522`) — by design (rtk has no LLM-turn concept). If
  group-by-session is ever applied while rtk rows are present, every rtk
  row within one session collapses to dedup key `sid + "\0" + "null"`,
  so only the first-seen row's (always-`None`) tokens/price get summed.
  Financially inert today (rtk's `tokens_input`/`price` fields are already
  always `None`), but the `count` shown is correct while the token/price
  sum silently represents 1 row's worth, not N — and `rtk_input_tokens`/
  `rtk_output_tokens`/`rtk_saved_tokens` are not summed by `groupBySession`
  at all (a separate, pre-existing gap, not introduced by this bug).
- **codex**: `turn_id` is a token-count-interval `source_line`
  (`_codex_attr`, `refiner.py:341-365`), chosen as the LAST interval whose
  `source_line <= line`. Because codex's `token_count` events are sparse
  relative to actual `exec_command` calls, multiple genuinely different
  commands can map to the identical chosen interval and therefore the
  identical `turn_id` — live-verified: several `turn_id` values recur
  30-103 times within `refined_commands` (`turn_id=16` → 103 rows,
  `turn_id=26` → 57, `turn_id=24`/`22` → 41 each). Grouped-session sums
  for these would undercount.

**How to avoid:** Split into two independently-scoped fixes: (1) a FLAT-view
display treatment that visually distinguishes "N rows, same compound
command" from "N unrelated rows" (e.g., a subtle grouping/indent or a
`step_index`/`step_count` badge — UI-SPEC's D-14 command-detail dialog
already surfaces `step_index`/`step_count`, this just needs it visible in
the table row too, not only the dialog); (2) `groupBySession`'s dedup key
robustness for `turn_id`-sparse runtimes — the lowest-risk fix is deduping
by `raw_ref` (always unique per decomposed step-row, confirmed by the
`refined_commands` schema's `UNIQUE(raw_ref, step_index)` constraint,
`refined_store.py:80`) plus `step_count == 1` OR an explicit `(session_id,
turn_id)`-membership check only when `turn_id` is non-null, falling back to
per-row (no dedup) when `turn_id` is null. This exact fallback design is
`[ASSUMED]` — flagged for explicit plan-time confirmation, not a locked
recommendation.

**Warning signs:** A fix PR that only touches `groupBySession()`'s `seen[key]`
line without also addressing the flat-view visual-confusion half of the
symptom has fixed half the user's actual complaint.

### Pitfall 4: family_of() applied uniformly regardless of `command_shape`

**What goes wrong:** `refiner.py`'s `_build_row()` (line 428) calls
`family_of(step["text"])` unconditionally:
```python
        "family": family_of(step["text"]),
        "command_shape": step["command_shape"],
```
For `command_shape in {"control_flow_script", "unclassified"}`, `step["text"]`
is the ENTIRE opaque block (never decomposed further, by design — see
SKILL.md's `command_shape` limitation section), so `family_of()`
(`family.py:29-58`) deterministically returns `os.path.basename()` of
whatever token happens to come first in that blob — a control-flow keyword
(`if`/`for`/`while`), or, for `unclassified` blobs (unterminated quotes,
unsupported shell shapes like `$(...)`/backticks), truly arbitrary garbage.

**Why it happens (live-verified against real `refined.db`, `WHERE
command_shape != 'simple'`):**
```
family      | count
cd          | 1370   (cd-prefixed control-flow/unclassified blobs)
if          | 179
cat         | 144
echo        | 125
python3     | 117
rtk         | 91
test        | 89
rev-parse   | 82
git         | 72
"$(git      | 41     (literal garbage — unterminated command-substitution token)
mkdir       | 36
gsd_run()   | 34     (a shell FUNCTION DEFINITION line treated as a command)
```
The `"$(git` and `gsd_run()` rows are the clearest evidence this is not
"random" — they are `os.path.basename()` applied literally to the first
whitespace-delimited token of a blob that was never meant to be read as a
single command. `command_shape` distribution: `simple` 80,896,
`unclassified` 2,868, `control_flow_script` 318 — so ~3.8% of all rows are
affected. `[VERIFIED: local refined.db query, this session]`

**How to avoid:** Guard `family_of()` (or its caller) so `family` is
only computed for `command_shape == "simple"` rows; for
`control_flow_script`/`unclassified` rows, either leave `family` empty
(so the dashboard's existing `displayFamily()`/UI-SPEC's `—` treatment
applies) or set it to the `command_shape` value itself as a distinct,
honest label. This is a small, surgical change — do not attempt to make
`family_of()` "smarter" about parsing inside opaque blobs; that
contradicts the decomposer's own documented philosophy ("mechanical,
never a real shell parser").

**Warning signs:** A "fix" that tries to special-case `if`/`for`/`while`/
`cd`/`cat` as known keywords rather than gating on `command_shape` will
keep missing new garbage patterns (like `"$(git` or `gsd_run()`) forever.

### Subfamily extraction (D-11) — reuses family.py's exact wrapper/assignment/flag-skip logic verbatim

```python
# Source: family.py:29-58 (family_of), read this session — the loop shape
# below is the SAME skip-loop, applied one token deeper for subfamily.
def subfamily_of(command_text: str) -> str:
    tokens = (command_text or "").split()
    i = 0
    while i < len(tokens):
        tok = tokens[i]
        if _ASSIGNMENT_RE.match(tok):
            i += 1
            continue
        if tok in _WRAPPERS:
            i += 1
            while i < len(tokens) and tokens[i].startswith("-"):
                i += 1
            continue
        break
    # i now points at the family-determining token (e.g. "git" in
    # "git -C /path commit"); advance past it, then skip its own leading
    # flags, then take the next non-flag token as subfamily.
    i += 1
    while i < len(tokens) and tokens[i].startswith("-"):
        i += 1
    return tokens[i] if i < len(tokens) else ""
```
