## Estrategia de rendimiento/render

| Option | Description | Selected |
|--------|-------------|----------|
| 7-day default via CLI flag | Prefilter embedded data to last 7 days, configurable via `--days N` | |
| 30-day fixed | Prefilter to last 30 days, no flag | |
| No prefilter, virtualization only | Keep full embedded dataset, fix only render cost | ✓ |

**User's choice:** No prefilter — "El problema no es los datos que se compilan sino el HTML dashboard como se filtra." Full dataset stays embedded (D-09 unchanged); the real problem is client-side render/filter cost.
**Notes:** User also rejected the local-HTTP-server escape hatch outright ("No nos preocupemos por server"). On virtualization approach, user pushed back on "vanilla only" as too archaic and asked whether an external dependency (CDN or bundled .js) could be used instead — confirmed acceptable, `<script src=CDN>` has no CORS issue when the page itself is opened via `file://`. Final sub-decision: CDN direct, no vendoring — user explicitly doesn't mind requiring internet to view the dashboard, prioritizing simplicity over offline capability.

User then specifically requested installing the `frontend-design` plugin from the marketplace.
**Notes:** Claude located `frontend-design@claude-plugins-official` (cached but not installed) and ran `claude plugin install frontend-design@claude-plugins-official` directly — succeeded (scope: user). No in-session reload mechanism existed, so the skill was not immediately callable. User then ran `/reload-skills` and `/reload-plugins` locally, confirming `frontend-design:frontend-design` is now active and available for planning/execution. Theme: default Material palette with automatic light/dark via `prefers-color-scheme`, no custom brand colors. Data-table/grid library: explicitly deferred to `frontend-design` + planner research rather than fixed now, to avoid locking a name before evaluating fit with Material Web Components.
