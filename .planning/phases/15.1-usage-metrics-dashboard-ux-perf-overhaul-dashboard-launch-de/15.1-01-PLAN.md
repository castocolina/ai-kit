## SD-2 — Virtualization DOM and `Virtualizer` contract (CANONICAL)

Plans 03, 04 and 05 all build on this structure. It is stated here in full and referenced
by id from the later plans; if it changes, it changes here first.

**DOM structure (valid HTML — this is the corrected shape).** A `<div id="table-scroll">`
wraps the **entire** `<table id="usage-table">`. That div is the only element carrying
`overflow-y: auto` and a bounded height, so it is the scrollport. `getScrollElement`
returns that div. A wrapper element is NEVER placed between `<table>` and `<tbody>` —
`<table>`'s only legal children are `<caption>`, `<colgroup>`, `<thead>`, `<tbody>`,
`<tfoot>` and `<tr>`, so the previously-planned "scroll container wrapping the `<tbody>`"
was invalid markup that browsers would have re-parented.

- `<thead>` is `position: sticky; top: 0` inside the scrollport, so the header row stays
  visible while the body scrolls.
- `<tbody id="usage-tbody">` carries `display: block; position: relative;` and has its
  inline `height` set to `virtualizer.getTotalSize() + "px"` on every paint. That height is
  what gives the scrollbar its correct full-dataset length; no spacer rows are used.
- Every materialized `<tr>` carries `position: absolute; top: 0; left: 0; width: 100%;
  height: 56px; display: flex;` and `transform: translateY(<virtualItem.start>px)`. Rows
  keep their correct HTML ancestry (`<tbody>` -> `<tr>` -> `<td>`).
- Because both the header `<tr>` and the body `<tr>`s are `display: flex`, column widths
  are declared once as a shared set of `flex` bases (a CSS custom property per column,
  applied by `nth-child`), so header and body stay aligned without a `<colgroup>`.
- `56px` is the constant row height from UI-SPEC.md's Spacing Scale exception (raised from
  40px so the two-line wrapped command cell D-12 requires fits inside a constant height).

**Virtualizer construction (raw `@tanstack/virtual-core` — headless, no framework
adapter).** Import `Virtualizer`, `observeElementRect`, `observeElementOffset` and
`elementScroll` from the pinned module URL. The headless core does NOT supply browser
adapters; omitting them is why an integration contract of only `count` / `estimateSize` /
`getScrollElement` cannot run. Construct with exactly these options:

- `count` — the length of the row array currently being painted
- `getScrollElement` — returns the `#table-scroll` div
- `estimateSize` — returns the constant `56`
- `observeElementRect`, `observeElementOffset` — the imported browser adapters
- `scrollToFn` — the imported `elementScroll`
- `overscan` — `8`
- `onChange` — calls the single painter described below

Lifecycle: call `_didMount()` once immediately after construction, and `_willUpdate()`
before each measure/paint cycle. When the row array changes length, call `setOptions` with
the same option object and the new `count`, then `measure()`, then paint.

**One painter, both modes (this is the fix for the unvirtualized grouped path).** There is
exactly ONE function in the file that writes to `<tbody>`. It reads two module-scoped
values — the current row array and the current cell-builder function — and materializes
only `virtualizer.getVirtualItems()`. `render()` selects the mode by setting the
cell-builder (a flat-row builder or a grouped-row builder) and the row array, then
reconfigures the one virtualizer's `count` and repaints. `renderGrouped`'s
append-every-row loop is deleted, not kept alongside. Group-by-session over the real
84,082-row dataset is exactly as bounded as flat mode.

**The DOM-free half is a real production function, not a test-only shim.**
`sliceForItems(rows, items)` lives inside the pure-function marker block and maps the
virtualizer's virtual items to `{index, start, row}` triples. The painter iterates
`sliceForItems(...)`'s output and nothing else, so a node test that feeds it an
84,082-element row array and a 20-element item list and asserts exactly 20 results is
proving the production materialization path, not a parallel one.
</shared_definitions>
