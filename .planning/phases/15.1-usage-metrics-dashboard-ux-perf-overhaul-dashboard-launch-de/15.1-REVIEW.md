## Warnings

### WR-01: Grouped-mode table is silently unsorted on the most common first user action

**File:** `skills/ai-kit-usage-metrics/ai_kit_usage_metrics/dashboard.py:1122` (default `sortKey`), `:1738-1751` (`buildCurrentRowsFromFiltered`), `:800-812` (`sortRows`)

**Issue:** `sortKey` defaults to `"date"` (line 1122) and is only ever changed
by clicking a `<th data-sort-key="...">` header (lines 1798-1809).
`groupBySession()`'s output rows are `{session_id, count, tokens_input,
tokens_output, price}` — there is no `date` field. When a user checks
"group by session" without having first clicked any column header (a very
plausible first action, since grouping is one of the dashboard's headline
features per SKILL.md), `buildCurrentRowsFromFiltered()` calls
`sortRows(groupBySession(currentFiltered), "date", "asc")`. In `sortRows`,
`av = a["date"]` and `bv = b["date"]` are both `undefined` for every row, and
`undefined == null` is `true` in JavaScript, so the comparator's very first
branch (`if (av == null && bv == null) return 0;`) fires for every pair —
the sort degenerates to a total no-op and the session list is presented in
whatever order `groupBySession()`'s internal `order` array happened to
accumulate sessions (first-seen order in the filtered set), not a
meaningful order like `session_id` or `count`. There is also no visual "this
column is the active sort" indicator anywhere in the markup/CSS, so a user
has no way to notice the session list isn't actually sorted by anything they
chose. This is the exact scenario the prior review's IN-01 finding
speculatively raised ("If the intent was in fact to guard against a
flat-mode-only sort key... that guard should instead fall back to a
grouped-valid default key") — it is real, not hypothetical, and the fix that
landed (dropping the dead ternary) did not address it because the original
ternary never addressed it either.

**Fix:** Fall back to a grouped-valid key (e.g. `"session_id"`) when the
active `sortKey` isn't one of the grouped row's own fields:

```javascript
var GROUPED_SORT_KEYS = ["session_id", "count", "tokens_input", "tokens_output", "price"];

function buildCurrentRowsFromFiltered() {
  var grouped = document.getElementById("group-by-session").checked;
  if (grouped) {
    var groupedKey = GROUPED_SORT_KEYS.indexOf(sortKey) === -1 ? "session_id" : sortKey;
    currentRows = sortRows(groupBySession(currentFiltered), groupedKey, sortDir);
    currentBuilder = groupedRowBuilder;
  } else {
    currentRows = sortRows(currentFiltered, sortKey, sortDir);
    currentBuilder = flatRowBuilder;
  }
}
```

### WR-02: Virtualizer failure fallback can strand the page in a permanent error state even after a late-but-successful mount

**File:** `skills/ai-kit-usage-metrics/ai_kit_usage_metrics/dashboard.py:1158-1167` (`showPageError`), `:1854-1856` (5s fallback timer), `:1564-1571` (`mountVirtualizer`)

**Issue:** The new fallback (`setTimeout(function () { if (!virtualizer)
showPageError(); }, 5000)`) correctly handles the two cases the task
description asked to verify (immediate mount, on-time event-driven mount).
It does not handle a third, realistic case: the `@tanstack/virtual-core`
script is merely slow (a cold CDN edge, a throttled connection, first-load
DNS latency) and the `virtual-core-ready` event fires *after* the 5-second
timer. In that sequence: the timer fires first, `virtualizer` is still
`null`, so `showPageError()` runs and unconditionally hides `filtersForm`,
`chartsRow`, and `scrollEl` and removes the loading bar (lines 1162-1166).
Shortly afterward the deferred `virtual-core-ready` listener still fires,
`mountVirtualizer()` still runs, `virtualizer` becomes non-null, and
`paint()` still populates `<tbody>` — but nothing ever un-hides
`filtersForm`/`chartsRow`/`scrollEl` or hides `pageErrorState` again, since
`showPageError()` has no inverse and nothing calls one. The user is left
looking at a permanent "Couldn't load usage data. Regenerate the dashboard
with `ai-kit-usage-metrics dashboard`." message telling them to re-run a
pipeline that, in this scenario, worked fine — the data loaded, it's just
invisible behind the error panel. This is a strictly better outcome than the
pre-fix silent-permanent-blank-table bug WR-02 was written to close, but it
trades "silently blank" for "confidently, incorrectly wrong," which is worse
for a user who acts on the error message's instructions. There is also no
test in `tests/test_ai_kit_usage_metrics.py` exercising either the timeout
firing or a late-mount-after-timeout sequence (grep for `virtual-core-ready`
finds only the production code).

**Fix:** Either (a) clear the fallback timer once the virtualizer mounts, so
a late-but-successful mount is a true no-op:

```javascript
var virtualizerFallbackTimer = null;
// ...
window.addEventListener("virtual-core-ready", function () {
  if (virtualizerFallbackTimer) clearTimeout(virtualizerFallbackTimer);
  mountVirtualizer();
}, {once: true});
virtualizerFallbackTimer = setTimeout(function () {
  if (!virtualizer) showPageError();
}, 5000);
```

or (b), if the timer firing first is considered acceptable, make
`mountVirtualizer()` itself reverse `showPageError()`'s effects (re-show
`filtersForm`/`chartsRow`/`scrollEl`, hide `pageErrorState`) when it
succeeds after the fact. Either way, add a node-executed test asserting the
late-mount-after-timeout sequence does not leave the page-error state
visible.

### IN-01: No test coverage for the new virtualizer-failure fallback path

**File:** `skills/ai-kit-usage-metrics/ai_kit_usage_metrics/dashboard.py:1854-1856`; `tests/test_ai_kit_usage_metrics.py`

**Issue:** The WR-02 fallback (5-second timer + `showPageError()`) shipped
with no accompanying test. `tests/test_ai_kit_usage_metrics.py` has no
reference to `virtual-core-ready`, `mountVirtualizer`, or the 5000ms
constant outside the production code itself, so both the intended
"never mounts -> error shown" behavior and the WR-02 finding above
("mounts late -> error should clear") are currently unverified by the suite.

**Fix:** Add a node-executed test (matching the existing `_extract_pure_js`
harness pattern used elsewhere in the suite) that stubs `window.__virtualCore`
as absent, fast-forwards past the timeout, and asserts `showPageError`-driven
DOM state; then a second case that fires `virtual-core-ready` shortly after
and asserts the error state is not left showing (this second case will fail
against the current implementation until WR-02 above is fixed).
