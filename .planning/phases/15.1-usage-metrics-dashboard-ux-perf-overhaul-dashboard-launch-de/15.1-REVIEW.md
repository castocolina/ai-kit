## Summary

Reviewed the full accumulated diff for Phase 15.1 (`family.py`, `refiner.py`,
`refined_store.py`, `cli.py`, `dashboard.py`'s embedded HTML/CSS/JS, and the
test suite) against the SKILL.md contract the phase itself writes. The
Python-side logic (decomposer/family/refiner/refined_store dedup identity,
codex/cursor timestamp inference, atomic-write/permission hygiene) is careful
and internally consistent, and the specific live-discovered fixes called out
in the task description (CDN transform, grouped-mode column width, checkbox
visibility) are correctly applied in the current source.

The most significant finding is a genuine, node-verified parity break between
`family.py`'s `subfamily_of()` and its JavaScript port embedded in
`dashboard.py`: a same-day live fix (`06b7e0b`) added `"export"` to the shared
`_WRAPPERS` constant that both `family_of()` and `subfamily_of()` read, but
never touched the JS mirror `SUBFAMILY_WRAPPERS`, and the shared parity-test
oracle (`SUBFAMILY_SPEC_CASES`) has no `export`-prefixed case, so the existing
`test_subfamily_js_matches_spec_table_and_python` test does not catch it. This
is exactly the drift the code's own comments warn against ("Any change here
must be mirrored in family.py, and vice versa").

Three further robustness/consistency gaps were found in the dashboard's
embedded JS around virtualizer-load failure, the `source_confidence` badge
being applied to every row (not just low-confidence ones), and missing
Subresource Integrity on third-party CDN assets loaded into a page that
embeds the user's full local command history.

## Warnings

### WR-01: `subfamily_of()` JS port drifted from Python after the `export`-wrapper fix

**File:** `skills/ai-kit-usage-metrics/ai_kit_usage_metrics/dashboard.py:680` (JS mirror) vs `skills/ai-kit-usage-metrics/ai_kit_usage_metrics/family.py:29` (Python source of truth)

**Issue:** Commit `06b7e0b` ("fix(15.1): stop family.py from surfacing
decomposer/tokenizer garbage") added `"export"` to `family.py`'s `_WRAPPERS`
frozenset, which is shared by both `family_of()` and `subfamily_of()`. The
dashboard's JS port of `subfamily_of()` (`dashboard.py`'s embedded
`SUBFAMILY_WRAPPERS`, line 680) was never updated and still reads
`["sudo", "env", "time", "nice", "ionice"]` — missing `"export"`. Verified by
direct execution:

```
$ python3 -c "from ai_kit_usage_metrics import family; \
  print(family.subfamily_of('export FOO=bar git commit -m x'))"
commit

$ node -e "<extracted PURE_FUNCTIONS block>; \
  console.log(subfamilyOf('export FOO=bar git commit -m x'))"
""
```

Python correctly resolves the subfamily to `"commit"`; the shipped dashboard
JS resolves it to `""`. Any row whose command starts with `export FOO=bar
...` (a common shape for CI/build commands, e.g. `export PNPM_HOME=/x/bin npm
run build`) silently loses its subfamily in the dashboard's filter dropdown
and the family/subfamily distribution chart, while the same command would
correctly resolve via the Python-side `family` column. The shared
parity-test oracle `SUBFAMILY_SPEC_CASES` (`tests/test_ai_kit_usage_metrics.py:262`)
has no `export`-prefixed case, so
`test_subfamily_js_matches_spec_table_and_python` (line 3104) passes despite
the drift — the test's own stated purpose ("a parity test that only proves
the JS and Python outputs agree ... BOTH violate the real spec table") is
exactly the trap this case fell into, just from the opposite direction (JS
alone drifted, not both).

**Fix:** Add `"export"` to `SUBFAMILY_WRAPPERS` in `dashboard.py`, and add at
least one `export`-prefixed case to `SUBFAMILY_SPEC_CASES` in the test file so
this class of drift is caught automatically going forward:

```javascript
var SUBFAMILY_WRAPPERS = ["sudo", "env", "time", "nice", "ionice", "export"];
```

```python
SUBFAMILY_SPEC_CASES = [
    ...
    ("export FOO=bar git commit -m msg", "commit"),
]
```

### WR-02: Virtualizer CDN-load failure leaves the table silently and permanently blank

**File:** `skills/ai-kit-usage-metrics/ai_kit_usage_metrics/dashboard.py:1836-1842` (mount gate), `:1537-1558` (`paint()`)

**Issue:** `initialize()` only mounts the row virtualizer when
`window.__virtualCore` is already set, or via a one-time
`"virtual-core-ready"` listener that the `@tanstack/virtual-core` module
script dispatches on successful load. If that CDN script fails to load
(network failure, ad-blocker, offline `file://` open with no connectivity —
a real scenario for a local-first tool whose own SKILL.md stresses "entirely
on this machine"), the event never fires, `virtualizer` stays `null`
forever, and `paint()` (the only function that writes rows into `<tbody>`)
early-returns on every call. Meanwhile `applyFilters()` still runs during
`initialize()`, so `currentRows` is non-empty and `shouldShowEmptyState()`
returns `false` — the "no results" empty state is correctly suppressed, but
nothing replaces it. The loading bar is unconditionally removed at the end of
`initialize()` regardless of whether the virtualizer mounted. The net result:
headers and filters render, the loading indicator disappears, and the table
body is permanently empty with no visible error — unlike the equivalent
Chart.js failure path, which explicitly checks `chartJsAvailable()` and shows
a `.chart-fallback` message per chart. There is no test exercising this path
(`grep` for `virtual-core-ready`/`__virtualCore` in the test suite only finds
the production code, not a failure-path test).

**Fix:** Add a timeout-based fallback (e.g. a few seconds after
`initialize()` starts) that calls `showPageError()` (or a table-scoped
variant of it) if `virtualizer` is still `null`, so a CDN failure surfaces the
same "Couldn't load usage data" state the JSON-parse-failure path already
uses, instead of silently leaving an empty table:

```javascript
setTimeout(function () {
  if (!virtualizer) showPageError();
}, 5000);
```

### WR-03: `source_confidence` badge applied to every row, not just low-confidence ones

**File:** `skills/ai-kit-usage-metrics/ai_kit_usage_metrics/dashboard.py:1382-1387`

**Issue:**

```javascript
var conf = document.createElement("td");
if (row.source_confidence) {
  conf.textContent = String(row.source_confidence);
  conf.className = "badge";
}
tr.appendChild(conf);
```

`refiner.py` sets `source_confidence` to `"high"` for every Claude/opencode
/codex/rtk row (`rec.get("source_confidence") or "high"`) and `"low"` only
for Cursor rows. Because the condition here is a truthiness check on the
column rather than `row.source_confidence === "low"`, essentially every row
in a real dataset (all non-Cursor rows) gets the same `.badge` styling — an
error-tinted, red-bordered treatment the CSS comment itself documents as
"error-tinted, per UI-SPEC's Destructive/warning role" (`dashboard.py:245-256`).
This directly contradicts SKILL.md's own requirement: "do not present a
Cursor row with the same certainty as a Claude Code or opencode row" — the
intended signal (this specific row is *low* confidence) is drowned out
because the *majority*-case ("high") gets the identical alarm styling. Compare
the `execution_certain` badge two lines below it (`isConditional(row)`),
which correctly badges only the exceptional case and leaves the cell blank
otherwise — `source_confidence` should follow the same pattern.

**Fix:**

```javascript
var conf = document.createElement("td");
if (row.source_confidence === "low") {
  conf.textContent = String(row.source_confidence);
  conf.className = "badge";
} else if (row.source_confidence) {
  conf.textContent = String(row.source_confidence);
}
tr.appendChild(conf);
```

### WR-04: No Subresource Integrity on third-party CDN assets loaded into a page embedding full local usage history

**File:** `skills/ai-kit-usage-metrics/ai_kit_usage_metrics/dashboard.py:49-50, 62-71, 74, 83`

**Issue:** The generated dashboard embeds the user's complete local command
history (including literal shell command text, which can contain paths,
hostnames, and other locally-sensitive strings) as inline JSON, then loads
several third-party scripts and stylesheets from `fonts.googleapis.com`,
`unpkg.com`, `esm.run`, and `cdn.jsdelivr.net` with no `integrity`/
`crossorigin` attributes. SKILL.md's own NEVER list states "Never send
session data off-machine or wire a hosted-database capability to it," but a
compromised or MITM'd CDN response for any of these (particularly the
classic `<script src="...chart.umd.min.js">` and the two `<link
rel="stylesheet">` tags, which do support SRI) could execute arbitrary JS in
the page with direct DOM access to the embedded dataset and exfiltrate it via
a normal cross-origin `fetch`/`img` request — undermining the "never leaves
the machine" guarantee this skill is built around. (The bare-specifier
`import "https://unpkg.com/..."` statements inside the `type="module"` script
cannot carry an `integrity` attribute at all, so this fix only closes the gap
for the assets that support it.)

**Fix:** Add `integrity`/`crossorigin="anonymous"` to the two Google Fonts
`<link>` tags and the Chart.js `<script src>` tag (hashes are stable for a
pinned CDN version):

```html
<script src="https://cdn.jsdelivr.net/npm/chart.js@4.5.1/dist/chart.umd.min.js"
        integrity="sha384-<pinned-hash>" crossorigin="anonymous"></script>
```

For the `@material/web`/`@tanstack/virtual-core` ES-module imports, consider
vendoring a local copy under the skill's own directory (consistent with the
"entirely on this machine" design goal) rather than relying on unpinned
runtime CDN fetches, since SRI is not available for bare-specifier module
imports.

## Info

### IN-01: Dead no-op ternary in `buildCurrentRowsFromFiltered()`

**File:** `skills/ai-kit-usage-metrics/ai_kit_usage_metrics/dashboard.py:1739`

**Issue:**

```javascript
currentRows = sortRows(
  groupBySession(currentFiltered),
  sortKey === "session_id" ? "session_id" : sortKey,
  sortDir
);
```

The ternary `sortKey === "session_id" ? "session_id" : sortKey` always
evaluates to `sortKey` regardless of the branch taken (both arms return the
same value) — it is equivalent to just passing `sortKey`. This reads as a
leftover from an earlier key-remapping step that no longer does anything,
and is confusing for a future maintainer trying to understand why grouped
mode's sort key would ever need special-casing.

**Fix:** Simplify to `sortRows(groupBySession(currentFiltered), sortKey,
sortDir)`. If the intent was in fact to guard against a flat-mode-only
sort key (e.g. `command_text`) leaking into grouped mode and producing a
silently-unsorted grouped view (grouped rows have no `command_text` field,
so `sortRows` degenerates to a no-op comparator), that guard should instead
fall back to a grouped-valid default key such as `"session_id"` when
`sortKey` isn't one of the grouped columns, not repeat `sortKey` itself.
