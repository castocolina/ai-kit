## 15.1-01

### Summary
The tracer correctly joins the opencode timestamp fix, dashboard generation, runtime column, browser launch, Material styling, and CDN dependencies. However, the virtualization contract is incomplete and only replaces the flat renderer, leaving the grouped renderer on the original unbounded DOM path. The current verification proves generated text, not an operational virtualized dashboard.

### Strengths
- The opencode date fix targets the correct boundary: capture stores `time_created` but no `timestamp`, while `_row_timestamp()` only checks timestamp fields today. Evidence: `capture_opencode.py:109-134`, `refiner.py:379-386`, `15.1-01-PLAN.md:172-182`.
- The browser-open change uses the single `cmd_dashboard()` integration point already shared by `run` and `dashboard`. Evidence: `cli.py:93-103`, `cli.py:112-122`, `15.1-01-PLAN.md:184-193`.
- Existing JSON escaping, atomic writes, and `textContent`-based rendering are explicitly preserved. Evidence: `dashboard.py:342-346`, `dashboard.py:434-474`, `15.1-01-PLAN.md:195-198`, `15.1-01-PLAN.md:233-236`.
- The package-legitimacy checkpoint is appropriately blocking and occurs before dependency integration. Evidence: `15.1-01-PLAN.md:115-149`.

### Concerns
- **HIGH: The raw `Virtualizer` integration contract is incomplete and the proposed DOM structure is invalid.** The plan supplies only `count`, `estimateSize`, and `getScrollElement`, but direct `@tanstack/virtual-core` use also needs the browser adapters and lifecycle wiring such as `observeElementRect`, `observeElementOffset`, `elementScroll`, `_willUpdate()`, and an `onChange` render callback. It also asks for a scroll container "wrapping the `<tbody>`," although the current valid structure has `<tbody>` directly under `<table>` and HTML does not permit an arbitrary wrapper there. Evidence: `dashboard.py:104-121`, `15.1-01-PLAN.md:200-209`, `15.1-01-PLAN.md:226-236`, and the official `Virtualizer` API for the pinned package.
- **HIGH: Grouped rendering remains unvirtualized.** Task 2 only replaces `renderFlat`, while the current grouped branch still loops over every grouped result and appends every row. This conflicts with the plan's truth that the table always materializes only viewport-near rows. Evidence: `dashboard.py:352-400`, `15.1-01-PLAN.md:37-40`, `15.1-01-PLAN.md:226-236`, `15.1-01-PLAN.md:336-339`.
- **MEDIUM: The tracer test cannot prove the tracer's central claim.** It asserts CDN strings, header order, and browser-open arguments, but never loads the page in a browser, checks module execution, inspects virtual row count, or detects console errors. The only operational check is manual. Evidence: `15.1-01-PLAN.md:249-273`, `15.1-01-PLAN.md:279-296`; existing dashboard tests likewise inspect HTML or execute only DOM-free functions under Node at `tests/test_ai_kit_usage_metrics.py:2404-2549`.
- **MEDIUM: The runtime chart has five real categories but only four specified colors.** The human check expects all five runtimes, while the implementation instruction uses only the first four palette entries. Evidence: `15.1-01-PLAN.md:237-242`, `15.1-01-PLAN.md:286-295`, `15.1-UI-SPEC.md:118-125`.

### Suggestions
- Define a valid table virtualization structure with the scroll container around the table, plus every raw-core adapter, lifecycle call, and ESM ownership boundary.
- Virtualize both flat and grouped result sets through one renderer.
- Add browser-DOM verification that fails on module-load errors and asserts the rendered `<tr>` count remains bounded for an 84,000-row fixture.
- Define deterministic color reuse or add a fifth accessible runtime color.

### Risk Assessment
**HIGH.** This is the foundation for every later plan, but its main performance mechanism is not yet executable from the written instructions and does not cover grouped mode.

## 15.1-02

### Summary
The family-shape guard and evidence-based Codex allow-list are well targeted. Three material defects remain: the prescribed subfamily algorithm contradicts D-11's locked example, the new Codex extractor cannot propagate `workdir` through the existing string-only interface, and the cursor branch permits documentation instead of the promised fix.

### Strengths
- Gating `family_of()` on `command_shape == "simple"` directly addresses the current unconditional assignment without turning the mechanical family parser into a shell parser. Evidence: `refiner.py:414-432`, `decomposer.py:39-65`, `15.1-02-PLAN.md:114-125`.
- The Codex branch uses `JSONDecoder.raw_decode()` and requires a negative non-shell fixture, reducing false-positive command attribution. Evidence: `refiner.py:121-142`, `refiner.py:446-454`, `15.1-02-PLAN.md:211-255`.
- The plan preserves the existing legacy Codex shape and scopes malformed input to a no-row result instead of aborting refinement. Evidence: `refiner.py:134-142`, `refiner.py:446-454`, `15.1-02-PLAN.md:240-255`.

### Concerns
- **CRITICAL: The prescribed subfamily algorithm cannot satisfy D-11.** Advancing past `git`, skipping only tokens beginning with `-`, then returning the next token makes `git -C /path commit` return `/path`, not `commit`. The existing family parser has no option-arity mechanism to know that `-C` consumes a value. Evidence: `15.1-CONTEXT.md:31`, `family.py:44-58`, `15.1-02-PLAN.md:289-307`.
- **HIGH: `workdir` has no path from the new extractor to `resolved_cwd`.** The plan requires the extractor to return `str | None`, and `_command_text()` consumes only command text. Codex remains wired to `_cwd_state_resolver()`, which discards the record and cannot see the extracted `workdir`; only opencode has a record-aware resolver. Evidence: `refiner.py:161-172`, `refiner.py:186-208`, `15.1-02-PLAN.md:189-202`, `15.1-02-PLAN.md:219-221`.
- **HIGH: Cursor's required fix can silently become a documentation-only outcome.** The phase says all date bugs are fixed now, but the plan allows leaving every Cursor date null whenever the local raw store is absent or no reliable field is found. Evidence: `15.1-CONTEXT.md:9`, `15.1-CONTEXT.md:37`, `capture_cursor.py:43-68`, `15.1-02-PLAN.md:127-149`, `15.1-02-PLAN.md:164-167`.
- **MEDIUM: Conditional `SKILL.md` editing is undeclared.** Task 1 may update `SKILL.md`, but neither the plan frontmatter nor the task's `<files>` includes it. Evidence: `15.1-02-PLAN.md:8-11`, `15.1-02-PLAN.md:93-102`, `15.1-02-PLAN.md:143-149`.

### Suggestions
- Define option-value handling that explicitly passes `git -C /path commit`, and add that exact locked example to the tests.
- Return a structured Codex extraction result containing `command` and `workdir`, or add a separately reusable `_codex_custom_tool_workdir()` consumed by a Codex-specific resolver.
- Resolve the Cursor outcome before execution. If no source timestamp exists, formally amend the phase goal instead of treating documentation as equivalent to a fix.
- Declare `SKILL.md` as a possible output of Plan 02.

### Risk Assessment
**HIGH.** The plan's canonical subfamily implementation is wrong for the user's explicit example, and one tested Codex behavior has no implementable data path.

## 15.1-03

### Summary
The filter/date/null-display work is logically grouped and uses the existing pure-JavaScript test harness well. It nevertheless propagates the incorrect subfamily oracle, recreates garbage subfamilies for opaque scripts, and explicitly implements command overflow opposite to D-12.

### Strengths
- Computing subfamily once at payload load avoids repeating derivation across every filter event. Evidence: `15.1-03-PLAN.md:117-133`; current filter events call `render()` on every input/change at `dashboard.py:391-419`.
- The Python-to-JavaScript parity test is a strong drift-control pattern and reuses the established marker harness. Evidence: `tests/test_ai_kit_usage_metrics.py:2281-2288`, `15.1-03-PLAN.md:135-149`.
- The date-range behavior is explicit for open bounds, same-day ranges, and null dates. Evidence: `dashboard.py:154-160`, `15.1-03-PLAN.md:176-184`, `15.1-03-PLAN.md:212-236`.
- Null-versus-zero rendering preserves genuine zero values and retains the existing XSS control. Evidence: `dashboard.py:342-346`, `15.1-03-PLAN.md:297-340`.

### Concerns
- **CRITICAL: The parity test only proves agreement with a wrong oracle.** Plan 03 ports Plan 02's flawed "skip flags, return next token" behavior, so both implementations can agree while both violate `git -C /path commit → commit`. Evidence: `15.1-CONTEXT.md:31`, `15.1-03-PLAN.md:117-143`.
- **CRITICAL: Command overflow directly contradicts D-12.** The context requires a wrapped command column; the plan says it must remain on one line and explicitly not wrap. Evidence: `15.1-CONTEXT.md:32`, `15.1-03-PLAN.md:35`, `15.1-03-PLAN.md:273-281`, `15.1-03-PLAN.md:323-326`. The approved UI spec repeats the conflicting single-line decision at `15.1-UI-SPEC.md:158`, so the design artifact also needs correction or an explicit user-approved amendment.
- **HIGH: Subfamily derivation recreates opaque-script garbage.** Plan 02 empties `family` for non-simple command shapes, but Plan 03 derives `subfamily` from every row's command text without checking `command_shape`. Opaque control-flow and unclassified blobs will therefore populate the new subfamily filter with arbitrary second tokens. Evidence: `decomposer.py:39-65`, `refiner.py:427-432`, `15.1-03-PLAN.md:125-133`.
- **MEDIUM: The Material select option contract is missing.** Current `fillSelect()` appends native `<option>` elements, while Task 2 replaces the controls with `md-outlined-select` but never directs `fillSelect()` to create `md-select-option` children or specifies the all-value option. Evidence: `dashboard.py:313-324`, `15.1-UI-SPEC.md:51-60`, `15.1-03-PLAN.md:190-209`.
- **MEDIUM: "Clear filters" has behavior but no implementation instruction or direct test.** The plan adds the button and says clearing restores all controls, but the action never defines its listener/reset sequence and the proposed Node test exercises `filterRows`, not DOM control reset. Evidence: `15.1-03-PLAN.md:176-201`, `15.1-03-PLAN.md:229-236`.

### Suggestions
- Fix the canonical Python algorithm first, then retain the cross-language parity test.
- Gate dashboard subfamily decoration on `command_shape === "simple"`.
- Reconcile wrapped versus ellipsized command display with D-12 before execution.
- Specify `md-select-option` creation, selection semantics, and the clear-button reset behavior.
- Add a browser-level test for Material select population and clear-filter interaction.

### Risk Assessment
**HIGH.** The plan can pass all proposed tests while violating two locked user decisions and reintroducing the family-noise problem through the new axis.

## 15.1-04

### Summary
The dialog, accessibility, error states, and delegated event handling are thoughtful. The plan overestimates what one refined row contains, and its null-turn fallback can overcount compound commands because it deliberately includes `step_index` in the dedup key.

### Strengths
- A single reusable dialog and delegated activation are appropriate for recycled virtual rows. Evidence: `15.1-04-PLAN.md:115-124`.
- Clipboard refusal, keyboard activation, focus restoration, bounded step-list height, and explicit accessible labels cover important interaction failures. Evidence: `15.1-04-PLAN.md:103-109`, `15.1-04-PLAN.md:131-159`.
- Error-state text remains fixed and row-derived content continues through `textContent`, preserving the existing XSS posture. Evidence: `dashboard.py:342-346`, `15.1-04-PLAN.md:157-167`, `15.1-04-PLAN.md:290-313`.

### Concerns
- **CRITICAL: One row does not contain the full decomposer breakdown.** `_build_row()` stores only that step's `command_text`, `step_index`, and trailing operator. The sibling steps exist as separate rows sharing `raw_ref`; the plan says the dialog is populated "from that row" and then asks for one entry per step without specifying a sibling lookup or index. Evidence: `refiner.py:414-432`, `refiner.py:446-473`, `15.1-04-PLAN.md:119-142`.
- **HIGH: The null-turn fallback overcounts null-turn compound commands.** Every step generated from one raw record inherits the same turn-level token and price attributes. Keying null turns by `raw_ref + step_index` deliberately treats each duplicated step as unique. The safer fallback is session plus `raw_ref`, which distinguishes separate commands while deduping sibling steps from one raw record. Evidence: `refiner.py:446-473`, `refined_store.py:3-7`, `refined_store.py:49-80`, `15.1-04-PLAN.md:217-245`.
- **MEDIUM: The loading indicator may never visibly paint.** Payload parsing and initialization currently execute synchronously in one inline script. Adding a progress element and removing it after synchronous row creation does not guarantee a browser paint between those operations; the plan does not require an event-loop or animation-frame yield. Evidence: `dashboard.py:290-419`, `15.1-04-PLAN.md:303-319`.
- **MEDIUM: Dialog tests do not exercise the actual interaction path.** Static markup assertions and a pure step-list helper cannot prove delegated row lookup, focus restoration, clipboard failure UI, keyboard activation, or Material dialog behavior. Only a manual check covers part of that surface. Evidence: `15.1-04-PLAN.md:161-177`, `15.1-04-PLAN.md:328-338`.

### Suggestions
- Build an index such as `rowsByRawRef` once at load and populate the dialog from all siblings sorted by `step_index`.
- Use `session_id + raw_ref` for null-turn aggregation, and test both a multi-step null-turn command and two distinct null-turn raw records.
- Yield with `requestAnimationFrame()` before heavy initialization and remove the progress indicator only after the first rendered frame.
- Add browser-DOM tests for keyboard opening, focus return, copy success/failure, and multi-step sibling lookup.

### Risk Assessment
**HIGH.** The principal dialog behavior has no defined data retrieval mechanism, and the proposed arithmetic fix introduces a new double-counting case.

## 15.1-05

### Summary
The closeout plan properly includes documentation, skill review, full repository gates, and real-store re-refinement. Its daily token/price chart would overcount compound commands, however, and the chart design leaves one of its two required measures non-visual while recomputing all chart datasets on every keystroke.

### Strengths
- Documentation updates are tied to shipped behavior and include confidence-qualified Cursor and Codex limitations. Evidence: `SKILL.md:84-121`, `SKILL.md:136-146`, `15.1-05-PLAN.md:216-278`.
- The skill-judge loop and aggregate project gates match repository policy. Evidence: `AGENTS.md` non-negotiable SKILL review rule, `Makefile:45-66`, `Makefile:72-122`, `15.1-05-PLAN.md:267-305`, `15.1-05-PLAN.md:309-383`.
- Re-refining through the normal CLI and existing UPSERT is preferable to ad hoc SQL. Evidence: `cli.py:72-81`, `refined_store.py:84-117`, `15.1-05-PLAN.md:326-339`.
- Chart labels remain in Chart.js's data API rather than being interpolated into markup. Evidence: `15.1-05-PLAN.md:171-176`, `15.1-05-PLAN.md:423-431`.

### Concerns
- **CRITICAL: The per-day token/price aggregation does not deduplicate turn-level values.** Tokens and price are duplicated onto every decomposed step, and consumers are explicitly required to dedup before summing. The plan describes summing rows and its test fixture omits a compound command sharing one `(session_id, turn_id)`, so chart totals will be inflated by step count. Evidence: `refined_store.py:3-7`, `SKILL.md:118-121`, `SKILL.md:209-211`, `15.1-05-PLAN.md:115-123`, `15.1-05-PLAN.md:151-184`.
- **HIGH: Chart 1 does not actually visualize both required measures.** D-18 asks for tokens and price per day, but the plan tells the executor to pick one rendered measure and put the other only in a tooltip. That produces one charted metric and one annotation, with no defined choice, scale, or acceptance expectation. Evidence: `15.1-CONTEXT.md:51`, `15.1-05-PLAN.md:134-140`.
- **HIGH: Recomputing all chart aggregations on every input and sort event risks restoring the original freeze.** The current form fires `render()` for every `input` event. Plan 05 adds three full-dataset aggregations and Chart.js updates to that path, even on sort events that do not change chart data. Evidence: `dashboard.py:391-419`, `15.1-05-PLAN.md:160-164`, `15.1-05-PLAN.md:200-207`.
- **MEDIUM: The family chart cap is non-actionable.** "A sensible fixed maximum" supplies neither a value nor deterministic tie/order semantics, despite requiring an exact Node assertion. Evidence: `15.1-05-PLAN.md:142-149`, `15.1-05-PLAN.md:178-184`.
- **MEDIUM: The palette remains underspecified for five runtimes.** The UI contract defines four colors, while the real dataset and chart tests expect five runtime series. Evidence: `15.1-UI-SPEC.md:118-125`, `15.1-05-PLAN.md:115-123`, `15.1-05-PLAN.md:171-173`.

### Suggestions
- Deduplicate token and price aggregation by runtime/date plus a stable attribution identity: `(session_id, turn_id)` when present, with the corrected null-turn fallback.
- Add a compound-command fixture proving tokens and price are counted once.
- Define whether Chart 1 uses dual axes, a metric toggle, or two aligned datasets; do not leave one metric tooltip-only.
- Recompute chart data only when filters change, debounce text/number input, and do not recompute on sort-only events.
- Fix the family-chart cap and tie ordering as explicit constants.
- Define fifth-series color behavior and test it.

### Risk Assessment
**HIGH.** The central spend-over-time chart would produce materially incorrect totals, and the update path risks undermining the phase's main performance goal.
