## SD-4 (inherited) — Turn-level dedup identity

Defined in full in `15.1-04-PLAN.md`'s shared_definitions. `turnKey(row)` returns
`session_id + turn_id` when the turn id exists and `session_id + raw_ref` when it is null,
and never includes `step_index`. **Plan 05 imports that exact function — it does not define
a second dedup identity.** Every token and price aggregation in this plan calls it.

## SD-5 — Chart 1: both measures rendered (CANONICAL)

D-18 item 1 asks for "tokens/price per day, line or stacked-bar broken down by runtime".
Both measures must be visible; putting one in a tooltip renders one metric and annotates
the other. Chart 1 is therefore a Chart.js **mixed** chart with `type: "bar"` at the top
level and two kinds of dataset:

- **One stacked bar dataset per distinct runtime**, `yAxisID: "y"`, sharing one `stack` id,
  whose data is the deduplicated total tokens (`tokens_input + tokens_output`, skipping
  nulls) per date for that runtime. Colours come from UI-SPEC.md's five-entry categorical
  palette by `runtimeIndex % 5`.
- **One line dataset** with `type: "line"`, `yAxisID: "y1"`, whose data is the
  deduplicated total price per date across all runtimes. It uses the Accent role
  (`--md-sys-color-primary`), which UI-SPEC.md's Color section already reserves for exactly
  "the primary line in the tokens/price-per-day chart".

Scales: `x` stacked; `y` stacked, left position, titled for tokens; `y1` right position
with `grid.drawOnChartArea: false`, titled for price. Chart.js's native stacked-bar and
mixed-chart support is why it was chosen over a heavier library — do not reach for a
plugin.

## SD-6 — Chart update path (CANONICAL)

Today `render()` fires on every `input` event, which for text and number fields means every
keystroke. Adding three full-dataset aggregations to that path would restore the freeze
this phase exists to remove. The render entry point is therefore split:

- `applyFilters()` — recomputes the filtered row set, repaints the table through the SD-2
  painter, AND recomputes all three charts' datasets from that same row set, updating the
  existing Chart.js instances in place via `chart.update("none")`. Instances are created
  once at mount and never destroyed or recreated.
- `applySort()` — re-sorts the already-filtered row set and repaints the table ONLY.
  Charts are untouched, because sorting cannot change any chart's contents. The `<th>`
  click listener calls this, not `applyFilters()`.

Listener wiring: the `#filters` `change` listener (selects, date inputs, the
group-by-session checkbox) calls `applyFilters()` immediately; the `#filters` `input`
listener (text and number fields) calls a **debounced** `applyFilters`, with a fixed
**150 ms** delay. The debounce factory is a DOM-free function inside the pure-function
marker block so it is node-testable.

## SD-7 — Chart 2: family/subfamily distribution, deterministic cap (CANONICAL)

- Aggregate over rows whose `family` is non-empty, on the composite label
  `row.subfamily ? row.family + " " + row.subfamily : row.family`. That is how a family is
  distinguished from its subcommands (D-18 item 2) in a single ranking.
- Rank by row count **descending**; ties broken by the label string **ascending** using a
  plain `<` comparison, not `localeCompare`, so node and the browser agree.
- `CHART_FAMILY_LIMIT = 15` — a module-level constant inside the marker block, not a
  phrase. The top 15 labels get their own bar; every remaining label is summed into ONE
  trailing bar whose label is exactly `"other (" + remainderCount + " more)"`, where
  `remainderCount` is the number of labels folded in.
- Horizontal bar (`indexAxis: "y"`) is the locked orientation, chosen specifically to avoid
  pulling in a treemap plugin.
- This chart counts ROWS, not tokens or price, so it needs no dedup — every decomposed step
  is a genuinely separate command invocation. State that reasoning inline so a future
  reader does not "fix" it into the dedup path.
