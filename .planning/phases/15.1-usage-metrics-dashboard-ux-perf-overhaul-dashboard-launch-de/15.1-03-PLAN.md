<objective>
Rebuild the filter bar and the table columns on top of the tracer's proven Material and
virtualizer foundation: add the `runtime` and `subfamily` axes that do not exist today
(D-10 / D-11), reorder both surfaces to the sequence the user asked for (D-12), collapse
the four separate date inputs into one from/to range control (D-13), wrap the command
column as D-12 requires, and make the table tell the truth about null values instead of
rendering them as blank cells (D-16 price, D-16 date).

Purpose: the price complaint that opened this phase was "price always renders as 0", but
RESEARCH.md's live query proved the dashboard never renders a zero for those rows — it
renders an empty string, because the cell helper maps null to `""`. 37,231 of 84,082 rows
carry a null price and read as blank. Until a null is visually distinct from a real zero,
the same misreading recurs for every future observer.

Output: a filter bar and table that match the ordering decision, carry the two new axes,
express a date range as one control, wrap long commands instead of hiding them, and mark
unknown values as unknown.
</objective>

  `shared_definitions`, including the `_VALUE_FLAGS` option-arity table, the

- **SD-2 — virtualization DOM and painter contract**: defined in full in
  `15.1-01-PLAN.md`'s `shared_definitions`. The relevant consequences for this plan: the
  scroll container wraps the whole `<table>`, `<tbody>` rows are absolutely positioned at a
  **constant 56px**, there is exactly **one** function writing to `<tbody>`, and the
  cell-builder is swapped rather than duplicated. Any new cell this plan adds goes into the
  flat cell-builder; it never introduces a second `<tbody>`-writing path.

## SD-8 — Material select option contract (CANONICAL)

`md-outlined-select` does not render bare `<option>` children. `fillSelect(id, values)` is
rewritten to:

1. Clear the select's existing children (making the call idempotent).
2. Create the all-value option FIRST: an `md-select-option` element whose `value` property
   is `"all"`, containing a child `div` with `slot="headline"` and `textContent` `"all"`.
3. Create one `md-select-option` per distinct value the same way, `value` property set to
   the value and the slotted headline `textContent` set to the value.
4. Set the select's `value` property to `"all"` after population.

Import `@material/web/select/select-option.js` alongside
`@material/web/select/outlined-select.js` from the pinned import map — the option element
is a separate module and the select renders nothing without it. Reading
`document.getElementById(id).value` continues to work unchanged, because
`md-outlined-select` exposes a `value` property mirroring the selected option's value, so
`readCriteria()` keeps its current shape. A select whose data yields only one distinct
value is still rendered (UI-SPEC's zero-one-many row locks that).

## SD-9 — Clear-filters reset sequence (CANONICAL)

`clearFilters()` performs exactly this sequence, then calls the render entry point **once**
at the end (never once per control):

1. Each of the four `md-outlined-select` ids (runtime, model, family, subfamily) — set
   `.value = "all"`.
2. Each of the five `md-outlined-text-field` ids (command, tokens-min, tokens-max,
   price-min, price-max) — set `.value = ""`.
3. `filter-date-from` and `filter-date-to` (native `<input type="date">`) — set
   `.value = ""`.
4. `group-by-session` is deliberately NOT reset. It is a view mode, not a filter; clearing
   filters must not silently flip the user out of grouped mode. State this in the SUMMARY.

Wired to a `click` listener on the `md-text-button` whose id is `clear-filters` and whose
copy is exactly `Clear filters` (UI-SPEC Copywriting Contract).

`clearedCriteria()` is the DOM-free companion inside the pure-function marker block: it
returns the criteria object a fully-cleared filter bar produces. `clearFilters` is
asserted against it structurally, and `filterRows(rows, clearedCriteria())` returning every
row is the node-testable proof that "cleared" really means unfiltered.
