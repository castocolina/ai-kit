## SD-3 — Sibling-row lookup for the decomposer breakdown (CANONICAL)

A single refined row does **not** carry the full decomposer breakdown. `refiner._build_row`
stores only that step's `command_text`, `step_index`, `operator` and the shared
`step_count`. The sibling steps exist as **separate rows**, and what ties them together is
`raw_ref`: `refiner._rows_for_record` builds every step of one decomposed command from one
raw record, so all of them carry that record's `raw_ref`, and `refined_store.py`'s
`UNIQUE(raw_ref, step_index)` constraint guarantees the pair is unique per row. That is the
real lookup mechanism; "the row has it" is not.

`indexByRawRef(rows)` is a pure function inside the pure-function marker block returning a
`Map` from `raw_ref` to an array of that record's rows sorted ascending by `step_index`.
It is built **once at load**, immediately after `decorateSubfamily`, over the **full
embedded payload** — not over the filtered set, so a sibling step the current filter
excludes still appears in the dialog. The dialog resolves
`rowsByRawRef.get(activatedRow.raw_ref)` and renders one entry per sibling, each naming
its one-based position (`step_index + 1`), the shared `step_count`, and that sibling's own
`operator`.

## SD-4 — Turn-level dedup identity (CANONICAL — Plan 05's chart aggregations reuse this)

`refined_store.py`'s module docstring makes the rule mandatory: token and price figures are
turn-level values duplicated onto every step-row sharing a `(session_id, turn_id)`, and any
consumer computing a session or date total MUST deduplicate before summing.

**That docstring is currently stale and Task 2 of this plan corrects it.** As checked out
today it prescribes `SELECT DISTINCT session_id, turn_id, tokens_input, tokens_output,
price` and names no fallback — which is precisely the bug this plan fixes, because SQLite's
`DISTINCT` treats two NULL `turn_id` values as equal, so every null-turn row in a session
collapses to one. Read the stale text as evidence of the mandate, never as the definition
of the identity; SD-4 below is the definition, and Task 2 rewrites the docstring to match
it so the source-level canonical statement and `turnKey()` stop disagreeing.

`turnKey(row)` is a pure function inside the marker block returning the dedup identity:

- when `row.turn_id != null` — the stringified `session_id`, then the same NUL separator
  `groupBySession` already writes today (the two-character escape backslash-zero inside the
  emitted JavaScript string literal), then the literal marker `t:`, then the stringified
  `turn_id`.
- when `row.turn_id == null` — the stringified `session_id`, that same NUL separator, then
  the literal marker `r:`, then the stringified `raw_ref`.

The `t:` and `r:` markers keep the two key namespaces from ever colliding, so a turn id
whose text happens to equal some other row's raw ref cannot merge two distinct identities.

The null-turn fallback keys on `raw_ref` and **deliberately NOT on `raw_ref + step_index`**.
Every step of one decomposed command inherits the same turn-level token and price
attributes, so including `step_index` would treat each sibling as unique and inflate the
total by the step count — the exact over-count the Round-1 review identified in the
previous plan. Two genuinely distinct commands in the same session remain distinct because
their `raw_ref` differs.

`turnKey` is defined once, here, in Plan 04. `groupBySession` uses it, and Plan 05's per-day
chart aggregation imports the same function rather than defining a second identity. One
definition, one test surface.

**Not fixed by this (documented limitation, not a defect this plan introduces):** codex's
`turn_id` is a token-count-interval `source_line` proxy, so several genuinely different
commands can share one and their grouped sum is a lower bound on the interval's real
attribution. Collapsing them is the conservative reading; splitting them would double-count
an interval's tokens across every command inside it. Plan 05's documentation task writes
this into SKILL.md.

## SD-10 — Loading-state paint guarantee (CANONICAL)

Payload parsing and initialization currently run synchronously in one inline script, so
adding a progress element and removing it after synchronous row creation guarantees no
paint in between — the browser would never show the bar. The bootstrap is therefore
restructured into three steps:

1. Synchronously: show the `md-linear-progress` bar and disable the filter controls.
2. Defer with a **double** `requestAnimationFrame` — schedule a frame, and inside that
   frame schedule another. The second callback runs after the browser has completed at
   least one paint of step 1. If `requestAnimationFrame` is not available (non-browser
   execution of the extracted pure block), fall back to `setTimeout(fn, 0)` so the node
   harness is unaffected.
3. Inside the deferred callback: run the blocking initialization — `decorateSubfamily`,
   `indexByRawRef`, the virtualizer mount and the first render — then remove the progress
   bar and re-enable the filter controls, in that order.
