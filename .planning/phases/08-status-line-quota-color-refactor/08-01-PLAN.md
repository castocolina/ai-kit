## Open Conflict -- Formula Direction (REVISION_CONFLICT, unresolved)

**Status: NOT resolved by this revision.** Revision cycle 1's cross-AI review
(`08-REVIEWS.md` cycle 1) flagged this as its one HIGH finding. Re-deriving the
math below confirms it is a genuine, mathematically-provable conflict between
two locked artifacts, not a wording nit a planner can silently pick a side on
-- so per this phase's planning instructions it is returned as
`REVISION_CONFLICT` rather than guessed. Task 1 below still implements
CONTEXT.md D-01's burn-rate formula unchanged (`pct / elapsed_fraction`)
because that is the currently-locked mechanism -- changing it unilaterally
would just be picking the other side of the same conflict. `must_haves.truths[0]`
above (ROADMAP SC1) is flagged open/contested until a human resolves this.

### The two locked artifacts, read verbatim

- **ROADMAP.md Phase 8 Success Criterion 1** (a general requirement, with no
  "e.g." qualifier): "Two rate-limit buckets with identical `used_percentage`
  but different time remaining before `resets_at` render different colors --
  the bucket with less time left is flagged more urgently." This matches the
  phase's own source todo
  (`.planning/todos/pending/2026-09-10-refactor-status-line-quota-percentage-and-colors-to-be-relat.md`):
  "80% used with 4 hours still left... reads the same color as 80% used with
  5 minutes left, even though the second is a much more urgent signal." Holding
  `used_percentage` FIXED, LESS time remaining (higher elapsed_fraction) must
  be MORE urgent (a higher-banded color).

- **ROADMAP.md Phase 8 Success Criterion 4** + **08-CONTEXT.md D-01** (an
  illustrative "e.g." worked example, implemented as the general formula
  `ratio = used_percentage / elapsed_fraction`): "50%+ used early in a 5h
  window reads red, but 30% used at hour 4-of-5 of the same window can read
  green/blue for the same ramp." D-01 computes this literally: 50% at
  elapsed_fraction=0.2 -> ratio=250 -> RED+bold; 30% at elapsed_fraction=0.8 ->
  ratio=37.5 -> GREEN. This is a burn-rate/pace signal:
  `used_percentage / elapsed_fraction` is literally "what % you'd have used by
  window-end if this pace continued" (the standard SRE error-budget
  burn-rate shape).

### Why these are mathematically incompatible, not just differently worded

For ANY fixed `used_percentage`, `ratio = pct / elapsed_fraction` is strictly
DECREASING as `elapsed_fraction` increases (`d/de (pct/e) = -pct/e^2 < 0` for
pct > 0). SC1 requires the opposite: strictly INCREASING urgency as
elapsed_fraction increases (less time left) for the SAME pct. Concretely, for
identical 50% used on a `five_hour` bucket: 4h remaining (elapsed_fraction=0.2)
-> ratio=250 -> RED+bold; 1h remaining (elapsed_fraction=0.8) -> ratio=62.5 ->
YELLOW. The bucket with LESS time left (1h) renders LESS urgently than the one
with MORE time left (4h) -- the exact reverse of SC1's plain-language
requirement, independently confirmed by the cross-AI reviewer's own computation
(`08-REVIEWS.md` cycle 1 HIGH concern).

This is not an artifact of these two specific numbers -- it is a structural
property. Any ratio that is monotonically increasing in elapsed_fraction for
fixed pct (required by SC1) while also reducing to `ratio(pct, e->1) = pct`
(D-04's zero-regression invariant -- the only sane way to avoid a discontinuity
at the "reset already happened" boundary) is necessarily BELOW pct for every
e < 1, so it can never reach 250 at pct=50 (SC4's own worked number). Relaxing
the D-04 continuity requirement doesn't rescue it either: a formula satisfying
both SC4 numeric data points AND a general SC1-compatible monotonic-in-elapsed
direction exists only in a vanishingly narrow, practically-flat range of
multipliers that would defeat SC4's own stated purpose (a meaningfully
elapsed-sensitive burn-rate signal). Task 1's spike step below tabulates this
directly, including the further observation that the formula, even for the
source todo's OWN original 80%-used example (4h left vs 5min left), renders
BOTH scenarios the same unbounded RED+bold color -- i.e. it doesn't even
visually distinguish the case the todo was written to fix, reinforcing that
this is a genuine direction defect, not a threshold-tuning nit.

### Alternatives considered

| Alternative | Satisfies SC1 (fixed-pct, less-time=more-urgent)? | Satisfies SC4/D-01's worked numbers? | Cost of adopting |
|---|---|---|---|
| Keep `pct / elapsed_fraction` (current Task 1 implementation) | No -- proven backwards | Yes, by construction | Amend ROADMAP SC1 + the source todo's own example to a pace framing ("burning faster than the clock is more urgent," not "less time left is more urgent") |
| Switch to `pct / (1 - elapsed_fraction)` (remaining-fraction-weighted) | Yes -- strictly increasing in elapsed_fraction for fixed pct | No -- 50%@elapsed=0.2 gives ratio=62.5 (YELLOW, not RED); 30%@elapsed=0.8 gives ratio=150 (RED, not green/blue) -- both land in the wrong band | Rewrite ROADMAP SC4's worked example and replace CONTEXT.md D-01 with a new decision |
| A hybrid/contrived formula threading both sets of numbers | Only in a razor-thin, near-flat parameter range | Only for these exact two (pct, elapsed) pairs, not generally | Not a principled "burn-rate formula" per SC4's own description; fails to generalize -- effectively curve-fitting two points |

**This revision does not choose an alternative.** It leaves Task 1 implementing
the status-quo D-01 formula going into this revision cycle, documents the
conflict here and in `08-REVIEWS.md`'s `## Plan-Revision Conflicts` slot, and
returns `## REVISION_CONFLICT` so the orchestrator can put this choice to the
user.
