<domain>
## Phase Boundary

The runner classifies every failure it sees by the channel the host used, from one closed list of classes with a locking test,
and its retry defaults follow the owner's recorded policy: a short first check, then every 10 minutes up to the 4-hour cap, plus
one extra check just after a stated reset time. The catalogue gains the real-run bodies and every host's captured model-missing
wording, plain stdout text counts for a failed attempt, and a router cooldown line is a quota cycle with its reset time on a
confirmed router lane.
</domain>

## Implementation Decisions

### Classes and the catalogue (SPEC R1, R2, R6, R7)

- **D-01: One new class, `bad_request`.** A request the provider itself refused (data inspection 400, context length 400): the
  same input never succeeds, so it is terminal and an owner stop, exit 69. The list is `quota`, `billing`, `auth`,
  `permission_blocked`, `bad_model`, `bad_request`, `transient`, `crash`. A single class plus the matched row id says which case;
  two classes would double the Python, SKILL and exit-table places for no caller difference. jev request_class low 0.41 (laya
  bad_model), low 0.63 (typesafe one_new). **Own reasoning.** Ledger. **Needs owner awareness** (a new status and class name in
  every table that lists them; the exit stays 69 so no caller changes its exit handling).
- **D-02: The lock test compares four places.** `ROW_CLASSES`, the class part of `STATUS_TABLE`, `--describe`'s `classes`, Python's
  `STATUS_TO_REASON` and the SKILL.md class table; a class added in one place fails it, and disjointness with Phase 37's reason
  list and Phase 38's `partial`/`locked` is asserted. Python maps `bad_request` to `real_error` (not `configuration`: nothing the
  owner configures fixes it, and waiting does not help). jev class_lock low 0.65, low 0.98. **Own reasoning.** Ledger.
- **D-03: Listed bodies get a class by family, labeled by evidence.** `provider_not_configured` is `bad_model` (the router's
  no-executable-targets code is the verified sibling; condition lasts until the owner configures; jev low 0.48 auth, low 0.74
  bad_model; own reasoning), label `unverified` (the code name is recorded in real runs, no body captured). `Policy budget exceeded`
  and `Account budget exceeded` are `billing` with `routerClass quota` (a spending cap, as the spending-limit and credits rows;
  jev choice 0.85), placed above the bare 429 row in tier order, `unverified` (names recorded in the 21.1 research and the
  2026-10-11 todo, bodies not re-observed). `data_inspection_failed` and `context_length_exceeded` are `bad_request`,
  `unverified`. The vendor plan-not-open code `1311` is `billing` with `routerClass quota` (as the access-disabled row; jev low
  0.53 bad_model, 0.94 billing_router_quota with the low flag; own reasoning), `unverified`. `Connection capacity reached` is a
  text `transient` row, `unverified`, so a body without a status code no longer ends `crash`. A label is `verified` only with a
  captured body and its date, and a verified row names its fixture file (a test checks it).
- **D-04: One row per captured host wording, narrow.** From the live captures of 2026-11-16: copilot `is not available`, pi `Model
  "<id>" not found`, opencode the `provider.no-route` event text `Model unavailable:`, claude `issue with the selected model`
  (plus the 404 status path of D-08), codex `model is not supported when using`, each scoped to its host, class `bad_model`,
  `verified` with host version and date, with a fixture. No bare `unavailable` or `not found` row exists (a transient outage must
  not read as a missing model); codex's `item.completed` metadata warning is not an event the runner reads and stays so. cursor's
  row already exists. jev bad_model_text low 0.50 (laya generic_regex), low 0.98 (typesafe per_host_rows). **Own reasoning.** Ledger.
- **D-05: `errorsUnverified` demotes by evidence, not by runtime.** A row scoped to its own host that has a captured fixture keeps
  its own label; wildcard rows and rows without a fixture are still demoted on a runtime flagged uncaptured. This is the
  owner rule that live evidence beats a runtime-level flag, applied to copilot (its model row is verified, the rest stay
  unverified). jev unverified_flag low 0.50 (laya drop_flag), low 0.74 (typesafe row_wins_with_fixture). **Own reasoning.** Ledger.
- **D-06: The five rows with recorded real evidence are promoted.** The vendor weekly-limit code row, the monthly limit, insufficient
  funds, model access disabled and the model-cooldown code row move from `unverified` to `verified`, with the evidence of the v1.3
  owner follow-up (sections 1 and 2: wordings found in past runs, the cooldown body seen in 45 cases). This changes printed
  `pattern=` values and the pinned template, so the template version is bumped and the live copy re-rendered. The cooldown row's
  class stays `transient` on wildcard routes (D-09 adds the router-scoped quota rows).
- **D-07: Plain stdout is a source only through a row that opts in.** A new `input: stdout` value (accepted by `validateRow`); such
  rows are matched against the plain stdout lines of an attempt that failed (non-zero exit, parse error, empty answer or timeout),
  never of an attempt that answered with exit 0, and never as a live kill (the live watcher still reads stdout as events only).
  `input: any` rows keep stderr and events, so the pinned answer-only cases stay `crash`. Initial rows: claude's limit sentences
  (`hit your limit`, the weekly form). Python's `classify_error` stays stderr-only (its docstring says so). jev stdout_channel low
  0.40 (laya all_rows), low 0.97 (typesafe row_opt_in). **Own reasoning.** Ledger.
- **D-08: claude's structured fields feed the existing code rows.** From the stdout JSON result: `api_error_status` (an integer
  100 to 599) as `status <n>` and `api_error_type` as a string, beside the result text, as the opencode path already does for its
  error status; the live 404 capture then classifies through the new text row and a 429 or 5xx through the bare-code rows. jev
  claude_fields choice 0.75 (laya). Live today: claude's JSON limit on stdout was already classed through the result event, so
  RUN-09's real gap is plain text only (the SPEC and RUN-09 say so).
- **D-09: A router cooldown line is `quota` on confirmed router lanes, with the reset as a display field.** Rows scoped to
  `route: router` (tier above the wildcard `cooling down` row) classify `all N active accounts cooling down for model <m> (reset
  after <t>)`, `All models failed | ...`, `has persisted cooldown until` and `usage balance exhausted`; `reset_after_s` (whole
  seconds from `<n>h <n>m <n>s` parts, a form that does not parse is absent) appears in `cross-ai: upstream fields=`; every other
  route keeps `transient`. Label `unverified`: the wording is from the router's own log (warning level, tag AUTH), and whether a
  client body carries it is unverified (the real client body today is `model <x> is unavailable`, transient, verified). On a router
  lane the class changes only the printed status word (both soft classes share one ladder); it matters for direct lanes, which
  stay transient. Observed durations (34 episodes): 24 under 2 minutes, 8 over 4 hours; so the class `transient` alone ("not a
  quota") fit neither end. jev cooldown_class low 0.68 (laya new_class), low 0.84 (typesafe quota_on_router_route). **Own
  reasoning.** Ledger. **Needs owner awareness** (the roadmap allowed "or a recorded owner decision says why not"; this is the
  chosen branch, unverified until a client body is captured).

### The retry policy (SPEC R5; owner decisions 2026-11-16)

- **D-10: The hard tier is a short first check, then every 10 minutes to the cap (owner decision).** `hard_waits_s` default
  `[60, 300]`, new `hard_every_s` (integer, 0 or 60..`capS`, default 600) issues `retry_after_s` repeatedly after the list until the
  cap, then `stopped=cap`; `hard_every_s = 0` keeps the list-end stop, and the shipped pattern is `[600, 900, 1800]` with
  `hard_every_s = 0`. Soft retries, the one session reset and the route rules do not change. `hardWaitFor` takes the periodic
  value; `RETRY_KEYS`, `validateRetryKey`, the `cross-ai: retry ...` line, `RETRY_DEFAULTS`, the rendered `CONFIG.retry`
  (curated-config) and the config documentation gain the key. A wait under 60 s (a configured value) runs inside the call when the
  remaining deadline admits it with the existing 60 s reserve, else it is a 60 s hint: the plan decides how it reuses the soft
  step's admission test. Decision record: `38.1-RETRY-POLICY.md` (evidence: 34 router cooldowns, 24 under 2 minutes, 8 over 4 hours;
  shipped five soft retries in about 13 s, then 600, 900, 1800 s). jev hard_tier_shape low 0.36 (laya shipped), low 0.53 (typesafe
  short_start_then_periodic): the owner decided.
- **D-22: What a client sees from the router's cooldown, read from the OmniRoute source (2026-11-16).** The log line of D-09
  never reaches a client. The client gets 429 with `Retry-After` and `code: "model_cooldown"`, or `ALL_TARGETS_SKIPPED` (429 with
  a hint, else 503), or 503 `all_targets_cooling_down` with `Retry-After`. A cooldown is restored lazily: the lock is deleted when
  `now > until`, so one request right after the stated reset succeeds and no probe is needed. Durations: an exact upstream hint
  (Retry-After, reset text, up to 30 days; header hints bypass the 30-minute cap), a daily quota exhaustion locks until midnight, and
  otherwise exponential backoff from the provider profile (connection bases 5 s OAuth, 3 s API key; model lockout base 120 s, cap
  30 min, off by default per one unverified read). The 24 short and 8 long episodes of the retry evidence fit this (hint-driven or
  midnight locks are the long ones). D-11 therefore reads `Retry-After`, `retry_after` and `reset_seconds` from a real client body.
  A manual clear exists (`DELETE /api/resilience/model-cooldowns`) but is the router owner's, never the runner's. The confirmed
  rows of D-09 match the codes above; the log-wording rows stay only for a runner that is handed router logs.
- **D-11: A stated reset time adds one extra check (owner decision).** Sources: the allowlisted upstream fields (`retry_after`,
  `reset_at`, `retry_after_seconds`, `resetsAt`) and D-09's `reset_after_s`. The check is at the stated time plus 120 s (a window
  clears about 2 minutes after its stated reset), taken only when it is at least 60 s ahead, inside the cap's remaining time and
  earlier than the next periodic check; the periodic checks continue; each stated time is used once per episode (a `reset_check`
  field in the cycle record). A time beyond the cap, in the past or unparseable changes nothing. It never lengthens a wait or lifts a
  stop (the untrusted-data constraint; the SKILL's "upstream fields are never a wait source" sentence is amended to say a stated
  time may add one bounded check and is otherwise data). The report line gains `check=first|periodic|reset|-`; the status line is
  unchanged. jev reset_time_use low 0.52, 0.57 (both extra_check_at_reset). **Needs owner awareness** (upstream text now influences
  one scheduled time; bounded below by 60 s and above by the cap).
- **D-12: A direct lane stays as decided on 2026-11-02 (owner decision).** A quota error on a direct lane stops at once; only
  confirmed router lanes wait on quota; transient (5xx, overloaded, capacity, a cut stream, a timeout attempt) waits on every lane.
  RUN-11's "periodic retries for quota errors" means router lanes only (dated amendment). Evidence recorded: direct vendor limits
  are mostly 5-hour or weekly windows, longer than the cap.
- **D-13: Idle-killed attempts ride the new tier.** Phase 38 D-04 made an idle kill a timed-out transient attempt, so a lane that
  hangs every time now retries about every 10 minutes for up to 4 hours (it used to stop after 55 minutes). Accepted as the
  consequence of one ladder for transient faults; `hard_every_s = 0` or a lower `max_retries` stops it sooner, and the SKILL says
  so. **Needs owner awareness.** Ledger.
- **D-14: The caller text changes, the one-shot rule does not.** Each hint is still one one-shot wait the caller schedules (never a
  repeated job); an episode can now hold about 24 hints. `ai-kit-cross-ai` section 6 and 7, `subprocess-quota-policy.md`, the
  goal-prompt quota rule text pinned in `tests/test_quota_policy_text.py` and the superpowers adapter's "single re-invoke only"
  wording (Phase 41 rewrites that adapter) are listed as places the plan updates or hands over.

  rewritten there.
