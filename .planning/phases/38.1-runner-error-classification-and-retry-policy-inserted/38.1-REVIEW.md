## Medium

### MEDIUM-1: the blocked-until record was skipped when the run ended on a dirty review tree or a failed git read (fixed, 258bf24)

`main` wrote the record only after the review-dirty return (`contract_violation`) and the git-failure returns, and
cleared it only inside the `r.ok` branch after the review-dirty return. R11 (a) and (b) key the record on the attempt's
class ("an attempt ends with class `quota`", "an ok attempt ... deletes the record"), not on the run's final status, so a
free-pool limit over a dirty review tree or a failed post-run git read left no record, and an ok review attempt that
dirtied the tree left a stale one. Both actions now run once, right after the post-run abort check. New cases
`blocked-review-dirty-writes`, `blocked-git-fail-writes`, `blocked-review-dirty-ok-clears` fail on the old template (red
check against `9ffee83`).

### MEDIUM-2: `classify-only-fixtures` took its expected pattern from the helper under test (fixed, 9ffee83)

Plan 38.1-03 changed the case to expect `patternFor(...)`, the function the `--classify-only` path itself calls, so the
pattern check could not fail. It now compares with each case's fixed `expect.pattern`, or `expect.cliPattern` where
copilot's runtime-level flag demotes the CLI result (`host-copilot-one-word-off`: `unverified`). Status and rule were and
are compared with fixed values, so the case still proves the classifier.

### MEDIUM-3: the fork-chain test's chain-length assertion raced the preview timeout (fixed, fa86b81)

`test_print_argv_preview_returns_none_and_leaves_no_process` failed once in a commit hook under parallel load; the hook
text was not kept beyond "pid alive after 5 s". A probe shows the chain reaches its fifth link in about 10 ms on a quiet
host and that a timeout of 1 to 6 ms fails the old `count == 5` assertion, so that assertion depends on timing; the
observed signature (a link still alive after the 5 s wait) was not reproduced (8 reruns under the guard in the run and
the probes here all passed). The test now proves only what the flood fix needs: the shim ran, no recorded link survives the
bounded reap wait (30 s, from `24dd17e`), and no link starts after the group kill; a survivor is reported with its
`/proc` state, parent, group and command, so a future failure explains itself. A leader-only kill (mutant) fails it.

### MEDIUM-4: an upgraded runner copy keeps its old hard waits, and the docs did not say so (fixed in the docs, d74c7ea; decision deferred)

`plan_runner_upgrade` keeps a copy's whole CONFIG `retry`, and `resolveRetry` fills the missing `hard_every_s` from
`RETRY_DEFAULTS`, so a copy rendered from template 10 waits 600, 900, 1800 s and then every 600 s to the cap (this

orchestrator decision (38.1-06, 38.1-12). SKILL section 6 and curated-config `references/runner.md` now state the hybrid
schedule and the `[runner.retry]` override; whether the upgrade should replace an unchanged old default is an owner
decision in the todo.

### MEDIUM-5: R11's shared pool-key fixture did not exist (fixed, 04131cd, d74c7ea)

The two existing tests compared the two regexes and read back a hand-written record; none derived a key for one lane
through both Phase 36's `lane_price.pool_key` and the runner's `blockedPoolKey`. New test
`test_phase36_pool_key_equals_the_runner_key_for_one_lane` (tests/test_runner_describe.py) feeds the same lanes to both:
the keys agree for every model id with a `/`; for an id without one the runner names no provider (Phase 36 falls back to
the entry's provider), which the test pins and the SKILL now states (such a lane writes a record only with `--pool`).

### MEDIUM-6: claude's structured status field was tested only in a pure case (fixed, 04131cd)
