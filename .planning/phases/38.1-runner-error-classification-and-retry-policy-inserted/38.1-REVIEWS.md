#### 38.1-08

##### Summary

**Revise before execution.** The plan keeps pool state separate from config and retry scheduling, and it gets the reset arithmetic right. But the proposed write path does not guarantee that the later deadline wins, and its first fake-lane test cannot pass as written. The checkout also differs from the pasted plan: the on-disk version clears a record only when the successful call passed `--pool`. I reviewed the checkout version and treated that difference as a handoff issue.

##### Strengths

- **Reuses the right state primitives.** `stateHome()` gives the same XDG/HOME resolution as the existing cycle records, and `writeCycleState()` creates a private directory, opens a unique temporary file at `0600`, and atomically renames it. This gives readers complete files without changing either config system. `skills/ai-kit-spec-review/references/cross-ai.mjs:3513`, `:3554–3567`.
- **Separates a pool block from an in-run retry hint.** The plan keeps `retryAfterMs` in milliseconds until record calculation and does not feed it into the reset-check scheduler. The predecessor explicitly enumerates its reset keys, so extending the display allowlist does not silently extend scheduling. `.planning/phases/38.1-runner-error-classification-and-retry-policy-inserted/38.1-08-PLAN.md:130–137`; `.planning/phases/38.1-runner-error-classification-and-retry-policy-inserted/38.1-07-PLAN.md:118–127`.

##### Concerns

1. **HIGH — Atomic replacement does not satisfy “later `blocked_until` wins.”** The plan both claims the R11 concurrency edge and explicitly accepts the opposite outcome: two processes can read the same prior record, compute different deadlines, and publish the shorter one last. The existing writer makes each replacement atomic, not the read–compute–write sequence. The existing execute lock is per checkout, not per pool, and review calls do not take it. A later caller can therefore try a still-blocked pool prematurely. `.planning/phases/38.1-runner-error-classification-and-retry-policy-inserted/38.1-08-PLAN.md:25–36`, `:141`; `skills/ai-kit-spec-review/references/cross-ai.mjs:3554–3567`, `:3580–3581`, `:6591–6600`; `tmp/run-2026-11-19/p381-plan/39tip-38.1-SPEC.md:273–276`.
2. **HIGH — Task 1’s one-spawn assertion counts model listing as a retry.** `both.calls1.length === 1` cannot hold for the specified pi fake: the runner does a model-list preflight, the fake logs `pi rpc`, and the inference invocation logs `pi freelimit`. Conversely, the first run’s status regex is never checked by the two-run harness; it checks both exits but only the second status. A different exit-75 outcome could slip through the first-status assertion. `.planning/phases/38.1-runner-error-classification-and-retry-policy-inserted/38.1-08-PLAN.md:156–157`; `skills/ai-kit-spec-review/references/cross-ai.mjs:6625–6636`; `skills/ai-kit-spec-review/references/cross-ai-selftest.mjs:1738–1752`, `:2321–2346`.
3. **HIGH — The observed structured free-limit event is not tested through persistence.** The fake-lane tracer uses a synthetic pi stderr error. The structured opencode case only checks class, label and rule; the file test builds `r.upstream.fields` by hand. The tests would not catch losing `retryAfterMs` between the raw stdout event and the stored record, or a regression that depended on the host exiting nonzero. There is also a policy collision to settle explicitly: the new row applies on all routes, but `runCli` sends any confirmed-router `quota` hit to the ladder, while R11 excludes in-run retry of a free-pool error. The proposed post-run guard cannot prevent that retry. `.planning/phases/38.1-runner-error-classification-and-retry-policy-inserted/38.1-08-PLAN.md:141`, `:148–156`, `:192–194`; `skills/ai-kit-spec-review/references/cross-ai-selftest.mjs:653–671`; `skills/ai-kit-spec-review/references/cross-ai.mjs:2295–2315`, `:5484–5525`; `tmp/run-2026-11-19/p381-plan/39tip-38.1-SPEC.md:286–294`, `:313–315`.
4. **MEDIUM — Malformed state is not reliably fail-open or secret-free.** `readOr()` performs an unbounded synchronous read before validation. A non-regular file can block that read, and an oversized file can use unbounded memory. The shape check also accepts arbitrary persisted `basis` text; `blockedNext()` can preserve it and `blockedAfterStop()` writes and logs it verbatim. Likewise, validating the pool’s character set does not ensure its value is safe to log. The six-key test with a benign pool does not prove either redaction or unchanged config bytes. `.planning/phases/38.1-runner-error-classification-and-retry-policy-inserted/38.1-08-PLAN.md:38–40`, `:137–142`, `:192–193`; `skills/ai-kit-spec-review/references/cross-ai.mjs:1283–1286`, `:3507`, `:3598–3599`, `:4497–4509`.
5. **MEDIUM — The caller handoff must carry pool identity on success.** The checkout’s named-pool-only rule correctly prevents a paid lane from clearing a free block. But a caller that omits `--pool` can still cause the record to be created via a catalogue row, then cannot clear it on success. Plans 38.1-10 and 38.1-11 currently say a successful attempt on the pool deletes the record without stating the flag prerequisite. Also specify whether “ok attempt” means host success or final runner `ok`: the proposed clear runs before execute results can become `no_change`, `partial` or a git/contract failure. `.planning/phases/38.1-runner-error-classification-and-retry-policy-inserted/38.1-08-PLAN.md:32`, `:142–146`; `.planning/phases/38.1-runner-error-classification-and-retry-policy-inserted/38.1-10-PLAN.md:134`; `.planning/phases/38.1-runner-error-classification-and-retry-policy-inserted/38.1-11-PLAN.md:117`; `skills/ai-kit-spec-review/references/cross-ai.mjs:6700–6717`.
