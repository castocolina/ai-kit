## Warnings

### WR-01: Mixed catalog whose only coding indexes are below 35 still gives an empty `mechanical` ranking, and no test pins it

**File:** `skills/ai-kit-spec-review/ai_kit_spec/model_ranker.py:130-138, 290-291`
**Issue:** `_call_floor` keeps the floor whenever any entry has a finite `coding_index`. Suppose one
candidate has a real index below 35 and every other one is null. The floor stays on, the sub-floor entry
fails it, every null entry fails it too, and the ranking comes back empty. That is the same empty result
HUB-04 set out to remove. Probe: `[{coding 20, price 1}, {null, price 2}, {null, price 3}]` →
`score_candidates(..., "mechanical", w)` returns `[]`. One entry with coding 50 instead returns only that
entry. So a pool full of null-index models loses its mechanical rows as soon as one scored model joins.
`catalog_adapter._purpose_scores_by_key` scores the whole cross-runtime pool in one call, so installing one
extra CLI can wipe out the haiku-tier (`mechanical`) scores of every other candidate. D-01 locks "mixed
catalog keeps the floor", so the behaviour itself is a decided trade-off. The gaps are these: no test pins
it, and the new toml comment ("the ranking still fills") and the design-doc line can be read as covering
it.
**Fix:** Keep D-01. Pin the edge so a later change cannot alter it silently, and name it in the toml
comment:
```python
def test_mixed_catalog_with_only_sub_floor_scores_ranks_nothing(self):
    entries = [
        {"key": "s20", "scores": {"coding_index": 20}, "pricing": {"input_per_1m": 1}},
        {"key": "n1", "scores": {"coding_index": None}, "pricing": {"input_per_1m": 2}},
    ]
    w = model_ranker.load_ranking_weights()
    self.assertEqual(model_ranker.score_candidates(entries, "mechanical", w), [])
```
and in `ranking-weights.toml`: `# ... when the only finite values are below the floor, the ranking is empty and the caller falls back.`
If the owner wants that case to fill as well, that is a D-01 amendment, not a reviewer fix.

### WR-02: Shipped-Python guard misses plan-numbered file names (`04-01-PLAN.md`, `15.1-02-SUMMARY.md`)

**File:** `tests/test_skill_text_history.py:76, 157-163` (pattern `PHASE_FILE_RE`, used through `POINTER_RULES[:2]`)
**Issue:** `PHASE_FILE_RE` requires an uppercase word right after the phase number:
`\d{1,2}(?:\.\d+)?-[A-Z]...\.md`. A plan or summary name has a plan number in between
(`04-01-PLAN.md`, `15.1-02-SUMMARY.md`). The match at the start fails on `01`, and the `(?<![\w.-])`
lookbehind blocks the later match at `01-PLAN.md`. Probe: `python_pointer_hits('"""see 15.1-02-SUMMARY.md"""', ...)`
and `... 04-01-PLAN.md ...` both return `[]`. This phase removed exactly those two names by hand
(`refiner.py:20`, `paths.py:93`), and they are the most common kind of planning-file pointer. So the
DEF-09 guard would not have caught either one, and it will not catch the next. The Markdown check
shares the regex and has the same hole.
**Fix:** Allow an optional plan number, and add a non-vacuity case for each shape:
```python
PHASE_FILE_RE = re.compile(
    r"(?<![\w.-])\d{1,2}(?:\.\d+)?(?:-\d{2})?-[A-Z][A-Z0-9]*(?:-[A-Z0-9]+)*\.md\b"
)
```
```python
def test_plan_numbered_file_fails(self):
    self.assertEqual(
        python_pointer_hits('"""see 15.1-02-SUMMARY.md"""\n', "demo.py"),
        ["demo.py:1: phase file 15.1-02-SUMMARY.md"],
    )
```
Run the Markdown tree check after the change. `rg` found no current hit in `skills/**/*.py`. The only
other match in `skills/` is `ai-kit-commit-fold/evals/evals.json`, which the Markdown check does not scan.
