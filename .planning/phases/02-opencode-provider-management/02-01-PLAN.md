## Decisions forced by cross-AI review round 1 (d222696)

- **Comment consumption during comma resolution — DECIDED: comments are never
  consumed.** A removal is two disjoint deletions (the entry's `key_start`..
  `value_end` bytes, plus one comma character); everything between and around
  them, including a whole comment, survives verbatim. Rationale: a comment is
  user content outside the entry's key..value span, and this phase's whole
  premise (ROADMAP SC-2) is that nothing outside that span changes. The
  alternative — consuming the skipped comment — is defensible as tidiness but is
  silent deletion of something the user wrote. Pinned by the hand-authored
  expected fixture (forward direction) and Task 2's last-entry case (backward).
- **Duplicate provider id at depth 1 — DECIDED: first match wins.** The first
  entry in file order is removed; a second entry with the same id is left
  byte-identical and a second invocation removes it. This is invalid JSONC that
  a hand-edit can produce, so the behavior is defined and tested rather than
  emergent. Documented in SKILL.md by Plan 02-02.
- **`EXIT_ERROR = 1` — DECIDED: wired, not deleted.** `write_preserving_mode`
  keeps propagating `OSError` (that is what its own test asserts); `cmd_remove`
  and `cmd_list` catch it and turn it into one `error:` line plus exit 1. A
  disk-full or read-only-filesystem failure is a real, reachable path for a tool
  whose entire job is writing a file, so a clean exit code is worth more than
  removing the constant.
- **Symlinked config — DECIDED: resolve, do not clobber.** `realpath` before the
  atomic write, so the link survives and its target is edited. See the corrected
  T-02-06 row.
- **Test subprocess discipline — DECIDED: one call site.** All shim invocations
  in `tests/test_ai_kit_opencode_providers.py` go through `run_cli`, which
  requires `cwd=` and always passes `stdin=subprocess.DEVNULL`. This aligns this
  plan with Plan 02-02's stated "no test reads the repo's own
  `.aikit/review-spec.toml`" rule, which the review found this plan's tracer
  quietly violating through an unpinned child cwd.

## Decisions forced by cross-AI review round 2 (4ec89b3)

- **`run_cli` gains `env=None` — DECIDED: one optional parameter, still one call
  site.** Pinning `cwd` closed the repo-file coupling; it did not close the HOST
  coupling. Plan 02-02's `collect_references` resolves the global review-spec and
  the cached model catalog from `XDG_CONFIG_HOME`/`XDG_CACHE_HOME`/`HOME`, so a
  subprocess-based test with no way to set those scans the developer's real
  machine state. `env` is forwarded verbatim and defaults to `None`, which is
  `subprocess.run`'s own inherit value — so nothing about the existing call
  behavior changes, the sole-call-site gate still holds, and the AST gate now
  proves the parameter exists and is forwarded. Considered and rejected: a second
  `subprocess.run` call site for env-scoped tests (breaks the sole-call-site
  invariant the round-1 revision established); and `unittest.mock.patch.dict` on
  `os.environ` (does not reach a child process at all, which is the whole point
  of `TestCrossReferenceNonBlocking`).
- **`significant_indices` seeding — DECIDED: one neutral seed per removal, at the
  `provider` object's opening brace.** A four-state walker started at an
  arbitrary offset has undefined state, so a block comment or string spanning the
  `start` boundary would desynchronize the sub-range walk. Rather than document a
  caller-side "pass token boundaries only" convention and hope, `remove_provider`
  computes the list ONCE over the whole `provider` object — a seed reached by
  walking from offset 0 and therefore provably neutral — and both comma searches
  are lookups into it. Enforced by an AST gate asserting exactly one
  `significant_indices` call inside `remove_provider`, and pinned behaviorally by
  a literal `,` decoy planted inside the fixture's `//` comment. The one other
  caller, `strip_trailing_commas`, is handed a whole balanced value slice, so it
  satisfies the same invariant by construction.
- **Non-object depth-1 `provider` value — DECIDED: skip, but report; never
  crash.** A provider is a depth-1 `provider` child whose value is an object.
  Anything else (a hand-edited `"legacy": "a-string"`, an array, a number) is not
  yielded by `iter_provider_entries`, IS returned by `non_object_provider_keys`
  from the same walk, and the depth-1 scan resumes past it with `{}`/`[]` nesting
  tracked so an array's internal comma is not read as the entry separator.
  Considered and rejected: (a) silently skipping — `remove` would then print
  "no provider ... nothing to remove" for a key that is visibly present in the
  user's file, and `list` would under-report the object's contents, both of which
  are exactly the "claiming more certainty than sourced" failure PROJECT.md's
  core value forbids; (b) removing non-object entries too — that would require
  generalizing value-span detection to every JSON value shape, which is real
  scanner surface for an input opencode itself rejects. So: `remove` prints a
  distinct message naming the key and stating its value is not an object,
  `list` prints a `note:` line per such key, and SKILL.md documents it.
