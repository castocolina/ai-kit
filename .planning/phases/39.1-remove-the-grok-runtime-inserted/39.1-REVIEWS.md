#### 39.1-01

##### Summary

The plan targets the right boundary: remove stale lanes before routing, preserve custom-command lanes, and use the existing warning mechanism. It is **not ready to execute as written**: its first commit makes the generated test listings stale, and the proposed pre-merge filter has cases that can select a lane the owner did not intend to run.

##### Strengths

- **The load-side boundary is appropriate.** `cfg_combine` produces the flat and role-specific views before callers route them (`skills/ai-kit-spec-review/ai_kit_spec/config_io.py:714-733`). Filtering there can prevent a removed lane from reaching both review and execute selection.
- **The plan preserves the trust boundary.** Project lanes are checked before `cfg_combine` receives them (`skills/ai-kit-spec-review/ai_kit_spec/config_io.py:613-641`), and the proposed filter operates on copies rather than rewriting the config (`.planning/phases/39.1-remove-the-grok-runtime-inserted/39.1-01-PLAN.md:131`).
- **The unknown-runtime pin is useful.** Unknown string IDs currently route as `unverified`, not as a refusal (`skills/ai-kit-spec-review/ai_kit_spec/routing.py:168-183`).

##### Concerns

- **HIGH — The first new test module leaves the commit gate red.** Task 1 creates and commits `tests/test_removed_runtime.py` alone (`.planning/phases/39.1-remove-the-grok-runtime-inserted/39.1-01-PLAN.md:129-130`). The runner discovers new modules automatically, but `tests/test_gate_scope.py:570-583` requires the generated Makefile and hook listings to include every discovered module. `tools/gen_test_groups.py:1-7` explicitly says to regenerate them after adding a module. Waiting until plan 09 is too late for the required green intermediate commits.

- **HIGH — Filtering before layer merge can resurrect an overridden lane.** Task 1 drops removed entries independently from the project and user layers (`.planning/phases/39.1-remove-the-grok-runtime-inserted/39.1-01-PLAN.md:131`). Today, a project lane with the same key overrides a user lane (`skills/ai-kit-spec-review/ai_kit_spec/config_io.py:373-398`). If the user layer has a `pi` lane `k` and the project layer overrides `k` with `runtime = "grok"`, dropping the project entry first exposes and can run the user lane. That conflicts with the prohibition on substituting a lane for the removed one. The planned tests use distinct keys and miss this case.

- **HIGH — The no-write proof bypasses the normal migration path.** Every `_load` test explicitly sets `migrate=False` (`.planning/phases/39.1-remove-the-grok-runtime-inserted/39.1-01-PLAN.md:129`), but normal `cfg_resolve` defaults to `migrate=True` and calls project and user migration before filtering (`skills/ai-kit-spec-review/ai_kit_spec/config_io.py:628-641`, `:671-679`). A pending legacy roster can therefore cause writes during the normal load. The plan must reconcile this with the locked no-user-file-write prohibition and test the default path, not only the no-migrate path.

- **MEDIUM — A removed lane in a configured ladder produces more than the promised single notice.** After the filter drops the lane, `role_orders` reports its ladder key as dangling (`skills/ai-kit-spec-review/ai_kit_spec/role_orders.py:44-56`). The planned one-message tests have no ladder (`.planning/phases/39.1-remove-the-grok-runtime-inserted/39.1-01-PLAN.md:131,166`). This is a common saved-config shape and needs an explicit expected result.

- **MEDIUM — A silent status preview can consume the once-only notice.** `capability_lines` calls `cfg_resolve` with a no-op warning callback (`skills/ai-kit-spec-review/ai_kit_spec/config_status.py:81-89`). The proposed `_note_once` records the label before calling that callback (`.planning/phases/39.1-remove-the-grok-runtime-inserted/39.1-01-PLAN.md:131`). A later load in the same process can therefore suppress the only visible removal message. Also, two malformed or duplicate-key entries in one role share the proposed label and receive only one notice.

- **MEDIUM — Task 1’s first commit conflicts with its own lint rail.** It instructs the executor to add imports including `io`, `json`, and `detection` before the later slice uses them (`.planning/phases/39.1-remove-the-grok-runtime-inserted/39.1-01-PLAN.md:129`), while requiring `make ruff` before a code commit (`:98`). As described, unused imports can stop the first commit. The task also has two commits and a dense multi-module implementation within one capped lane, so the 1,800-second limit is a material risk.

##### Suggestions

- Generate and stage the listings in the **first** commit that creates the test module; update the later guard-registration handoff accordingly.
- Specify and test same-key collisions across both layers and roles. Preserve override semantics without dispatching a removed entry or implicitly selecting its shadowed predecessor.
- Add a default-migration-path, whole-scratch-tree no-write test; explicitly define how pending legacy files are handled.
- Test a role-specific ladder and a status-preview-then-load sequence. Do not mark a notice delivered to a no-op callback as visible.
- Add imports when first used and split the tracer task at a green, mechanically checkable boundary.

##### Risk assessment

**HIGH.** There is a concrete unintended-lane execution case and the first planned commit cannot satisfy the repository’s generated-listing gate as written.

##### Ponytail findings

- **MEDIUM — Tasks 1–3 are needed for R4/D-02/D-03, and reuse is appropriate:** `_emit_legacy_note` and `cfg_combine` already provide the warning and merge paths (`config_io.py:252-261,714-733`). The small shared dedupe split is justified, but it must preserve delivery semantics.
- **HIGH — Task 1 does not yet reach the layered override and migration callers.** Fix those existing paths rather than adding a parallel loader.
- **LOW — Task 3’s status change is a reasonable consequence of dropping a lane**, but it should share the same notification behavior rather than silently consuming it.
