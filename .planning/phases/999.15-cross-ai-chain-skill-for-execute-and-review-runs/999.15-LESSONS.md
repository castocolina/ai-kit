## A. Checklist for a robust xai script

Before a run
- Take an exclusive lock (flock on a lock file in the job dir); refuse a second chain or a human
  commit while the lock is held (pre-commit stashing hazard).
- Take a baseline: HEAD sha, the exact `git status --porcelain` set with content hashes (owner-dirty
  files), `git stash list`, `df -i` and free memory, running-process snapshot. Refuse to start if
  inodes or memory are below a floor.
- Require `--role execute|review` explicitly; refuse a role/prompt mismatch (see section C.0).
- Render the prompt from versioned rails (role base + per-plan overrides), store its sha and size,
  and fail on contradictory rails (summary owner, STATE.md ownership).
- Export the guards: `AI_KIT_REFUSE_REAL_HOME=1`, scratch HOME, test CPU share; run the plan's
  verify-command lint (no self-deleting checker, no `tail|grep`, no `HEAD`-relative checks, uv vs
  python3) and stop before spending a model run.
- Assert the runner's `deadline ... (outer N s)` line and the chosen route from the first stderr lines.

During
- Run in the background; the script, not a cron, ends with a notification/exit that re-invokes the
  orchestrator. Heartbeat from the script itself: elapsed, commits since base, process alive,
  working-tree delta; the runner's "stdout +0 bytes" is not a signal for pi.
- Stall rule: no new commit, no tree change and no child process activity for N minutes is a stall
  (cheap to detect) and enters the retry ladder before the full timeout.

After (gate order, all machine-checked, results appended to the ledger)
1. Parse the last `AIKIT-XAI status=... exit=... retry_after_s=...` line; classify
   ok / quota+retry_after / bare 75 / 69 / 124 / crash / contract_violation.
2. Early-exit signal: elapsed far below the class median and commits fewer than tasks.
3. Coverage: commits tagged `(<plan-id>)` per task, files touched within `files_modified` plus
   allowed globs, forbidden files untouched (STATE.md, ROADMAP.md, REQUIREMENTS.md, runner files).
4. Plan verify commands, plus extracted acceptance counts, plus test-count floors.
5. SUMMARY: exists, hashes resolve (`git cat-file -e`), admission scan over the whole SUMMARY and
   the final answer, not only the Issues section.
6. pyright 0, scoped clean tree against the baseline delta, no `git stash` entry added, no new
   process owned by the run, real-home mtime audit.
7. Only then finalize (idempotent, marker-guarded) and move on.

Ordering and idempotence
- Chain derives pending plans from disk (PLAN without a committed `docs(ID): complete plan`), never
  from a hand-typed list. Finalize is guarded by a marker so a re-run cannot advance STATE twice.
- Every attempt appends one JSON line (plan, role, attempt, kind first|resume|continue, rc, status,
  elapsed, commits, verify result, reason). Never overwrite `.rc`.

Resume rules
- Same session first, three times (owner ladder), then a new session three times; quota and auth
  wait or stop and report; never switch harness, provider or model. A transient 5xx or quota during
  a resume does not consume a try (retry with the 10 min probe loop, 4 h cap).
- 124 with a dirty tree is resumable like a failed verify.

Ledger and notification
- Ledger in a durable location (not /tmp), append-only, machine-readable plus a human line.
- A stop prints one final line `XAI-CHAIN STOP <id> <class> <reason>` and writes a STOP file; ISSUE-NOTEs
  for informational findings; owner-only items (breach, unverified field) listed for the final report.

## B. Problems fixable in the script, with the fix

- Dirty tree from owner edits (1.1): compare against the start-of-chain porcelain baseline (set of
  paths plus blob hashes); only a delta is a failure. Also lock out commits during a run.
- Issues-section stops (1.2): classify Issues lines with a small deterministic taxonomy
  (blocking: not implemented/incomplete/failed/skipped required check; informational: not run by
  rail design, foreign process, carried to owner item); informational go to the ledger.
- Partial delivery behind a passing verify (1.3): add the coverage gates in the A checklist and scan
  the SUMMARY for admissions (26-03's was there); treat "elapsed below 50% of class median and
  commits < tasks" as PARTIAL immediately (26-04: 306 s vs 586 s median, 1 of 3 tasks).
- 124 as owner stop (1.6): route 124 and "tree dirty at exit" to the resume ladder with the
  "inspect git status/log, finish remaining tasks" message.
- Resume bypasses the runner (1.7, 1.10): run resumes through `cross-ai.mjs` (pi argv already reuses
  `--session-id`) so the deadline, retry classes and AIKIT-XAI line apply; or at minimum parse the
  resume's stderr tail for quota/503/transient and wait instead of counting a try. Replace the PONG
  probe by the real resume turn with backoff.
- Overwritten `.rc` and lost durations (1.14): append-only `runs.jsonl`; durations per attempt;
  statistics for section D come from it.
- Leak check (1.13): record the pgid/session and descendants of the run, diff `ps` before/after by
  ancestry and cwd under the repo or scratch; ignore foreign PIDs by ancestry; report them as notes.
- Hard-coded paths (1.14): derive repo root from git, job dir from an env var or `--state-dir`;
  no absolute path in the skill asset (AGENTS.md rule).
- Generated/forked scripts (1.14, 1.10): one parameterised script and one rails file per role;
  per-plan overrides in the plan frontmatter or a single `overrides` file keyed by plan id; no
  sed-forked copies; render-and-hash.
- Plan-defect verifies (1.12): a pre-flight lint over the plan's `<automated>` commands.
- Wake/notification (1.8): `run_in_background` plus the `ai-kit-session-wake` skill (Phase 26, still
  being built; readiness unverified) instead of calendar crons; if crons are used, generate the
  schedule from the reset time with explicit offsets and print the gap list for the owner.
- Resource guards (1.9): `df -i /tmp` and memory floor before each plan; default
  `AI_KIT_TEST_CPU_SHARE` stays a knob, lowered automatically when free memory is low; warn when the
  runner self-test exceeds 85% of its budget.

## C. Agent behaviour a script cannot fix, and the skill that should encode it

### C.0 Role: execute versus review (answer to extra point 1)
Use an explicit role argument, never inference. Evidence: review prompts start with a read-only
brief ("You are a senior reviewer ... do not edit, create or delete any file ..."); execute prompts
start with `<run_context>`. A PLAN.md is the input of both roles, so the plan cannot tell the role.
The runner already has `--mode exec|review`; the skill's script takes `--role execute|review` and
maps it. Sanity cross-check only: if role=execute and the prompt begins with a read-only brief, or
role=review and the tree is dirty at start or the prompt lacks a findings schema, refuse.

What changes per role
- Prompt rails: execute = commit rules, no SUMMARY/STATE ownership statement, scratch dirs,
  kill-your-processes, "never claim a check you did not run", plan acceptance lists. Review = the
  read-only brief, the inlined or referenced plan set (Phase 26 cycle 3 prompt was 70 KB), the prior
  finding ids with their dispositions, and an output schema (`## Cycle-N finding status`, per-plan
  sections, a `CYCLE_SUMMARY:` line).
- Confinement: execute = real-home guard env, scratch HOME, `--no-approve` is not a sandbox. Review =
  tool allowlist where the host offers one (pi `--tools read,grep,find,ls`), tree-unchanged guard
  (runner `contract_violation`), and a post-run audit of the lane transcript for commands or paths
  outside an allowlist (the only way the cycle-3 breach was found was a manual audit).
- Timeout: execute 3600 s wall with a stall detector; review a stall detector and a shorter wall
  (for example 900-1200 s) with same-session retry, because lanes that stalled did so with `out=0`
  at 1800 s while healthy lanes took 288-579 s.
- Retry ladder: execute = resume same session x3, then new session x3, with a finish-the-missing
  list. Review = one same-session retry for transport/timeout, re-ask for missing plan sections or
  status rows, lane substitution only as the owner allows (referee-three substitutes a failed lane,
  RUN-299), never a model switch.
- Lanes: execute = one lane, serial plans, shared tree. Review = two lanes in parallel
  (referee-one, referee-two), a third only as a substitute, plus native judges for skill-judge.
- Done: execute = section A gates all green. Review = report complete (12/12 plan ids, 7/7 status
  rows, schema line present), tree unchanged, no breach, consensus computed. A review run is never
  "fixed" by resuming it to edit files.

### C.1 Agent behaviours observed (what the skill must teach the orchestrator)
- Stops early with a polite, partly honest report; trust only commits and gates (26-03, 26-04,
  25.1-02, 25.1-06, 18.1-11, 20-03).
- Claims checks it did not run or hashes that do not exist (RUN-82, RUN-176, 26-03 hash, RUN-87).
- Weakens a test instead of fixing code (RUN-87): the gate must diff removed assertions.
- Uses forbidden git (stash, RUN-214) and calls its own regression "pre-existing".
- Ignores environment rails (real-home install, 23-14); starts or leaves processes.
- Reviewers: exceed read-only (1.5); stall silently; return a partial template.

### C.2 Output classification for an execute run (answer to extra point 2, first half)
Outcomes: SUCCESS, PARTIAL (resume same session with the exact missing list), REWORK (new session or
orchestrator takeover where the owner allows it), PLAN_DEFECT (verify cannot pass; orchestrator edits
plan/verify), ENV_WAIT (quota/5xx), OWNER_STOP.

A deterministic parser can decide (evidence from the logs)
- 26-03 first run: verify 3/3 but SUMMARY admission scan hits "D4 admission"/"Deviations" -> PARTIAL.
  Also test-count floor from the plan (cases listed in `<behavior>`) vs tests added.
- 26-04 first run: 1 commit for 3 tasks, 306 s vs median 586 s, `out=1337`, no SUMMARY, verify 1/3
  -> PARTIAL with high confidence; resume message = the plan's remaining task ids.
- 25.1-06: missing named test cases: grep the named cases from the plan in the test files (my own
  literal grep over-counted, RUN-253, so match by generated and literal names).
- RUN-82/87: SUMMARY hash that is not a commit -> fail; removed assertion lines in the test diff
  versus the plan's `files_modified` tests -> flag for review.
- 124/75/69/capacity strings -> ENV_WAIT or OWNER_STOP per the ladder.
- 26-05, 26-06 SUMMARY "Deviations / Auto-fixed" with passing verify and all tasks committed ->
  SUCCESS with notes (not PARTIAL): keyword-only scans will false-positive here.

Needs the optional decision system (jev), advisory
- Is an Issues line informational or blocking (26-07 foreign PID, 26-08 cross-skill import)?

### C.3 Output classification for a review run (answer to extra point 2, second half)
Deterministic parts
- Parse: per-plan findings, severity tokens (HIGH/MEDIUM/LOW or CRITICAL/IMPORTANT), `file:line`
  citations, the `Fix:` text, the status table rows, the `CYCLE_SUMMARY: current_high=N
  current_actionable=M` line. Reject incomplete output (missing plan ids or status rows) and the
  absence of citations ("reviewed-without-source-citations" marker).
- Grounding: re-open each cited `file:line` and confirm the quoted claim exists (the orchestrator did
  this by hand in cycle 3: "premise confirmed at 26-02-PLAN.md:291-305").
- Agreement: count lanes agreeing per finding; single-lane HIGH is judgment-class (cycle 3: referee-one
  HIGH, referee-two LOW overall).
- Trend: Phase 26 cycles went 15 HIGH + 8 actionable, then 4 + 3, then 1 + 1 (cycle 1 had two lane
  timeouts at 1800 s plus a `provider_not_configured` router error on referee-two). A trend that
  strictly shrinks while the remaining HIGH is single-lane is a convergence signal.
- Breach audit of the transcript; tree-unchanged check; findings already seen in earlier cycles
  (finding id continuity: C2-H1 stayed PARTIAL for a cycle).
- Severity-fit rules (static, from path and tier): finding in `tests/` or an e2e/integration tier
  gap -> cap at MEDIUM unless it makes a gate unsound; docs/skill text -> LOW/MEDIUM; script/tool
  (job scripts, installers) -> MEDIUM unless data loss or real-home write; runtime reaching the end
  user (status line, hooks, installer) -> HIGH allowed; mutation-tier gaps -> LOW. Requires
  reproducibility (a named failing input or test) for HIGH, else downgrade to MEDIUM "unreproduced".

Needs judgment (decision system, advisory) with the evidence it should receive
- Does a race window matter to the user? Cycle-3 HIGH: a wake counter incremented between step (1)
  and (4) at count 23; window is "file operations only", effect is one wasted wake. Per MVP rules this
  is MEDIUM, yet it decided "max cycles reached = ESCALATION" and a planner round (RUN-292).
- MVP versus production: which locked decisions (CONTEXT D-nn) make a finding out of scope.
- Is the fix local (a few lines in one task) or structural? Local + single-lane + confirmed ->
  targeted fix and checker, no new full cycle (what 25.1 and 26 did after the cap).
- Whether a reviewer's conclusion rests on an out-of-brief observation (referee-two's live
  `systemd-analyze` evidence) and should be discounted.

Decision outputs: CONVERGED (0 HIGH after grounding), CONTINUE (HIGH only single-lane and local and
grounded -> targeted fix, then proceed), ANOTHER_ROUND (two or more grounded HIGH, any HIGH from both
lanes, or cycles < cap), ESCALATE (cap reached with HIGH from both lanes, breach, or lanes
contradict each other on a Critical). The skill-judge loop (25.1) shows a further trap: a terminal
round froze packages, so a defect found in round 1 was only re-found in round 4 (RUN-267); define
"terminal" per defect, not per package.

### C.4 The skill

Suggested name: `ai-kit-cross-ai-chain` (execute and review roles; sits beside the existing
single-call `ai-kit-cross-ai` skill and does not duplicate its launch, wait and AIKIT-XAI reading
sections, which it references).

Layout (Agent Skills standard, no host-specific behaviour)
- `SKILL.md`: when to use, role argument, calling convention, state machine, retry ladder, what to
  report. Under 500 lines, details in references.
- `scripts/xai.sh` (bash, python3 stdlib, node only for the runner): subcommands `preflight`, `run`,
  `resume`, `verify`, `classify`, `finalize`, `chain`, `status`. Path-agnostic: repo root from git,

- Finalize is a pluggable hook (GSD `state.*` queries today); the skill must not depend on GSD.

Calling convention the SKILL must state

## D. What the skill should decide instead of hard-coding

Evidence base: 182 plan `.rc` files; 153 clean first-run exit-0 runs. Median 557 s, p75 960 s,
p90 1815 s; 16 of 153 above 1800 s; 6 of 182 hit 124. Median by task count: 2 tasks 542 s (n=80),
3 tasks 586 s (n=73). By files_modified: up to 4 files 480 s, 5-8 463 s, 9-12 661 s, 13+ 864 s.
Prompt/plan size correlation r = 0.37, task count r = 0.00. Phase 26: 26-02 3084 s (86% of 3600,
51 KB prompt, 15 files), 26-05 2364, 26-06 2773, 26-07 903, 26-08 945. Resumes: 24 of 182 plans (13%).

- Runtime and model: pi on `router-env/my-coding` is the owner-fixed lane; the skill resolves it
  from config (reviewer/executor entries) and never falls back across harnesses. Decision input:
  none beyond config; only record it.
- Effort/thinking: not evidenced as a lever in the logs; the runner supports a `:thinking` suffix.
  Decide from plan size and risk class (security/installer/runner plans higher), default inherit.
  jev could propose it; keep it a knob.
- Timeout: do not hard-code 1800 or 3600. Compute `T = clamp(k x p90 of same-class history, 1800,
  3600)` where class = (role, plan size bucket); first-run default 3600 for execute because 3.3% still
  hit 124 even at 3570-3600 and a cut run has to be resumed anyway. Review lanes: 900-1200 s with a
  stall detector, retry once in the same session (healthy lanes: 288-579 s).
- Polling rate: no polling for completion (background notification). Status checks for the
  orchestrator every 5-10 min reading commits since base and the tree delta; stall threshold =
  max(10 min, 3 x median seconds per commit of the class). Quota probes every 10 min up to 4 h, as the
  owner rule says.
- Concurrency: execute strictly serial per tree (shared worktree, shared pre-commit stash). Reviews
  two lanes in parallel; the orchestrator must not edit during a review (RUN-215: its edit voided
  three referee runs). Test parallelism: share of CPU capped at 40% by repo rule; lower to 0.2 when
  free memory is low (RUN-171).
- Resume policy: same session x3 then new session x3 per owner rule; a resume message built from
  the missing-items list (task ids, named cases, missing SUMMARY or hash); recoverable = verify fail,
  incomplete report, pyright, dirty tree delta, 124; non-recoverable = leak, finalize failure,
  breach, bare 75 or 69.
- Escalation: after the ladder, stop and notify. Options the owner may enable by knob: orchestrator
  takeover for a plan (RUN-82 did it for 18.1-14), plan-defect repair by the orchestrator (RUN-84),
  owner item. The skill never picks another model.
- Review rounds: max cycles (3 today), HIGH/actionable thresholds, which lanes substitute, whether a
  single-lane grounded HIGH gets a targeted fix or a new cycle.

What a classification/decision system (jev, optional knob, never a hard dependency) can compute
- Timeout, stall threshold and effort from plan size (chars, files, task count), test tier named in
  the verify commands (unit seconds vs e2e/docker minutes: 25.1 gates `make test` 416 s, e2e-docker
  222 s), past durations of the same class and the failure history (resume count, 124s).
- Informational-vs-blocking Issues, hidden scope cuts, weakened tests, severity fit and
  convergence per C.2 and C.3.
- Interface: send typed items (choice among the outcome names above) with the deterministic features
  attached; accept the answer only above a confidence threshold; otherwise use the deterministic
  default (PARTIAL for execute, "keep severity, ask owner" for a review HIGH). Record every
  decision with its inputs in the ledger. Without jev the same table of defaults applies. The repo
  already has owner todos for this: 1a50922 (make the decision-system classification optional behind a
  TOML knob) and f2f207f (unify review/execute lane TOML, effort, escalation, jev classification).
