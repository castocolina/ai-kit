## Decisions this plan makes on the planner's authority

These resolve `15-RESEARCH.md`'s two flagged Open Questions. Neither is left open.

- **D-04 (resolves Open Question 1 -- which sibling subcommand is subprocess-invoked).** Both of
  the orchestrator's own CLI subcommands, `check` and `remediate`, run the exact same underlying
  pipeline: `dispatch_all(repo_root)` then `aggregate(domain_results)`. Internally, `dispatch_all()`
  ALWAYS subprocess-invokes each sibling's `remediate` subcommand -- never a bare `check` subprocess
  call -- because every sibling's own `remediate` already calls that sibling's own `check` internally
  before running the shared `build_remediation()` builder (confirmed verbatim in all 6 siblings'
  `cli.py`: `def remediate(repo_root): return build_remediation(check(repo_root))`). SC1's "invokes
  all 6 checkers' check" is therefore literally true one layer down, without this orchestrator
  re-deriving `build_remediation`'s `auto_apply`/near-miss branching itself -- exactly the
  duplication RESEARCH.md's Don't-Hand-Roll guidance and Pitfall 2 warn against. Because every
  per-finding classification already happened inside each sibling's own `remediate` call, there is no
  further classification step left for THIS skill's `remediate` command to do beyond the cross-domain
  merge `check` already performs -- so `remediate(repo_root)` is defined as `return check(repo_root)`,
  matching the textual shape every sibling's own `remediate = build_remediation(check(...))` uses,
  while its own docstring says plainly why the two commands return identical output at this level.
- **D-05 (resolves Open Question 2 -- the failure-entry schema).** A per-domain dispatch failure
  (non-zero exit, `subprocess.TimeoutExpired` past a 30-second per-domain budget, an unresolvable
  entrypoint, or `json.JSONDecodeError` on stdout) produces exactly this shape:
  `{"domain": <domain-key>, "status": "failed", "error": <one-line message>, "returncode": <int-or-null>}`.
  `status: "failed"` is the field a reader checks to tell this apart from a real payload (whose
  top-level keys are always `remediate`/`blocked`, never `status` -- confirmed verbatim in
  `remediation.py:122`'s return statement). `returncode` is the subprocess's real exit code when one
  exists, `null` for a timeout or an unresolvable entrypoint (no process ever ran, so there is no exit
  code to report). These entries are collected into `aggregate()`'s own top-level `failed` list, in
  fixed `DOMAIN_ORDER`, never folded into `remediate`/`blocked` -- the mechanism that keeps "checked,
  no findings" and "couldn't check" visibly distinct (RESEARCH.md Pitfall 1, `PROJECT.md`'s
  confidence-labeling Core Value, D-02).
- **D-06 (dispatch is sequential, not parallel).** `dispatch_all()` calls the 6 siblings one at a
  time, in fixed `DOMAIN_ORDER`. RESEARCH.md's Alternatives Considered table leaves this to planner
  discretion; sequential is chosen because results must be reassembled into the same fixed order
  before the stable sort regardless of completion order, so parallel dispatch buys only wall-clock
  speed at the cost of a second source of non-determinism to rule out in tests. Six subprocess calls
  against a local filesystem are I/O-light enough that worst-case sequential runtime (6 x 30s timeout
  budget = 180s) is an acceptable, simple-to-reason-about ceiling.
