## Summary

Scope: the diff `71258ca..HEAD` for the eight listed files, with the surrounding code read where needed
(`detect_statusline*`, `unwire_statusline*`, `persist_statusline`, `_persist_layout`, `render_preview`,
`launch_wizard`/`run_wizard` crash handling, Textual's `App._get_dom_base`).

detection states (`unset`/`ours`/`foreign` are the only values `detect_statusline*` returns). The pinned

The main problems are in the consent and backup path for foreign status lines:
- A queued second key on Review can open a second confirm modal, and the commit can then run underneath it.
- Every Enter on Review takes a new backup, even when the user then declines.
- The backup is never checked against the bytes the commit overwrites.

Three other problems:
- In a dry run, the in-wizard doctor shows a value as applied when nothing was written.
- The Playwright row reports "ok" in a case where the plugin cannot launch.
- A crash in the new post-commit doctor screen throws away the commit log.

## Warnings

### WR-01: A queued second key on Review can open a second confirm modal, and the commit runs while one is still open

**File:** `tools/wizard_app.py:1655-1688` (`_confirm_or_commit`, `_confirm_foreign`, `_on_foreign_answer`)
**Issue:** `_confirm_foreign` delays the push with `call_after_refresh`. Textual runs that callback only after it has
processed every queued message. The `len(self.screen_stack) > 1` guard in `on_key` is therefore still false for
any key already in the queue.

Scenario: a fast double Enter, or key repeat, on Review with a foreign `remove`/`customize` pending.
1. `_key_review` runs twice, so `prepare_foreign` runs twice (two backups) and two `ForeignConfirm` modals are
   pushed for the same host.
2. The user answers `y` on the top modal. `_on_foreign_answer` sets `foreign_ok`, `_confirm_or_commit` finds
   nothing left to confirm, and `_commit_now()` starts the real commit.
3. The second modal is still on screen over Done. The user's `n` there only clears `foreign_ok` on a state that
   has already been serialized. The foreign entry is removed or replaced even though the user's last answer was No.

Done's `d` has the same window and can push two doctor screens.
**Fix:** Add a one-shot guard that is set before the push and cleared in the answer callback:
```python
def _confirm_foreign(self, host):
    if self.flow.confirm_pending:
        return True
    ...
    self.flow.confirm_pending = True
    self.call_after_refresh(self.push_screen, ForeignConfirm(...), functools.partial(self._on_foreign_answer, host.id))
    return True

def _on_foreign_answer(self, host_id, yes):
    self.flow.confirm_pending = False
    ...
```
Make `_key_review` (and `_key_done` for `d`) return `True` while `confirm_pending` is set.

### WR-02: The foreign backup is taken on every Review Enter and is not tied to the bytes the commit overwrites

**File:** `tools/setup.py:3782-3802` (`_prepare_foreign`), `tools/setup.py:3852-3866` (`_commit_host_statusline`),
`tools/wizard_app.py:1664-1677`
**Issue:** There are two problems in the same lifecycle.
1. **Backup churn.** Each Enter on Review calls `prepare_foreign`, which runs `backup_before_write` and then
   `prune_backups(keep=10)`, before the user answers. A user who declines and retries ten times (No → Enter …)
   pushes every older `settings.json.*.bak` out of `backups/claude/`. That folder is shared with the doctor's
   applies, so it can also delete the only backup taken before ai-kit's changes.
2. **Backup detached from the write.** The backup is a copy of the file as it was when the modal opened. The
   commit runs later, possibly after several modals, and only re-checks that the `statusLine` command still equals
   the pinned `adopt_command`. It never compares the file bytes with the backup. If anything else changes
   `settings.json` or `cli-config.json` in between, the commit still writes. The backup is then not the file
   "before the change" that SPEC R3's acceptance requires, and restoring it would lose those other edits. The
   doctor's `apply_guarded` (D-14) does run this byte comparison; the foreign path does not.

**Fix:**
- Cache the prepare result per host for the session. Reuse it while the file's bytes still match the backup, and
  take a new backup only when they differ.
- In `_commit_host_statusline`, for `remove_foreign`/`replace_foreign`, read the target bytes and compare them with
  `info["backup"]`'s bytes before writing. Refuse on a mismatch, with the same message style as the
  `adopt_command` mismatch, or take a fresh backup.
- `_commit_host_statusline` will need the backup path. Carry it in the host state, e.g.
  `model.state["foreign_backup"] = info["backup"]` when the user answers Yes.

### WR-03: In a dry run, the in-wizard doctor shows a value as applied when nothing was written

**File:** `tools/setup.py:4795-4807` (`_make_doctor_factory`), `tools/config_doctor_app.py:242-264` (`_on_apply_dismissed`)
**Issue:** With `install --dry-run`, the factory wraps `apply` so that every confirm is a dry call. Dry appliers
still return `{"ok": True, "current_display": <target>}`. `ConfirmApplyScreen.action_confirm` dismisses with that
result, and `_on_apply_dismissed` writes `<target>` into the row's **Current** cell and `row["current_display"]`.
The table now shows the recommended value as the machine's current state, but nothing was written. The exit hint
on another line does not change what the cell says. This breaks the AGENTS.md rule that a diagnostic result is
never shown with more certainty than its sourcing.
**Fix:** Mark the dry result in the wrapper so the cell says what really happened:
```python
def dry_apply(row_id, _dry):
    res = base(row_id, True)
    if isinstance(res, dict) and res.get("ok"):
        shown = res.get("current_display", res.get("after"))
        res = {**res, "current_display": f"{shown} (dry run, not written)"}
    return res
ctx = ctx._replace(apply=dry_apply)
```

### WR-04: The Playwright row reports "ok", and refuses to fix, when the configured executable path is broken but the default Chrome exists

**File:** `tools/config_doctor_checks.py:650-660` (`read_claude_playwright_browser`), `tools/config_doctor_checks.py:662-672`,
`tools/config_doctor_checks.py:683-687`
**Issue:** `read_claude_playwright_browser` returns `ok: Chrome at /opt/google/chrome/chrome` before it looks at
`env.PLAYWRIGHT_MCP_EXECUTABLE_PATH`. When that variable is set, Playwright MCP launches that path instead of the
default channel. If the variable names a file that does not exist, the plugin fails to launch even though the
default Chrome is installed.

The checks get this case wrong in three places:
- The row reports "ok".
- `_playwright_apply_when` hides the apply.
- `_apply_claude_playwright_chrome` refuses with "nothing to fix".

The code follows SPEC R7's wording, but that wording has the same logic error.
**Fix:** Check the configured variable first:
```python
configured = _configured_env_value(data)
if configured:
    return (f"ok: {PLAYWRIGHT_ENV_KEY} names {configured}" if _is_executable(configured)
            else f"problem: {PLAYWRIGHT_ENV_KEY} names no executable at {configured}")
if _is_executable(PLAYWRIGHT_DEFAULT_CHROME):
    return f"ok: Chrome at {PLAYWRIGHT_DEFAULT_CHROME}"
```
Apply the same order in `_playwright_apply_when` and the applier's `compute`. Amend SPEC R7's "ok" rule to match.

### WR-05: A crash in the post-commit doctor screen throws away the commit log and exits 2 after a successful install

**File:** `tools/wizard_app.py:1804-1812` (`_key_done`), `tools/wizard_app.py:1838-1843` (`run_wizard`), `tools/setup.py:4131-4134`
**Issue:** The doctor now runs inside the wizard App after the commit has finished. `run_wizard` turns any
unhandled exception into `WizardCrash`. `launch_wizard` then prints "wizard failed" and calls `sys.exit(2)` before
it reaches the per-host `_commit_log` output or `cmd_install`'s examples and summary.

A bug anywhere in the doctor would therefore hide a completed install's warnings and refusals and report failure.
That covers `ConfigDoctorScreen.on_mount` (`row["id"]`), the DataTable, `ConfirmApplyScreen`, or a factory
exception outside the narrow `(OSError, ValueError, RuntimeError, ImportError)` tuple. Before this phase, Done ran
no such code.
**Fix:** Keep the commit result when a crash happens after the commit. Either attach it to the exception
(`raise WizardCrash(exc, result=app.flow.result)`), or have `launch_wizard` print the logs and return the result
when `app.flow.result` is set and only the post-commit UI failed. Also widen the factory guard in `_key_done` to
`Exception`, with a notify, since this is a UI boundary.

### WR-06: The Playwright row's "why" text tells every user that their machine's Chrome is a flatpak

**File:** `tools/config_doctor_checks.py:1186-1192`
**Issue:** The static `why` says "on this machine Chrome is a flatpak, so the row offers …". Every user with the
plugin enabled sees it, including users whose Chrome is at the default path (row "ok") or who have no flatpak. This
states something as fact about the user's machine that the code never checked, which AGENTS.md's certainty rule
forbids.
**Fix:** Make the wording conditional, e.g. "where Chrome is installed as a flatpak
(`/var/lib/flatpak/exports/bin/com.google.Chrome` exists), the row offers …". If the text needs to reflect the
machine, build it from `_playwright_apply_when`.

## Info

### IN-01: The "unchanged" outcome for an on, ai-kit-owned host still writes and validates

**File:** `tools/setup.py:3844`, `tools/wizard_app.py:1250-1266`
**Issue:** When the host is on, the start state is `ours` and the board is not dirty, the action is `unchanged`.
The early return in `_commit_host_statusline` only covers `unchanged and not adopt`, so this host still runs:
- `_commit_known_ext_ids`, which installs every example segment into the provider directory;
- `persist_statusline`, including the status-line doctor's validation.

Review says "unchanged" and leaves out the "Validate with the status line doctor" line, but a validation failure
here still produces "install incomplete" for a host the user was told would not change. The docstring claim
"Review and commit never disagree" overstates what the code does.
**Fix:** Either skip persistence for `unchanged` (keeping only the upkeep that is genuinely required), or name it on
Review, e.g. "unchanged (layout re-validated)", and add `unchanged`-with-adopt to the set of actions that show the
validate line.

### IN-02: Review shows sample text without the "render unavailable" note while its real render runs

**File:** `tools/wizard_app.py:1191-1216` (`_review_host_preview`)
**Issue:** While the render runs (`out is None`), Review shows the inventory samples with no note. Review has no 2 s
deadline, and `render_preview`'s subprocess timeout is 10 s. For up to 10 s, sample text appears where the real
preview should be, and the user can press Enter to install during that time.
**Fix:** Add a short "rendering…" note, or reuse `PREVIEW_FALLBACK_NOTE` while the render is in flight.

### IN-03: The WizardContext comments are out of date

**File:** `tools/wizard_app.py:222-225`, `tools/wizard_app.py:249-250`
**Issue:** The comments say "Injected by setup.py in plans 04 and 05 … before those plans land" and "Unused until
then", but both hooks are now wired. They also describe `doctor(...)` as running "the status-line doctor for one
host". In fact it is a zero-argument factory that returns the config doctor's `ConfigDoctorScreen`. `prepare_foreign`
is never called for `keep`. AGENTS.md treats stale docs as a defect.
**Fix:** Rewrite them to describe the current behaviour: `doctor() -> Screen` for Done's `d`, and
`prepare_foreign(host_id) -> {"entry", "file", "backup"} | {"error"}` for remove/customize.

### IN-04: A pruning failure after a successful backup is reported as "backup failed" and blocks every later write

**File:** `tools/config_doctor_appliers.py:437-458`, `tools/config_doctor_appliers.py:501-502`
**Issue:** `prune_backups` runs inside `backup_before_write`. An `os.remove` or `os.stat` error on an old backup
(read-only file, a parallel prune) raises `OSError` after the new backup is already on disk. `_commit_guarded` then
reports "refused: backup failed" and `_prepare_foreign` reports an error. From then on, every write to that file
is refused until the user fixes the folder by hand.
**Fix:** Run the prune best-effort, e.g. `with contextlib.suppress(OSError): prune_backups(...)`. Optionally report
what it could not delete.

### IN-05: Impossible-state guard: chmod 0600 on a file that mkstemp already created as 0600

**File:** `tools/config_doctor_appliers.py:501`
**Category:** necessity
**Issue:** `tempfile.mkstemp` always creates the file readable and writable only by its owner (0600, per the
stdlib documentation). `os.link` gives the backup name the same inode, so `os.chmod(new_path, 0o600)` cannot change
anything. This rests on the stdlib's documented behaviour rather than on code in this repository, hence Info.
**Fix:** Remove the call, or keep it with a one-line comment if it is meant as explicit hardening.

### IN-06: The resize hook overrides Textual's private `App._on_resize`

**File:** `tools/wizard_app.py:1017-1024`
**Issue:** The hook works on the pinned Textual 8.x (the method exists at `textual/app.py:4345`). It depends on a
private name, though. If an 8.x minor release renames it, the override stops being called, or `super()._on_resize`
raises `AttributeError` on every resize.
**Fix:** Handle `events.Resize` on the default screen through a public handler instead, or add an arch or unit test
that asserts `hasattr(App, "_on_resize")` so an upgrade fails loudly.

### IN-07: The renderer-output sanitizer leaves C1 controls in place

**File:** `tools/wizard_app.py:111-113`, `tools/wizard_app.py:1134-1139` (`_preview_text`)
**Issue:** The filter removes OSC, non-SGR CSI and C0 controls. It does not remove U+0080 to U+009F: an 8-bit CSI
`\x9b` or OSC `\x9d` in renderer output passes through to Textual. User provider segments run inside the preview
render, so this output is the trust boundary the comment names. The risk is low, because most UTF-8 terminals do
not act on encoded C1 codes, but the filter does not do everything its comment claims.
**Fix:** Widen `_C0_RE` to `r"[\x00-\x08\x0b-\x1a\x1c-\x1f\x7f-\x9f]"`.
