# Phase 30.1: Setup wizard, component cards and host status-line panes — Specification

**Created:** 2026-11-03
**Ambiguity score:** 0.135 (gate: ≤ 0.20)
**Requirements:** 9 locked

## Goal

The owner runs the setup wizard and sees one card per component kind, a styled status-line pane per host that has an
on/off toggle that can also restore the host's default status line, a board preview that is a real render, and the
config doctor one key away on Done. The doctor fixes the Playwright MCP browser path on Bazzite and never writes
over a file it cannot parse.

## Scope

All requirements are **ai-kit's own setup** (`tools/setup.py`, `tools/wizard_app.py`, `tools/config_doctor_*.py`).
Cursor status-line parity (icons on every segment, a Cursor process-memory segment, Claude-style quota rendering,
the `alt_term_dimensions` fix) is **Phase 30.2**, split out on 2026-11-03 at the owner's request. This phase's
real-render preview (R4) is what makes 30.2's work visible in the wizard.

**Terms used below.**
- **Kind**: one of the component categories the wizard offers: skills, agents, commands, hooks.
- **Host pane**: one host's status-line step in the wizard (today's Arrange step for that host).
- **Wired entry**: the host's status-line setting: `statusLine` in Claude's `settings.json`, `statusLine` in
  Cursor's `cli-config.json`. It is **ai-kit's** when its command runs ai-kit's entry script, **foreign** otherwise,
  **unset** when absent (today's `detect_statusline` / `detect_statusline_cursor` states).
- **Host default**: the status line the host shows when no entry is wired.
- **Scratch HOME**: a temporary HOME with every host root inside it and `AI_KIT_REFUSE_REAL_HOME=1` (Phase 28).

## Background

Live-verified on 2026-11-03 in the ai-kit checkout, base `d6339d6` (scratch HOMEs, `AI_KIT_REFUSE_REAL_HOME=1`;
probes under the gitignored `tmp/p30.1/`):

- **Today's wizard** (driven with Textual's pilot through the real `_build_wizard_context`, both hosts detected,
  screens dumped to text): Choose is one box, "select components", with category headers: agents 1, skills 25,
  hooks 6, and no commands (the repo ships none). The Arrange step walks Claude, then Cursor, each behind a yes/no
  gate ("Wire your … status line?"). A declined gate leaves the host untouched, so a wired entry, ai-kit's or
  foreign, can never be removed from the wizard; only `uninstall` removes ai-kit's, and nothing removes a foreign one.
- **Board preview**: built from the fixed `sample` strings in `tools/segments_inventory.toml`, not from a render.
  Cursor's board borrows Claude's `Opus` model sample and shows `inc 42%`, `↺ Nov 20`. A real-render helper already
  exists per host (`_engine_ns` → `render_preview` with the host's entry script and sample payload) and the board does
  not use it. The preview's border title is set once at compose time and reads "live preview — Claude Code" on
  Cursor's board too.
- **Tray title**: "OFF — disabled (Space activates → its home line)" calls every switched-off chip disabled.
- **Cursor `statusLine` schema** (`tools/setup.py` `_CURSOR_STATUSLINE_KEYS`): `type == "command"`, a non-empty
  `command`, optional `padding`, `updateIntervalMs`, `timeoutMs`. `unwire_statusline` and `unwire_statusline_cursor`
  remove ai-kit's own entry only; ai-kit's backups dir is `paths.backups_dir` (XDG state, `ai-kit/backups`).
- **Config doctor**: started only by `setup.py --config-doctor` → `cmd_config_doctor` → `run_config_doctor`, a
  separate Textual `App` (`ConfigDoctorApp`) over `config_doctor_checks.build_catalog`. Textual cannot run that App
  inside the wizard's App. Its Claude settings appliers (`_apply_claude_retention`, `_apply_claude_sandbox_enabled`)
  replace an unparseable `settings.json` with `{}` plus their key, and no applier takes a backup.
- **Playwright MCP**: the `playwright@claude-plugins-official` plugin's `.mcp.json` is `npx @playwright/mcp@latest`
  with no args and no env. `@playwright/mcp` 0.0.83 (playwright-core 1.64 alpha) reads `PLAYWRIGHT_MCP_EXECUTABLE_PATH`
  and `PLAYWRIGHT_MCP_BROWSER` (its README). Its default `chrome` channel needs `/opt/google/chrome/chrome`, absent
  here; a headless launch failed with "Chromium distribution 'chrome' is not found". Headless launches through
  `/var/lib/flatpak/exports/bin/com.google.Chrome` (Chrome 156), the flatpak Chromium wrapper and
  `~/.cache/ms-playwright/chromium-1246` all succeeded. Claude Code's docs: the settings `env` key sets variables "for
  every session and its subprocesses"; plugin MCP servers get the same environment as user-configured servers; the
  docs do not say outright that `env` reaches an MCP process (inferred until a live session confirms it).
- **Mermaid render test**: `mmdc` 11.17.0 needs `chrome-headless-shell` from `$HOME/.cache/puppeteer`; with a scratch
  HOME it fails. Phase 28 D-09 stays as written (the real-render test skips with a named reason); nothing here.
- **Phase 30 coupling**: Phase 30 (D-11, SPEC R11) adds the `--with-global-rules` item to today's Review screen,
  pre-checked with a diff per file. This phase keeps it on the new Review.

## Requirements

1. **One card per component kind on the first screen**: Choose shows one bordered card per kind that has at least one
   installable item, in the order skills, agents, commands, hooks.
   - Current: one "select components" box with category headers; a kind with no items is simply absent.
   - Target: each kind with items gets its own card, titled with the kind and its "on/total" count; a kind with zero
     items shows no card; Space, `a`/`n` (this card), `A`/`N` (every card) and the cursor work across cards; Review
     lists the selected components per card with the same counts.
   - Acceptance: a pilot test over a fixture context with skills, agents and hooks but no commands shows exactly three
     cards and no commands card; toggling an item changes only its card's count and the Review count for that kind;
     `a` selects every item of the focused card only.
   - *Amended 2026-11-03 (30.1 D-01):* the cards are tabs, one card on screen at a time: a tab row
     `[skills 25/25] agents 1/1 hooks 3/6` lists only kinds with items, ←→ switches kind, ↑↓ move inside the card on
     screen. "Shows exactly three cards" reads as three tabs and no commands tab. Item rows keep today's description
     text (D-02).

2. **Host panes keep today's layout with a host accent**: each host pane keeps today's board layout and adds a host
   band: Claude's in an orange accent with "Claude Code" in bold, Cursor's in a gray accent with "Cursor CLI" in bold.
   - Current: both host panes look the same, apart from the step title naming the host.
   - Target: the band's accent colours come from named constants (one per host); text on each accent meets a contrast
     ratio of at least 4.5:1; the lines, focused chip, tray and preview keep their current order and keys.
   - Acceptance: a pilot test finds the band on each host pane with the host's accent colour and bold host name; a
     test computes each band's text-to-background contrast ratio and it is at least 4.5; the board widget order on
     both panes equals today's.

3. **An on/off toggle on both host panes replaces the yes/no gate**: each host pane has an on/off toggle that starts
   at what is wired now (on for ai-kit's entry, off for unset or foreign); on wires ai-kit's entry; off removes whatever
   entry is wired, so the host default shows.
   - Current: a yes/no gate per host; declining leaves any wired entry in place; a foreign entry can only be kept or
     replaced, never removed.
   - Target: confirming on Review with the toggle on wires ai-kit's entry (a foreign one is replaced only after
     today's replace confirmation); confirming with it off removes ai-kit's entry, or, for a foreign entry, first
     shows that entry, takes a backup of the host's config file into `paths.backups_dir`, asks a separate
     confirmation, and then removes only the `statusLine` key; off with nothing wired writes nothing. Every other
     key and byte of the host's config file stays as it was, and writes are atomic. Review states each host's outcome
     ("wire ai-kit", "remove ai-kit's", "remove the foreign entry, backed up", "unchanged"). Nothing is written before
     Review is confirmed.
   - Acceptance: scratch-HOME tests per host and starting state (unset, ai-kit's, foreign) with the toggle on and off:
     the host config afterwards has ai-kit's entry, no `statusLine`, or is byte-identical, as listed above; a foreign
     removal leaves a backup byte-identical to the file before the change and is refused when its confirmation is
     declined; every other top-level key is unchanged; a PTY run under `uv run` of `tools/setup.py install` turns
     Cursor off with ai-kit's entry wired and the scratch `cli-config.json` has no `statusLine` afterwards.
   - *Amended 2026-11-06 (owner decision, 30.1 D-06; the owner's words: "Keep current, Remove and show default,
     customize using aikit"; clarified the same day: "Remove and show default" means the default that Claude shows
     when it has no status line):* a host whose status line is **foreign** has three states instead of on/off,
     cycled with `o` (keep → remove → customize → keep): **keep current**, the start state, leaves the entry
     untouched and writes nothing to that host's file (no backup, no confirmation; the install continues);
     **remove** takes the backup, asks the default-No confirmation on Review, then removes only `statusLine` and
     writes no ai-kit line, so the host shows its own built-in default; **customize** takes the backup, asks the
     same confirmation, then writes ai-kit's entry with the arrangement the owner made on the unlocked board, which
     starts from ai-kit's default arrangement (accepting it unchanged is allowed). Review's outcomes for a foreign
     host: "keep its current status line; nothing written", "remove the foreign entry, backed up; <label> shows its
     own default", "replace the foreign entry with your ai-kit layout, backed up". Hosts with ai-kit's entry or no
     entry keep the on/off toggle above. Acceptance for a foreign start: keep leaves the host file byte-identical
     and takes no backup; remove and customize leave a backup byte-identical to the file before the change, then
     no `statusLine` (remove) or ai-kit's entry (customize), every other top-level key keeping its value; both are
     refused (file byte-identical) when the confirmation is declined, when the file cannot be parsed, or when the
     entry changed after approval.

4. **The board preview is a real render named for its host**: each host pane's preview runs that host's own renderer
   on that host's sample payload, its title names the host on screen, and the tray title drops "disabled".
   - Current: the preview is fixed inventory samples; its title reads "Claude Code" on Cursor's pane; the tray is
     titled "OFF — disabled (Space activates → its home line)".
   - Target: the preview shows the renderer's output (icons, colours, formats) for the board's current lines and
     on/off state, refreshed after each board change; when a render fails or exceeds 2 s, the preview shows the
     inventory samples with a visible "sample text, render unavailable" note; the title reads "live preview —
     <host label>" for the host on screen *(amended 2026-11-03, 30.2 D-08: "live preview — <host label> (sample
     data)", since the preview renders the host's sample payload; needs confirmation)*; the tray title is "OFF" plus its key hint, without "disabled".
   - Acceptance: with a fake renderer injected through the host's engine, the preview equals the fake's output and
     changes after a chip toggle; with a failing or slow fake, the fallback text and note appear; on Cursor's pane the
     preview title contains "Cursor CLI" and not "Claude Code"; no widget title contains "disabled".

5. **The config doctor opens from Done and returns there**: on Done, `d` opens the config doctor's screen inside the
   wizard, and Esc returns to Done; `ConfigDoctorApp` (`--config-doctor`) shows the same screen, so there is one
   implementation.
   - Current: the doctor is a separate App reached only by `setup.py --config-doctor`; the wizard never offers it.
   - Target: the doctor's table, detail panel and per-row confirm move into one screen class that both
     `ConfigDoctorApp` and the wizard push; the catalog and apply closure come from the existing
     `config_doctor_checks` engine through setup's injection, as today; Done's footer and help name the `d` key; after
     Esc, Done shows the same outcome as before.
   - Acceptance: a pilot test presses `d` on Done, finds the doctor screen with the fixture catalog's rows, presses Esc
     and is back on Done with the same outcome text; `setup.py --config-doctor` still opens the same screen class; a
     structural test finds exactly one class that composes the doctor table.

6. **Doctor applies never destroy a file and always back up first**: every config-doctor applier refuses a target
   file it cannot parse and backs the file up before any write.
   - Current: the Claude settings appliers replace an unparseable `settings.json` with `{}` plus their key; no applier
     takes a backup.
   - Target: an unparseable or non-object target returns `{"ok": False, "reason": …}` and the file stays
     byte-identical; before each non-dry write, the target is copied into `paths.backups_dir` (a missing target needs
     no backup) and the result names the backup path; the write itself stays atomic.
   - Acceptance: for each applier, a test with an unparseable target gets a refusal and an unchanged file; a test with
     a valid target finds a backup byte-identical to the file before the write and the new value in the target; a
     dry run writes neither.

7. **A doctor row detects and fixes the Playwright MCP browser path**: the config doctor gets a row for the Claude
   Playwright MCP plugin's browser that reports whether Playwright's default Chrome path exists, whether
   `env.PLAYWRIGHT_MCP_EXECUTABLE_PATH` is set in `~/.claude/settings.json` and whether that path exists, and offers an
   apply that sets it to the flatpak Chrome wrapper.
   - Current: no row; the plugin's default `chrome` channel fails on this machine.
   - Target: the row appears when the plugin is enabled; it reports "ok" when the default path exists or the variable
     names an existing executable, "problem" otherwise; its apply, offered only when the variable is unset or names a
     missing file and `/var/lib/flatpak/exports/bin/com.google.Chrome` exists, writes that path to
     `env.PLAYWRIGHT_MCP_EXECUTABLE_PATH` through the doctor's atomic JSON writer with R6's backup and refusal; the
     row's confidence label says that the variable reaching the MCP process and a headed launch are inferred, not
     verified.
   - Acceptance: scratch-HOME tests with a fake plugin listing, fake executables and synthetic `settings.json` files:
     default path present → ok; variable naming an existing file → ok; neither → problem with the apply offered;
     the apply adds only that key and keeps every other byte-equivalent JSON key; the wrapper missing → no apply; the
     label carries the inferred wording.

8. **The global-rules Review item stays on the new Review**: the `--with-global-rules` item from Phase 30 stays
   pre-checked on Review, with its diff per file, next to the per-card components and the per-host outcomes.
   - Current: Phase 30 adds the item to today's Review.
   - Target: the item renders and toggles as Phase 30 specified; unchecking it means the rewrite does not run.
   - Acceptance: a pilot test finds the item pre-checked with one diff per synthetic global file; unchecked, the
     commit callable receives no global-rules action.

9. **Tests, run and docs**: the wizard and doctor tests follow Phase 28's rules, the wizard is run for real, and the
   docs match.
   - Current: the README section "The install wizard" describes the old picks and summary screens.
   - Target: every new test uses a scratch HOME, no host CLI and the Phase 28 env baseline; the wizard is driven
     under `uv run` with a scratch HOME through cards, both host panes (toggle on and off), Review, Done and the
     doctor screen, and the run is recorded in the phase's verification; the README wizard section and
     `docs/wizard-redesign/mockup-textual.html` (or a note that it is superseded) describe the cards, the toggle, the
     real preview and the doctor key.
   - Acceptance: `make test` passes with no tripwire hit; the verification record holds the `uv run` screen captures;
     the README wizard section names the cards, the on/off toggle, the foreign-entry backup and the `d` key.

## Boundaries

**In scope:**
- Choose cards per kind, Review per card (R1).
- Host bands and accents on both panes (R2).
- The on/off toggle on both hosts; for a foreign entry, keep current, remove (host default) or customize, the last
  two with backup and confirmation (R3, amended 2026-11-06).
- The real-render board preview, its host-named title and the tray title (R4).
- The doctor screen shared by `ConfigDoctorApp` and the wizard, `d` on Done (R5).
- Refusal and backup for every doctor applier (R6).
- The Playwright MCP browser row and apply (R7).
- Keeping Phase 30's global-rules Review item (R8).
- Tests, the `uv run` check and docs (R9).

**Out of scope:**
- Cursor status-line parity: segment icons, a Cursor process-memory segment, Claude-style quota rendering and windows,
  the `alt_term_dimensions` `116×0` fix, Cursor-shaped inventory samples — Phase 30.2 (split 2026-11-03).
- Adding, removing or renaming components — Phases 31, 45, 48-49 and 52-53 change the component list after this.
- The doctor reachable from steps other than Done — owner choice: Done only, so doctor writes never interleave with
  a pending wizard commit.
- Playwright MCP on hosts other than Claude Code, or other browsers — the owner's problem is the Claude plugin on
  Bazzite.
- Overriding the plugin's MCP entry in `~/.claude.json` — a file Claude Code rewrites itself; rejected by the owner.
- Live checks that `env` reaches the MCP process and that a headed launch works — Phase 54 (FEAT-04).
- The Mermaid render test's browser cache — Phase 28 D-09 stays as written.

## Constraints

- `tools/wizard_app.py` and `tools/config_doctor_app.py` import nothing from `tools/setup.py`; data and callables
  arrive through their contexts (today's seam).
- Runtime paths stay stdlib-only; Textual is wizard-only behind the existing guard (AGENTS.md).
- Every config write is atomic through the existing helpers (`_atomic_write_json`,
  `config_doctor_appliers.atomic_write_json`).
- No test calls a host CLI or reads a real config; scratch HOME and the Phase 28 tripwire PATH apply.
- The preview render runs off the UI thread or within its 2 s bound, so a key press never waits on it.
