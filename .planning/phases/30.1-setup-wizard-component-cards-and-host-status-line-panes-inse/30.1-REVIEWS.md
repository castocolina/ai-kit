#### 30.1-01

##### Summary
The shared guarded-apply path addresses a real configuration-loss bug and sensibly reuses the existing atomic writers. Backup naming, collision handling and pruning are well specified. The main gap is end-to-end apply eligibility: adding a catalog predicate does not make the running doctor stop offering an already-completed fix. The Playwright predicate also contradicts one of its own acceptance cases.

##### Strengths
- **Fixes the actual destructive fallback.** Both Claude appliers currently substitute `{}` when parsing fails, then write it back (`tools/config_doctor_checks.py:198–204`, `:209–222`). Moving both behind parse-before-write protection addresses the root cause.
- **[ponytail] Reuses the existing persistence layer.** `atomic_write_json` already preserves target permissions and performs temporary-file, fsync and replace operations; `atomic_write_text` provides the corresponding surgical-text path (`tools/config_doctor_appliers.py:23–61`, `:109–142`). A shared guard around those writers is justified, not speculative abstraction.
- **Backup coverage includes important retention edges.** The planned fixed-clock collision and out-of-order timestamp tests protect against overwriting or pruning the newest backup (`.planning/phases/30.1-setup-wizard-component-cards-and-host-status-line-panes-inse/30.1-01-PLAN.md:140–141`).

##### Concerns
- **HIGH — Apply eligibility is not refreshed or enforced end to end.** The plan adds `apply_when` only to catalog evaluation, while the existing doctor success callback updates `current_display` but leaves `apply_eligible` unchanged (`tools/config_doctor_app.py:222–244`). Dispatch also checks only whether an applier exists, not its eligibility (`tools/config_doctor_checks.py:146–164`). Consequently, after fixing Playwright, the running screen can still offer and execute another apply. The planned applier checks wrapper availability but does not explicitly refuse replacing an already-valid browser override.  
  **Plan location:** `.planning/phases/30.1-setup-wizard-component-cards-and-host-status-line-panes-inse/30.1-01-PLAN.md:217–218`.

- **MEDIUM — The Playwright eligibility predicate contradicts the default-Chrome acceptance case.** The acceptance behavior requires “default path present → no apply,” but `_playwright_apply_when` is specified only as “variable unset or missing, and wrapper executable.” When both Chrome installations exist and the variable is unset, that predicate returns eligible despite the row already being healthy.  
  **Evidence:** `.planning/phases/30.1-setup-wizard-component-cards-and-host-status-line-panes-inse/30.1-01-PLAN.md:209`, `:218`.

- **MEDIUM — The new safety helper’s failure branches lack explicit tests.** Backup failure must prevent the write, and write failure must retain the backup, but the specified tests cover successful backups, malformed input, dry runs, collisions and concurrent edits—not injected backup/write failures. These are central guarantees of the new helper, even though the underlying writers already have cleanup handling (`tools/config_doctor_appliers.py:50–53`, `:131–134`).  
  **Plan location:** `.planning/phases/30.1-setup-wizard-component-cards-and-host-status-line-panes-inse/30.1-01-PLAN.md:111`, `:135–141`, `:173–176`.

##### Suggestions
- Revalidate Playwright applicability against the **freshly parsed file inside the applier**, and define how successful applies refresh the screen’s eligibility. Add a real-screen test: apply once, press `a` again, and verify no second apply is offered.
- Make the predicate explicitly exclude the healthy-default-Chrome case.
- Add failure-injection tests proving backup failure never reaches the writer and write failure preserves both the original target and recovery backup.
- **[ponytail] Keep `apply_target` authoritative.** Ignoring the argument solely because tests patch constants introduces an unnecessary exception to the existing dispatch contract. Patch the row’s target in tests instead (`tools/config_doctor_checks.py:149–164`; `.planning/phases/30.1-setup-wizard-component-cards-and-host-status-line-panes-inse/30.1-01-PLAN.md:218`).

##### Risk Assessment
**HIGH until the eligibility lifecycle is resolved.** The backup/refusal design is sound, but a stale action can still rewrite the newly configured browser preference. The remaining changes are localized.

#### 30.1-03

##### Summary
The tabs and real-render preview use the correct existing seams and preserve the locked interaction choices. However, the prescribed implementation contains two concrete state-management problems: cursor reconciliation can undo navigation, and preview generation changes happen too late to reject every stale result. Width refresh and worker-resource behavior also need more precise handling.

##### Strengths
- **[ponytail] Reuses the selection model.** `Selection` already provides `set_category`, cursor toggling and stable item order (`tools/setup.py:1536–1570`). Restricting operations to `KINDS` avoids accidentally changing the separate global-rules selection.
- **Reuses the real host renderer rather than creating another renderer.** `_engine_ns` already selects the host’s entry, sample payload and base configuration (`tools/setup.py:3399–3425`). `render_preview` already handles subprocess failures and temporary-resource cleanup (`tools/setup.py:378–406`).
- **Correctly isolates preview workers from commit workers.** Existing housekeeping and commit workers use the default group (`tools/wizard_app.py:1037`, `:1293`). Giving previews their own group avoids cancelling installation work (`.planning/phases/30.1-setup-wizard-component-cards-and-host-status-line-panes-inse/30.1-03-PLAN.md:125`).

##### Concerns
- **HIGH — Cursor reconciliation can undo every ↑/↓ move.** `_sync_kind_cursor` is specified to restore the remembered cursor—or the kind’s first item—at the top of every Choose render. The key handler saves remembered positions only when switching tabs, not when moving within a tab. Existing `on_key` immediately re-renders after a handled key (`tools/wizard_app.py:960–964`), so an ↑/↓ assignment can be replaced by the old remembered position before the user sees it.  
  **Plan location:** `.planning/phases/30.1-setup-wizard-component-cards-and-host-status-line-panes-inse/30.1-03-PLAN.md:170`, `:173`.

- **HIGH — Preview invalidation occurs too late and misses terminal states.** The sequence advances in `_kick_preview`, after the debounce, while `_apply_preview` checks only sequence, step and host. An old request finishing during the next debounce can therefore publish obsolete content. More seriously, the all-segments-off branch writes its message without explicitly invalidating the previous worker or timeout, allowing either to overwrite that message. The later toggle-off handoff has the same exposure unless invalidation is part of this seam.  
  **Plan locations:** `.planning/phases/30.1-setup-wizard-component-cards-and-host-status-line-panes-inse/30.1-03-PLAN.md:123–127`, `:211`; downstream handoff `.planning/phases/30.1-setup-wizard-component-cards-and-host-status-line-panes-inse/30.1-05-PLAN.md:162`.

- **MEDIUM — Width is part of the cache key, but resizing does not schedule a render.** The plan samples `content_size.width` only when `_schedule_preview` runs. Existing wizard rendering is initiated on mount and handled keys, with no resize handler (`tools/wizard_app.py:537–538`, `:943–964`). Thus resizing alone can leave output rendered for the old width; the initial measurement can also precede layout and use the arbitrary `100` fallback. This weakens D-11’s “what fits this window” guarantee.  
  **Plan location:** `.planning/phases/30.1-setup-wizard-component-cards-and-host-status-line-panes-inse/30.1-03-PLAN.md:123`.

- **MEDIUM — A display timeout does not bound outstanding render work.** The plan correctly acknowledges that cancelling a thread worker does not stop its execution, yet each debounced change can start another renderer. The real renderer can run for ten seconds (`tools/setup.py:392–395`); the two-second timer only changes displayed content. Repeated edits during a slow-render failure can accumulate threads/subprocesses and obsolete queued work.  
  **Plan location:** `.planning/phases/30.1-setup-wizard-component-cards-and-host-status-line-panes-inse/30.1-03-PLAN.md:95`, `:124–127`, `:246`.

##### Suggestions
- Preserve a valid active cursor during ordinary renders, or update the remembered position on every navigation change. Reconcile only when the active kind or selection actually changes.
- Invalidate the request generation **when the desired state changes**, before debounce or empty/off handling. Bind callbacks and deadlines to an immutable request identity; invalidate them on pane exit.
- Add tests that release an old renderer **before the replacement debounce fires**, and after all segments become off. Also fire an old timeout after leaving Arrange.
- Schedule width-dependent rendering after layout/resize, and test `pilot.resize_terminal` without an intervening keypress.
- Bound active renderer work and coalesce pending changes to the latest request; cancellation flags alone are insufficient.
- **[ponytail] Remove `_preview()` once its only caller is replaced.** It currently merely delegates to `_preview_lines` (`tools/wizard_app.py:456–457`, `:796–798`). Keep `_preview_lines`, which Review still uses (`tools/wizard_app.py:833–839`).

##### Risk Assessment
**HIGH.** The architectural choices are appropriate, but the current instructions can produce broken navigation and stale previews. These are implementation-contract corrections, not reasons to remove any locked feature.

##### Summary

##### Strengths

##### Concerns

- **HIGH — The approved-entry check occurs too early to protect the final mutation.**  
  [Plan line 100](.planning/phases/30.1-setup-wizard-component-cards-and-host-status-line-panes-inse/30.1-04-PLAN.md#L100) retains an outer `adopt_command` check before calling the persistence/removal paths. A foreign command changed **after the outer check** can therefore become the value subsequently accepted with `assume_overwrite=True`.
