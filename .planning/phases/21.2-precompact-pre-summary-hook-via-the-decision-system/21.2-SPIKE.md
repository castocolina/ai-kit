## S1 — Laya truncation and latency

**Run:** 2026-10-19 by plan 21.2-03 Task 2, via
`python3 .planning/phases/21.2-precompact-pre-summary-hook-via-the-decision-system/spike/s1_laya.py`
from the repo root with the output kept in `tmp/p212/s1.json`. Reproduced twice
with identical truncation bounds (latency varies by a few ms run to run).

measured: true (backend `laya`, endpoint `http://127.0.0.1:8010/v1/systemone`)

**Method:** the spike loads the repo client and the precompact core by path,
runs the core's `--probe` (a child env whose HOME and XDG roots sit under
`tmp/p212/s1/`, never the real user config), then per fixture bisects the
largest prefix length L in [100, 8000] whose Laya answer is not truncated
(`usage.truncated` truthy or `usage.state_tokens_dropped` positive means
truncated), POSTing the client's own `request_body` shape. State sizes are
recorded in `request_state_chars(build_request(...))` units — the same units
`fits()` and the client's laya `state_chars_limit` guard count. Three
deterministic fixtures of at least 10,000 characters each: `code` (Python-like
lines with brackets, quotes and symbols), `prose` (plain English),
`non_english` (Spanish with accents plus Japanese). All three truncated inside
the range, so each bound is an interior bisect result.

**Truncation bounds (largest non-truncating prefix and its state size):**

| fixture | prefix L (chars) | state_chars at L | truncation reached |
|---------|------------------|------------------|--------------------|
| code | 757 | 1179 | yes |
| prose | 1605 | 1975 | yes |
| non_english | 2523 | 5953 | yes |

**Latency (seconds):** probe p50 0.057 / max 0.063 (10 runs, 10 usable);
classify call p50 0.085 / p95 0.089 / max 0.089 (30 calls on a 1000-character
prose chunk through `core.classify_chunk`). The 1000-character fixture exceeds
the client's own 2000 laya guard, so every call is forced `needs_fallback`
(labeled 0/30) — the figure is still the real per-call cost: one client process
plus one POST, answered in ~85 ms. `GET /health` body verbatim:

```
{"status":"ok","loaded":["multilingual","english"],"revisions":{"english":"55cf4c4ebb4ebe31b2550e8bdf3bd21b99753851","multilingual":"55cf4c4ebb4ebe31b2550e8bdf3bd21b99753851"},"device":"cuda","device_is_preference":false,"checkpoint_devices":{"multilingual":"cuda","english":"cuda"},"cpu_fallbacks":{"multilingual":{"count":0,"last_reason":null},"english":{"count":0,"last_reason":null}},"idle_unload_seconds":600.0,"idle_seconds":0.0}
```

`usage` keys observed: `input_tokens`, `output_tokens`, `state_tokens`,
`state_tokens_dropped`, `truncated`, `truncated_questions`.

**Derived chunk constant:** smallest non-truncating state length = 1179 (the
code fixture); floor(0.8 x 1179) = 943; the smallest non-remote
`state_chars_limit` in the client TABLE is 2000 (laya).
`CHUNK_STATE_CHARS = min(943, 2000) = 943`. The floor rule does not trigger:
an empty-context request measures 370 state chars, and 943 >= 370 + 200.

classified per run = floor((CLASSIFY_SECONDS - probe p50) / call p50)
                 = floor((8.0 - 0.057) / 0.085) = 92

30 x call p95 = 2.67 s <= 9, so no long-transcript caveat applies beyond the
standing one: classification covers only the newest chunks of a long transcript
(MAX_CHUNKS caps the number, not the time).

**Caveat recorded:** during this session the Laya server answered with
inconsistent truncation flags for a short window right after being woken from
idle (a probe series reported an 8000-character prose prefix as non-truncating,
then the same request truncated again once warm). The bounds above were
taken warm and reproduce; a cold-server run must be repeated before its numbers
are trusted.

**Result: measured (D-03 satisfied; the constant comes from the measurement,
not the client guard).**

## S2 — Claude Code (SPEC R5 live check)

**Observe (a-e):**
- (a) whether `session_id` is identical across the PreCompact and the
  compact-SessionStart payloads;
- (b) whether the newest message is already in `transcript_path` at PreCompact
  time (write a unique marker as the last user turn, compact, inspect the file);
- (c) whether the injected marker is visible to the model after compaction, and
  where — **the R5 live check**;
- (d) the real `compact_boundary` field names in a fresh scratch session's
  transcript (never the real projects dir; fields are reverse-engineered until
  recorded here);
- (e) whether the per-hook `timeout` is honored.

**Steps:**
1. `export HOME="$PWD/tmp/p212/claude/home"`, `export CLAUDE_CONFIG_DIR="$PWD/tmp/p212/claude/config"`;
   create both. Set `AI_KIT_MEASURE_LOG="$PWD/tmp/p212/claude/measure.log"`.
2. Install the logging hooks only (baseline arm):
   wire `tools/hooks/claude_log_hook.py` — actually
   `python3 -S .planning/phases/21.2-precompact-pre-summary-hook-via-the-decision-system/measure/claude_log_hook.py` —
   as PreCompact (matchers `manual` and `auto`), PostCompact and
   SessionStart `compact` entries in the scratch settings.
3. Authenticate the host interactively (human, in the scratch HOME).
4. Open one scratch interactive Claude Code session, run three manual
   compactions (and auto-style ones where practicable) of a scripted short
   session; ask the model after each compaction to report the injected marker.
5. Read the measure log and the scratch transcript for (a), (b), (d); try a
   >timeout hook payload for (e).

**Pass/fail:** pass = (a) identical session ids, (c) the model reports the
marker, (b)/(d) recorded either way. If (a) differs: record it — a follow-up
plan changes the injector key to the `transcript_path` basename. If (c) fails:
that is a delivery-route gap; the close-out records `gap: ` for Claude.

**Result: pending (orchestrator)**
