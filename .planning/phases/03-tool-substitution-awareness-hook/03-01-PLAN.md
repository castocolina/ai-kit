<objective>
Build the shared, host-agnostic detection and message-composition core for the
tool-substitution briefing, the Claude Code `SessionStart` wrapper that emits
it, and the atomic append-if-absent installer wiring that registers that
wrapper in `~/.claude/settings.json`.

Purpose: ROADMAP Phase 3 success criteria 1, 2 and 3 — a Claude Code session
starts with an accurate, live-verified statement of which curated `rtk`
substitutions are genuinely active on this machine, degrading to a shorter
message rather than erroring when `rtk` is absent, hung, or unreadable. The
detection composition is D-06's (ai-kit's own curated pair list x binary
presence x `rtk init --show` hook-active parse), the delivery channel is
D-01's (`hookSpecificOutput.additionalContext`, never a `PreToolUse`
mechanism), the message is D-03/D-04/D-05's two compact parts, and the wiring
is D-02/D-08's separate append-if-absent array entry that never touches
`rtk`'s own registration. The new scripts live under `tools/hooks/` and stay
stdlib-only per D-07.

Output: a new `tools/hooks/` directory holding `detect.py` and
`claude_session_start.py`; `_read_json_checked()`, `_atomic_write_json()` and
`wire_hook_claude()` in `tools/setup.py`, wired in from the wizard's own commit
callback (`_make_wizard_commit`) where every other `settings.json` mutation
already lives; a new `tests/test_tool_substitution_hook.py` registered in both
explicit unittest module lists, with the new directory added to the
`py-compile` and `pyright` gates and its `py-compile` coverage asserted rather
than assumed.
</objective>

## Planner decisions recorded here (not silent)

1. **RESEARCH Open Question 1 is resolved in favour of RESEARCH's own
   recommendation.** `compose_message()` produces one host-agnostic string
   shared byte-for-byte by both wrappers, and no AI-CLI host product name
   appears in the message body. Rationale: the message's factual content —
   which curated substitutions are available and whether a rewrite is active —
   does not depend on which host-specific rtk subcommand is registered, so
   naming a host would add an asymmetry with no informational gain. Enforced by
   `TestCompose.test_message_is_host_agnostic`.

2. **The `rtk init --show` line `[ok] Cursor hook: registered in hooks.json` is
   deliberately NOT used as a detection signal**, even though it is present in
   the verified output. RESEARCH Assumption A3 flags its semantics as
   unverified — it may report file presence rather than entry-active state,
   which would OVERSTATE certainty. The single `Hook:` + `rtk hook` line
   (D-06's locked signal) is used for both hosts. The consequence is
   understating on a machine where rtk is wired for one host and not the other;
   understating is the correct failure direction under PROJECT.md's core value.

3. **`_write_json()` is not reused for this phase's new writes, and its
   pre-existing non-atomicity is not fixed here.** D-08 says to reuse the
   `_read_json`/`_write_json` primitives; RESEARCH Pitfall 1 found
   `_write_json` opens the target directly in `w` mode with no temp file, which
   contradicts AGENTS.md's atomic-write rule. This plan honours D-08's intent
   (reuse the established JSON helpers and their exact output shape) while
   correcting the mechanism: `_read_json` is reused verbatim, and
   `_atomic_write_json` is added alongside `_write_json` producing byte-for-byte
   the same output shape. `wire_statusline`/`unwire_statusline` are NOT
   retrofitted — they are outside this phase's literal scope (03-CONTEXT.md
   locks nothing about them) — so the pre-existing gap survives this phase and
   should not be mistaken for fixed. Recorded here so it is visible rather than
   silently perpetuated.

4. **Phase 2's `write_preserving_mode()` is adapted, not imported.** A module
   under `tools/` importing a package under `skills/` would invert this repo's
   layering (skills are standalone, portable Agent Skills). The adaptation also
   has to handle a case Phase 2's version does not: a target that does not exist
   yet, since `settings.json`/`hooks.json` may be absent on a fresh machine and
   `os.stat` on the target would raise. The docstring cites the origin file.

5. **Whole-file re-serialization is value-preserving, not byte-preserving, and
   that is the accepted contract for plain JSON.** PROJECT.md's byte-preservation
   requirement is scoped to JSONC surgical edits ("for JSONC surgical edits,
   preserves every other byte"); `settings.json` and `hooks.json` are plain
   JSON, and this is already how `wire_statusline` behaves today. The property
   asserted by tests is therefore value-identity of every untouched key, not
   byte-identity of the whole file.

6. **The ownership marker is the relative script-path fragment, not the install
   dir.** `unwire_statusline` matches on `install_dir in command`. This phase
   uses `CLAUDE_HOOK_MARKER` (`tools/hooks/claude_session_start.py`) instead, so
   an entry written by a previous install at a DIFFERENT install dir is still
   recognised as ai-kit's own — otherwise a moved install would both duplicate
   the entry on reinstall and orphan the old one on uninstall. The fragment is
   specific enough that no third-party command can collide with it: rtk's own
   registration is `rtk hook claude` under a different event entirely
   (`PreToolUse`, verified live at index 9 of 10).

7. **`pylint` and `vulture` scopes are deliberately NOT widened to
   `tools/hooks/`.** Both are pinned to a curated file list in
   `pyproject.toml`/`.pre-commit-config.yaml` whose thresholds were tuned for
   the status-line render path; widening them is a repo-wide gate change beyond
   this phase's scope. `ruff` (already matching `^(tools|tests)/.*\.py$`),
   `py-compile` and `pyright` do cover the new directory, which is the same
   coverage Phase 2's new package received.

8. **RESEARCH Pitfall 4 does not apply but is pinned anyway.** The known
   Claude Code bug where `hookSpecificOutput.additionalContext` is executed but
   never surfaced applies to hooks declared inside a PLUGIN's `hooks.json`.
   This phase wires exclusively into `~/.claude/settings.json`'s top-level
   `hooks.SessionStart` (D-08), matching the already-working GSD precedent
   scripts under `~/.claude/hooks/`. No task here may route the registration
   through `.claude-plugin/plugin.json` instead.

9. **Tests never read the ambient PATH.** Every detection test injects
   `search_path=`, and every subprocess test sets `PATH` to exactly its own
   scratch bin dir and re-invokes the wrapper through `sys.executable` rather
   than the PATH `python3`. Without this, the suite would pass on this dev box
   (where all five modern tools and rtk are installed) and behave differently
   inside `make e2e-docker`'s clean-room container, where none of them exist.

## Added in review round 1 (REVIEWS.md @ ceb37d2)

10. **`_read_json` is wrapped, not changed** (F1). The corruption path is real:
    `_read_json` returns `{}` for a missing file, a malformed file and a
    valid-JSON non-dict alike, so any caller that reads `{}` as "fresh file"
    will clobber an unparseable-but-recoverable config. The fix is a NEW
    three-state reader (`_read_json_checked`) plus a shared guard
    (`_load_hook_config`) that both hosts' wiring routes through — not an edit
    to `_read_json` itself. Rationale: `_read_json` has three pre-existing
    callers (`wire_statusline`, `unwire_statusline`, `detect_statusline`) whose
    behaviour is outside this phase's locked scope, and its docstring pins it to
    mirroring `install.sh`; changing its contract would silently change three
    other code paths and a shell mirror in a phase that decided nothing about
    them (ONESHOT-RULES Rule 4). This is the same correction shape as note 3
    (`_atomic_write_json` added ALONGSIDE `_write_json`), for the same reason.
    The pre-existing hazard therefore survives this phase for the statusline
    paths and should not be mistaken for repo-wide fixed — it is recorded here,
    visible, and is a clean follow-up.

11. **Hook wiring moved into the wizard's commit callback** (F4). The
    originally-planned call site was `cmd_install`'s post-wizard
    `if result is not None:` branch. That is abort-safe, but it would put two
    writers of `settings.json` in one install flow, since every existing
    settings mutation runs inside `_make_wizard_commit`'s `commit` closure —
    and `launch_wizard`'s own comment (tools/setup.py:2191-2194) records that
    the in-UI placement is deliberate so the Done screen reflects the actual
    result. The wiring therefore runs in that closure, after
    `apply_selection(...)` and OUTSIDE the `if adopt:` gate (the briefing is
    independent of the status-line adoption decision, per D-01/D-02). Two
    consequences are accepted deliberately: (a) the returned
    `{"ok", "adopt", "log"}` dict is NOT extended with a hook field, because
    rendering it would require a `wizard_app` UI change that belongs to Phase
    2's locked scope — the hook's one-line result reaches the user through the
    captured `log` that `launch_wizard` prints after the app exits, exactly as
    every other install diagnostic does; and (b) abort-safety is now structural
    (the closure runs only on Review-confirm) rather than conditional, and is
    pinned by `TestWiring.test_wizard_abort_leaves_settings_untouched`.

12. **The new `tools/setup.py` functions must fit pylint's defaults without a
    disable** (F6). `tools/setup.py` is inside both the `pylint` hook's
    `files:` regex and `[tool.vulture] paths`, and `[tool.pylint.design]` sets
    `max-locals=15`, `max-branches=12`, `max-returns=6`, `max-statements=50`.
    A `wire_hook_*` function that inlined its own read, three shape guards, the
    dry branch and the write would sit right at `max-returns`. Extracting
    `_load_hook_config` (shared by both hosts) is what keeps both wire functions
    and both unwire functions comfortably inside the budget while removing the
    duplication, and `uv run pylint tools/setup.py` is run as an explicit
    `<verify>` step rather than being left to `make validate` at the end of the
    phase. A blanket file-level disable is forbidden; if a localized
    per-function disable ever proves genuinely unavoidable it must carry a
    one-line reason comment, matching the existing precedent recorded in
    `pyproject.toml`'s `[tool.pylint.design]` comment.

## Added in review round 2 (REVIEWS.md @ a800399)

13. **The fresh-file mode is `0o600`, decided here rather than deferred to the
    executor — corrected in review round 3 from round 2's `0o644`.** Round 2
    chose `0o644` on the stated grounds that it was "the mode both hosts' own
    config files carry today". That premise was never measured, and it is
    false: `stat -c '%a' ~/.claude/settings.json ~/.cursor/hooks.json` returns
    `600` for both. This note is left here rather than quietly rewritten
    because the error is the exact class of error this phase exists to police —
    a plan asserting more certainty than it had earned, in the same document
    that forbids the shipped tool from doing so about `rtk`. The decision
    re-taken against the real observation: copy the umask (rejected — the
    `os.umask(0)`-then-restore dance is process-global and not thread-safe, and
    this code runs on a Textual worker thread inside the wizard's commit
    closure, where a concurrent file creation could land at the wrong mode);
    `0o644` (rejected — it diverges from the measured host convention and
    leaves a file that can later hold `env` blocks and API keys readable by
    every account on the machine, T-03-20); an explicit `0o600` (chosen —
    deterministic, thread-safe, matches what both hosts actually produce, and
    is the tighter option, so the failure direction of a wrong guess is a
    permission the user must loosen rather than one they never knew they had).
    The `os.chmod` is written even though `mkstemp` already yields `0o600`: the
    guarantee then belongs to this function and its test, not to a `tempfile`
    implementation detail. The existing-target path still copies the target's
    real mode, so ai-kit never changes a mode a user set deliberately. Pinned
    by `TestWiring.test_created_settings_file_is_mode_0600`.

14. **The wrapper's sibling-module import is function-scoped, and the previously
    cited precedent was misread.** Round 1's plan text pointed at
    `launch_wizard`'s `import wizard_app` as a bare-import-after-path-insert
    precedent without pinning the scope; that import is in fact INSIDE
    `launch_wizard` (tools/setup.py:2182, carrying
    `# pylint: disable=import-outside-toplevel`). At module level the same
    pattern is `E402`, since ruff covers `^(tools|tests)/.*\.py$` and
    `[tool.ruff.lint.per-file-ignores]` exempts `tests/*` only — so the round-1
    wording pointed an executor at a red `make validate` whose most obvious
    "fix" is a new per-file ignore, i.e. plan drift into repo-wide gate config.
    Both the `sys.path` insert and the `import detect` now live inside `main()`,
    a dedicated `<verify>` runs `ruff check` over the hook scripts, and
    `TestGateRegistration.test_hook_scripts_need_no_lint_suppression` asserts the
    per-file-ignores table never grew a hook-directory key.

15. **A malformed array ELEMENT is refused, not copied through.** The reviewer's
    suggested fix was `isinstance` guards at each walk site with foreign
    elements copied through untouched. This plan instead validates elements once
    in `_hook_entries_shape_ok`, called from `_load_hook_config`, and treats a
    violation exactly like every other foreign shape: a loud refusal that writes
    nothing. Two reasons for the deviation. First, consistency: a non-dict
    `hooks` and a non-list `SessionStart` already abort the write, and it would
    be incoherent for a malformed element one level deeper to be quietly
    tolerated in a file ai-kit then rewrites wholesale. Second, blast radius: a
    single central check means no downstream walker — two wire functions and two
    unwire functions across both plans — needs its own guard, so there is no
    site left where a future edit can reintroduce the crash. The refusal is
    loud (path AND reason on stderr), which is what keeps it from being the
    silent skip the reviewer rightly warned against.

16. **`wire_hook_claude` gained the Claude-dir gate rather than an explanation
