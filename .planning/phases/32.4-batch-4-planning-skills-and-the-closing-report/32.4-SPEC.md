## Requirements

1. **Goal-prompt wraps long lists and commands (DEF-03)**: a rule line built from a list (phases, plans, skills, gates, dependents) or from a command (the runner command) that would pass 200 characters is wrapped onto continuation sub-lines instead of refusing the render.
   - Current: such a line stays one line, and `check_text` refuses the file with "rule line over 200 characters".
   - Target: the line is split between list items or between command words onto three-space continuation sub-lines, each at most 200 characters; no list item or command word is cut or dropped; the render refuses only when the 60-line or 7,000-character cap is passed, and the refusal names the cap.
   - Acceptance: unit tests render a 40-phase work set, a 30-skill candidate list and a 300-character runner command; every item and word appears in order, no line passes 200 characters, and the render exits 0; a work set that passes 60 lines is still refused with the line-cap message.
   - *Amended 2026-11-13 (32.4 D-02):* the commands include each e2e command line: a long one wraps between command words, each piece keeping its code formatting, and a 300-character e2e command renders.

2. **Goal-prompt FLOW-09 rails**: every rendered rails section tells the run to ask the owner only for a locked-decision ambiguity, a package or security gate, or a call only human eyes can make (otherwise verify, decide and report); never to end a turn with a waiting message while independent work remains; and to give the local time, the running step and when it started in every progress or resume ping.
   - Current: DECISIONS says "Never pause for questions or UAT"; none of the three rails exists.
   - Target: each rail is a rule line in every family's rails (GSD, superpowers, free text) and survives every strategy block.
   - Acceptance: a doc-contract test per rail asserts its words in a rendered file for each family; the renders pass `check_text`.

3. **Owner run rules as optional answers**: the answers file can carry six optional fields — push after fold, turn cap, model split, review lens, per-phase end sequence and report language — and the rails reflect each one that is set.
   - Current: no field exists; the rails always say never push, always carry a turn cap and name no models, lens, phase end or language.
   - Target: push set → the rails say to fold and then push the working branch instead of every "never push" line; turn cap set to none → STOP IF and every `/goal` condition carry no turn cap; a model split → one rule names the planner and executor model and effort; a review lens → one rule gives it to the planner and reviewers and names its review skill; a per-phase end sequence → its steps appear in order; a report language → REPORT says to write the report in it while files stay in the project's language. A field that is absent leaves today's text. A wrong type is refused with the field's name, never its value.
   - Acceptance: one unit test per field (set and absent); a render with every field absent equals today's output apart from the R1 wrapping and the R2 rails; `_check_answers` rejects one wrong type per field; the SKILL.md documents the fields and says how they are filled without a fifth question.
