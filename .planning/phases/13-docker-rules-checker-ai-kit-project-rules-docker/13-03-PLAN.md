## Decisions this plan makes on the planner's authority

`13-CONTEXT.md` locks D-03 (dedicated local-dev filenames, not profiles), D-04 (the stack-aware
expansion) and D-05 (extend the existing shared catalog rather than hardcoding a third list), and
leaves "the exact shape of D-05's catalog extension" to Claude's discretion. These settle it:

- **D-D13 -- what a local-dev service IS (13-CONTEXT D-03).** Every service defined in a file
  returned by `discover_local_dev_compose_files(repo_root)` -- and no other service. A service
  defined only in the base compose file is NEVER evaluated for hot-reload, because the convention
  is about the local-dev definition and flagging a production definition for not hot-reloading
  inverts it. A repo with no local-dev compose file produces no hot-reload finding at all; that is
  a limit plan 13-04's `SKILL.md` states to the user, not a finding this plan invents.
- **D-D14 -- the convention, in three parts.** A local-dev service CONFORMS when all three hold:
    (i) it declares at least one BIND MOUNT (D-D17);
    (ii) it declares a `command:` or `entrypoint:` override (either scalar or sequence form);
    (iii) that override resolves to a recognized stack-appropriate hot-reload marker (D-D16).
  Clause (iii) is 13-CONTEXT D-04's expansion and the reason this plan exists as its own plan.
- **D-D15 -- THREE outcomes, and the third is the point.**
    1. All three clauses hold -> no finding.
    2. Clause (i) or clause (ii) fails -> `issue: "docker_hot_reload_convention_missing"`,
       `CRITICALITY_MEDIUM`, NOT advisory. This is ROADMAP SC4's literal case: the production image
       or entrypoint baked at build time. The summary names WHICH half is missing -- "no bind
       mount", "no command or entrypoint override", or both -- because the fix differs.
    3. Clauses (i) and (ii) hold but clause (iii) cannot be CONFIRMED ->
       `issue: "docker_hot_reload_tool_unrecognized"`, `CRITICALITY_ADVISORY`, `advisory: True`,
       plus a `reason` field carrying exactly one of:
         - `no_stack_detected` -- `detect_stacks(repo_root)` returned nothing, so no stack's
           convention applies;
         - `stack_without_baseline` -- a stack was detected but the shared catalog carries no
           hot-reload markers for it. This is the same explicit-known-gap treatment the arch
           sibling gives Rust/Go for architecture-fitness tooling, and it must name the stack;
         - `script_indirection` -- the override starts with a known script-runner prefix
           (`npm run`, `yarn`, `pnpm`, `bun run`, `make`), so the real command lives in
           `package.json`'s scripts or a Makefile and this skill does not follow it. The
           recommendation names the file to look in;
         - `command_not_matched` -- a stack with a baseline was detected and the command matched
           none of its markers;
         - `volumes_unreadable` -- the service's only candidate mount is an entry whose source the
           parser could not read (an interpolation), so "has a bind mount" is itself uncertain.
           This reason OUTRANKS outcome 2: it fires even when the override is ALSO missing, because
           an unreadable volume must never contribute to a confident convention-missing finding (see
           D-D17's mixed-state rule). In that combined case the recommendation states the missing
           override as a fact and the mount as unknown, in that order.
      The five reasons are mutually exclusive, and their EVALUATION ORDER is fixed so the same
      service always reports the same one: `volumes_unreadable` (D-D17's mixed-state precedence)
      -> `script_indirection` (the override starts with a known script-runner prefix, so no marker
      lookup can be meaningful) -> `no_stack_detected` (`detect_stacks` returned an empty set)
      -> `stack_without_baseline` (every detected stack's tuple is empty) -> `command_not_matched`
      (the fallthrough: a stack with markers was detected and none matched). Do NOT fold an empty
      stack set, or a stack with no markers, into `command_not_matched` -- those three say different
      things to the reader, and the last one implies a marker table was consulted that in fact was
      not.
      The recommendation for every reason says plainly that the mount and the override are present
      and that this skill could not confirm the command reloads on change. It must NOT say the
      service has no hot reload. The one exception is the mixed state D-D17 pins, where the mount is
      NOT known to be present: there the text states the missing override as a fact and the mount as
      unknown, and still does not claim the service has no hot reload.
  Rationale: this is the difference between a checker a user trusts and one they turn off. The
  per-stack marker list is hardcoded baseline knowledge that goes stale (see D-D16), and outcome 3
  is where that staleness surfaces honestly instead of becoming a confident false accusation.
- **D-D16 -- the shared catalog extension (13-CONTEXT D-05).** Add to
  `skills/_shared/ai_kit_rules_common/tool_catalog.py`, beside the six-category taxonomy and
  explicitly NOT part of it:
    - `HOT_RELOAD_TOOLS: dict[str, tuple[str, ...]]`, keyed by exactly the stack names
      `detect_stacks` can return (`python`, `node`, `java`, `rust`, `go`), each value a tuple of
      lowercase command MARKERS. Seed it with:
        - python: `--reload`, `--reload-dir`, `flask run`, `runserver`, `watchmedo`, `watchfiles`,
          `hupper`, `adev runserver`
        - node: `vite`, `webpack-dev-server`, `webpack serve`, `nodemon`, `next dev`, `nuxt dev`,
          `ng serve`, `react-scripts start`, `tsx watch`, `ts-node-dev`, `--watch`, `remix dev`,
          `astro dev`
        - go: `air`, `compiledaemon`, `realize`, `gow`, `reflex`, `fresh`
        - rust: `cargo watch`, `cargo-watch`, `bacon`, `dioxus serve`, `trunk serve`
        - java: `spring-boot:run`, `bootrun`, `quarkus:dev`, `quarkus dev`, `--continuous`
      Two transcription notes belong in the module as comments, because a later reader will
      otherwise "fix" them: `flask run` is listed WITHOUT requiring a debug flag on the command
      line, deliberately, because Flask's reloader is commonly enabled through `FLASK_DEBUG` in the
      environment -- the permissive direction here avoids a false "no hot reload" claim against a
      real Flask dev service, and the cost is only a missed advisory. And `--reload`/`--watch` are
      bare flags on purpose: they are the shared reload idiom across `uvicorn`, `gunicorn`,
      `node` and several others, and matching the flag rather than enumerating every server that
      accepts it is what keeps this table small enough to stay honest.
    - `HOT_RELOAD_BASELINE_GAPS: tuple[str, ...]` -- the stack names whose tuple is deliberately
      empty. Empty today, and it must stay a named constant anyway: it is the structure that lets a
      future stack be added as a stated gap rather than as a silent blank, and `resolve_hot_reload`
      reads it to distinguish `stack_without_baseline` from `command_not_matched`.
    - `SCRIPT_INDIRECTION_PREFIXES: tuple[str, ...]` -- `npm run`, `yarn`, `pnpm`, `bun run`,
      `make`. These are NOT hot-reload markers; they are the signal for D-D15's
      `script_indirection` reason.
    - `resolve_hot_reload(command_text, stacks) -> str | None` -- returns the matched marker, or
      `None`. Case-insensitive, whitespace-normalized, and TOKEN-BOUNDARY-AWARE on both ends in the
      spirit of `recipe_mentions_target`: `vite` must not match inside `invited` and `air` must not
      match inside `airflow`. Markers are scoped to the passed stacks -- a Node marker must NOT
      match for a repo where only Python was detected, which is the entire point of D-04's
      "stack-appropriate" wording. An empty `stacks` set resolves to `None` rather than matching
      everything.
      **Selection among multiple matches is a TOTAL ORDER, not "prefer the longest".** Collect every
      marker that matches, then pick the first under this key, in this order:
        (1) LONGEST marker text wins;
        (2) tie on length -> EARLIEST POSITION in its own stack's tuple wins;
        (3) still tied because the two markers came from DIFFERENT stacks -> the stack whose name
            sorts first (plain `sorted()` over the passed stack names) wins.
      Clause (2) is not hypothetical and clause (1) alone does not decide the seeded table: `nodemon`
      and `--watch` are both seven characters and both `node` markers, so `nodemon --watch src` is a
      length tie that iteration order alone would resolve arbitrarily -- which is exactly why the
      `LONGEST-MATCH-OK` criterion below asserts `nodemon`, and why that criterion was undefined
      before this rule existed. Clause (3) exists so a polyglot repo cannot return different answers
      on two runs over the same file: `stacks` arrives as a SET, whose iteration order is not
      guaranteed to be stable across processes, so any rule that stops at clause (2) is
      non-deterministic in precisely the repos D-04 cares most about. Implement the order explicitly
      (a sort key over `(-len(marker), stack_index, marker_index)` with `stack_index` taken from
      `sorted(stacks)`), never as "whatever the first loop finds".
  **Three prohibitions, each because the alternative is silent:** `HOT_RELOAD_TOOLS` must not be
  merged into `BASELINE_STACKS`; its markers must not be fed to `_derive_tool_category_index` or
  added to `TOOL_CATEGORY_INDEX`; and `resolve_tool_category` must keep answering `None` for them.
  A dev server is not a static analyzer, and teaching the pre-commit sibling's classifier otherwise
  would misclassify a real hook in a skill this plan never opens.
  **A fourth prohibition, about where marker TEXT may appear:** `hot_reload.py` must not contain a
  marker literal anywhere -- not in code, not in a docstring, not in an example. Every advisory or
  recommendation string that lists "the markers this skill knows for the detected stacks" BUILDS
  that list at runtime by joining from `HOT_RELOAD_TOOLS` for the stacks actually passed (and
  likewise for `SCRIPT_INDIRECTION_PREFIXES` when naming script-runner prefixes). Two reasons, and
  the second is the one that bites: a hardcoded example list is a fifth copy of knowledge D-05 gave
  one home, so it goes stale silently while the catalog is corrected; and the `NO-LOCAL-COPIES-OK`
  criterion inspects this module's own source for marker strings, so a docstring example would fail
  a criterion the behavior actually satisfies -- a false failure that invites an executor to weaken
  the check instead of the docstring. Runtime-joined text also gets the correction for free the day
  a marker is added.
  Stack attribution is REPO-WIDE: resolve against the union of all detected stacks. A compose
  service definition carries no language signal, and deriving one from an image name would be a
  guess. State the consequence in the SUMMARY and in plan 13-04's `SKILL.md`: in a polyglot repo a
  Node dev server satisfies a Python service's command line.
- **D-D17 -- bind-mount detection, with an unreadable third answer.** Read the service's `volumes:`
  sequence through the parser. An entry is:
    - a BIND MOUNT when it is a short-form `src:dst[:opts]` whose `src` begins with `.`, `..`, `/`
      or `~`, or a long-form mapping entry declaring `type: bind`;
    - a NAMED VOLUME (not a bind mount) when `src` contains no `/` and begins with none of those
      characters;
    - UNREADABLE when `src` contains an interpolation. An unreadable entry is NOT evidence of
      absence: if a service's only candidate mount is unreadable, the service goes to D-D15's
      outcome 3 with reason `volumes_unreadable`, never to outcome 2. Reporting "no bind mount"
      from a value the parser could not read is the same false-confidence failure D-D15 exists to
      avoid.
  Evaluate the bind-mount answer as a THREE-VALUED result -- `present` / `absent` / `unreadable` --
  before any branching, and resolve entries in that order of authority: one readable bind mount
  makes the answer `present` no matter how many unreadable entries sit beside it; with no readable
  bind mount, ANY unreadable entry makes the answer `unreadable`; only an all-readable,
  all-non-bind-mount volume list (or no `volumes:` key at all) makes it `absent`.
  **The MIXED state is pinned, because it is the one an implementation gets silently wrong.** When
  the bind answer is `unreadable` AND the override is missing, D-D15's outcome 3 still wins:
  `volumes_unreadable` takes precedence over the missing-override half, the finding stays ADVISORY,
  and the text names both facts in their correct epistemic status -- no `command:`/`entrypoint:`
  override was found (a fact this skill CAN assert), and the service's only candidate mount could
  not be read, so whether a bind mount exists is unknown. The prohibition is absolute in the other
  direction: an `unreadable` bind answer must NEVER produce `docker_hot_reload_convention_missing`,
  and no finding's summary may say "no bind mount" for a service whose volumes could not be read.
  Two invariants hold across all of this: one finding per service (D-D18) -- the mixed state does
  not emit two -- and outcome 2 is reachable only when BOTH the bind answer and the override answer
  are confidently known.
  An override is present when the service block declares `command:` or `entrypoint:` in either
  scalar or sequence form; the resolver is given the joined text either way. Unlike the bind answer,
  the override answer is two-valued: a key is declared or it is not, and that is directly readable.
- **D-D18 -- finding vocabulary.** ONE new category, `docker-hot-reload`, with the two issues named
  in D-D15. Fields are 13-01 D-D5's six, plus `service`, `compose_file`, and (on the advisory only)
  `reason`. **No finding carries `target`** (13-01 D-D3). One finding per (local-dev compose file,
  service); a service never produces both issues at once, since outcome 2 and outcome 3 are
  mutually exclusive branches of one evaluation.
