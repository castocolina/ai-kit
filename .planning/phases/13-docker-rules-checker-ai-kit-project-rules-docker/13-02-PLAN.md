## Decisions this plan makes on the planner's authority

`13-CONTEXT.md` locks D-01 (indentation-aware, stdlib-only, no YAML library), D-02 (no new
dependency) and D-06 (the healthcheck bounds and `depends_on` discipline accepted as ROADMAP writes
them), and explicitly leaves the "exact regex/indentation-tracking implementation" to Claude's
discretion. These settle that discretion once, so the executor implements one parser rather than
inventing one and plan 13-03 can build on it:

- **D-D6 -- compose-file discovery, from ONE pair of tuples.** `compose_parse.py` owns two
  module-level tuples, in candidate order:
    - `BASE_COMPOSE_FILENAMES = ("docker-compose.yml", "docker-compose.yaml", "compose.yml",
      "compose.yaml")`
    - `LOCAL_DEV_COMPOSE_FILENAMES = ("docker-compose.override.yml", "docker-compose.override.yaml",
      "docker-compose.local.yml", "docker-compose.local.yaml")` -- 13-CONTEXT D-03's dedicated
      file-name convention, defined here now so plan 13-03 consumes it rather than re-deriving it.
  `discover_compose_files(repo_root)` returns the existing ROOT-level files from both tuples, base
  first, in tuple order; `discover_local_dev_compose_files(repo_root)` returns the existing ones
  from the second tuple only (13-03's entry point). Both return absolute paths and never raise.
  Plan 13-01's applicability-gate clause (i) must be REPOINTED at these tuples rather than keeping
  its own copy -- one list, two readers. Root-scoped, matching 13-01 D-D4: no walk, no descending
  glob.
  This plan's two checks run against EVERY discovered compose file, base and local-dev alike: the
  healthcheck and `depends_on` conventions are not local-dev-specific, and a repo that puts its
  only service definitions in an override file must not escape them. Each finding names its file,
  so two services with the same name in two files stay distinguishable.
- **D-D7 -- the parser contract.** `compose_parse.py` exposes exactly these, and every one returns
  an empty/None result rather than raising for any input:
    - `iter_services(text)` -> yields `(service_name, service_block_text)` for every key directly
      under a top-level `services:` mapping.
    - `block_scalar(block_text, key)` -> the scalar value of `key:` at the block's own first nesting
      level, quotes stripped, or `None`.
    - `block_subblock(block_text, key)` -> the nested block text under `key:`, or `None`.
    - `block_sequence(block_text, key)` -> the items of a `key:` sequence in EITHER block form
      (`- item` lines) or flow form (`[a, b]`), quotes stripped, or `[]`.
    - `block_mapping_keys(block_text, key)` -> the key names of a `key:` mapping, in file order.
  Structural rules, pinned because this is the discretion 13-CONTEXT hands over:
    - Indentation is `len(line) - len(line.lstrip())` -- a count of leading whitespace CHARACTERS,
      via the shared `yaml_text.line_indent`. YAML forbids tab indentation, so a tab-indented file
      may be mis-attributed; that is a STATED limit (plan 13-04's `SKILL.md` says so) rather than a
      silent claim, and it must not crash.
    - A line is structural when it is neither blank nor a comment (first non-whitespace character
      `#`). Blank and comment lines never end a block and never set an indentation level.
    - `services:` is a top-level key at indent 0. The SERVICE indentation level is the indent of the
      first structural line inside the `services:` block; only lines at exactly that indent matching
      a `name:` header are service names. This is the whole reason a flat line-scan is insufficient
      (13-CONTEXT D-01): `healthcheck:` and `depends_on:` sit DEEPER than a service name and must
      never be mistaken for one.
    - A block owned by a key at indent `i` runs from the line after that key until the first
      structural line whose indent is <= `i`.
    - A `---` document separator at indent 0 is skipped as structural noise rather than treated as
      a key. A file with no `services:` key at all yields no services.
  Do NOT implement the whole of YAML. This is a convention checker reading a narrow, well-known
  document shape, and the honest statement of that scope belongs in the module docstring and in
  plan 13-04's `SKILL.md`.
- **D-D8 -- the shared `yaml_text.py` module.** `strip_yaml_quotes(value)` (a matched leading and
  trailing `'` or `"` pair removed, otherwise the value unchanged -- the exact rule
  `precommit_parse._strip_yaml_quotes` already implements), `line_indent(line)`, and
  `is_structural_line(line)`. It lives in `skills/_shared/` rather than inside this skill because
  Phase 14's `ai-kit-project-rules-cicd` parses CI YAML the same stdlib way and will reach for the
  same three primitives -- the same convergence argument `makefile_parse.py` records for its own
  move. `precommit_parse._strip_yaml_quotes` is NOT repointed: Phase 11 closed that file, and
  repointing it is a separate, reversible follow-up rather than this plan's business. That is not a
  silent duplication -- `criticality.py` already records exactly this arrangement for `rules.py`,
  and the same mitigation applies: a drift guard in `tests/test_ai_kit_rules_common.py` pins the two
  implementations against each other over the same input set, so they cannot disagree unnoticed.
- **D-D9 -- durations and the three bounds (ROADMAP SC2).**
    - `parse_duration(value) -> float | None` accepts a Go-style duration of one or more
      `<number><unit>` pairs with units `ns`, `us`, `ms`, `s`, `m`, `h` (`1m30s` is 90.0), and a
      bare number as seconds. It returns `None` -- never a guess and never `0` -- for anything else,
      including an interpolated `${VAR}`, an empty value, or a unit it does not know.
    - ONE module-level bounds table, in this order so output is deterministic:
      `timeout` 2.0s, `start_period` 10.0s, `interval` 5.0s. The numbers come straight from ROADMAP
      SC2 and the design spec; do not re-derive them and do not add a fourth key.
    - A key DECLARED with a parseable value STRICTLY GREATER than its bound is a finding. Equal to
      the bound is conforming -- SC2 says "exceeding", and the paired fixture uses exactly
      2s/10s/5s so an off-by-one `>=` implementation fails there rather than in production.
    - A key declared with an UNPARSEABLE value gets an ADVISORY finding naming the raw value.
      Silence is the wrong answer: an unreadable `timeout` is precisely where a real violation
      hides, and reporting the service as conforming would be a claim built on a value never read.
    - A key that is ABSENT gets nothing. Compose's own defaults (30s interval, 30s timeout) would
      exceed two of these bounds, but SC2 and D-06 scope this check to DECLARED values. That gap is
      real and must be STATED in plan 13-04's `SKILL.md` as a known limit, not quietly closed here
      and not quietly forgotten.
    - A service with no `healthcheck:` block, or one declaring `disable: true`, gets nothing. Same
      treatment: a stated limit, since "every service must have a healthcheck" appears in no source
      artifact for this phase.
- **D-D10 -- `depends_on` forms (ROADMAP SC3).** For each dependency a service declares:
    - Block sequence (`- db` lines) or flow sequence (`[db, cache]`): BARE ORDERING -- flag,
      `CRITICALITY_HIGH`, not advisory.
    - Mapping entry with `condition: service_healthy`: conforming, no finding.
    - Mapping entry with `condition: service_started`, OR a mapping entry with NO `condition:` key
      at all: bare ordering written long -- flag, `CRITICALITY_HIGH`, with its own issue name so a
      reader can tell the long form from the short one. The no-condition case is not an edge case:
      Compose's own default IS `service_started`, so an implementation that treats "mapping form"
      as conforming-by-construction misses the form real repos most often write.
    - Mapping entry with `condition: service_completed_successfully`: ADVISORY
      (`advisory: True`, `CRITICALITY_ADVISORY`). This is the legitimate form for a one-shot
      init/migration container, and flagging it as a plain violation would train the reader to
      ignore the whole category. The recommendation says so in one sentence.
    - Mapping entry with an unreadable condition (an interpolation, an unknown token): ADVISORY,
      naming the raw value -- same reasoning as D-D9's unreadable case.
  `CRITICALITY_HIGH` rather than MEDIUM on purpose, and it is the only HIGH band in this skill: a
  bare `depends_on` produces a real startup race, which is the concrete failure the convention
  exists to prevent, whereas a missing Makefile target or runbook is a convention gap in a workflow
  that still runs.
- **D-D11 -- finding vocabulary for this plan.** Two new categories; neither reuses 13-01's and
  neither is reused by 13-03:
    - `category: "docker-healthcheck-bounds"` with issues `docker_healthcheck_out_of_bounds`
      (`CRITICALITY_MEDIUM`) and `docker_healthcheck_unreadable` (`CRITICALITY_ADVISORY`,
      `advisory: True`, plus a `reason` field naming the case).
    - `category: "docker-depends-on"` with issues `docker_depends_on_bare` (HIGH),
      `docker_depends_on_weak_condition` (HIGH), `docker_depends_on_completion_condition`
      (ADVISORY + `advisory: True`) and `docker_depends_on_unreadable` (ADVISORY + `advisory: True`
      + `reason`).
  One finding per (compose file, service, offending key) for healthchecks and per (compose file,
  service, dependency) for `depends_on`, so a service with three bad timings produces three
  findings each naming its own key and bound. **No finding in this plan carries `target`** --
  13-01 D-D3's prohibition side. The service name, the compose file's repo-relative path, the key
  or dependency name, the declared value and the bound travel in `summary`/`recommendation` prose
  and in non-identifying data fields (`service`, `compose_file`, plus `key`/`declared`/`bound` or
  `depends_on`), the shape `check_precommit_prepush_split` already uses for
  `slow_hooks_missing_push_stage`.

| target repo `docker-compose.yml` -> the new parser | An arbitrary repo's compose file is untrusted text fed to a hand-written text parser.
