## Decisions this plan makes on the planner's authority

- **D-D19 -- the limits are a required section, not editorial taste.** Each traces to a
  decision an earlier plan made deliberately, and each changes how a reader interprets a report:
    1. **Root-scoped applicability** (13-01 D-D4). The skill evaluates a repo only when root-level
       Docker evidence exists, and reports nothing otherwise. A repo whose Docker assets live only
       below the root -- ai-kit's own CI-only `tests/e2e/docker/Dockerfile` is the live example --
       is not evaluated at all.
    2. **A text parser, not a YAML implementation** (13-02 D-D7, 13-CONTEXT D-01/D-02). Compose
       files are read with an indentation-aware stdlib scan and no YAML library. A tab-indented
       file (invalid YAML) may be mis-attributed rather than rejected.
    3. **Healthcheck bounds cover DECLARED values only** (13-02 D-D9). An absent `interval`
       inherits Compose's own 30s default, which exceeds the 5s bound, and is NOT flagged; a
       service with no `healthcheck:` block at all is NOT flagged. This is the limit most likely to
       be read as a bug by a user who knows Compose, so it must be stated rather than discovered.
    4. **Repo-wide stack attribution** (13-03 D-D16). Hot-reload commands are matched against the
       union of every stack detected at the repo root, because a compose service carries no
       language signal. In a polyglot repo a Node dev server therefore satisfies a Python service's
       command line.
    5. **A hardcoded, staleable hot-reload baseline** (13-03 D-D16/D-D15). The per-stack marker
       table is knowledge that ages, which is exactly why an unrecognized command is an ADVISORY
       with a reason rather than a defect. Say both halves: a tool this skill has not heard of will
       produce an advisory, and that advisory is not an accusation.
    6. **No local-dev compose file means no hot-reload finding** (13-03 D-D13). The check's subject
       is the local-dev service definition; a repo that does local development from its base
       compose file is not evaluated for it.
    7. **Same-line flow-mapping bodies are unread** (13-02 D-D7), CONDITIONAL on what 13-02 actually
       shipped. `healthcheck: {interval: 30s}` and `depends_on: {db: {condition: service_healthy}}`
       are valid Compose the block-indent parser does not read, so such a service is neither flagged
       nor confirmed conforming. Read `13-02-SUMMARY.md` to decide: if it records the limit as
       surviving into the shipped parser (it is required to record it either way), this is limit 7
       and it is written like the other six -- a standalone sentence naming the forms and the
       consequence. If that SUMMARY instead records that the gap was closed, do NOT invent the
       limit; note the reconciliation in `13-04-SUMMARY.md` and keep six.
  The count is therefore SIX REQUIRED plus one conditional, and the rule generalizes: a stated limit
  that an earlier plan's SUMMARY records and this document omits is a defect, whether or not it
  appears in this plan's list. This plan was written before those plans executed and cannot outrank
  what they shipped.
  A judge optimizing for concision will read these as hedging. They are PROJECT.md's core value
  expressed in the document, and removing one makes the skill claim more certainty than it has.
  One note on how they are defended: `SKILL-SHAPE-OK`'s keyword check is NECESSARY BUT NOT
  SUFFICIENT. It greps for one token per limit, so it proves a limit was not deleted and nothing
  more -- a clause softened until it no longer states anything a user would act on still carries its
  keyword and still passes. The verbatim-quote backstop in `13-04-SUMMARY.md` is the real control
  and must not be swapped for a paraphrase, a bullet summary, or an assertion that the limits "are
  still present".
- **D-D20 -- the name is confirmed, never changed by this plan.** `/naming-analyzer` runs because
  the project's skill-authoring pipeline says it does, and its verdict is recorded in full. But
  `ai-kit-project-rules-docker` is fixed by `REQUIREMENTS.md`'s `REQ-rules-docker`, by ROADMAP
