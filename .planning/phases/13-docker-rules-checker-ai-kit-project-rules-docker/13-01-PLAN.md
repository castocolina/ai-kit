## Decisions this plan makes on the planner's authority

`13-CONTEXT.md` locks D-01/D-02 (stdlib-only indentation-aware compose parsing -- plan 13-02's
subject), D-03/D-04/D-05 (local-dev identification and the stack-aware hot-reload check -- plan
13-03's subject), and D-06 (the target family, healthcheck bounds, `depends_on` discipline and
runbook check accepted as written). It leaves this plan's own mechanics open. They are settled here
so the executor implements one rule rather than inventing one, and so the later plans agree:

- **D-D1 -- the eight-target family is a FIXED NAME LIST, matched exactly after normalization.**
  Normalize a Makefile target name by casefolding it and folding `_` to `-` (the same normalization
  the arch sibling uses), then require the normalized name to EQUAL one of the eight literals:
  `docker-up`, `docker-health`, `docker-stop`, `docker-clean`, `docker-prune`, `docker-events-up`,
  `docker-events-monitor`, `docker-events-test`. So `DOCKER_UP` counts as `docker-up`;
  `docker-start`, `docker-run` and `up` do not count as anything. Rationale: ROADMAP SC1 names the
  eight literally and the convention IS those names -- a shape rule here would silently accept a
  repo that renamed half the family, which is the false-negative direction. Keep the eight in ONE
  module-level tuple in declaration order; that tuple is what the finding text, the tests and plan
  13-04's `SKILL.md` all read.
  Do NOT reuse or import the Makefile sibling's `_DOCKER_UP_SHAPE_RE`: it answers a different
  question, it is that skill's module-private name, and reaching for it would be the cross-skill
  import `constraints.md` forbids.
- **D-D2 -- one finding PER missing target.** ROADMAP SC1 says "flagged by name for each missing
  target". Emit one finding per missing name rather than one aggregate finding carrying a list:
  the aggregate form gives the remediate payload a single entry for eight distinct pieces of work,
  and Phase 15's cross-domain ordering then treats eight missing targets as one item. Order the
  findings by the family tuple's own order, not alphabetically, so two runs over the same repo
  produce byte-identical output.
- **D-D3 -- identifier discipline, pinned in BOTH directions.** `build_remediation` at
  `remediation.py:88` reads `finding.get("target", finding.get("category"))`, so `target` WINS when
  present:
    - Target-family findings **carry** `target: "<the missing target name>"`. The value is a real
      Makefile target name -- exactly what the key means in the Makefile sibling
      (`makefile_checker.py:463`) -- and it is what makes N missing targets produce N distinct
      remediate ids. This is the one place in this skill where that key is right.
    - The runbook finding **must not** carry `target`. It is about a file, not a target; a `target`
      key there would point its remediate id at a Makefile target name that has nothing to do with
      it.
    - Every finding plans 13-02 and 13-03 add is likewise PROHIBITED from carrying `target` (they
      are about compose services, not Makefile targets). Those findings name their service in
      `summary`/`recommendation` prose and may carry a non-identifying `service` data field, the
      shape `check_precommit_prepush_split` already uses for
      `slow_hooks_missing_push_stage`. Two findings in the same category then share one remediate
      `id`, which the shared builder explicitly documents as acceptable (`id` is "a human-readable
      LABEL, not a unique key"); the discriminator travels in `summary`, which the builder copies
      verbatim into the payload.
- **D-D4 -- applicability gate, evaluated FIRST and short-circuiting.** Before any check runs,
  decide whether the target repo uses Docker at all. It does when ANY of these holds at the
  REPOSITORY ROOT (never deeper -- see the rationale below):
    (i) a root file named `docker-compose.yml`, `docker-compose.yaml`, `compose.yml`,
        `compose.yaml`, `docker-compose.override.yml`, `docker-compose.override.yaml`,
        `docker-compose.local.yml` or `docker-compose.local.yaml`;
    (ii) a root file whose name is `Dockerfile` or begins with `Dockerfile.`;
    (iii) a root directory named `docker`;
    (iv) the root `Makefile` declaring at least one target whose D-D1-normalized name is `docker`
         or starts with `docker-`.
  If none holds, `check` returns an EMPTY finding list and nothing else runs.
  Rationale, and it is the load-bearing decision of this plan: 13-CONTEXT's scouting confirms
  ai-kit's own repo has no local-dev Docker setup, so without this gate the very first invocation
  a developer makes -- against this repo -- returns eight missing targets and a missing runbook for
  a repo that has no containers to run. Two edges must both hold, and both have a live example in
  this repository: ai-kit's `tests/e2e/docker/Dockerfile` is a NESTED, CI-only image and must NOT
  trip the gate (which is why the evidence is root-scoped), and ai-kit's `e2e-docker` target is
  docker-SUFFIXED and must NOT trip clause (iv) (which is why clause (iv) is a prefix rule, not a
  substring rule). Both are pinned as acceptance criteria rather than left to the implementer's
  taste.
  The gate's cost is a real, stated limit rather than a hidden one: a repo whose local-dev Docker
  assets live entirely below the root is not evaluated at all. Plan 13-04's `SKILL.md` states that
  limit to the user.
- **D-D5 -- finding vocabulary, pinned.** Two categories in this plan, and no later plan reuses
  either:
    - `category: "docker-target-family"`, `issue: "docker_target_missing"`, `CRITICALITY_MEDIUM`,
      plus `target`.
    - `category: "docker-local-runbook"`, `issue: "docker_runbook_missing"`, `CRITICALITY_MEDIUM`.
  Every finding carries `category`, `issue`, `criticality`, `summary`, `recommendation`,
  `needs_research` -- `recommendation` never `None` in this plan, `needs_research` always `False`
  (this skill has no research surface, D-D12), and `summary` equal to the recommendation. Both
  bands are MEDIUM because both are convention gaps in a workflow that still runs; the HIGH band is
  reserved for plan 13-02's `depends_on` finding, where the convention's absence causes a real
  startup race.
  The runbook recommendation must name what the runbook is FOR, not merely that it is missing --
  the design spec pins the content (how an agent interacts with the containers, which networks and
  secrets are required, how to copy `.env` files into a new worktree, and whether a new worktree
  needs fresh containers or can reuse a sibling worktree's). A recommendation that says only
  "create `docker/local/README.md`" hands the reader an empty file to create.
- **D-D12 -- no research step, no cache, two subcommands.** The design spec's
  `ai-kit-project-rules-docker` section assigns hardcoded knowledge and no research dispatch. Do
  NOT port `cache-update`, `stack_cache.py`, `tooling_payload.py` or a cache namespace into this
  skill. `check` and `remediate` are the whole CLI surface, and an unknown subcommand keeps the
  siblings' stderr line and return code 2.
