## Decisions this plan makes on the planner's authority

`12-CONTEXT.md` locks D-01/D-02 (the AST-only scope, plan 12-02's subject) and D-03 (the five
ROADMAP success criteria accepted as written). It leaves this plan's whole subject -- what counts
as an `arch-test`-SHAPED target, what counts as CHAINED, and the finding vocabulary -- entirely
open. These are settled here so the executor implements one rule rather than inventing one, and so
plan 12-02 and the tests agree with each other:

- **D-A1 -- `arch-test`-SHAPED is a naming RULE, not a literal.** Normalize a target name by
  casefolding it and folding `_` to `-`. It is arch-test-shaped when the normalized name fully
  matches either
  `^(arch|architecture)(-(test|tests|check|checks|lint|fitness|rules))?$` or
  `^(test|check|lint)-(arch|architecture)(-(test|tests|check|checks))?$`.
  So `arch-test`, `arch_test`, `arch`, `arch-check`, `architecture-test`, `test-arch` and
  `check-architecture` all qualify; `archive`, `arch-docs` and `architecture-diagrams` do not.
  Rationale: ROADMAP SC2 says "no `arch-test`-SHAPED target", and a single-literal implementation
  would emit a false missing-target finding against every repo that spells its target differently
  -- the most common way a form-only checker becomes noise its user turns off. Anchor the match
  fully; an unanchored pattern would accept `archive` through the `arch` alternative and make the
  rule silently wrong in the direction that produces false NEGATIVES. Choose ONE anchoring
  mechanism and record which in the SUMMARY, because Task 2's non-vacuity mutation has to un-anchor
  whichever one you chose: either `re.fullmatch` with NO `$` in the pattern, or `re.match` with an
  explicit trailing `$`. Do NOT combine `re.fullmatch` with a trailing `$` -- belt-and-braces here
  is not free, because it makes the obvious mutation (drop the `$`) a no-op that appears to confirm
  non-vacuity while confirming nothing, which is exactly the trap Task 2's protocol is written
  around.
  When several targets qualify, evaluate the FIRST in Makefile declaration order and name it in
  every downstream finding, so a repo with both `arch` and `arch-test` gets one coherent report
  rather than two competing ones. Declaration order comes from the shared
  `parse_makefile_targets_ordered` this plan adds -- never from a header scan written inside this
  skill, which would be the private re-implementation the shared module exists to prevent, and
  never from iterating `parse_makefile_targets`, which returns a set and therefore has no order to
  iterate.
- **D-A2 -- CHAINED means reachable from `test`, by any of three real mechanisms.** Given the
  arch-test-shaped target `T` found by D-A1, chaining is satisfied when ANY holds:
  (i) `T` is a direct prerequisite of `test` (`parse_makefile_prerequisites(path, "test")`);
  (ii) `T` is reachable from `test` through the prerequisite graph -- walk prerequisites
  breadth-first from `test`, carrying a visited set, a depth bound of 8 AND a breadth bound of 512
  visited targets, so a repo whose `test` chains through an intermediate aggregate
  (`test: test-all`, `test-all: … arch-test`) is correctly considered chained and neither a
  self-referential/mutually-referential Makefile nor a bushy one can hang the checker. Depth alone
  is not a bound: a generated Makefile can put tens of thousands of distinct prerequisites within
  two hops of `test`, and each one costs a `parse_makefile_prerequisites` re-read of the whole
  file. When either bound is reached before `T` is found, STOP the walk and fall through to clause
  (iii) rather than concluding anything from the truncation -- and if clause (iii) also does not
  hold, the chaining finding fires, which is the honest answer for a graph this checker could not
  finish reading. Record the two bounds in the SUMMARY;
  (iii) `test`'s own recipe invokes `T` by name, checked with the shared
  `recipe_mentions_target(parse_makefile_recipe(path, "test"), T)` -- a `$(MAKE) arch-test` recipe
  line is a real chain and the shared helper's both-ends token boundary is what stops
  `arch-test-integration` from satisfying it.
  If no `test` target exists at all, chaining is UNSATISFIED and the recommendation says which of
  the two things is missing (there is no `test` aggregate to chain into) rather than implying the
  prerequisite list merely omits it.
- **D-A3 -- finding vocabulary, pinned.** Two DISTINCT categories, not one category with two
  issues, because ROADMAP SC2 requires the chaining finding to be distinguishable from the
  existence finding and because `build_remediation` derives each `remediate` entry's `id` from
  `finding.get("target", finding.get("category"))` -- one shared category would give the two
  findings the same `id` in the hand-off payload:
    - `category: "arch-test-target"`, `issue: "arch_test_target_missing"`, `CRITICALITY_HIGH`.
    - `category: "arch-test-chaining"`, `issue: "arch_test_not_chained"`, `CRITICALITY_HIGH`.
  The field set is EXACTLY `{category, issue, criticality, summary, recommendation,
  needs_research}` -- `recommendation` never `None` in this plan, `needs_research: False`, and
  `summary` equal to the recommendation. That is the field set the shared structural branch reads.
  Plan 12-02 adds `category: "arch-test-ast-only"` (plus the `advisory` and `reason` fields its
  D-A9 pins) and reuses neither of these two categories.

  **A `target` key is PROHIBITED on every finding this skill emits -- not merely omitted from the
  list above.** `build_remediation` at `remediation.py:86` reads
  `finding.get("target", finding.get("category"))`, so `target` WINS over `category` whenever it is
  present, and the Makefile sibling's findings really do carry it (`makefile_checker.py:463`). This
  skill's findings are all ABOUT a Makefile target, so copying the sibling's field onto them is the
  natural mistake: both arch findings would then derive the same remediate `id` from the same
  target name -- defeating the very reason D-A3 pins two categories -- and would additionally
  collide with an unrelated `makefile` finding about a same-named target in the single merged list
  Phase 15 reads. Name the target inside `summary`/`recommendation` prose instead, where it is
  readable and load-bearing for nothing. The same prohibition binds plan 12-02's third category.
  Chaining is `CRITICALITY_HIGH` rather than something softer on purpose: an arch-test target that
  exists but is never reached is strictly worse than an absent one, because the repo looks covered
  and is not.
- **D-A4 -- evaluation gate: downstream checks require the target.** The chaining check runs ONLY
  when D-A1 found a target. A repo with no arch-test-shaped target therefore produces EXACTLY ONE
  finding. Rationale: reporting "no arch-test target" and "arch-test not chained" about the same
  absence is a cascade that makes a report look three times worse than the single fact behind it.

  The gate has two sides, and plan 12-02 adds something to EACH -- state this precisely, because
  saying "12-02's two additions sit behind the gate" is wrong in a way that would hide ROADMAP SC4:
  - **Target FOUND branch:** 12-02's AST-only check (ROADMAP SC3) is a new, third FINDING and runs
    only here, beside the chaining check. Structure the aggregator now so 12-02 extends this
    branch by appending a call, never by adding an ungated top-level call.
  - **Target MISSING branch:** 12-02's per-stack canonical-tool text (ROADMAP SC4) attaches to the
    existence finding, which by construction exists only here. It is extra RECOMMENDATION TEXT, not
    a finding, so the "exactly one finding" property above is unchanged by it. Gating it on
    target-found would make it unreachable and would silently drop SC4 entirely.
- **D-A5 -- report key and remediation.** `check(repo_root)` returns `{"arch": [...]}` sorted by
  `criticality` ascending, and the SORT is `cli.py`'s job exactly as it is in both siblings.
  `remediate(repo_root)` returns `build_remediation(check(repo_root))`. `"arch"` is appended to the
  shared `STRUCTURAL_KINDS`; nothing else in that module changes.
- **D-A6 -- no research step, no cache, two subcommands.** The design spec's
  `ai-kit-project-rules-arch` section gives this skill HARDCODED baseline knowledge and no
  research dispatch -- unlike the Phase 10 and Phase 11 siblings, whose per-stack tooling genuinely
  goes stale. Do NOT port `cache-update`, `stack_cache.py`, `tooling_payload.py` or a cache
  namespace into this skill. `check` and `remediate` are the whole CLI surface, and an unknown
  subcommand keeps the siblings' stderr line and return code 2.
