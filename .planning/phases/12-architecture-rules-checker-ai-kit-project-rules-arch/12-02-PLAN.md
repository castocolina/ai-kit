## A live-verified correction to 12-CONTEXT D-01's scouting claim

D-01's DECISION -- the AST-only check is target-aware rather than a file-level blanket scan -- is
locked and is implemented here faithfully. D-01's supporting SCOUTING CLAIM is not accurate against
the live tree, and this plan records the correction rather than quietly designing around it.

D-01 states that `tests/test_arch.py` loads `tools/setup.py` "for incidental inventory-test
helpers, while its actual architecture-fitness checks ... parse `tools/status-line.py` -- the real
checked target -- via pure `ast.parse`, never importing it." The first half is correct. The second
half is not: `TestSegmentInventory._sl` at lines 605-611 loads `tools/status-line.py` itself
through `spec_from_file_location` + `exec_module`, in the same file, for the segment-inventory
tests. The architecture-fitness METHODS are AST-only; the FILE is not.

Three consequences, all binding on this plan:

1. **D-01 is still the right decision, and target-awareness still buys something real.** Without
   it, `tools/setup.py` would produce a finding too, and the report would name the wrong module.
   With it, the finding (if any) names precisely the module that is both parsed and executed.
2. **A faithful implementation DOES flag ai-kit's own repository**, at `arch-test-ast-only`. That
   is a TRUE statement about this repo, discovered by live verification, and it is disclosed to uz
   (Task 3's human-check) rather than suppressed. Phase 10 and Phase 11 each made the same kind of
   disclosure about this repo being a live target for its own checker.
3. **ROADMAP SC1 is unaffected.** SC1 is scoped to "no finding for target existence or chaining" --
   it says nothing about the AST-only check, and SC3 asks only for the paired fixture. Task 1
   re-reads SC1's live wording and confirms that scoping before relying on it.

**The prohibition this section exists to state:** do NOT narrow the correlation -- to a per-class
scope, a per-method scope, an allowlist, or a "only when the parse and the load are in the same
test class" rule -- in order to make ai-kit's own repository come back clean. Every one of those
would be tuning the checker to its author's own repo, and PROJECT.md's core value forbids
presenting a result with more certainty than its sourcing. If the finding is unwelcome, the honest
fix is a change to `tests/test_arch.py` in a later, separately-decided piece of work, not a change
to the checker here.

## Decisions this plan makes on the planner's authority

`12-CONTEXT.md`'s "Claude's Discretion" block explicitly leaves two things open: the heuristic for
locating the backing test file ("where discoverable" implies best-effort), and the exact
correlation mechanism for D-02. These are settled here so the executor implements one rule:

- **D-A7 -- backing-test-file discovery, best-effort and recipe-driven.** Take
  `parse_makefile_recipe(makefile_path, <the D-A1 target>)`, split it into whitespace tokens across
  all recipe lines, and skip any token beginning with `-` (a flag) or containing `=` (an
  assignment). For each remaining token, in recipe order, form candidates:
  (i) the token itself, joined to `repo_root`, if it ends in a source extension
      (`.py`, `.ts`, `.tsx`, `.js`, `.java`, `.kt`, `.go`, `.rs`);
  (ii) the token with `.` replaced by `/` plus `.py`, joined to `repo_root`, when the token is a
       dotted identifier path -- this is what turns `tests.test_arch` into `tests/test_arch.py`,
       which is exactly how ai-kit's own `arch-test` recipe names its backing file.
  The FIRST candidate that is an existing regular file is the backing file. A candidate that
  resolves to a directory is skipped. If none resolves, the backing file is not discoverable.

  **Containment: reuse this family's existing guard, do not invent a second one.** The shape is the
  one already in `skills/ai-kit-project-rules-agents/ai_kit_project_rules_agents/cli.py:65-69`:
  compute `real_repo_root = os.path.realpath(repo_root)` once, compute
  `real_candidate = os.path.realpath(candidate)`, and accept only when
  `real_candidate == real_repo_root or real_candidate.startswith(real_repo_root + os.sep)`.
  Two properties do the work and both are load-bearing: `realpath` on BOTH sides is what stops a
  `../../etc/passwd`-shaped token and a symlink that points out of the tree, and the `os.sep`
  boundary is what stops a SIBLING directory whose name merely extends the root's -- a bare
  `real_candidate.startswith(real_repo_root)` accepts `/tmp/repo-evil/leak.py` for a repo root of
  `/tmp/repo`. Note that `os.path.join(repo_root, token)` returns the TOKEN unchanged when the token
  is absolute, so an absolute recipe token reaches the guard directly and the sibling case is not
  hypothetical. Reject before opening, not after.
- **D-A8 -- the target-aware correlation (implements D-01/D-02).** Parse the backing file with
  `ast.parse`. Then:
  - **Parser helpers.** Collect the module's function names whose body contains a call to
    `ast.parse` (an `ast.Attribute` `parse` on `ast`, or a bare `parse` imported from `ast`).
    Extend that set to a fixed point: a function that calls a parser helper is itself one. This is
    what makes `_parse("status-line.py")` count even though `ast.parse` is one level down.
  - **Parsed subjects.** For every call to `ast.parse` or to a parser helper, collect every string
    literal appearing anywhere inside that call's argument expressions, plus -- for any bare `Name`
    argument -- the string literals from that name's assignments within the same function scope, or
    module scope if the call is at module level. One level of local name resolution, no more.
  - **Executed subjects.** The same literal collection, INCLUDING the same one-level local name
    resolution, over every call to `importlib.import_module`, `__import__`,
    `importlib.util.spec_from_file_location`, and any `exec_module` call; PLUS the module name of
    every `import X` / `from X import ...` statement in the file.
    The name resolution is not optional on this side and is not a later refinement. The live load
    this whole plan is grounded against assigns the path to a local and passes the NAME:
    `sl_path = os.path.join(_TOOLS, "status-line.py")` then
    `spec_from_file_location("status_line_inv", sl_path)` (`tests/test_arch.py:605-611`). The only
    string literal inside that call is an unrelated alias, and it normalizes to `status-line-inv`,
    which the parse side never produces. So a string-in-call-only implementation sees NOTHING on the
    execute side of that file -- and of most real loaders, which build a path before passing it. It
    would pass every fixture whose path sits inline in the call while being permanently inert in the
    field, with every command exiting 0.
  - **Normalization, shared by both sides.** Take the last path component, strip a known source
    extension, take the last dotted component, casefold, fold `_` to `-`. So `tools/status-line.py`,
    `status-line.py` and `status_line` all normalize to `status-line`. The two extractors MUST call
    the same normalizer function -- two normalizers that drift make the intersection empty for
    every real file, and the check silently never fires.
  - **The finding fires** exactly when `parsed_subjects & executed_subjects` is non-empty, and it
    NAMES the intersecting module(s). An empty intersection is no finding, which is D-01's whole
    point: a file that parses X and separately loads unrelated Y is clean.
  - **Stated limits** (they belong in `SKILL.md` too, plan 12-03): no cross-module dataflow, no
    resolution of a name assigned in another function, and no dynamic/computed module names. Where
    the mechanism cannot see, it produces no finding rather than a guess.
- **D-A9 -- the AST-only finding vocabulary.** One category, two issues:
  - `category: "arch-test-ast-only"`, `issue: "backing_file_executes_checked_target"`,
    `CRITICALITY_MEDIUM`, `advisory` absent (a real, actionable finding). Its `summary` and
    `recommendation` name the backing file, the intersecting module(s), and the fix (parse the
    module with `ast` instead of importing or executing it).
  - `category: "arch-test-ast-only"`, `issue: "ast_only_not_verifiable"`, `CRITICALITY_ADVISORY`,
    `advisory: True`, carrying a `reason` field whose value is EXACTLY one of these four pinned
    tokens -- a closed enum, not a summary of one:
      - `not_discoverable` -- no candidate in the arch-test recipe resolved to an existing regular
        file inside the repo root (including a candidate rejected by D-A7's containment guard).
      - `not_python` -- the backing file resolved but is not a `.py` file, so this skill's
        `ast`-based check does not apply to it.
      - `unparseable` -- the backing file is a `.py` file that `ast.parse` refused.
      - `no_parse_call` -- the backing file parsed, but contains no call reaching `ast.parse`
        (directly or through a helper), so what it architecturally checks cannot be identified.
    The `summary`/`recommendation` still say the same thing in prose for a human, but the enum is
    what a caller branches on. **Free text in place of these tokens is prohibited**, and so is a
    fifth value: the four-distinct-reasons requirement in this task's verify is satisfiable by any
    four differing prose strings, which is a check with no teeth, whereas a pinned enum is the thing
    plan 12-03's `SKILL.md` names, this plan's suite asserts, and any later consumer switches on.
    A repo using a config-driven architecture tool with no backing test file lands in
    `not_discoverable`, which is honest rather than a defect.
  - **12-01 D-A3's schema prohibition binds both of these**: neither carries an identifier key that
    `build_remediation` would prefer over `category` at `remediation.py:86`. The backing file's path
    belongs in the prose fields, where naming it is the point and shadowing nothing is the effect.
  MEDIUM rather than HIGH is deliberate: a file that parses its subject in its architecture methods
  and loads it elsewhere is a real but bounded issue, and over-banding it would push a user to
  distrust the whole report.
- **D-A10 -- the canonical-tool baseline (ROADMAP SC4).** ONE module-level mapping keyed on the
  exact five stack names `detect_stacks` can return:
  `python` -> import-linter; `node` -> dependency-cruiser; `java` -> ArchUnit;
  `rust` and `go` -> a known-gap statement, not a tool.
  The three tool rows each carry a one-line reason transcribed from the design spec (static
  AST-only contracts; the broadest static rule surface; ordinary tests rather than a side lint
  pass). The gap rows state that no equally canonical dedicated architecture-fitness tool surfaced
  for those ecosystems and that this skill declines to assert one -- the literal phrase `known gap`
  must appear in the emitted text so the statement is findable, and no tool name may appear in a
  rust-only or go-only recommendation.
  The missing-target recommendation is built as 12-01's structural sentence FIRST, then one
  stack-specific clause per detected stack, in sorted stack order so the text is deterministic. A
  repo whose stack set is empty gets the structural sentence plus an explicit statement that no
  stack marker was detected -- never a silent omission and never a default to Python.
