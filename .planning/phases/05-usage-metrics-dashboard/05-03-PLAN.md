## Facts live-verified on this machine during planning (2026-09-10)

- A real Codex rollout file
  (`~/.codex/sessions/YYYY/MM/DD/rollout-<timestamp>-<uuid>.jsonl`) is
  JSONL, one object per line, each with a top-level `{"timestamp": "...",
  "type": "<line-type>", "payload": {...}}` shape. Observed `type` values
  on this machine's own real sessions: `session_meta` (payload has
  `session_id`, `cwd`, `originator`, `cli_version`, `model_provider`),
  `event_msg` (payload has its OWN nested `"type"`, e.g. `task_started`,
  `token_count` — the latter's payload:
  `{"type":"token_count","info":{"total_token_usage":{"input_tokens":N,
  "cached_input_tokens":N,"cache_write_input_tokens":N,"output_tokens":N,
  "reasoning_output_tokens":N,"total_tokens":N},"model_context_window":N}}`),
  `response_item` (payload has ITS OWN nested `"type"`, e.g. `"message"`
  with `role`/`content`, or `"function_call"` with `name` (e.g.
  `"exec_command"`), `arguments` (a JSON-STRING, not a nested object — must
  be `json.loads`-parsed a second time to reach `{"cmd": "...", "workdir":
  "...", ...}`), `call_id`). `turn_context` events (nested under
  `event_msg`) carry per-turn `cwd` — Codex's own session-level/turn-level
  cwd is present but, per `05-CONTEXT.md` D-05, opencode/Codex/Cursor all
  "lack per-command cwd" in general — this plan's capture step records
  whatever cwd-adjacent fields the raw format actually carries (verbatim,
  D-02); 05-04 decides how to use them.
- The single-quoted `arguments` STRING inside a `function_call` payload is
  itself escaped JSON text (e.g. `"{\"cmd\":\"...\",\"workdir\":\"...\"}"`)
  — this is Codex's own encoding choice, not a bug; this plan's capture
  does NOT double-parse it (that would be an interpretive step, not
  verbatim capture) — the raw envelope's `payload` carries the
  `function_call` line exactly as read, `arguments` string and all; 05-04's
  refiner is the layer that `json.loads`s `arguments` when it needs
  `cmd`/`workdir`.
- A real Cursor agent-transcript file
  (`~/.cursor/projects/<project-slug>/agent-transcripts/<uuid>/<uuid>.jsonl`)
  is JSONL, one object per line, shape `{"role": "assistant", "message":
  {"content": [{"type": "tool_use", "name": "Shell", "input": {"command":
  "...", "description": "...", "working_directory": "..." (OPTIONAL — not
  present on every observed Shell call on this machine)}}, ...]}}` — other
  observed `content[].type` values on this machine's own real transcripts
  include `"text"`; other observed `tool_use.name` values include
  `StrReplace`, `Task`, `Write`, `GetDynamicTools`. Only `name == "Shell"`
  entries represent a shell command this pipeline's family/decomposer axes
  care about (mirrors opencode's `tool == "bash"` distinction from 05-02);
  every other `tool_use`/`text` entry is still captured losslessly (D-02)
  but is out of scope for command-shape classification.
- Cursor's `store.db` (`~/.cursor/chats/<md5-hash>/<session-id>/store.db`)
  schema is `blobs(id TEXT PRIMARY KEY, data BLOB)` and
  `meta(key TEXT PRIMARY KEY, value TEXT)` — live-queried on this machine:
  `meta` is EMPTY (0 rows) on the sampled session, `blobs` has opaque
  entries with no queryable sub-structure exposed by the schema itself.
  This is the concrete evidence behind this plan's own `must_haves` truth
  that `store.db` is out of scope for this wave — parsing 12 opaque BLOB
  rows with no documented format would produce a confidently-labeled
  result this plan has no actual basis to stand behind.
</live_verified_facts>
