# Phase 25.1: Configurable cross-AI retry ladder and upstream error propagation - Context

**Gathered:** 2026-10-24 (assumptions mode, `--analyze --all --batch`, jev screening, best over easy); updated 2026-10-24 (owner requests: SPEC R8–R10)
**Status:** Ready for planning after Phase 25 lands (25-06..25-11 are the base)

<domain>
## Phase Boundary

The runner template's failure ladder becomes configurable (soft exponential backoff, one session
reset, a second soft series), the caller owns the hard waits (10/15/30 minutes) and the user
notice, the upstream error is passed through verbatim (no runner-side reset parsing), the error
catalog becomes owner-extensible data, and the runner takes exactly one runtime. The WHAT is
locked in `25.1-SPEC.md` (R1–R10; R1, R5 amended by D-07, D-10, D-15; R8–R10 added 2026-10-24); this file locks the
HOW. Phase 26 consumes the hard tier's stop record and the instruction-file pointer.
</domain>

<decisions>
## Implementation Decisions

### Retry config
- **D-01: One lookup helper reads any `workflow.<key>`** with the existing `cross_ai_timeout`
  order (scoped `.planning[/$GSD_PROJECT][/workstreams/$GSD_WORKSTREAM]/config.json`, then the
  root config under a workstream). `ownTimeout` becomes a caller of it. The config is read once
  at call start. Python-dispatched runs get the same precedence because `runner_dispatch.py`
  runs the template with the project `cwd`.
  - Evidence: `cross-ai.mjs:1682-1705`, `runner_dispatch.py` (cwd at lines 73, 423, 542).
  - Confident (analyzer); no jev item.
- **D-02: The project key is hand-edited and documented; nothing writes it.** gsd-tools 1.17.0
  `config-set workflow.cross_ai_retry.*` fails with `Unknown config key` (live, scratch project),
  while `config-get` reads it and later `config-set` calls keep the block. The docs show the JSON
  block and say the setter refuses it.
  - TypeSafe hand_edit_documented 0.95 (Laya hand_edit_documented 0.49 (fb)).
- **D-03: The user file is `${XDG_CONFIG_HOME:-~/.config}/ai-kit/cross-ai.json`, holding
  `{"cross_ai_retry": {...}}`** — the same inner object and the same validator as the project
  key. JSON because the runner is dependency-free Node (Node 24.21.0 has no TOML parser,
  verified); not `review-spec.toml`.
  - **Own reasoning** (Laya named_block 0.46 (fb), TypeSafe named_block 0.54 (fb)): both lean the
    same way and the named block reads the same in both places. Ledger.
- **D-04: The rendered defaults use the file keys verbatim** in one CONFIG `retry` object
  (`base_s`, `factor`, `max_retries`, `session_resets`, `hard_waits_s`) plus the CONFIG-only
  `capS` (≤ 14400). Phase 25's `backoffS`, `sameSessionRetries`, `newSessionRetries` and
  `cooldownS` leave the template; an upgraded old copy keeps its unused keys (the 25-10 `retries`
  precedent). Tuning happens in the project or user file, never in CONFIG, because a CONFIG edit
  makes the copy `edited` and the next render writes `.new` (`cross_ai_script.py:57-69,202`).
  - **Own reasoning** (Laya mapping 0.39 (fb), TypeSafe identical_names 0.53 (fb)): one validator
    over three sources and docs that match CONFIG byte for byte (SPEC R7 edge). Ledger.

### Catalog
- **D-05: The canonical catalog is a JSON data file in the skill
  (`skills/ai-kit-spec-review/references/cross-ai-errors.json`), compiled into the runner's
  `<patterns>` block by a generator, with a byte-equality drift test; the owner extends it with
  an overlay `${XDG_CONFIG_HOME:-~/.config}/ai-kit/cross-ai-errors.json`.** Rendered copies stay one
  file under the sha256 header (25 D-02 kept). Overlay rows pass the same checks as shipped rows
  (known class, label, source, route and provider `*` or a known value); a bad overlay row is
  refused by id, the way R2 refuses bad keys. Rows gain `route` and `provider` columns.
  - **Own reasoning** (Laya embedded_plus_overlay 0.54 (fb), TypeSafe
    source_data_compiled_plus_overlay 0.55 (fb)): the only option that satisfies QTA-10's "data
    file", R5's "no code changes" and D-02's single file together. Ledger.
- **D-06: Row order is an explicit `tier` field, then file order.** Tiers: router reason codes
  (`ALL_TARGETS_SKIPPED`, `all_targets_cooling_down`, `circuit_open`, `model_not_in_catalog`, the
  model cooldown or "unavailable" pause), vendor structured codes, billing/access text, quota
  text, auth text, capacity and type hints, bare status codes (25 D-03 order kept). `route` takes
  `router`, `unknown` or `*` (the runner resolves only `router`, `router-inferred`, `unknown`;
  25 D-06's direct prefix list was never built). `provider` filters non-router lanes by model-id
  prefix and is informational on router lanes, where the member appears only in the body.
  - **Own reasoning** (Laya explicit_tier 0.44 (fb), TypeSafe fixed_slot 0.49 (fb)): positional
    order cannot place overlay rows at their class's position (SPEC R5 ordering edge). Ledger.

### Hard tier and notice
- **D-07: Both soft-ladder classes (transient and confirmed-router quota) carry the retry hint
  and get the caller's hard tier**, sharing the lane's state file and the 4-hour cap (SPEC R1
  amended). The owner described the hard tier after the soft retries for "a 400, a quota error or
  another kind of error"; an `[400]: event: error` storm holds a lane at most 55 minutes before
  the notice.
  - **Own reasoning** (Laya router_quota_and_transient 0.48 (fb), TypeSafe router_quota_only
    0.65 (fb)): the owner's wording decides over the earlier orchestrator ruling. **Needs
    confirmation.** Ledger.
  - **Confirmed 2026-10-24 (uz):** both classes get the hard tier.
- **D-08: The runner owns the hard-tier count.** The state file's `cycle` picks
  `retry_after_s = hard_waits_s[cycle]`; the re-invoke after the last entry exits 69 with
  `stopped=hard-waits`, or `stopped=cap` when the cap comes first. Callers are stateless: they
  read `retry_after_s` from the `AIKIT-XAI` line, wait once, and re-invoke the same lane.
  - Confident (analyzer; SPEC R3 and AC 6; 25-06 state file).
- **D-09: The notice is the evidence in the caller's reply plus a persisted stop record.** On
  `stopped=hard-waits|cap` the skill or agent prints the runner's `cross-ai: report`, the upstream
  lines and the `AIKIT-XAI` line verbatim, marks the lane stopped and schedules nothing more. The
  runner's state file records the terminal stop (`stopped`, `stopped_at`) so a later session or
  Phase 26's wake can surface it. Each wait is one one-shot `CronCreate` on Claude Code; other
  hosts print `retry_after_s`, the state path and the re-invoke command (unverified, 25 D-16).
  - TypeSafe reply_plus_stop_record 0.91 (Laya plus_desktop 0.39 (fb)).
- **D-10: A CLI with no session resume runs each soft retry as a new session**, under the
  dirty-tree rule; `session_resets` does nothing there (SPEC R1 amended). Phase 25's
  `ladderNext` gate `st.fresh === 0` goes, since same-session retries run again after a reset.
  - **Own reasoning** (Laya each_retry_new_session 0.58 (fb), TypeSafe skip_to_reset 0.51 (fb)):
    sandboxed codex exec (the GSD hook default) cannot resume, and skipping the first series would
    give it fewer retries than every other CLI for the same transient error. Ledger.
- **D-11: On the GSD path the caller answers GSD's retry/skip/abort prompt:** wait
  `retry_after_s` then **retry**; after `stopped=hard-waits|cap` give the notice and **abort**;
  never **skip** (skip runs the plan on the main session's executor, a harness switch). Stated in
  the policy reference.
  - TypeSafe retry_wait_abort_never_skip 0.86 (Laya ask_human 0.65 (fb)).

- **D-15: Route confirmation is the owner's.** The dogfood lane `router-env/my-coding` resolves to

### Upstream pass-through
- **D-16: The upstream body goes on its own lines** after `cross-ai: report` and before the final
  `AIKIT-XAI` line: `cross-ai: upstream body=<JSON-encoded string>` and
  `cross-ai: upstream fields=<JSON object>`; the report line carries only `upstream=present|-`.
  `classifyStop` returns the match position so the matched line (stderr) or the error object
  (event) is what gets passed through; the allowlisted structured fields (`retry_after`,
  `reset_at`, `retry_after_seconds`, `resetsAt`) are copied with values unchanged and never feed
  any wait.
  - **Own reasoning** (Laya encoded_token 0.50 (fb), TypeSafe encoded_token 0.72 (fb)): the waiting
    agent must read the body to infer reset times; an encoded token is unreadable to it, and
    JSON-encoded lines keep `parse_status_line`'s whitespace split and the last-line status rule
    intact. Ledger.
- **D-17: One extended redactor runs on every relayed child line and on the report.** Order:
  strip ANSI, decode, redact, then cap at 2000 code points with `Array.from` (no split surrogate
  pair). The redactor adds key-context rules (JSON or label keys for account, connection, org,
  user and request ids) and bare UUIDs inside upstream bodies; pi's own session-id echo being
  masked is pinned by a test.
  - TypeSafe relay_and_report 0.80 (Laya allowlisted_fields 0.37 (fb)).

### Added 2026-10-24 (owner requests, after 25.1-SPEC R8–R10)
- **D-18: `skills/ai-kit-cross-ai/` is a high-level, canonical skill.** SKILL.md carries the
  decision flow (choose runtime and model, launch, wait, read the status, chain review or
  execution, hard tier and notice, GSD retry/abort, never switch) and the pitfalls; one
  reference holds the per-host launch-and-wait patterns (Claude Code background tasks with
  notices; pi, opencode, cursor, codex foreground waits flagged unverified). It does not
  document each runtime's flags or model grammar: the script owns those (D-19, D-21). The 25-09
  policy reference moves into this skill (its text tests follow), and the other skills keep a
  one-line pointer.
  - TypeSafe high_level_canonical 0.99 (Laya high_level_canonical 0.50 (fb)).
- **D-19: One `--model <id>` for the selected runtime;** `--model-<cli>` stays an alias, and
  `--model` wins with a notice when both are given.
  - **Own reasoning** (Laya single_model_flag 0.36 (fb), TypeSafe single_model_flag 0.61 (fb)):
    both lean the same way and the owner wants the script to own the forms. Ledger.
- **D-20: Named per-CLI tool profiles, `--tools-profile exec|review|none`,** defined in the
  runner's runtime table; the mode picks the default profile. pi: `review` =
  `--tools read,grep,find,ls --no-mcp --no-context-files`, `none` =
  `--no-tools --no-mcp --no-context-files` (flags verified in this machine's `pi --help`). A CLI
  without a profile refuses it (usage). No raw passthrough, so a caller cannot widen review's
  read-only set.
  - **Own reasoning** (Laya mode_only 0.45 (fb), TypeSafe named_profiles 0.59 (fb)): a third
    mode would mix the tool set with the exec/review contract (tree checks, preamble); raw
    passthrough breaks the read-only guarantee. Ledger.
- **D-21: Each runtime's model grammar lives in its runner table row** (today `MODEL_ID`,
  `CURSOR_MODEL_ID` with bracket parameters such as effort, fast or context, pi's `modelSuffix`
  thinking levels), and `--print-argv` shows the resolved argv. `detection.py` `RUNTIMES` stays
  the source of truth for ids, binaries and host signals (AGENTS.md architecture rule).
- **D-22: Copilot runs with the prompt on argv and stdin `ignore`.** A per-row field marks argv
  prompts. A prompt over 100 KB is refused as usage (well under Linux's argv limit; inference,
  unverified per platform). `COPILOT_GITHUB_TOKEN`/`GH_TOKEN` pass through `scrubEnv`; the
  redactor gains GitHub token shapes (`gh[pousr]_…`, `github_pat_…`); a missing token is `auth`.
  The `review` profile denies write and shell tools through `--deny-tool`; `exec` allows the
  tools with `--allow-tool`. Every flag and pattern is labelled unverified (CLI not installed;
  source: the owner's relayed CLI form).
  - *(Amended 2026-10-25, research live check, see 25.1-SPEC R10.)* Copilot CLI 1.0.103 is
    installed. Exec adds `--allow-all-tools` (required for non-interactive mode per its help);
    the `review` profile uses `--excluded-tools` (stronger than `--deny-tool`, which only changes
    approval prompts); `GITHUB_TOKEN` joins the pass-through as the third token name. The prompt
    stays on argv. Flags are now `documented` (from `--help`); error rows stay unverified.
- **D-23: Pointers.** `ai-kit-spec-review` (`references/cross-ai-dispatch.md`),
  `ai-kit-spec-execute-gsd`/`-superpowers`, `ai-kit-gsd-curated-config`
  (`references/runner.md`) and `ai-kit-spec-config` point to the skill; the instruction-file
  pointer names the runner and the skill (Phase 26 R19's signals follow it, 26 D-33); the README
  lists the skill. Each changed SKILL.md passes skill-judge.
- **D-24: The pitfalls come from the field notes** written for the agent-toolkit session
  (2026-10-24): prompt on stdin, never argv with an inherited stdin; two timeouts and gsd-core's
  300 s default; no idle watchdog (the heartbeat's `stdout +0 bytes` is normal for `pi -p`); the
  review tree check (`contract_violation tree=dirty` when anything edits the tree); kill by
  recorded PID, never by pattern; executor guards (`AI_KIT_REFUSE_REAL_HOME=1`, no stash, check
  "pre-existing" claims); atomic rewrites keep the file mode.
