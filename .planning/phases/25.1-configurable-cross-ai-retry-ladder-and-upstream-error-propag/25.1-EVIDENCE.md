## Captured bodies (verified, 2026-10-25)

Seen in the Phase 25 skill-judge runs (opencode `router-env/my-referee-*`, review mode, through the
template-7 runner); connection ids replaced by `conn:<id>`.

- **OmniRoute, combo with an empty account pool** (`router-env/my-referee-two`, every run of
  rounds 3 to 5, within 3 s): HTTP 404, opencode event `provider.invalid-request`, body
  `{"error":{"message":"Combo has no executable targets","type":"invalid_request_error",
  "code":"model_not_found"},"diagnostics":{"poolSize":0,"attempted":0,"excluded":[],
  "attemptOrder":[],"terminalReason":"no_executable_targets","recovery":{"action":"switch-combo",
  "next_step":"This combo has no executable targets in the current account pool. Pick a different
  combo or reconnect the missing providers."}},"recovery_hint":{...same...}}`. The template-7
  runner matched no pattern (`status=crash`, `stopped=class`). The `code` says
  `model_not_found`, but the `terminalReason` is an empty pool, not a bad model id: a status code
  or `code` alone would misclassify it. OmniRoute's `recovery.action` suggests switching combos;
  the owner rule forbids that in the runner, so it is reported, never acted on.
- **OmniRoute, 5-hour sessions at 100%** (`router-env/my-referee-one`): `Service temporarily
  unavailable: all targets were skipped by pre-dispatch filters (Session (5h) 100% conn:<id>;
  Session (5h) 100% conn:<id>)`, and from a member `[429]: The usage limit has been reached (reset
  after 4h 15m 3s)` with structured `"retry_after":15303,"reset_at":"2026-10-25T08:42:03.640Z"`.
  The runner ran its 7 attempts and exited 75 with `retry_after_s=600 cycle=0`: the upstream reset
  (4 h 15 m) is past the 4-hour cap, so every 10-minute cycle was wasted. This is the case the
  pass-through of `retry_after`/`reset_at` (R3) exists for.
- Connection ids appear as `conn:` plus 8 hex digits inside the message text; the redaction rules
  must cover that shape.

## OmniRoute reason codes (documented, CHANGELOG)

- `ALL_TARGETS_SKIPPED`: every combo member skipped at pre-dispatch (quota filters, persisted
  cooldowns, short transient model cooldowns; a fix stopped answering it as a hint-less 503).
- `all_targets_cooling_down`: every member behind an open circuit breaker, naming
  `provider/model: circuit_open (Ns)` with `Retry-After`.
- A 400 or 429 reading "endpoint is unavailable" pauses only that model for 5 minutes.
- `model_cooldown` 429 bodies carry a `retry_after` ISO timestamp and a credential count.
- `model_not_in_catalog`: a combo member missing from the live catalog is skipped.
- Usage, budget, token, request-rate, provider-account and combo-exhaustion errors expose the
  earliest known reset as structured `retry_after` seconds.
- `/v1/responses` error frames sent after an early HTTP 200 keepalive carry `status_code`,
  `error_type` and `retry_after_seconds`.
- `RETRY_AFTER_PROVENANCE_ENABLED` (opt-in, default off): aggregated 429/503 responses omit
  `Retry-After` when no concrete future retry time is known.

## Consequences for 25.1

- Classify by route, then by body and reason code; never by status code alone.
- Structured upstream fields (`retry_after`, `reset_at`, `retry_after_seconds`, `resetsAt`) are
  copied through as-is; free-text reset times are passed through for the waiting harness or agent
  to interpret (owner decision 2026-10-24: no runner-side reset parsing).
- A router lane's "unavailable" or all-skipped answer can be a temporary block list or cooldown
  rather than quota exhaustion; the report must say which reason code OmniRoute gave.
