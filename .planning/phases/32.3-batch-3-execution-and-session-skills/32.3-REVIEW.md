## Critical Issues

### CR-01: Keys right after an escaped newline/tab or a percent escape are no longer redacted (regression)

**File:** `skills/ai-kit-spec-review/ai_kit_spec/secret_shapes.py:17-37` (all copies, and `cross-ai.mjs:1515`). Callers: `reset_parse.py:131-146`, `flow_pr.py:21-22`, `cross-ai.mjs:1257,1262`, `gp_common.py:104-105`.
**Issue:** Every row starts with `(?<![A-Za-z0-9_])`. In JSON-escaped text a key that starts a line is preceded by `n` (from `\n`) or `t` (from `\t`). In URL-encoded text it is preceded by a hex digit (from `%3D` or `%20`). In all of these the lookbehind blocks the match. Before the phase:
- the runner's and session-wake's `(sk|rk)-…` rule had no boundary;
- `flow_pr._TOKEN` and gp_common's `sk-`/`ghp_` rules had no boundary either.

All of these caught such keys. The runner itself builds this text: `log(redactSecrets(\`cross-ai: upstream body=${JSON.stringify(fields.upstream.body)}\`))` at 1257. A multi-line upstream body whose `sk-` key starts a line is now logged in clear, and KEY_VALUE_RE does not help when the JSON key is `message`. Reproduced by `escape_probe.py`:
- `session-wake leaks sk after \n: True`, and the old rule caught it: `True`;
- `flow_pr leaks percent-encoded gh token: True`, old rule: `True`;
- `flow_pr leaks gh token after escaped tab: True`.

D-05 accepts only the upper-case loss, so this regression is not covered by a decision.
**Fix:** Also allow a preceding escape in the shared guard. The widths are fixed, so Python and JavaScript read it the same way, and it adds no capture group. Change the prefix guard in every row (canonical file, then copies, then the runner's KEY_SHAPES line):
```python
_G = r"(?:(?<![A-Za-z0-9_])|(?<=\\[nrt])|(?<=%[0-9A-Fa-f]{2}))"
# e.g. ("github_token", _G + r"gh[pousr]_[A-Za-z0-9]{20,}")  -- written out literally,
# since SHAPES must stay a plain literal for ast.literal_eval and the KEY_SHAPES JSON line.
```
Add one test per caller: `redact(json.dumps("x\n" + sample))` contains no sample, and so does `"token%3D" + sample`.

## Warnings

### WR-01: The JWT row's time grows with the square of the input (ReDoS)

**File:** `skills/ai-kit-spec-review/ai_kit_spec/secret_shapes.py:29-32` (and `cross-ai.mjs:1515`)
**Issue:** The lookbehind does not exclude `-`, but the body class `[A-Za-z0-9_-]` includes it. So in `"eyJ-" * n` every `eyJ` is a valid start, and each start scans to the end of the text before the required `\.eyJ` fails. Measured:
- Python: 0.52 s per 64 KiB for `detect` and the same for `redact`;
- Node runner rule: 67 ms at 16 KiB, 1.1 s at 64 KiB (one relay line at `INPUT_CAP`), 16.4 s at 256 KiB.

`flow_pr.redact` and the runner apply this to child or gh output of any length. The PEM row got a cap for the same class of problem (D-04 amendment), but the JWT row did not.
**Fix:** Add `-` to the JWT row's lookbehind only. Measured: 0-1 ms at every size, and a real JWT still matches.
```python
("jwt", r"(?<![A-Za-z0-9_-])eyJ[A-Za-z0-9_-]{10,}\.eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}"),
```
Add a timing test beside `test_many_unclosed_opening_lines_finish_quickly`: `"eyJ-" * 16384` finishes in under 1 s.

### WR-02: An unclosed PEM block keeps its body; only the header is redacted

**File:** `skills/ai-kit-spec-review/ai_kit_spec/secret_shapes.py:21`
**Issue:** If there is no `-----END …-----` within 16384 characters, the optional tail matches nothing. Only the `-----BEGIN …-----` header is replaced and the base64 key material stays visible. `redos.py` shows `unclosed pem body visible: True`. The runner cuts text itself, so this case really occurs:
- `pending.slice(0, INPUT_CAP)` at `cross-ai.mjs:1645` keeps BEGIN and drops END;
- `normalizeInput` at 1582 keeps the tail instead.

session-wake and flow_pr redact text that the child or gh may already have cut. D-04 records only the line relay and the `Bearer` limit, not an unclosed block. The header is not the secret. The body is.
**Fix:** Give the tail a greedy base64 fallback when END is missing:
```python
r"-----BEGIN [A-Z0-9 ]+-----(?:[\s\S]{0,16384}?-----END [A-Z0-9 ]+-----|[A-Za-z0-9+/=\r\n]{0,16384})?"
```
Then mirror the change in the runner line and add a test: header plus 20 body lines, no footer, gives one marker.

### WR-03: The new-copy guard misses key shapes written with `\w`, `\S`, `\d` or `.`

**File:** `tests/test_arch.py:1877-1881`
**Issue:** `_REGEX_SYNTAX` accepts only `[`, `(` or `{digit` right after the prefix. `guard_probe.py` shows these new copies pass the guard with no hit: `ghp_\w{36}`, `AKIA\w{16}`, `xai-\S{16,}`, `sk-.{20,}`, `github_pat_\w+`. Shorthand classes are the most common way to write such a pattern. The guard therefore does not do its job (D-11/D-12: flag a new key-shape copy).
**Fix:** Widen the syntax set. On the current tree this adds 0 hits (measured):
```python
_REGEX_SYNTAX = r"(?:\[|\(|\{\d|\\[wWdDsS]|\.[*+{])"
```
Then add the shorthand cases to `test_new_key_shape_list_is_flagged`.

### WR-04: The jev guard silently stopped refusing non-Stripe `sk_` values

**File:** `skills/jev-fast-decision/scripts/jev_ladder.py:58,76-78`
**Issue:** The old `_SECRET_RE` refused `\b(?:sk|…)[-_][A-Za-z0-9_-]{12,}`, so it caught any `sk_` value of 12 or more characters. Now `sk_` is caught only as `sk_(live|test)_…` (stripe_key). The 48+ base64 rule does not help, because the `_` breaks the run. So `sk_` followed by 12-47 alphanumerics now passes the guard. D-04 lists the jev variants it drops on purpose (`ghp-`, `gho-`, `xox?_`, bare `pk-`/`pk_`), but `sk_` is not on that list. D-06 says "never ... drop a catch".
**Fix:** Either record the drop in D-04 (CONTEXT/SPEC amendment), or keep the catch in jev as a caller-local rule next to `_BASE64_RUN_RE`, for example `re.compile(r"(?<![A-Za-z0-9_])sk_[A-Za-z0-9_-]{12,}")`. If you keep it, add a test case to `test_every_shared_key_shape_is_refused`.
