<objective>
Apply the configuration anti-pattern rules the design spec assigns to this skill: flag
enable-everything rulesets across ecosystems (ROADMAP SC3), apply the three ruff-specific checks and
the golangci-lint redundancy check (ROADMAP SC5), and evaluate tool pairs against the locked pairs
table with unresearched pairs defaulting to presumed-complementary (11-CONTEXT D-03/D-04).

Purpose: plans 11-01 and 11-02 answer "do the two files agree" and "what tooling is here, by
category". This plan answers "and is that tooling configured in a way its own ecosystem's
maintainers discourage" -- the part of the design spec that turns an inventory into an audit, and
the last of ROADMAP Phase 11's five success criteria.

Output: one reader layer for untrusted target-repo configuration, three check modules, paired
fixtures for every check, and an explicit, visible statement wherever a config format cannot be
read statically at all.

## Decisions this plan makes on the planner's authority

The design spec states these rules as prose. ROADMAP SC3/SC5 fix the outcomes that must
discriminate. The detection shapes below are settled here so the executor implements one rule per
check and the fixtures and `SKILL.md` agree with it:

- **D-C1 -- configuration discovery, per ecosystem, in a fixed order, from a BOUNDED candidate
  list.** Ruff: the project metadata file's ruff table, then a dedicated ruff config file at the
  repo root in either of its two conventional names. Go: the golangci configuration at the repo
  root in any of its conventional extensions. Node: the JSON-form ESLint configuration.
  Java: the PMD ruleset, discovered from a NAMED candidate list and nothing wider -- `pmd.xml` and
  `ruleset.xml` at the repo root, then `rulesets/*.xml` one directory deep, then a ruleset path
  named inside the project's Maven build file if one is present. Every ecosystem's discovery is an
  ordered list of concrete candidates; NONE of them is a search for a shape. "A ruleset XML
  referenced from the repo" as a discovery rule would license an unbounded hunt through an
  untrusted tree for anything XML-shaped -- a smaller instance of T-11-15's own threat, and the
  reason the other three ecosystems got named candidates in the first place. Any candidate reached
  by a walk rather than by a direct path uses the SAME bounded, pruned walk Task 2's child-config
  discovery uses (the sibling skill's `_PRUNED_DIR_NAMES` at `makefile_checker.py:92-94`), never a
  second walk with different limits.
  First file found per ecosystem wins; absence of every candidate means that ecosystem's checks do
  not apply and produce nothing -- never a finding about a missing config, which would flag every
  repo that does not use that ecosystem.
- **D-C2 -- enable-everything markers, one per ecosystem, data-driven.** Ruff: the rule selection
  containing the everything token. Go: the golangci configuration enabling all linters. Node: the
  JSON ESLint configuration extending a preset whose name ends in the everything segment. Java: a
  ruleset referencing a whole category file rather than named rules. Encode these as one table of
  `(ecosystem, config candidates, marker predicate, spec citation)` so a fifth ecosystem is a row
  rather than a branch, and so the finding can name which ecosystem and which file triggered it.
- **D-C3 -- the statically-unreadable config is a visible advisory, not a silent skip.** The
  JavaScript-module form of the ESLint flat configuration cannot be read statically with the
  standard library, and guessing at its contents by regex would be exactly the false certainty
  PROJECT.md forbids. When such a file is present and no statically-readable ESLint configuration
  is, emit an advisory-band finding naming the file and saying the enable-everything check could not
  be applied to it. The design spec's own convention -- an open gap is explicitly flagged, never
  silently dropped -- is the precedent, and the same finding shape covers any future unreadable
  format.
- **D-C4 -- "a real type-checker is present" is the classifier's answer, not a new keyword list.**
  The type-safety finding fires only when the ruff selection carries annotation-presence or
  type-import rule families AND nothing resolves into the type-checking category -- neither a
  classified hook nor a tool-shaped Makefile target. This repository itself carries such a hook, so
  a check that ignored the Makefile-and-hooks evidence would flag ai-kit's own repo wrongly on its
  first real run.
- **D-C5 -- "pinned version" is any of three concrete pins, not a guess.** A pinned tool version
  means: an exact-equality specifier for that tool in the project's dependency declarations, a
  revision pin on the hook repository that provides it in the pre-commit configuration, or a
  lockfile in the repo naming that tool. Any one suffices. This is deliberately generous: the
  finding's purpose is catching an unpinned preview-rule surface, and a repo that pins by lockfile
  is not the repo the spec is warning about.
- **D-C6 -- the child-configuration check is structural, and the mechanism claim is the spec's.**
  Flag when a non-root configuration extends a parent configuration, declares its own rule
  selection, and does not itself declare the ignore list the parent declares. The claim that the
  parent's ignore list is thereby discarded is the design spec's locked, already-researched finding
  (11-CONTEXT D-03) -- state it as the finding's reason and cite the spec, do not re-derive it and
  do not soften it into a maybe.
- **D-C7 -- finding vocabulary, pinned.**
  `category: "enable-everything"`, `issue: "uncurated_ruleset"`, high.
  `category: "ruff-type-safety"`, `issue: "annotation_rules_are_not_type_checking"`, high.
  `category: "ruff-preview"`, `issue: "preview_without_pinned_version"`, medium.
  `category: "ruff-config-inheritance"`, `issue: "child_select_discards_parent_ignore"`, high.
  `category: "tool-pair"`, `issue: "confirmed_redundant_pair"` or `"superseded_tool"`, medium, with
  `advisory: True` so the remediation entry arrives with auto-apply off -- removing a tool from
  someone's gate is a judgement call, never a safe automatic edit.
  `category: "check-limitation"`, `issue: "config_not_statically_readable"`, advisory band, with
  `advisory: True`.
  Every finding also carries `config_path` (repo-relative) so a reader can go straight to the file.
