## Decisions this plan makes on the planner's authority

11-CONTEXT.md's "Claude's Discretion" block leaves the catalog's exact shape open and D-02 hands
the category reconciliation to this phase's planner. Settled here so the executor implements one
design and plan 11-03's checks can rely on it:

- **D-T1 -- the tool index is DERIVED, the tables are the source.** The baseline stacks table and
  the pairs table are transcribed from the design spec and are the only hand-written tool data. The
  tool-name-to-category index is computed from BOTH at import time (baseline first, then D-T7's
  pairs pass). A tool appearing in several stacks (`jscpd`) must land in one category; a derivation
  that would put one tool name in two categories must raise at import rather than silently pick one,
  because that is a transcription error in the table.
- **D-T7 -- every pairs-table tool name must be CLASSIFIABLE, enforced at import.** A pairs row is
  only reachable by plan 11-03's evaluation if both of its tools classify, and into the same
  category. So: at import, after the baseline derivation and the D-T3 defaults are in place, walk
  the pairs table and require every tool-token member to resolve. Raise, naming the row and the
  unresolved member, if one does not. Raise, naming the row and both categories, if a row whose
  relationship is a confirmed redundancy or a supersession has members resolving to two DIFFERENT
  categories -- that row is the kind that produces a finding, and a cross-category one would be
  researched advice that can never fire. A complementary or overlapping row resolving
  cross-category is permitted and harmless, because those rows emit nothing by design.

  Why this exists: three tools appear ONLY in the pairs table. The spec's Go dead-code cell is
  `staticcheck unused` and its Go linting cell names `staticcheck` only inside a parenthetical
  list of `golangci-lint`'s defaults, so a bare `staticcheck` hook (`staticcheck ./...`) matches
  nothing under D-T2's token-bounded longest match; the Node dead-code cell names `ts-prune` only
  inside a don't-use note; the Rust security cell names `cargo-audit` only inside a supersession
  parenthetical. Under a baseline-cells-only derivation all three classify as nothing, three
  researched rows silently become unreachable -- including the one ROADMAP SC5's final clause is
  about -- and every fixture in THIS plan still passes green. That is the cross-plan break the
  cross-AI review named as the phase's load-bearing risk.

  The resolution is three EXPLICIT, individually-cited index entries, not an automatic rule. Each
  carries the spec line that justifies its category, as an inline comment:
  bare `staticcheck` → the Go LINTING category, because the Go linting cell names it among
  `golangci-lint`'s bundled defaults -- it is that same linter run standalone, which is precisely
  what the pairs row is about; its dead-code sibling entry `staticcheck unused` stays a distinct,
  longer, more specific string that D-T2's longest-first matching keeps winning for the invocation
  that really is the dead-code pass. `ts-prune` → the Node DEAD-CODE category, from the dead-code
  cell that names it as the superseded alternative to `knip`. `cargo-audit` → the Rust SECURITY
  category, from the security cell that names it as the tool `cargo-deny` supersedes on the
  advisory axis.

  Do NOT generalize this into "derive an unresolved member's category from its partner's". That
  rule looks tidier and is wrong: the Python `ruff` vs `vulture` row's first member is a bare tool
  name that the baseline cells carry only as `ruff format` and `ruff check`, so partner-derivation
  would index `ruff` as DEAD-CODE and make every bare ruff hook in every repo classify as a
  dead-code tool. That row is complementary, it emits nothing either way, and `ruff` already
  resolves through D-T3's documented default -- so the cross-category outcome there is correct and
  must be left alone. Three cited entries plus an import-time guard beats one clever rule.

  A pairs member that is a RULE FAMILY rather than a tool -- exactly one row today, the Python
  row pairing a linter's security rule selector against a dedicated security scanner -- is marked
  as such in the data and is exempt from this requirement entirely. It is not a tool a repo can
  declare as a hook, so indexing it would put a rule selector into a structure whose every other
  key is an invocable tool name. Its row stays in the table as researched data; plan 11-03 records
  that generic hook-pair evaluation cannot reach it rather than implying it can.

  Confidence for any of these matches is still `baseline` (D-T3): all of it is the same hardcoded,
  already-researched spec content. Record the SOURCE per index entry anyway, so a classification's
  evidence names which part of the catalog answered.
- **D-T2 -- longest match wins, and matching is token-bounded.** The spec's table carries
  multi-word entries (`ruff format`, `ruff check`, `tsc --noEmit`, `cargo clippy`). Classification
  matches catalog entries against the lowercased `"<hook id> <entry command>"` haystack, longest
  entry first, with token boundaries on both ends -- so `eslint-plugin-security` never resolves as
  `eslint`, and `ruff format` never resolves as `ruff check`.
- **D-T3 -- three confidence levels, always reported, and staleness is a FLAG not a fourth level.**
  `baseline` (matched the hardcoded catalog -- either table, per D-T7), `cache` (matched a per-stack
  cache entry this skill's own `cache-update` wrote), `inferred` (the config is genuinely ambiguous
  and a documented hook-id convention decided it). Anything else is `unclassified` with
  `needs_research`. This is PROJECT.md's core value expressed as a field: a classification is never
  presented at higher confidence than its sourcing.
  The shared `read_stack_cache` has a third state -- it returns `state: stale` with the data still
  populated (`stack_cache.py:50-78`). A stale hit is reported as `confidence: "cache"` PLUS a
  separate boolean `stale` field set true, never as a fourth confidence string. Rationale: `stale`
  is not a different SOURCE, it is a caveat about the same source, and the enum has exactly four
  members that plan 11-03, plan 11-04's `SKILL.md` limits section and Phase 15 all read. A fresh hit
  carries the same field set false, so a consumer never has to distinguish "absent" from "false".
  The ONE ambiguity that exists in the spec's own table today is `ruff`, which appears in two
  categories (`ruff format` formatting, `ruff check` linting). A bare `ruff` hook id with no
  disambiguating entry resolves to `linting` at `inferred` confidence, because the upstream
  `ruff-pre-commit` repository's hook id for the linter is the bare name while the formatter's is
  suffixed. Encode that as a small, explicitly-commented defaults mapping, not as a special case
  buried in the matcher.
- **D-T4 -- out-of-taxonomy is a third outcome, not a gap.** The six categories describe static
  analysis. A test runner, a file-hygiene fixer, or a compile check is not in any of them and must
  NOT be reported as unclassified-needing-research, which would make every real repo's report
  mostly noise. Pin an explicit marker set (test-runner markers, and the standard `pre-commit-hooks`
  hygiene ids) whose matches are reported as out-of-taxonomy with a stated reason. A hook matching
  neither the catalog nor this set is genuinely unclassified and DOES need research.
- **D-T5 -- absence is computed from the classification, never from a second keyword scan.** The
  two absence checks ask "did the classifier put anything in this category?" -- so a repo can never
  be told it has no dead-code tooling by one part of the output while another part lists one.
- **D-T6 -- finding vocabulary, pinned.** `category: "tool-taxonomy"`, `issue:
  "unclassified_tool"`, `CRITICALITY_MEDIUM`, `needs_research: True`, no `recommendation` (so it
  routes to `blocked`). `category: "category-absence"` with `issue: "duplicate_code_absent"` /
  `issue: "dead_code_absent"`, `CRITICALITY_MEDIUM`, with a `recommendation` naming the concrete
  baseline tool when the stack is known, or `needs_research: True` and no recommendation when it is
  not. Medium rather than high on both counts: the design spec calls these the two most commonly
  skipped categories across every ecosystem surveyed, which makes them a real gap but not a broken
  gate.
