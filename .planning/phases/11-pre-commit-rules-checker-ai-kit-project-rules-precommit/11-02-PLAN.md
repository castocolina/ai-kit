## Decisions this plan makes on the planner's authority

11-CONTEXT.md's "Claude's Discretion" block leaves the catalog's exact shape open and D-02 hands
the category reconciliation to this phase's planner. Settled here so the executor implements one
design and plan 11-03's checks can rely on it:

- **D-T1 -- the tool index is DERIVED, the table is the source.** The baseline stacks table is
  transcribed from the design spec and is the only hand-written tool data. The tool-name-to-category
  index is computed from it at import time. A tool appearing in several stacks (`jscpd`) must land
  in one category; a derivation that would put one tool name in two categories must raise at import
  rather than silently pick one, because that is a transcription error in the table.
- **D-T2 -- longest match wins, and matching is token-bounded.** The spec's table carries
  multi-word entries (`ruff format`, `ruff check`, `tsc --noEmit`, `cargo clippy`). Classification
  matches catalog entries against the lowercased `"<hook id> <entry command>"` haystack, longest
  entry first, with token boundaries on both ends -- so `eslint-plugin-security` never resolves as
  `eslint`, and `ruff format` never resolves as `ruff check`.
- **D-T3 -- three confidence levels, always reported.** `baseline` (matched the hardcoded table),
  `cache` (matched a per-stack cache entry this skill's own `cache-update` wrote), `inferred` (the
  config is genuinely ambiguous and a documented hook-id convention decided it). Anything else is
  `unclassified` with `needs_research`. This is PROJECT.md's core value expressed as a field:
  a classification is never presented at higher confidence than its sourcing.
  The ONE ambiguity that exists in the spec's own table today is `ruff`, which appears in two
  categories (`ruff format` formatting, `ruff check` linting). A bare `ruff` hook id with no
  disambiguating entry resolves to `linting` at `inferred` confidence, because the upstream
  `ruff-pre-commit` repository's hook id for the linter is the bare name while the formatter's is
  suffixed. Encode that as a small, explicitly-commented defaults mapping, not as a special case
  buried in the matcher.
- **D-T4 -- out-of-taxonomy is a third outcome, not a gap.** The six categories describe static
  analysis. A test runner, a file-hygiene fixer, or a compile check is not in any of them and must
  NOT be reported as unclassified-needing-research, which would make every real repo's report
  mostly noise. Pin an explicit marker set (test-runner markers, and the standard `pre-commit-hooks`
  hygiene ids) whose matches are reported as out-of-taxonomy with a stated reason. A hook matching
  neither the catalog nor this set is genuinely unclassified and DOES need research.
- **D-T5 -- absence is computed from the classification, never from a second keyword scan.** The
  two absence checks ask "did the classifier put anything in this category?" -- so a repo can never
  be told it has no dead-code tooling by one part of the output while another part lists one.
- **D-T6 -- finding vocabulary, pinned.** `category: "tool-taxonomy"`, `issue:
  "unclassified_tool"`, `CRITICALITY_MEDIUM`, `needs_research: True`, no `recommendation` (so it
  routes to `blocked`). `category: "category-absence"` with `issue: "duplicate_code_absent"` /
  `issue: "dead_code_absent"`, `CRITICALITY_MEDIUM`, with a `recommendation` naming the concrete
  baseline tool when the stack is known, or `needs_research: True` and no recommendation when it is
  not. Medium rather than high on both counts: the design spec calls these the two most commonly
  skipped categories across every ecosystem surveyed, which makes them a real gap but not a broken
  gate.
