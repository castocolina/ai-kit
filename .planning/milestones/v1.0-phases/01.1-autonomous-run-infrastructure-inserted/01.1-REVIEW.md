# Phase 1.1: Code Review Report

**Reviewed:** 2026-09-09
**Depth:** standard
**Files Reviewed:** 6
**Status:** issues_found

## Summary

Reviewed commit `ce62d63` (the only commit in this phase touching real source,
plus its test file) against `tools/setup.py`, `tests/test_wizard_pty.py`,
`tests/e2e/docker/Dockerfile`, `tests/e2e/docker/run.sh`, `.dockerignore`, and
`tests/e2e/docker/fixtures/README.md`. The Dockerfile, `.dockerignore`,
`run.sh`, and fixtures README changes are small, correct, and match their
stated intent — no findings there.

`tools/setup.py`'s `_make_wizard_commit` fix is where the real risk lives. The
diagnosis (doctor rejects a bundled example id referenced in `state["layout"]`
before it physically exists on disk) is correct and independently confirmed by
tracing `_serialize_state` in `tools/wizard_app.py` (tray/OFF segments *are*
folded into every `[[line]]`'s `segments` array via `off_home`, contradicting
nothing — the fix's own code comment is right on this point). However, the fix
as implemented introduces a genuine, unverified-by-any-test regression: it
installs **every** discovered bundled example unconditionally (not just the
ones the user actually enabled in the wizard), and the `known_ext_ids`
pre-install snapshot it threads through `persist_statusline`/`_persist_layout`
means **no explicit `false` can ever be written** for a newly-installed
example — so a user who explicitly declines (or simply never enables) a
bundled example on a first-time install still gets it installed to disk *and*
rendered by default, silently overriding their choice. This is traced end to
end below (`tools/status-line.py`'s `seg_defaults.setdefault(s.id, True)`
confirms the renderer's authoritative default for any id physically present
under the segments dir). No test — including the one this same commit
widened/isolated — exercises the declined-example path, so this shipped
without a failing test to catch it.

## Critical Issues

### CR-01: Wizard-driven install silently enables a bundled example the user declined (or a fresh `--examples=none` install)

**File:** `tools/setup.py:2038-2045` (interacting with `tools/setup.py:1742-1781` `_persist_layout` and `tools/status-line.py:617-623` `cfg_resolve_status`)

**Issue:**

`_make_wizard_commit`'s `commit()` callback, when `adopt` is True, does this
(verbatim):

```python
known_ext_ids = {e["id"] for e in _discover_user_segments(paths.segments_dir)}
examples_dir = os.path.join(paths.install_dir, "examples", "segments")
examples = discover_example_segments(examples_dir)
if examples and not dry:
    install_example_segments(examples, paths.config_dir)
ok = persist_statusline(paths, state, adopt, dry, tty=None,
                        assume_overwrite=True,
                        known_ext_ids=known_ext_ids)
```

Two problems compound into one observable regression:

1. `discover_example_segments(examples_dir)` returns **every** bundled
   example, unfiltered by `state["segments"]` (the wizard's own on/off
   toggles). `install_example_segments` then unconditionally copies *all* of
   them into `paths.config_dir/segments/` and `chmod`s them executable —
   regardless of whether the user enabled, disabled, or never touched that
   example in the Arrange board. This contradicts `cmd_install`'s own
   documented invariant a few lines below in the same file ("the wizard's own
   segment toggles drive what gets installed" — `tools/setup.py:2173-2177`),
   which correctly filters to `chosen = [e for e in examples if
   seg_state.get(e["id"], False)]` (`tools/setup.py:2189-2190`). The new
   commit-time install path bypasses that filter entirely.

2. `known_ext_ids` is snapshotted **before** the install above runs, so it
   never contains the id of a just-installed example. In `_persist_layout`
   (`tools/setup.py:1766-1775`), the boolean-toggle write loop only considers
   ids present in `known_ext_ids`:

   ```python
   for ext_id in ext_ids_for_write:      # == known_ext_ids here
       if ext_id not in state["segments"]:
           continue
       desired = bool(state["segments"][ext_id])
       if desired != _external_enabled_in_toml(paths.config_toml, ext_id, default_on=True):
           seg_changes[ext_id] = desired
   ```

   Since the newly-installed example's id is never in `ext_ids_for_write`,
   this loop can **never** emit an explicit `segments.<id> = false` for it —
   no matter what the user chose. The one-sided in-code comment
   (`tools/setup.py:2023-2033`) only reasons about preventing an incorrect
   `false` for an example the user turned **on**; it never considers an
   example the user left/turned **off**.

3. `tools/status-line.py`'s config resolver confirms the actual runtime
   consequence: any external segment id discovered under the segments
   directory defaults to enabled unless an explicit `[segments] <id> = false`
   exists in the TOML:

   ```python
   seg_defaults = dict(base.segments)
   for s in specs:
       seg_defaults.setdefault(s.id, True)   # tools/status-line.py:620-622
   ```

   Because step 1 physically installs the file and step 2 guarantees no
   explicit `false` is ever written for it, the example renders **on** by
   default in the status line — even when the user explicitly declined it in
   the Arrange board, and even for a fresh `install --examples=none` run
   (the wizard's own commit callback runs and eagerly installs before
   `cmd_install`'s `examples_flag` branch at `tools/setup.py:2178-2194` is
   ever reached, so `--examples=none` cannot prevent this either).

Net effect: on a genuinely fresh machine, every bundled example ships and
renders by default regardless of the user's wizard choice or an explicit
`--examples=none` override. Today this is exactly one segment
(`system_memory`, which surfaces host RAM usage in the status line), but the
mechanism is general and will affect every future bundled example.

This was not caught because:
- `tests/test_wizard_pty.py`'s `TestPhase2E2E.test_pick_skill_and_confirm_creates_symlink`
  (the test this same commit widened/isolated) never touches the Arrange
  board's example toggle — it accepts all defaults, so the toggle-mismatch
  path is never exercised.
- `tests/test_system_memory_e2e.py` only drives `install --examples=all`
  (`tests/test_system_memory_e2e.py:242`) — there is no test for
  `--examples=none` or for declining the example in the wizard UI.
- No unit test calls `_make_wizard_commit`/`known_ext_ids` directly (`grep -rn
  known_ext_ids tests/` finds no test file).

**Fix:** Keep installing all discovered examples to satisfy the doctor's
structural `[[line]]` check (that part of the diagnosis is correct and
necessary — the layout array references every discovered id regardless of
on/off state), but make `known_ext_ids` reflect only the ids that should be
treated as "already at their renderer default" — i.e. add back any
newly-installed id whose *desired* state does NOT match the post-install
default (`True`), so an explicit `false` still gets written for a declined
example:

```python
known_ext_ids = {e["id"] for e in _discover_user_segments(paths.segments_dir)}
examples_dir = os.path.join(paths.install_dir, "examples", "segments")
examples = discover_example_segments(examples_dir)
if examples and not dry:
    install_example_segments(examples, paths.config_dir)
# Any example newly installed just now defaults to enabled at render time
# (tools/status-line.py: seg_defaults.setdefault(id, True)). Only ids whose
# desired state MATCHES that default can skip an explicit write; a
# newly-installed id the user left/turned off still needs an explicit
# `false` written, or it silently renders on.
newly_installed_desired_off = {
    e["id"] for e in examples
    if e["id"] not in known_ext_ids and not state["segments"].get(e["id"], False)
}
ok = persist_statusline(paths, state, adopt, dry, tty=None,
                        assume_overwrite=True,
                        known_ext_ids=known_ext_ids | newly_installed_desired_off)
```

Add a regression test (unit-level, no PTY needed) that calls
`_make_wizard_commit`'s `commit()` (or `_persist_layout` directly) with a
`state["segments"]` entry that is `False` for a not-yet-installed bundled
example, and asserts the written `statusline.toml` contains an explicit
`segments.<id> = false` (or equivalently that the doctor/render pipeline
reports it disabled) — this is the exact case CR-01 currently has zero
coverage for.

## Warnings

### WR-01: `--examples=none`/wizard-decline path has no test coverage at all

**File:** `tests/test_system_memory_e2e.py`, `tests/test_wizard_pty.py`

**Issue:** Every existing test for the example-segment feature drives the
"install and enable" path (`--examples=all`, or accepting all wizard
defaults). There is no test asserting that declining a bundled example (via
wizard toggle or `--examples=none`) actually results in it staying disabled.
This gap is precisely what let CR-01 ship unnoticed, and it remains open
after this phase's fix.

**Fix:** Add a fast unit test (not a PTY/E2E test — `_persist_layout`/
`_make_wizard_commit` are unit-testable in isolation) covering the
decline/`none` path, per the CR-01 fix suggestion above.

### WR-02: `_persist_layout`'s `known_ext_ids` docstring documents only the ON case, not the OFF case it silently breaks

**File:** `tools/setup.py:1747-1754`

**Issue:** The docstring added for `known_ext_ids` says it "lets a caller that
pre-installs a bundled example ONLY to satisfy the doctor's structural
validation ... still have that example treated as 'not yet installed' ...
preserving the ... 'no explicit boolean write → renderer shows it by default'
outcome for a first-time install." This is accurate for a user who wants the
example ON, but the docstring (and the code it documents) never accounts for
a first-time install where the user wants the example OFF — which is exactly
the CR-01 defect. The docstring reads as though this was a deliberate,
fully-reasoned design rather than a partial fix.

**Fix:** Once CR-01 is fixed, update this docstring to state the actual
invariant: an id excluded from `known_ext_ids` skips an explicit write only
when the caller has independently confirmed the desired state matches the
post-install default.

## Info

### IN-01: Redundant example install between `_make_wizard_commit` and `cmd_install`

**File:** `tools/setup.py:2038-2042` and `tools/setup.py:2179-2194`

**Issue:** `_make_wizard_commit`'s commit callback now unconditionally
installs every discovered bundled example, and `cmd_install` (the same
process, immediately after `launch_wizard` returns) installs its own
`chosen` subset again via a second `install_example_segments` call. The
in-code comment acknowledges this is "redundant... and safe" because the
function is idempotent, which is true for the copy-to-disk operation itself,
but the redundant call also emits a second (currently swallowed by
`contextlib.redirect_stdout`, but only in the commit-callback instance) i/o
pass and makes the actual install semantics harder to follow across two call
sites with different filtering logic (see CR-01). Once CR-01's fix makes
`_make_wizard_commit`'s installed set intentional, consider having
`cmd_install`'s post-wizard step no-op instead of re-invoking
`install_example_segments` with a second, differently-filtered list.

**Fix:** Non-blocking; worth a follow-up cleanup once CR-01 is fixed so there
is a single source of truth for "which examples got installed this run."
