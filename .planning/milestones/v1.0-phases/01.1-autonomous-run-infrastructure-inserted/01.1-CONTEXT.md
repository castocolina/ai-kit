<domain>
## Phase Boundary

Phases 1.2-5 of this milestone can run unattended under `/gsd-autonomous`: every
plan is mandatorily routed through cross-AI plan-review convergence, execution
may delegate to cross-AI, and any phase touching runtime code or the installer
is re-verified in a genuinely clean-room container before being trusted. This
phase wires `.planning/config.json`, builds the clean-room Docker/Podman E2E
harness, and writes the `.planning/ONESHOT-AUTONOMOUS.md`/`ONESHOT-RULES.md`
playbook. No product code changes — Phases 1.2-5's own scope is untouched.

<decisions>
## Implementation Decisions

### Phase numbering (why this phase is 1.1, not 0.1)
- **D-01:** The user's original request was to insert this infrastructure phase
  "just before Phase 1" as **Phase 0.1**. Live investigation against
  `gsd-core`'s own `phase-id.cjs` found `SENTINEL_RANGES = Object.freeze([0,
  999])` — under this project's "legacy/bare" phase-numbering convention (no
  bracket project code), any phase whose leading integer is `0` is
  unconditionally treated as a non-milestone sentinel, the exact same bucket as
  this roadmap's own `999.x` Backlog entries. `gsd_run query init.phase-op
  "0.1"` confirmed `phase_found: false` even with a correctly-formatted
  `### Phase 0.1:` heading present, while `"1"` and `"999.1"` both resolved —
  proving this is a hard tool constraint, not a formatting issue. The user
  then chose the fix: **renumber the original Phase 1 to 1.2, and make this
  infrastructure phase 1.1** (both children of integer milestone 1, ordered
  1.1 → 1.2) — live-verified as resolving correctly (`phase_found: true`,
  correct `padded_phase`/`expected_phase_dir`) before proceeding.
  — **Reversibility:** costly — undoing this means renaming the phase
  directory, its `CONTEXT.md`/`DISCUSSION-LOG.md` files, and every
  cross-reference to "Phase 1" across `REQUIREMENTS.md`, `ROADMAP.md`,
  `STATE.md`, and Phase 2/4's own `CONTEXT.md` files a second time — all of
  which were already updated once for this renumber (see Canonical
  References).

### Cross-AI plan-review convergence (mandatory, not GSD's opt-in default)
- **D-02:** Unlike GSD's own default (plan-review convergence is opt-in per
  project), this milestone requires it unconditionally for every `PLAN.md` —
  this was the user's original ask ("all the plans need that to trigger cross
  ai plan review"). `.planning/config.json` sets
  `workflow.plan_review_convergence: true` with `review.default_reviewers:
  ["opencode"]` and `review.models: {"opencode": "router-env/my-plan-review"}`
  — live-verified reachable on this machine (`opencode.jsonc`'s `router-env`
  provider declares the `my-plan-review` combo; `opencode auth list` confirmed
  live credentials).
- **D-03:** Plan-review fallback, if the primary route fails: `opencode run
  --model openai/gpt-5.6-sol` at high reasoning effort — live-verified as a
  real, listed model (`opencode models` output) with live OpenAI oauth
  credentials present. Never substitute the execution fallback model (D-05)
  for this role or vice versa — different jobs.

### Cross-AI execution delegation
- **D-04:** `.planning/config.json` sets `workflow.cross_ai_execution: true`
  and `workflow.cross_ai_command: "opencode run --model router-env/my-coding"`
  — the user's explicit choice (`router-env/my-coding`, the same local combo
  router already used for plan-review, just a different combo). No absolute
  path in the command (user corrected an earlier draft that had one) — relies
  on `opencode` resolving via `PATH`.
- **D-05:** Execution fallback, if the primary route fails: `opencode run
  --model xai/grok-4.6` — live-verified as a real, listed model with live xAI
  oauth credentials present. Every generated `PLAN.md` whose execution should
  delegate to cross-AI must carry `cross_ai: true` in its frontmatter — that
  field is what makes `execute-phase.md` actually delegate instead of falling
  back to a local `gsd-executor`.
- **D-06:** `workflow.cross_ai_timeout: 3600` (1 hour) — carried over
  unmodified from the equivalent `wezterm-setup` playbook value; not
  separately re-discussed since no gray area was raised about it.

### Real-machine-mutation policy — absolute, not per-phase judgment
- **D-07:** Unlike a project where "does this legitimately need to touch the
  real machine" is decided per phase, this milestone makes it an absolute for
  any *verification* activity during an autonomous run: never run
  `tools/install.sh`, `tools/setup.py`'s interactive wizard, or any Phase
  4/1.2-scope config-doctor apply action against the user's real `~/.claude`,
  `~/.cursor`, `~/.config/opencode`, or `~/.codex`. This is a direct
  consequence of `.planning/PROJECT.md`'s own core value (never corrupt uz's
  AI-CLI configuration) — the highest-risk surface in this repo, distinct from
  `wezterm-setup`'s per-phase-judgment-call version of the same rule (that
  project has legitimate real-machine-mutating dev-provisioning phases; this
  one doesn't). Verification instead uses a scratch
  `HOME`/`CLAUDE_CONFIG_DIR`/`AI_KIT_DIR` (the pattern
  `tests/test_wizard_pty.py` already establishes) or the clean-room Docker/
  Podman harness (D-08).

### Clean-room E2E harness
- **D-08:** `tests/e2e/docker/` (Dockerfile + `run.sh`) builds a container with
  no cached `uv`/`textual` and no pre-existing `~/.claude`/`~/.cursor`/
  `~/.config/opencode`/`~/.codex`, then re-runs the **existing** `make
  test`+`make lint` suite (unit tests + the real PTY wizard E2E scenarios +
  `tests/test_install.sh`) inside it — proving the installer/wizard works on a
  machine that's never seen ai-kit before, not just on this already-provisioned
  dev box. Deliberately reuses the current suite rather than inventing a
  parallel bespoke e2e battery. `podman` (not `docker`) is the container engine
  actually available on this machine; the `Makefile`'s `e2e-docker` target
  auto-detects either (`docker` preferred if present, `podman` fallback). Image
  build was verified to complete successfully during this discussion; the full
  `run.sh` suite has not yet been run to green — that's this phase's own plan
  work, not something decided here.
- **D-09 (fixture depth — this discussion):** Multi-CLI config fixtures (fake
  `~/.claude/settings.json`, `~/.cursor/hooks.json`, `opencode.jsonc`, a Codex
  TOML) are **not** all built now. This phase establishes only the **shared
  convention** — a `tests/e2e/docker/fixtures/` directory plus a documented
  pattern for how a fixture file gets mounted into the harness's scratch
  `HOME` — and each later phase (2: opencode.jsonc; 3: Claude + Cursor hooks;
  4: all four runtimes) adds its own fixture file(s) as it needs them, grounded
  in that phase's own research rather than speculating on shapes ahead of time.
  Rejected alternative: building all 4 runtime fixtures now, which would guess
  at config shapes phases 2-4 haven't researched yet (e.g. Phase 4's own Cursor
  config-doctor research, not yet done).
  — **Reversibility:** reversible — the convention is additive; a later phase
  extending it doesn't require reworking this phase's output.
- **D-10 (clean-room gate cadence — this discussion):** `make e2e-docker` is
  required at the close of every phase (1.2, 2, 3, 4) whose plan actually
  touched `tools/*.py`, `tools/install.sh`, or a runtime-config-writing
  `SKILL.md` — not unconditionally every phase, and not only once at milestone
  close. Phase 5 (usage-metrics dashboard, mostly read-only against session
  logs) likely won't trigger it. This confirms `ONESHOT-RULES.md` Rule 6 /
  Per-Phase Checklist item 6 exactly as already drafted — the trade-off (catch
  a clean-room-only failure at the phase that introduced it vs. a faster but
  harder-to-isolate single end-of-milestone check) was decided in favor of
  per-phase, scoped to phases that could plausibly break clean-room behavior.

### Skill-quality / language-discipline (carried forward from AGENTS.md)
- **D-11:** This phase, like every phase in this repo, is bound by
  `AGENTS.md`'s Non-Negotiable Rules unmodified — English-only in every
  artifact this phase produces, stdlib-only runtime code, atomic config
  writes, `skill-judge` gate on any `SKILL.md` change. Not re-discussed here
  since these are already-established, non-negotiable project rules, not gray
  areas.

### Claude's Discretion
None remaining — every gray area surfaced in this discussion (fixture depth,
gate cadence) had an explicit user decision. The phase-numbering fix (D-01)
was investigated live and the user chose the resolution directly, not left to
discretion.

</decisions>
