## Phase numbering: 0.1 vs. 1.1

Before this formal `/gsd-discuss-phase 1.1 --analyze` invocation, the user
originally asked for this infrastructure work to be inserted as **Phase 0.1**
(just before Phase 1). Running `/gsd-discuss-phase 0.1 --analyze` returned
`phase_found: false` from `gsd-core`'s own `init.phase-op` even with a
correctly-formatted ROADMAP.md heading present.

**Investigation performed:** read `gsd-core/bin/lib/phase-id.cjs` directly and
found `SENTINEL_RANGES = Object.freeze([0, 999])` — under the legacy/bare
phase-numbering convention this project uses, any phase number whose leading
integer is `0` is unconditionally read as a non-milestone sentinel (the same
bucket as `999.x` backlog entries), never a real phase. Verified live:
`gsd_run query init.phase-op "0.1"` → `false`; `"1"` and `"999.1"` → `true`.

| Option | Description | Selected |
|--------|-------------|----------|
| Renumber Phase 1 → 1.2, insert this as 1.1 | Both children of integer milestone 1; resolves correctly per live verification | ✓ |
| Fold into Phase 1 itself | No renumbering needed, but conflates infra scope with product scope | |
| Skip formal GSD phase tracking entirely | No renumbering, but loses phase-tracking/verification loop for this work | |

**User's choice:** "shift 1 to 1.2 and our initiative 0.1 as 1.1" — renumber.
