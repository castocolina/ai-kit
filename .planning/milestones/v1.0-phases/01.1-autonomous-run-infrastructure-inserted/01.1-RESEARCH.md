## Summary

Most of the "wiring" for this phase already exists and is committed: `.planning/config.json`'s cross-AI keys, the `Makefile`'s `e2e-docker` target, `tests/e2e/docker/Dockerfile`/`run.sh`, `.dockerignore`, and both `ONESHOT-*.md` files. The real work is narrower and more concrete than "build infrastructure" — it is **making two specific, already-written claims actually true**, both of which this research disproved as currently written and both of which are now backed by first-hand evidence gathered this session:

1. **`make e2e-docker` does not currently pass.** Live-running it in this exact environment (rootless Podman 5.8.4, the only engine present) reproduces a deterministic, first-failure bug: the Dockerfile's `apt-get install` list (`bash git curl ca-certificates shellcheck`) omits `make`, so `tests/e2e/docker/run.sh`'s `make test` line fails immediately with `run.sh: line 15: make: command not found` / `Error 127`. This must be fixed before anything else in this phase can be verified. After patching in a scratch probe image with `make` added, the suite actually runs (1160 tests) and fails **again**, deterministically across 2 independent runs, on `tests.test_wizard_pty.TestPhase2E2E.test_pick_skill_and_confirm_creates_symlink` — a PTY-driven timeout waiting for the "ai-kit is installed" Done screen within `_SUMMARY_DEADLINE = 30.0` seconds, which the constrained container CPU does not meet in time even though the identical test passes on the host. Both findings are pasted verbatim below with real command output.

2. **Success Criterion 4 as literally written cannot be satisfied by GSD's actual behavior.** `ROADMAP.md:51` says *"Running `/gsd-plan-phase 1.2` after this phase closes visibly triggers plan-review convergence."* Reading `gsd-core`'s own `workflows/plan-phase.md` (1727 lines) end-to-end shows `workflow.plan_review_convergence` is referenced there **only** inside the `REVISION_CONFLICT` return-handling block (recording an entry into `REVIEWS.md`'s `## Plan-Revision Conflicts` slot) — never to auto-invoke the convergence loop. The convergence loop only runs when the user (or the autonomous driver) explicitly runs `/gsd-plan-review-convergence <phase>` or `/gsd-autonomous --converge`/`--cross-ai`. A bare `/gsd-plan-phase 1.2` invocation, even with `workflow.plan_review_convergence: true` set, runs the plain planner and never triggers a review cycle. This phase's plan must either amend `ROADMAP.md`'s Success Criterion 4 wording (the `AGENTS.md`/`ONESHOT-RULES.md` Rule-4 precedent: live-verify, then formally correct the roadmap rather than silently reinterpreting it) to name the actual entry point (`/gsd-plan-review-convergence 1.2` or `/gsd-autonomous --to 5 --converge`), or add a wrapper/reminder that makes the bare command route there. `ONESHOT-AUTONOMOUS.md`'s own entry prompt already uses the correct invocation (`/gsd-autonomous --to 5 --converge --opencode`) — so the *autonomous run* itself is fine; only the literal roadmap success-criterion wording is unverifiable as written.

**Primary recommendation:** Fix the Dockerfile (`add make` to the apt-get list), diagnose/adjust the PTY-test timing headroom for constrained-container CPU (raise `_SUMMARY_DEADLINE`/`_BOARD_DEADLINE` or accept a container-specific override), formally amend `ROADMAP.md` Success Criterion 4 to name the real entry point that triggers convergence, then create `tests/e2e/docker/fixtures/` with only the shared mounting-convention doc (no per-runtime fixture files yet, per D-09) — mirroring the `shutil.copy`-into-scratch-directory pattern `tests/test_system_memory_e2e.py` already establishes.

### Pattern 2: Fixture-copy-into-scratch (existing precedent — the pattern D-09's `fixtures/` convention should follow)

**What:** A static fixture file lives at a fixed repo-relative path; test setup `shutil.copy`s it into the scratch instance tree before pointing env vars at that tree. The fixture itself is never referenced live in place.

**When to use:** D-09's `tests/e2e/docker/fixtures/` directory — this is the existing, already-proven pattern in this exact codebase for "a fixture needs to exist inside a scratch/copied tree", so the new convention should reuse it rather than invent a container-volume-mount mechanism.

**Example (verbatim, the load-bearing precedent):**


**Applied to `tests/e2e/docker/fixtures/`:** because `tests/e2e/docker/Dockerfile:26` already does `COPY --chown=aikit:aikit . /home/aikit/ai-kit` (the *entire* repo, and `.dockerignore` does not exclude `tests/`), any file placed under `tests/e2e/docker/fixtures/` is automatically baked into the image at build time — no `podman run -v` volume mount is needed or should be added. The convention to document in `tests/e2e/docker/fixtures/README.md`: a later phase's fixture (e.g. Phase 2's `opencode.jsonc` fixture) is copied by test/setup code at run time from `tests/e2e/docker/fixtures/<runtime>/<file>` into a scratch `$HOME`-relative path (e.g. `$XDG_CONFIG_HOME/opencode/opencode.jsonc`) before the code under test reads it — exactly the `shutil.copy`-into-scratch-tree shape above, never a live in-place reference and never a container volume mount.

### Anti-Patterns to Avoid
- **Volume-mounting `~/.claude`/`~/.cursor`/`~/.config/opencode`/`~/.codex` into the container "to save COPY time":** defeats the entire purpose of D-08 — the container's value is that it has *never seen* real AI-CLI config. Never mount the host's real config directories, even read-only.
- **Reinterpreting Success Criterion 4 silently:** per `ONESHOT-RULES.md` Rule 4 (`.planning/ONESHOT-RULES.md:104-112`), a live-verified contradiction between a locked roadmap wording and actual tool behavior must be resolved by a **formal, dated amendment** to `ROADMAP.md`, not by silently treating the bare `/gsd-plan-phase` command as "close enough."
- **Building all four runtime fixtures now:** explicitly rejected by D-09 — guesses at config shapes that Phases 2-4 haven't researched yet.

### Pitfall 2: A PTY wizard E2E test times out under container CPU constraints even though it passes on the host
**What goes wrong:** After patching a scratch probe image to add `make` and re-running, the suite executes (1160 tests) but fails deterministically (2/2 independent runs) on `tests.test_wizard_pty.TestPhase2E2E.test_pick_skill_and_confirm_creates_symlink`. The failure is a `drive_until` timeout: `AssertionError: drive_until: marker b'ai-kit is installed' not found before deadline` — the wizard did not finish writing symlinks + validating the status-line config + rendering the Done screen within `tests/test_wizard_pty.py`'s `_SUMMARY_DEADLINE` (30.0s, `tests/test_wizard_pty.py:400`).

**Why it happens:** Rootless Podman + a shared/constrained CPU allocation makes the container's wall-clock throughput for the same PTY-driven Textual render loop measurably slower than the host's. This is exactly the class of flake `tests/test_wizard_pty.py`'s own deadline comments already anticipate ("generous: uv + textual init from warm cache") but tune for a *host*, not a fresh, cold, resource-constrained container.

**How to avoid:** Either (a) raise the relevant `_SUMMARY_DEADLINE`/`_BOARD_DEADLINE`/`_DRAIN_DEADLINE` constants specifically when running under the container (e.g., an env-var-gated multiplier), or (b) accept a documented, wider deadline unconditionally since the tests already poll via `select()` rather than sleeping (no cost to a longer ceiling on a fast host). Do not disable or skip this test inside the container — that would silently narrow exactly what D-08 exists to prove.

### Pitfall 3: Success Criterion 4's literal wording is not achievable by bare `/gsd-plan-phase`

Reading `gsd-core`'s `workflows/plan-phase.md` shows `workflow.plan_review_convergence` is read there only inside the `REVISION_CONFLICT` handling path (`workflows/plan-phase.md:1265-1273,1287,1313`) — never to decide whether to run the convergence loop. The convergence loop lives entirely in `workflows/plan-review-convergence.md`, gated by its own `1.5. **Why it happens:** The roadmap's success criterion was almost certainly written assuming `workflow.plan_review_convergence: true` acts like a "master switch" that reroutes every planning invocation — but `gsd-core`'s actual design keeps convergence strictly opt-in per invocation (via an explicit command/flag), with the config key only serving as a fail-fast gate on those specific entry points, not a global behavior override.

**How to avoid:** Amend `ROADMAP.md` Success Criterion 4 to name the real entry point — either `/gsd-plan-review-convergence 1.2` (explicit) or `/gsd-autonomous --to 5 --converge` (the actual entry point `ONESHOT-AUTONOMOUS.md:28` already uses) — rather than the bare `/gsd-plan-phase 1.2` command. **Warning signs:** Attempting to verify Success Criterion 4 literally (running bare `/gsd-plan-phase 1.2` and expecting a review cycle to fire) will always "fail" even after this phase's own config wiring is perfectly correct — because the config wiring was never the thing standing between the bare command and convergence.

### Pitfall 4: `run.sh` calling `make test`+`make lint` sequentially means one failure hides the other
**What goes wrong:** Because of `set -euo pipefail`, any failure in `make test` prevents `make lint` from ever running inside the container — a plan or CI reader could wrongly conclude lint is untested when it simply never got the chance to run.
**Why it happens:** `run.sh:14-18`'s straightforward `make test` then `make lint` sequencing, matching the host `Makefile`'s own philosophy (`make test` then `make lint` are two separate, sequential targets there too) — this is consistent with host behavior, not a container-specific bug, but worth calling out so it isn't mistaken for a lint failure during debugging.
**How to avoid:** No change needed to the harness's design intent — just be aware when reading a failed `e2e-docker` run.log that a `make test` failure means lint status is simply unknown, not "passing."

## Open Questions

1. **Does `make lint` pass inside the container once `make test` is fixed?**
   - What we know: `make test` currently fails before `make lint` ever runs (Pitfall 1, Pitfall 4).
   - What's unclear: whether `shellcheck` (installed via apt, version may differ from the host's Homebrew-installed `shellcheck`) or `python3 -m py_compile` behave identically in the container.
   - Recommendation: this phase's plan should include a task that reaches `make lint` (by fixing Pitfalls 1 and 2 first) and captures its real output before declaring Success Criterion 2 met.

2. **Should the PTY-test deadline fix be container-conditional or a blanket increase?**
   - What we know: the timeout fired consistently at the `_SUMMARY_DEADLINE = 30.0` boundary for one specific test; other PTY tests in the same run passed within their own deadlines.
   - What's unclear: whether a blanket increase (simplest, `tests/test_wizard_pty.py` currently has no environment-conditional deadline logic at all) risks masking a genuine future regression by giving CI too much slack.
   - Recommendation: prefer a blanket, moderate increase (e.g., 30s → 45-60s) over an environment-conditional branch, given `drive_until` already returns as soon as the marker appears (no fixed-sleep cost) — the wider ceiling only matters when something is actually slow.
