  <behavior>
    - **[Round 1]** `classify_loop.py::normalize_skeleton(command_text)`
      implements the CORRECTED 4-step algorithm (see `key_links` for the
      full worked-through spec): (1) `$`-prefixed variable references →
      `<VAR>`; (2) remaining quoted spans → `<STR>`; (3) punctuation-aware
      tokenization preserving shell keywords/operators verbatim; (4) a
      left-to-right walk replacing the loop-variable DECLARATION token
      (right after `for`) with `<VAR>`, keeping the command/tool name
      (the first bare token after `do`/`;`/`&&`/`then`/start) literal, and
      replacing every OTHER bare non-keyword token with `<ARG>` —
      **[Round 2]** EXCEPT a token that is already exactly `<VAR>`,
      `<STR>`, or `<ARG>` (produced by step (1)/(2)), which the walk
      leaves untouched rather than re-substituting (guards against step
      (4) silently rewriting a step-(2)-produced `<STR>` to `<ARG>`, which
      would still leave both PRD examples matching each other — since the
      bug is symmetric — but would silently break the documented,
      stable-across-runs skeleton string). Both of
      the PRD's own worked examples — `for f in *.py; do rg pattern "$f"; done`
      and `for x in *.md; do rg other "$x"; done` — reduce to the
      IDENTICAL skeleton `for <VAR> in <ARG>; do rg <ARG> <STR>; done`
      (this is the Round 1 fix: the original draft's quote/`$`-only
      substitution left `f`/`x`, `*.py`/`*.md`, and `pattern`/`other`
      un-normalized, so the two examples never actually matched).
    - `classify_loop.py::mine_recurring_shapes(rows, min_occurrences)`
      groups the given `control_flow_script`/`unclassified` rows by their
      `normalize_skeleton` output, and returns only the groups whose size
      is `>= min_occurrences` — a default `DEFAULT_MIN_OCCURRENCES = 2`
      constant, with a comment citing the PRD's own "exact threshold TBD
      once real data volume is known" framing, so this default is
      understood as a documented placeholder, not a researched constant.
    - **[Round 1]** For each recurring group found,
      `classify_loop.py::infer_family_for_group(skeleton, sample_command_text)`
      builds ONE flat set of every `CURATED_SUBSTITUTIONS` pair member
      (`{"cat","bat","grep","rg","find","fd","sed","sd","ls","eza"}`) and
      scans the sample's own whitespace-delimited tokens, treating a
      token as a CANDIDATE when it IS a member of that set (via direct
      set membership, NOT `family.family_of(token) != token` — the
      original draft's inequality check incorrectly rejected a literal
      curated member like `grep` itself, since `family_of("grep") ==
      "grep"`) AND is not itself a shell keyword; when exactly one such
      candidate is found, returns `(family.family_of(candidate), "LOW")`
      (resolving THAT candidate to its family — e.g. `rg` → `grep`,
      `grep` → `grep`); when zero or more than one candidate is found
      (ambiguous), returns `(None, None)` — this group is left
      unclassified rather than guessing between two candidates.
    - **[Round 1]** `classify_loop.py::run_classification(conn, min_occurrences=DEFAULT_MIN_OCCURRENCES)`
      runs ENTIRELY inside one transaction (`conn.execute("BEGIN")` ...
      `conn.commit()`, `conn.rollback()` on any exception): it FIRST
      resets `inferred_family=NULL, inferred_confidence=NULL` for EVERY
      row whose `command_shape` is `control_flow_script` or
      `unclassified` (one parameterized `UPDATE`), THEN reads that SAME
      now-reset row set (regardless of WHEN each was refined — including
      rows from a prior `refine` run, proving the historical-
      reclassification requirement), mines recurring shapes, and for each
      group with a successfully inferred family, calls
      `refined_store.update_inferred_family` on EVERY row in that group
      — returns a summary dict (`{"groups_found": int,
      "rows_reclassified": int}`). This reset-then-remine design is what
      makes an IMPROVED rule/threshold correctly CLEAR a stale annotation
      from a group that no longer qualifies, not just add new ones.
    - `run_classification` NEVER modifies a row's own `family` or
      `command_shape` column — only `inferred_family`/
      `inferred_confidence`.
    - `refined_store.py::update_inferred_family(conn, row_id,
      inferred_family, inferred_confidence)` is a simple, single
      parameterized `UPDATE refined_commands SET inferred_family=?,
      inferred_confidence=? WHERE id=?` call — **[Round 1]** it does NOT
      itself call `conn.commit()`; the caller (`run_classification`)
      owns the transaction boundary, per the behavior above.
    - Running `run_classification` a SECOND time against the SAME
      connection, immediately after the first, with the SAME
      `min_occurrences`, is idempotent (no error, same result — the
      reset-then-remine design naturally reproduces the identical
      outcome). Running it a THIRD time with a LOWER `min_occurrences`
      reclassifies a group that didn't meet the original, higher
      threshold.
