## Facts live-verified on this machine during planning (2026-09-10)

- `opencode.db`'s real schema (`sqlite3 ~/.local/share/opencode/opencode.db
  ".schema"`): `session(id, project_id, workspace_id, directory, title,
  cost, tokens_input, tokens_output, tokens_reasoning, tokens_cache_read,
  tokens_cache_write, model, time_created, time_updated, ...)`;
  `message(id, session_id, time_created, time_updated, data)` where `data`
  is a JSON blob whose real shape (assistant turn) is
  `{"role":"assistant","cost":0,"tokens":{"total":N,"input":N,"output":N,
  "reasoning":N,"cache":{"write":N,"read":N}},"modelID":"...",
  "providerID":"...","path":{"cwd":"...","root":"..."},
  "time":{"created":ms,"completed":ms},"finish":"..."}`;
  `part(id, message_id, session_id, time_created, time_updated, data)`
  where a Bash-tool-call `data` value looks like
  `{"type":"tool","tool":"bash","callID":"...","state":{"status":
  "completed","input":{"command":"...","workdir":"..."},"output":"...",
  "metadata":{"exit":N,"truncated":false},"time":{"start":ms,"end":ms}}}`
  — `json_extract(data,'$.tool')` values observed on this machine's own
  live DB include `task, read, glob, bash, todowrite, edit, grep, write,
  webfetch, skill, question, websearch, apply_patch` and several MCP-tool
  names; ONLY `tool == "bash"` parts represent a shell command this
  pipeline's family/decomposer axes care about — every other `tool` value
  is still captured losslessly (D-02) but is out of scope for command-shape
  classification (05-04's job, not this plan's).
- `rtk`'s `history.db` (`sqlite3 ~/.local/share/rtk/history.db ".schema"`):
  `commands(id INTEGER PRIMARY KEY, timestamp TEXT, original_cmd TEXT,
  rtk_cmd TEXT, input_tokens INTEGER, output_tokens INTEGER, saved_tokens
  INTEGER, savings_pct REAL, exec_time_ms INTEGER, project_path TEXT)`;
  `parse_failures(id INTEGER PRIMARY KEY, timestamp TEXT, raw_command TEXT,
  error_message TEXT, fallback_succeeded INTEGER)`. `commands`' own
  `input_tokens`/`output_tokens`/`saved_tokens` are RTK'S OWN
  rewrite-savings bookkeeping (tokens `rtk`'s rewrite saved vs. the
  original command), NOT an LLM session's token usage — do not conflate
  these with `refined_commands.tokens_input`/`tokens_output`, which mean
  LLM usage everywhere else in this schema; this plan's job is capture
  only, so this distinction only needs to be RECORDED here (verbatim in
  `payload`), not resolved — 05-04's refiner decides how (or whether) to
  surface rtk's savings figures on the `refined_commands` row it attaches
  them to.
- `~/.local/share/rtk/tee/*.log` filenames observed on this machine:
  `<epoch-seconds>_<sanitized-command-hint>.log`, e.g.
  `1788953554_brew_install_--help.log`,
  `1788969769_grep_0_e0_scratchpad_host_make_test_log.log` — the sanitized
  hint is best-effort and lossy by construction (this is `rtk`'s own
  filename-safe encoding of the original command, not a reliable parse
  target); this plan extracts the leading epoch integer via a regex
  (`^(\d+)_`) for the timestamp and keeps the REST of the filename as an
  opaque `filename_hint` string — it does not attempt to reverse-engineer
  the original command from the hint. `[tee]`'s own `mode="failures"` /
  `max_file_size=1048576` / `max_files=20` config caps this directory's
  size — this plan's capture must tolerate a directory containing UP TO
  the configured `max_files` entries without issue (no artificial limit of
  its own).
- **[Round 1, live-verified during this revision, 2026-09-10]**
  `sqlite3 ~/.local/share/opencode/opencode.db "PRAGMA table_info(part)"`
  confirms `id` is declared `TEXT PRIMARY KEY` (same for `message.id` and
  `session.id`) — NOT an auto-incrementing integer. The original draft's
  `last_part_rowid`/`id > cursor` integer-comparison cursor design does

  `(time_created, id)` tuple cursor (see `must_haves.truths` above),
  ordered `ORDER BY time_created, id` — `time_created` is an epoch-ms
  integer column present on all three tables, verified via the same
  `PRAGMA table_info` query.

  `~/.local/share/opencode/storage/` still exists on this machine

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `opencode.db` / `rtk/history.db` (live, externally-written files) → this pipeline's read path | These files are actively written by their OWN tool's running process. A read connection from an unrelated pipeline must never risk becoming a write, a lock contention that blocks the owning tool, or a crash if the file is mid-write when opened. |
| rtk tee log content → raw capture | Tee logs capture FAILURE-only command output (`[tee] mode="failures"`), which can contain arbitrary stderr/stdout text from any command the user ran, including secrets a command might have printed. This is unchanged risk surface (the file already exists, already locally readable) — this plan's capture step does not increase exposure, it copies already-local content into a second already-local, same-permission-class file. |
