# Phase 01.2: Code Review Report

**Reviewed:** 2026-09-09
**Depth:** standard
**Files Reviewed:** 11
**Status:** issues_found

## Summary

This phase's code (the `ai_kit_spec` catalog/detection/config machinery, `tools/install.sh`, and
the two `ai-kit-spec-*` skill docs) is unusually well-hardened already: the full `tests.test_ai_kit_spec`
suite (457 tests) and `tests/test_install.sh` (14 checks, including a `shellcheck` pass) both run
clean, and much of `cli.py`/`model_catalog.py` carries inline comments documenting prior review
rounds ("CRITICAL finding," "round-2 re-review," etc.) that have already been fixed and covered by
tests. No hardcoded secrets, `eval`, unguarded `shell=True` with attacker-controlled input, or
empty `except`/`catch` blocks were found. The remaining issues below are genuine but narrower:
one silent-data-corruption edge case in vendor derivation, a resource-leak edge case in the
installer's tarball fetch path, and a couple of un-validated/under-specified spots that could
misbehave on unusual input. Nothing here rises to Critical/BLOCKER — no crash, injection, or
data-loss path was found on the tested/expected inputs — but the WARNING items below should be
fixed since they degrade correctness on edge-case input the code was clearly written to
anticipate (the file already handles the adjacent, more common case correctly).

## Warnings

### WR-01: `_slugify`'s empty-result case is unguarded at one of its two call sites, unlike the other

**File:** `skills/ai-kit-spec-review/ai_kit_spec/cli.py:337-341` vs. `skills/ai-kit-spec-review/ai_kit_spec/cli.py:364-365`

**Issue:** `_slugify()` (line 91-93) can legitimately return an empty string when its input is
entirely non-alphanumeric (e.g. an Artificial Analysis `model_creator.name` of `"—"` or similar) —
`re.sub(r"[^a-z0-9]+", "-", name.lower()).strip("-")` on such input yields `""`. The code already
knows this and guards against it once, at the `md_enrich_match` provider-hint derivation:

```python
aa_provider_hint = _slugify(
    (aa_match.get("model_creator") or {}).get("name", "")) or None
if aa_provider_hint:
    md_enrich_match = match_models_dev(...)
```

But the *primary* provider-derivation branch a few lines later does not apply the same `or None`
guard:

```python
elif aa_match and (aa_match.get("model_creator") or {}).get("name"):
    provider = _slugify(aa_match["model_creator"]["name"])
```

This `elif` only tests the *raw* `name` string for truthiness before calling `_slugify`, not the
slugified result. If Artificial Analysis returns a `model_creator.name` that is non-empty but
slugifies to `""`, `provider` becomes `""` (a string, not `None`) — this passes the later
`if provider is not None` gate, so the code proceeds to mint
`canonical_key("", bare_model_part(model_id))`, i.e. a malformed catalog key like
`"/gpt-5.6-sol"` with an empty vendor segment, and writes it to the catalog as if it were a
legitimate entry (`"provider": ""` passes `validate_catalog_entry`'s type check since `""` is a
valid `str`). The correct behavior — matching the `vendor_unknown=True` branch a few lines below,
which exists precisely to prevent silently persisting a bogus vendor guess — never triggers,
because that branch is only reached when the raw name itself is falsy/missing, not when it
slugifies to nothing. No test in `tests/test_ai_kit_spec.py` covers a `model_creator.name` that
slugifies to empty (only `{}`/absent-name is covered, e.g.
`test_aa_match_with_no_usable_model_creator_name_routes_to_unmatched_without_crashing`).

**Fix:**
```python
elif aa_match and _slugify((aa_match.get("model_creator") or {}).get("name") or ""):
    provider = _slugify(aa_match["model_creator"]["name"])
```
or, mirroring the existing guarded call site directly:
```python
elif aa_match and (_slugify((aa_match.get("model_creator") or {}).get("name", "")) or None):
    provider = _slugify(aa_match["model_creator"]["name"])
```

### WR-02: `tools/install.sh` leaks a temp directory when the tarball fetch/extract fails

**File:** `tools/install.sh:108-134`

**Issue:** In the no-git tarball-fetch branch, `tmp="$(mktemp -d "$parent/.ai-kit.XXXXXX")"` is
created before the fetch, then:
```bash
if have curl; then
  curl -fsSL "$tarball" | tar xz --strip-components=1 -C "$tmp"
else
  wget -qO- "$tarball" | tar xz --strip-components=1 -C "$tmp"
fi
```
Under `set -euo pipefail` (line 34), a failure in either half of this pipeline (network error,
404 on `$REPO_BRANCH`, corrupted/partial archive, `tar` failure) causes the whole script to exit
immediately via `set -e` — before the atomic-swap logic below it ever runs. There is no `trap`
registered anywhere in this script to clean up `$tmp` on early exit, so a failed fetch leaves an
orphaned `.ai-kit.XXXXXX` directory (potentially containing a partial, corrupt extraction) behind
in `$parent` (typically `${XDG_DATA_HOME:-~/.local/share}`) every time this happens — e.g. a flaky
network during the curl-piped-into-bash one-liner this script is explicitly designed for. This
does not corrupt an existing install (the existing `$INSTALL_DIR` is never touched at this point),
but it is an unbounded, silent disk-space/clutter leak on every transient fetch failure. Not
covered by `tests/test_install.sh`, which only exercises the swap contract structurally (test 4)
without a real curl/tar failure.

**Fix:** register a cleanup trap before creating `$tmp`, scoped to the fetch:
```bash
local tmp; tmp="$(mktemp -d "$parent/.ai-kit.XXXXXX")"
trap 'rm -rf "$tmp"' RETURN
if have curl; then
  curl -fsSL "$tarball" | tar xz --strip-components=1 -C "$tmp"
else
  wget -qO- "$tarball" | tar xz --strip-components=1 -C "$tmp"
fi
trap - RETURN   # clear before the swap so a mid-swap failure's own cleanup path (which already
                # handles $tmp explicitly) isn't double-triggered
```
(or equivalent — the key fix is that a `curl|tar`/`wget|tar` failure must not leave `$tmp` behind).

### WR-03: `config_io.py`'s TOML writer has no guard against a dict-valued reviewer field

**File:** `skills/ai-kit-spec-review/ai_kit_spec/config_io.py:85-93, 183-187`

**Issue:** `cfg_render_toml` writes every key of a `[[reviewers]]` entry via `_toml_value`:
```python
def _toml_value(v) -> str:
    if isinstance(v, bool): ...
    if isinstance(v, (int, float)): ...
    if isinstance(v, list): ...
    escaped = str(v).replace("\\", "\\\\").replace('"', '\\"')
    return f'"{escaped}"'
```
There is no branch for `dict` — a dict value falls through to the final `str(v)` branch, which
renders Python's `repr()`-like `str()` of the dict (e.g. `"{'timeout_tiers': [900, 1800]}"`) as a
quoted TOML *string*, not a table. `validate_reviewer_fields` (same file, lines 100-125) only
type-checks the handful of fields this design specifically added (`purpose`, `native_runtime`,
`is_router`, `fallback_quota`) — any other field name on a reviewer entry, including a nested
`extra = {...}` object a caller might mistakenly pass through (e.g. a bug in a future wizard
version, or a hand-edited JSON config fed to `render-toml --json-config`), is written through
unchecked and silently corrupted into a meaningless string value rather than being rejected at
validation time. `skills/ai-kit-spec-config/SKILL.md` (line 265-268) documents this exact failure
mode as a known constraint users must avoid ("this config format has no nested-object support...
so a nested `extra = { timeout_tiers = [...] }` would be written out as a string and silently fall
back to the policy default") — i.e. the silent-corruption behavior is a known, accepted quirk, but
there is no code-level guard (rejection + `WARNING:` stderr line, matching the existing pattern
used for other invalid reviewer fields) preventing it from actually happening. No test in
`tests/test_ai_kit_spec.py` exercises `_toml_value`/`cfg_render_toml` with a dict-valued field.

**Fix:** either raise/reject a dict-valued field the same way `validate_reviewer_fields` rejects
other malformed fields (emit it via the existing `rejections` list so it surfaces through Step 4's
existing `WARNING:` reporting path instead of writing corrupted TOML silently), or add an explicit
`isinstance(v, dict)` branch to `_toml_value` that raises immediately rather than falling through
to the string branch:
```python
def _toml_value(v) -> str:
    if isinstance(v, dict):
        raise ValueError("cfg_render_toml: nested object values are not supported "
                          "in this TOML schema (no dict branch in the writer)")
    ...
```

### IN-01: `--if-stale` has different flag semantics across two subcommands in the same CLI

**File:** `skills/ai-kit-spec-review/ai_kit_spec/cli.py:496-502` vs. `518-527`

**Issue:** `detect-runtimes --if-stale` takes a required PATH value (`p_detect.add_argument(
"--if-stale", default=None, metavar="PATH", ...)`), while `fetch-model-catalog --if-stale` is a
boolean flag (`p_catalog.add_argument("--if-stale", action="store_true", ...)`). Both are
correctly implemented for their own subcommand's contract and are well covered by tests, but the
same flag name doing structurally different things (value-taking vs. boolean) one subcommand apart
in the same `argparse` program is an easy source of copy-paste mistakes for anyone extending this
CLI or writing new skill documentation that calls it (the two `references/`/`SKILL.md` docs
reviewed here do use each form correctly today).

**Fix:** rename one of the two (e.g. `fetch-model-catalog`'s boolean flag to `--skip-fetch-if-fresh`
or similar) to make the two subcommands' option sets textually distinct, or add a one-line note in
each subcommand's own `--help` string cross-referencing the other's different contract.

### IN-02: `cli-model-selection.md`'s inline `python3 -c` filter snippet leaves `kept_clis`'s scope ambiguous

**File:** `skills/ai-kit-spec-config/references/cli-model-selection.md:49-58`

**Issue:** The filtered-runtimes-snapshot snippet does:
```python
snap['clis'] = {name: ({**data, 'models': chosen[name]} if name in chosen else data)
                for name, data in snap.get('clis', {}).items() if name in kept_clis}
```
`chosen` is explicitly scoped to multi-provider CLIs only ("`chosen = {<cli>: [<chosen model
id(s)>], ...}  # only for multi-provider CLIs`" per the surrounding comment), but `kept_clis` is
described only as `{<CLI names the user kept>}` with no explicit statement of whether it must
include single-provider CLIs (codex, grok) the user separately kept at Step 1's per-CLI ask. Since
the dict comprehension filters on `if name in kept_clis`, an agent that populates `kept_clis` with
only the multi-provider CLI names it was iterating over in this step's own grouping loop (the most
locally-obvious reading, since this whole numbered item is scoped to "For each kept multi-provider
CLI...") would silently drop every kept single-provider CLI from `$FILTERED_RUNTIMES_JSON` —
directly contradicting this same paragraph's own claim that "single-provider CLIs, which have no
`models` array to narrow, pass through unchanged." This is a documentation-clarity gap that could
produce a real omission bug during an actual wizard run, not a code defect in the reviewed `.py`
files themselves.

**Fix:** make the snippet's own comment explicit, e.g. `kept_clis = {<ALL CLI names the user kept
at Step 1, both multi- and single-provider>}` so the two paragraphs (comment vs. prose) cannot be
read as contradicting each other.
