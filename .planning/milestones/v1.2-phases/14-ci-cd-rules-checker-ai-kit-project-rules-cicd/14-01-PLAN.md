- **D-C1 -- applicability gate, evaluated FIRST and short-circuiting.** This repo has CI config
  when EITHER holds at the repository ROOT:
    (i) a root file named `.gitlab-ci.yml` or `.gitlab-ci.yaml`;
    (ii) a root directory `.github/workflows/` containing at least one entry whose name ends in
         `.yml` or `.yaml`.
  If neither holds, `check` returns an EMPTY finding list and nothing else runs. Root-scoped:
  `os.path.isfile`/`os.path.isdir` against explicitly-joined paths plus ONE non-recursive
  `os.listdir` of the workflows directory. No walk, no descending glob.
  Clause (ii) is declared HERE even though this plan reads no workflow file, because the gate must
  not change answer when plan 14-02 lands -- a gate that grows a clause mid-phase means the SUMMARY
  of this plan describes a different skill from the one that ships.
  Stated cost, carried into plan 14-04's `SKILL.md`: a repo whose CI lives anywhere else
  (CircleCI's `.circleci/config.yml`, a Jenkinsfile, Azure Pipelines, a nested workflows directory)
  is not evaluated at all. That is scope, and the document says so rather than letting a user read
  silence as a pass.
- **D-C2 -- the repo's OWN commands define the vocabulary; the catalog is a supporting input, never
  the gate.** The question this skill answers is "does an equivalent command already exist HERE",
  so the reuse-source inventory is built from the target repo's own Makefile/hooks/scripts/tasks,
  and `resolve_tool_category` is consulted only to judge whether an extracted identity is
  tool-shaped (D-C4) and to widen the match (D-C5). A catalog-GATED design was considered and
  rejected on live evidence: `resolve_tool_category("pytest")` is `None` (pytest lives in
  `OUT_OF_TAXONOMY_GROUPS`, not the six-category index) and `tsc` is indexed only as
  `tsc --noEmit`, so a catalog-gated checker would silently fail to flag a CI `pytest -q` line
  beside a `test:` target that runs exactly that. Verified live at planning time; re-verify before
  implementing.
- **D-C3 -- reuse-source identity extraction, Makefile surface.** For each target `T` in the root
  `Makefile`, compute `identity(T)` from its recipe and name, in this order, under a GLOBAL cap
  evaluated first:
    - Cap: count REAL recipe lines (blank and `#`-comment-only lines are not real). More than 2
      real lines -> `T` is an aggregate and has NO identity. A target with prerequisites and an
      empty recipe is likewise an aggregate with no identity. This is Phase 11's
      `classify_target_shape` cap, re-expressed; it exists so `make validate` never becomes the
      recommended replacement for one tool's invocation.
    - Clause (a): if any real recipe line matches the `pre-commit run <id>` delegate shape, the
      identity is the delegated hook id (Phase 11's clause (i) and its recorded resolution that the
      comparison identity is the DELEGATED id, not the target's own name).
    - Clause (b): otherwise, if there is exactly one real recipe line, the identity is that line's
      command key per D-C5, computed after `command_text`'s prefix stripping.
    - Clause (b2): otherwise, if there are exactly TWO real recipe lines, the identity is their
      shared command key IF both lines compute the SAME key, and otherwise `T` has NO identity.
      This clause exists because of what the old "otherwise the identity is the target's own name"
      fallback silently admitted: a two-line `ruff:` target running `ruff check .` on one line and
      `ruff format .` on the other resolved to the name `ruff`, was admitted by the catalog, and
      then had `make ruff` recommended as the replacement for a CI `ruff check .` line -- advice
      that, if followed, makes CI also reformat. Two lines running the same tool are one command
      wearing two flag sets and are a legitimate reuse source; two lines running different tools are
      an aggregate, which is the judgement the cap, D-C15 and D-C18 all make everywhere else.
    - Clause (c): otherwise -- meaning ZERO real recipe lines and no prerequisites, a bare name
      declaration -- the identity is the target's own name. Note what this clause no longer covers:
      it is now a genuinely narrow case rather than the catch-all it was, and D-C4's third admission
      route is closed to it (see below), so a clause-(c) identity must be answerable by the catalog
      or be an out-of-taxonomy marker to be usable at all.
  The reuse invocation this identity recommends is always `make <T>` -- the target's real name,
  never the identity.
- **D-C4 -- the tool-shaped identity gate, with its third route closed to name-only identities.**
  An extracted identity makes its source USABLE only when at least one holds:
    - Route 1: `resolve_tool_category(identity)` is not `None`;
    - Route 2: `identity` is a marker in `OUT_OF_TAXONOMY_GROUPS` (flattened over both groups,
      exact match);
    - Route 3: `normalize(identity) == normalize(<source's own name>)` **AND the identity was
      derived from a real command body** -- a recipe line, a hook `entry:`, a `package.json` script
      body -- rather than being the source's own name used as a stand-in because no command body
      was available.
  Everything else is discarded silently. This is the single most consequential rule in the skill
  and the reason it can be pointed at a real repo without burying its user: without it, a `clean:`
  target running `rm -rf dist` makes every CI `rm` a duplicate of `make clean`, and a `greet:`
  target running `echo hello` does the same for `echo`. Neither of those targets exists in ai-kit's
  own `Makefile` (re-verified live 2026-09-14: there is no `clean` target, and `validate:` is
  prerequisites-only with an empty recipe) -- they are required SYNTHETIC negative fixtures, and an
  earlier draft of this plan wrongly cited them as live shapes.

  Route 3's qualifier is the part that changed and the part that matters. Written without it, Route 3
  is a tautology for every identity that IS the source's own name: D-C3 clause (c), D-C15's
  entry-less hook branch and D-C19's declared-Gradle-task route all produce exactly that shape, so
  the gate would admit every one of them unconditionally and the "tool-shaped" requirement would
  apply only to command-derived identities -- the opposite of the intent. With the qualifier, a
  name-only identity has to be a name the catalog or the out-of-taxonomy set can actually answer,
  and Route 3 does the job it was written for: admitting a source that is literally NAMED for the
  tool its command runs (a `"eslint": "eslint ."` script, a `myformatter:` target whose one recipe
  line runs `myformatter --fix`) even when the catalog has never heard of that tool.

  Consequences downstream, stated here so plans 14-02 and 14-03 inherit one rule rather than three:
  an entry-less upstream hook `id: ruff` is admitted by Route 1 (`linting` via
  `AMBIGUOUS_TOOL_DEFAULTS`) and an entry-less `id: trailing-whitespace` by Route 2, both unchanged;
  an entry-less `id: my-house-style` hook is now correctly rejected rather than admitted by its own
  name; and a Gradle `tasks.register("jscpdReport")` is rejected while `tasks.register("jscpd")` is
  admitted by Route 1 (see plan 14-03's Task 2, where this closes a fixture that was unsatisfiable
  under D-C5).
- **D-C5 -- the match rule: exact keys, with exactly ONE catalog-grounded widening.** 14-CONTEXT
  D-03 delegates strictness; this is the resolution, and it is deliberately nearer the exact end
  than the fuzzy one.
    - A COMMAND KEY is computed from a command line by: splitting into segments (D-C6), stripping
      leading `VAR=value`/`env VAR=value` assignments and runner prefixes (D-C6), then taking the
      longest KNOWN form over the first two remaining tokens -- try the two-token form first
      (`ruff check`, `go test`, `tsc --noEmit`), then the one-token form -- where KNOWN means
      `resolve_tool_category` answers it or it is an `OUT_OF_TAXONOMY_GROUPS` marker. If neither
      form is known, the key is the one-token form and is marked UNKNOWN. Tokens are normalized by
      taking the path basename (`./bin/ruff` and `.venv/bin/ruff` both become `ruff`), casefolding,
      and folding `_` to `-` -- Phase 11's `normalize_name` rule plus the basename step CI lines
      need.
    - Two keys MATCH when their normalized strings are equal, OR when their FIRST TOKENS are equal
      AND `resolve_tool_category` answers both keys with the SAME non-`None` category.
    - The widening's whole job is the `ruff` triad, and it is a mandatory fixture: a pre-commit
      hook id `ruff` (`linting` via `AMBIGUOUS_TOOL_DEFAULTS`) MATCHES a CI `ruff check .`
      (`linting`), while `ruff format` (`formatting`) matches NEITHER. A first-token-only matcher
      collapses that last pair and tells a repo to replace its formatter call with its linter
      target; a strictly-equal matcher misses the first pair and silently withdraws what SC1
      promises for the most common hook id in this ecosystem.
    - No substring matching, no suffix stripping, no edit distance, anywhere.
- **D-C6 -- CI line segmentation and the reuse-invocation table, COMPLETE in this plan.**
    - Segmentation: split a command line on top-level `&&`, `||` and `;`. A `|` pipeline is NOT
      split -- the first stage is the invoked tool and the rest is consumption, so the segment's
      key comes from the text before the first unquoted `|`. Quoted regions (`'...'`, `"..."`) are
      never split inside. A line containing a heredoc (`<<`) is skipped entirely and recorded as a
      stated limit rather than mis-parsed.
    - Prefix stripping, bounded to 3 rounds, in this order per round: leading `VAR=value` tokens;
      a leading `env` plus its assignments; a two-token direct-runner form (`uv run`, `poetry run`,
      `pdm run`, `hatch run`, `pipenv run`, `pnpm exec`, `pnpm dlx`, `yarn dlx`, `bun x`); a
      one-token direct-runner form (`npx`, `bunx`).
    - The REUSE-INVOCATION table, checked AFTER prefix stripping and BEFORE key computation. A
      segment matching a row is a reuse invocation and is NEVER a finding:
      `make <anything or nothing>` -> makefile; `pre-commit run <id>` -> precommit;
      `npm run|run-script|test|start <...>`, `pnpm run <...>`, `yarn run <...>`, bare
      `yarn <script>`, bare `pnpm <script>` -> package-json; `gradle <task>`, `gradlew <task>`,
      `./gradlew <task>` -> gradle.
    - The table is COMPLETE here while the reuse-source inventory is not, and that asymmetry is
      deliberate: recognizing an invocation as reuse prevents a FALSE POSITIVE, while inventorying
      a reuse source enables a TRUE positive. Staging the first would hand plans 02 and 03 findings
      that look real and are not. The two-token direct-runner forms are checked before the table so
      `pnpm exec eslint .` is read as a direct `eslint` invocation rather than as package-json
      reuse.
- **D-C7 -- identifier discipline: NO `target` key, uniformly, in every plan of this phase.**
  `build_remediation` reads `finding.get("target", finding.get("category"))`, so `target` WINS when
  present and its established meaning across this family is "a real Makefile target name". Three of
  this phase's four reuse surfaces are not Makefile targets, so a `target` key here would mean a
  Makefile target name on some findings and a hook id, an npm script or a Gradle task on others --
  the exact per-surface meaning flip Phase 13's D-D3 exists to prevent, and one that is silent
  (`check` output looks right; only the remediate ids mislabel). Every finding therefore identifies
  as its category, exactly as plans 13-02/13-03's compose-derived findings do, and the
  discriminator travels in `summary`, which the shared builder copies verbatim. The shared builder
  documents this explicitly: `id` is "a human-readable LABEL, not a unique key".
- **D-C8 -- `yaml_text.py` grows; `compose_parse.py` is not repointed.** Append six public
  functions generalizing `compose_parse.py`'s six module-private helpers: a document-separator
  test, an effective-structural test, an unquoted-`#` inline-comment truncator, a `key:` header
  matcher returning `(key, rest)`, a block-end finder, and an own-level-line iterator. The CI
  reader needs every one of them, and 14-CONTEXT's own instruction is to extend `yaml_text.py`'s
  shared primitives rather than duplicate. `compose_parse.py` is NOT repointed at them: Phase 13
  closed that file, and `yaml_text.py`'s existing docstring already records this precise
  arrangement for its own first duplication. Mitigation is the same one that docstring names -- a
  drift guard in `tests/test_ai_kit_rules_common.py` pinning each new shared primitive against its
  private counterpart over a shared input table, loading `compose_parse.py` BY FILE PATH (its only
  imports are `os`, `re` and `ai_kit_rules_common.yaml_text`, all resolvable) rather than importing
  the docker skill's package, and skipping with a stated reason if that file is absent.
- **D-C9 -- `command_text.py` carries GRAMMAR; this skill carries POLICY.** The new shared module
  owns segment splitting, prefix stripping, token normalization (basename + casefold + `_`->`-`)
  and nothing else. The reuse-invocation table (D-C6) and the tool-shaped gate (D-C4) stay in this
  skill: they encode this skill's own judgement about what counts as calling an existing command,
  and a future checker asking a different question should reuse the grammar without inheriting the
  policy. `parity_checker._RUNNER_PREFIX_RE` is not repointed for the same closed-file reason as
  D-C8.

  **What the drift guard pins, stated exactly, because "the same pattern" is ambiguous and the two
  readings have opposite consequences.** `command_text.py` declares ONE module-level constant whose
  regex pattern literal is BYTE-IDENTICAL to `parity_checker._RUNNER_PREFIX_RE`'s -- that constant,
  and only that constant, is the drift guard's subject. Verified live on 2026-09-14,
  `_RUNNER_PREFIX_RE` is
  `r"^(?<![-\w])[A-Za-z0-9_.-]+(?![-\w])[ \t]+(?<![-\w])run(?![-\w])[ \t]+"` -- it recognizes the
  generic `<runner> run <rest>` SHAPE and nothing else. It cannot express D-C6's `npx`,
  `bunx`, `pnpm exec`, `pnpm dlx`, `yarn dlx` or `bun x` forms, none of which contain the token
  `run`, and it does not strip `VAR=value` assignments either.

  So `command_text.py` holds that one pinned constant PLUS separately-named constants and helpers
  for the rest of D-C6's stripping rounds, and the guard asserts equality on the pinned constant
  ALONE. It never asserts that the module's whole stripping behavior equals `parity_checker`'s --
  that reading would force `command_text` to shrink to the one shape and break the `npx`/`pnpm exec`
  handling D-C6 and plan 14-03's `package.json` surface both require. The guard is therefore an
  equality check on one named literal, not a behavioral equivalence check on two modules, and the
  guard's own non-vacuity method must prove it by mutating that ONE constant and observing the guard
  fail, while the `npx`/`pnpm exec` tests stay green.
- **D-C10 -- degradation, and where each half lives.** Every shared-Makefile-parser call this skill
  makes is wrapped in `try/except (OSError, UnicodeDecodeError)` inside this skill -- exactly those
  two types, never a bare `except` or `except Exception`, and only around the parser calls, so a
  `KeyError` in this skill's own finding construction still surfaces. A failed Makefile read means
  "no reuse sources", which yields zero findings rather than an exception. CI-file reads route
  through ONE local reader returning `""` on any `OSError`/`UnicodeDecodeError`, the shape
  `compose_parse.read_compose_text` already uses. Do NOT "fix" this by editing `makefile_parse.py`:
  it has five consumers and widening its contract is a shared-package change no plan in this phase
  owns.

  skill emits, in every plan, carries `category: "cicd-command-reuse"`,
  `issue: "ci_duplicates_existing_command"`, `CRITICALITY_MEDIUM`, `needs_research: False`,

  `ci_file` (repo-RELATIVE, so output is machine-stable across checkouts), `job`, `command` (the
  duplicated segment as written), `tool` (the matched command key), `reuse_surface` (one of
  `makefile`, `precommit`, `package-json`, `gradle`) and `reuse_command` (the exact command to call

  convention gap, not a missing gate -- the HIGH band in this family is Phase 11's parity finding,

  The recommendation text must name BOTH the duplicated invocation and the replacement command;

- **D-C13 -- determinism.** Findings are emitted in a fixed order: CI files in discovery order
  (`.gitlab-ci.yml`/`.gitlab-ci.yaml` first, then `.github/workflows/` entries sorted by filename
  once plan 14-02 lands), then command sites in file-declaration order, then segments in line
  order. Two runs over the same repo produce byte-identical output. `cli.check`'s criticality sort
  must be STABLE so this order survives within a band.
- **D-C28 -- CI composition is NEVER followed, in any form, on either platform, and that is a
  first-class stated limit rather than an unmentioned gap.** This skill reads the CI files D-C1's
  gate found and no others. Concretely, on GitLab: `include:` is a reserved non-job key, so it
  contributes no command site, and NONE of its forms is resolved -- not `template:`, not `project:`,
  not `remote:`, not `component:`, and **not `local:` either**. On GitHub (plan 14-02's half): a
  `uses:` step's action and a `jobs.<id>.uses` reusable workflow are likewise never fetched or
  opened. One rule, both platforms, no exceptions.

  This is a real blind spot on a real file, not a hypothetical: ai-kit's own `.gitlab-ci.yml` lines
  15-16 are `include:` / `- template: Security/Secret-Detection.gitlab-ci.yml`, and a repo whose
  `include: local: ci/lint.yml` runs `ruff check .` inside the included file gets a zero-finding
  result from this skill. Both directions were weighed:

    - **Fetching remote composition (`template:`, `project:`, `remote:`, `component:`) is refused on
      security grounds.** It is a network read of a third-party file on every invocation, against a
      target the user did not choose -- the identical surface T-14-13 refuses for GitHub `uses:`
      actions. Refusing it on one platform and performing it on the other would be incoherent.
    - **Following `include: local:` was considered and REFUSED on scope-consistency grounds, not
      because it is hard.** It is a same-repo read and is technically bounded. But this skill is
      root-scoped on every single surface it has -- D-C1's gate stats root paths and does one
      non-recursive `os.listdir`; D-C18 reads the root `package.json` only; D-C19 reads the root
      build scripts only; T-14-02, T-14-15 and T-14-31 each accept the resulting monorepo blind spot
      as a stated limit rather than open a directory walk. `include: local:` is the one place the
      reader would descend out of the root, and doing it properly is not one `open()`: `local:` can
      be a string, a list, or a mapping; it accepts GLOBS (`ci/*.yml`); an included file can itself
      include (so the reader needs a recursion bound and a visited set); included jobs MERGE with and
      can be OVERRIDDEN by the main file's jobs (so a finding computed from an included job can be
      wrong about a job the root file redefined); and a `local:` path from an untrusted repo is a
      path-traversal read primitive that has to be resolved and confined to the repo root. Each of
      those is a correctness or safety obligation this phase would be taking on in its tracer, for a
      case no success criterion names. Phase 13's descope-with-disclosure precedent for long-form
      Docker volumes is the same call.
    - **A "this pipeline is composed, so my answer is partial" finding was also considered and
      rejected**: it would need a second finding category, contradicting D-C12's one-category rule
      for the whole phase, and it would fire on ai-kit's own repository root, breaking the
      zero-findings invariant three plans assert. The disclosure belongs in the document and the
      docstring, where a reader meets it before they trust a clean run -- not in the finding stream.

  What this decision therefore REQUIRES, and what makes it a disclosure rather than a silence:
    (i) `ci_parse.py`'s module docstring states it plainly, naming `include:` and its forms, and
        saying in the same sentence that a zero-finding result on an include-composed pipeline is
        not evidence the pipeline is clean;
    (ii) Task 2 pins it with a real fixture -- a repo whose root `.gitlab-ci.yml` carries
         `include:` / `- local: ci/lint.yml` and whose `ci/lint.yml` contains a `script:` running
         `ruff check .` beside a matching `ruff` Makefile target returns ZERO findings, with the
         test's docstring naming this as scope. The fixture must also assert the included file was
         never read, so a later "improvement" that starts following includes fails this test
         loudly instead of silently changing the phase's scope;
    (iii) plan 14-04 carries it to `SKILL.md` as its own numbered limit, with the pinned token
          `include-composed`, and it is the ELEVENTH limit there rather than being folded into the
          `uses:` one -- the two have different rationales (one is a remote fetch this skill must
          not perform, the other is a local file it deliberately does not open) and folding them
          would lose the honest half.
