## Decisions this plan makes on the planner's authority

Plan 14-01's D-C1 through D-C13 are inherited unchanged and are NOT re-decided here. These four
extend them for this plan's two additions.

- **D-C14 -- the sequence-of-mappings reader stays skill-local.** `compose_parse.block_sequence`
  states scalar-items-only as its own limit and has no mapping-item reader to converge with, so
  this capability exists exactly once in this repository. The family's convergence rule, applied
  consistently across Phase 10 D-01, Phase 11 D-01, 14-CONTEXT D-01 and plan 14-01's D-C8/D-C9, is
  "move a primitive to `skills/_shared/` when it ALREADY exists twice" -- every one of those moves
  had a real counterpart to pin a drift guard against. Pre-placing a single-consumer reader in the
  shared package grows five skills' import surface for a second consumer that does not exist.
  Write it in `ci_parse.py`, give it a docstring naming `compose_parse.block_sequence`'s stated
  limit as the reason it exists here, and record in the SUMMARY that promoting it is a clean
  additive follow-up whenever a second consumer appears.
- **D-C15 -- pre-commit hook identity.** For each hook id `H` with entry `E` from the SHARED
  `parse_precommit_hooks`:
    - If `E` is not `None`, **strip YAML quoting from `E` FIRST, via the shared
      `yaml_text.strip_yaml_quotes`**, and only then compute its command key. This step is not
      optional and not cosmetic: verified live on 2026-09-14, `parse_precommit_hooks` normalizes the
      hook ID across bare/single/double-quoted forms but returns the ENTRY exactly as written, so a
      real `entry: "ruff check"` comes back as the 12-character string `"ruff check"` WITH its
      quotes, whose first token is `"ruff` and which therefore matches nothing. The failure is
      silent and asymmetric -- fixtures written with a bare `entry: ruff check` all pass while every
      quoted config in the wild is invisible -- and it is exactly the kind of gap the shared reader's
      own id-vs-entry asymmetry invites. `strip_yaml_quotes` already handles all three forms
      (confirmed live: `"ruff check"` -> `ruff check`, `'black .'` -> `black .`, and a bare value
      unchanged), so this is one call, not a parser.
    - Then, with `E` unquoted: the identity is `E`'s command key, computed by exactly the same
      `command_text` stripping and D-C5 key resolution a CI line goes through. A hook whose entry
      is a multi-segment shell line (it contains a top-level `&&`, `||` or `;`) has NO identity --
      it is an aggregate, the same judgement D-C3's real-line cap makes on the Makefile surface.
      Evaluate the multi-segment test AFTER quote-stripping too, so a quoted aggregate is judged on
      its real content.
    - If `E` is `None` (a non-`local` `repo:` block, whose command lives in an external hook-repo
      manifest this skill does not fetch), the identity is `H` itself. This is the common case for
      the upstream `ruff-pre-commit` and `pre-commit-hooks` repositories, and it is why the
      `AMBIGUOUS_TOOL_DEFAULTS` bare-`ruff` entry matters on this surface specifically.
    - D-C4's gate then applies unchanged, through the SAME function the Makefile surface calls --
      including the Route 3 qualifier plan 14-01 settled during review incorporation. Pass the
      command-derived fact honestly per branch: an entry-carrying hook's identity IS derived from a
      command body, so Route 3 is available to it (a `local` hook `id: myformatter` /
      `entry: myformatter --fix` is admitted even though the catalog has never heard of it); an
      entry-less hook's identity is its own id with no command body behind it, so Route 3 is NOT
      available and it must pass Route 1 or Route 2. That distinction is what keeps entry-less
      `id: ruff` (Route 1, `linting` via `AMBIGUOUS_TOOL_DEFAULTS`) and `id: trailing-whitespace`
      (Route 2, hygiene group) admitted while an entry-less `id: my-house-style` is correctly
      rejected rather than admitting itself by name.
    - The reuse invocation is `pre-commit run <H> --all-files` -- the hook's REAL id, never its
      identity. Deliberately without the `uv run` prefix the Phase 11 sibling's recommendation
      carries: that prefix is ai-kit's own local convention, while this recommendation is going
      into a CI file in an arbitrary repo whose runner may not have `uv` at all. Record the
      divergence and its reason in the SUMMARY so a later reader does not "fix" it into agreement.
- **D-C16 -- surface precedence, declared once for all four surfaces.** The inventory is built in
  the fixed order `makefile`, `precommit`, `package-json`, `gradle`, and when two surfaces produce
  the same command key the FIRST one inventoried wins -- one recommendation per key, chosen
  deterministically. `make <target>` leads because ROADMAP SC1's own worked example recommends
  exactly that, and because a Makefile target is the one surface every stack in this family's
  taxonomy can have. This rule is declared here rather than in plan 14-03 so that plan appends to a
  settled order instead of inventing a tie-break for its own two surfaces.
  The losing source is not reported anywhere: one duplicated invocation is one finding, and naming
  two possible replacements in one recommendation is how a reader ends up doing neither.
- **D-C17 -- the `job` field carries the most specific site name, and the field SET does not grow.**
  For a GitLab site the value stays what plan 14-01 shipped. For a GitHub Actions step it is the job
  key, or `"<job-key> / <step-name>"` when the step declares a `name:`. Adding a sixth data field
  (`step`) would change a vocabulary plan 14-01's SUMMARY already records and Phase 15's
  orchestrator reads; carrying the specificity inside the existing field costs nothing and keeps
  D-C12 true as written.
- **D-C29 -- one CI-file list, built once, visited once.** `ci_parse`'s discovery function is the
  SINGLE source of the list of CI files to read, and it returns repo-relative paths in D-C13's
  order (GitLab file(s) first, then root `.github/workflows/` entries sorted by filename). It
  DEDUPLICATES by repo-relative path before returning. `cicd_checker` has exactly ONE loop over
  exactly that list and dispatches to a reader per file by filename; it gains no second way to
  reach a workflow file and never calls discovery twice.

  This is written as a decision rather than left to taste because the two obvious implementations
  compose badly and the failure is silent. "Extend discovery to also yield workflow files" and
  "append a workflow source to the aggregator's iteration" are each complete-looking on their own,
  live in different files, and do not appear together in any one diff -- so doing both visits every
  workflow file twice and emits every GitHub finding twice, while nothing raises, `check` still
  exits 0, and D-C13's determinism still holds because the duplication is itself deterministic. A
  reader sees two identical findings and concludes the checker is broken in some deeper way.
  Extending discovery is the shape this plan picks, for the reason plan 14-01 already gave when it
  declared the GitLab filename tuple and the workflows-directory path in `ci_parse`: D-C1's gate and
  this discovery must read ONE filename rule, and they cannot if the file list is assembled in two
  places. The `NO-DOUBLE-SCAN-OK` criterion below asserts the property from the outside, on output,
  rather than by inspecting which shape was written.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| target-repo workflow YAML -> the step reader | GitHub Actions files carry arbitrary shell text, third-party action references and template expressions, all written by whoever controls the repo. The reader tokenizes and pattern-matches that text and must never execute, expand, interpolate or fetch any of it. |
| third-party action reference -> this skill | A `uses:` value names a repository this skill does not control. Reading it would mean a network fetch of untrusted content on every invocation. This boundary is deliberately never crossed. |
| target repo `.github/workflows/` listing -> discovery | One non-recursive listing of an untrusted directory decides how many files are parsed. An unbounded or recursive listing turns a large monorepo into a per-invocation traversal. |
| target-repo `.pre-commit-config.yaml` -> the shared reader | An arbitrary repo's hook config becomes reuse-source vocabulary. A bad read here does not crash the skill but does change what it accuses the CI file of duplicating. |
| shared package -> this skill | `precommit_parse` and `yaml_text` are READ here and not edited, so this plan's blast radius on the other four skills is zero by construction -- an acceptance criterion asserts no path under `skills/_shared/` is in either commit. |
