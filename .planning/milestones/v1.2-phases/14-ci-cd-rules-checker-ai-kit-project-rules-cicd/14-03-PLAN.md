## Decisions this plan makes on the planner's authority

Plans 14-01 and 14-02's D-C1 through D-C17 are inherited unchanged. 14-CONTEXT's Claude's-Discretion
note explicitly leaves this plan's two readers' shape to the planner; these five settle it.

- **D-C18 -- `package.json` script surface.** Read the ROOT `package.json` with the stdlib `json`
  module. For each `(name, command)` in a `scripts` object that really is an object with string
  values:
    - If `command` has more than one top-level segment (a top-level `&&`, `||` or `;`), the script
      is an aggregate and has NO identity -- the same judgement D-C3's real-line cap makes on the
      Makefile surface and D-C15 makes on a hook entry. A `"validate": "npm run lint && npm run test"`
      script must never become the recommended replacement for one tool's invocation.
    - Otherwise the identity is `command`'s key, computed through the SAME `command_text` stripping
      and D-C5 key resolution a CI line goes through. This is what makes `"lint": "eslint ."` cover
      a CI `eslint .` line.
    - D-C4's gate then applies unchanged, through the same function the other surfaces call, with
      command-derived=true passed for this branch (a script's identity always comes from its body).
      Route 3 is therefore available here, and it is what admits a script literally NAMED for its
      tool -- `"eslint": "eslint ."` resolves even for a tool the catalog has never heard of, while
      `"lint": "some-unknown-tool"` does not, because its identity and its name differ and no other
      route can answer it.
    - Every failure mode yields no sources and never raises: absent file, unreadable file, invalid
      JSON, a `scripts` key that is absent or not an object, a script value that is not a string.
      The wrap is `(OSError, UnicodeDecodeError, ValueError)` -- `json.JSONDecodeError` subclasses
      `ValueError` -- and nothing broader; a `KeyError` or `TypeError` in this module's own logic is
      this skill's defect and must surface.
    - ROOT file only. A workspace member's `package.json` is not read, and that is a stated limit.
- **D-C18b -- the recommended runner follows the lockfile actually present.** The reuse invocation
  is `<runner> run <script>`, where `<runner>` is decided by the FIRST of these that exists at the
  repository root: `pnpm-lock.yaml` -> `pnpm`; `yarn.lock` -> `yarn`; `bun.lockb` or `bun.lock` ->
  `bun`; otherwise `npm`. A repo with several lockfiles gets the first in that order,
  deterministically, rather than an arbitrary one. Rationale: the tool half of a recommendation can
  be perfectly right while the runner half is wrong, and `npm run lint` in a pnpm-only repo fails
  at the moment it is followed -- the same class of confidently-wrong actionable advice D-C5's
  match rule exists to prevent on the tool axis. Plan 14-04's `SKILL.md` states the precedence so a
  reader can predict it.
- **D-C19 -- Gradle task surface, two routes, both requiring real evidence in the repo.** Read the
  ROOT `build.gradle` and `build.gradle.kts` as text (both, when both exist; Groovy and Kotlin DSL
  are two spellings of the same information and reading only one silently halves the coverage).
    - Route 1, DECLARED tasks: a task name extracted from the build script's own declaration forms
      -- `task <name>`, `task("<name>")`, `tasks.register("<name>")`,
      `tasks.register<Type>("<name>")`, `tasks.named("<name>")`, and the Kotlin
      `val <name> by tasks.registering` / `by tasks.creating` forms. Text/regex extraction, in the
      same stdlib-only spirit 14-CONTEXT D-02 inherits from Phase 13's D-01. The identity is the
      task NAME, and this skill never sees the task's body, so the name is all the evidence there is.

      **What that costs, stated as a rule rather than discovered at fixture-writing time.** A
      declared task's identity is a name with no command body behind it, so D-C4's Route 3
      (name-equality) is unavailable to it under the qualifier plan 14-01 settled during review
      incorporation -- a declared task must be answerable by the shared catalog, be an
      `OUT_OF_TAXONOMY_GROUPS` marker, or come through Route 2's plugin table. Combined with D-C5's
      match rule (exact keys, or same first token AND same non-`None` category; no substring
      matching and no suffix stripping, anywhere), the consequence is concrete and must be written
      into the fixtures rather than worked around:
        - `tasks.register("jscpd")` COVERS a CI `jscpd .` line -- the name is the tool name, the
          catalog answers it (`jscpd` -> `duplicate-code`, verified live 2026-09-14), and the keys
          are exactly equal.
        - `tasks.register("jscpdReport")` covers NOTHING. The catalog does not answer `jscpdReport`,
          it is no hygiene or test-runner marker, Route 3 is closed to it, and even if it were
          admitted D-C5 could not match `jscpdreport` to `jscpd` -- different strings, different
          first tokens. Both halves have to be true for a match, and neither is.
      That second case is REAL Gradle convention (`<tool><Purpose>` task names are everywhere), so
      it is a genuine blind spot rather than a contrived one, and it gets a paired negative fixture
      plus a stated limit -- NOT a mapping mechanism. Adding a Route-1 identity map would mean
      either suffix stripping, which D-C5 forbids by name and which is exactly how a formatter call
      gets recommended as a linter target, or a second hand-maintained table with none of the
      plugin table's saving grace (that table's rows are verifiable against real plugin ids present
      in the build script; a name-shape table would be a guess about an arbitrary repo's naming
      convention). The plugin table exists for tasks CONTRIBUTED by a known plugin, which is a
      different question from what an arbitrary repo chose to call its own task.
    - Route 2, PLUGIN-CONTRIBUTED tasks: a small pinned table mapping a task name to
      `(plugin_id_fragment, tool_identity)`, admitted ONLY when that plugin-id fragment actually
      appears in the build-script text. Seed it with the rows a Java/Kotlin repo in this family's
      taxonomy really has: `spotlessCheck`/`spotlessApply` (`com.diffplug.spotless` -> `spotless`),
      `checkstyleMain` (`checkstyle` -> `checkstyle`), `pmdMain` (`pmd` -> `PMD`),
      `spotbugsMain` (`spotbugs` -> `SpotBugs`), `detekt` (`io.gitlab.arturbosch.detekt` ->
      `detekt`), `ktlintCheck` (`org.jlleitschuh.gradle.ktlint` -> `ktlint`),
      `dependencyCheckAnalyze` (`org.owasp.dependencycheck` -> `dependency-check`). Each row carries
      its plugin id as a comment-adjacent literal so a later reader can check it.
      The evidence requirement is the load-bearing half: without it, this skill tells a plain Java
      repo to call `spotlessCheck`, a task that repo does not have, and the advice fails the moment
      it is followed.
    - The generic lifecycle tasks (`check`, `build`, `test`, `assemble`) are deliberately NOT in the
      table: each runs many tools, so recommending one as the replacement for a single tool's
      invocation is the aggregate mistake D-C18 and D-C3 both refuse. Record that exclusion as a
      decision rather than leaving it to look like an omission.
    - ROOT build scripts only. A subproject's `build.gradle` and `settings.gradle`'s project list
      are not read, and that is a stated limit.
- **D-C19b -- the plugin table is a FOURTH admission route inside D-C4's gate, added additively and
  scoped to the Gradle surface by an EXPLICIT off-by-default flag.**
  A Route-2 task's identity is its table row's tool identity, and some of those (`ktlint`,
  `detekt`, `dependency-check`) are not in the shared catalog and are not name-equal to their task
  name, so they would fail all three existing routes. Verified live 2026-09-14:
  `resolve_tool_category` returns `None` for all three, while `spotless`, `checkstyle`, `PMD` and
  `SpotBugs` resolve normally. Rather than letting the Gradle surface carry its own private bypass
  -- which is how two surfaces start disagreeing about what a tool is -- the gate gains ONE new
  route: "the identity came from the pinned Gradle plugin table, whose plugin id was found in the
  build script". The route is a cited table, not an open door: it admits exactly the rows listed
  and nothing else.

  **The route is a parameter, not a membership test.** The gate's signature gains one explicit
  argument that DEFAULTS TO OFF, and only the Gradle surface passes it on. The gate must not decide
  for itself whether an identity is plugin-table-shaped by testing membership in the table, because
  membership is a property of the STRING, not of where the string came from: `ktlint`, `detekt` and
  `dependency-check` are perfectly ordinary names a repo can use for a pre-commit hook id, a
  `package.json` script or a Makefile target, and a bare membership check would silently admit
  those identities on three surfaces that must still reject them. Passing the flag from the caller
  makes the route mean what it says -- "this identity came out of the plugin table" -- rather than
  "this identity happens to look like something in the plugin table".

  A leak here is invisible on the Gradle surface's own tests (they pass either way) and changes
  answers only on surfaces this plan does not touch, which is why the mitigation is a discriminating
  FIXTURE rather than inspection: a repo with a pre-commit hook `id: ktlint` carrying no `entry:`,
  and a CI step running `ktlint` directly, must return ZERO findings -- the name is in the plugin
  table, the catalog cannot answer it, it is no hygiene marker, and D-C4's Route 3 is closed to a
  name-only identity, so every route must refuse it on that surface. The same repo with a
  `build.gradle` applying the ktlint plugin returns ONE finding. That pair is the `NO-GATE-LEAK-OK`
  criterion below. The three existing routes keep their exact behavior, and the Makefile and
  pre-commit surfaces' answers must be byte-identical before and after -- proven by re-running plans
  14-01's and 14-02's own acceptance commands, not by inspection.
- **D-C20 -- wrapper-aware Gradle invocation.** The reuse invocation is `./gradlew <task>` when a
  root `gradlew` file exists and `gradle <task>` otherwise. The wrapper is what a CI job can run
  without a preinstalled Gradle, so recommending the bare command to a wrapper repo tells a
  maintainer to take on a toolchain dependency they deliberately avoided.
- **D-C21 -- both readers stay local to this skill.** 14-CONTEXT's Claude's-Discretion note records
  that no other skill in this family needs `package.json` or Gradle parsing, so unlike the
  Makefile-parsing convergence its D-01 resolves there is no cross-skill pressure here. This is the
  same rule plan 14-02's D-C14 applied: converge what already exists twice, do not pre-place what
  exists once. Each reader is its own module inside the skill package so the two are separately
  readable and separately testable; neither lives inside `reuse_sources.py`, which stays the
  inventory's assembly point rather than becoming a fourth parser.
