## Decisions this plan makes on the planner's authority

11-CONTEXT.md's "Claude's Discretion" block leaves the exact parity matching algorithm open.
ROADMAP SC1 fixes only the two outcomes that must discriminate. These are settled here so the
executor implements one rule rather than inventing one, and so plans 11-02/11-03 and the tests
agree with each other:

- **D-P1 -- normalized name matching.** A hook id and a Makefile target match when their
  casefolded forms are equal after `_` is folded to `-`. Not exact-string (a `py_compile` hook
  and a `py-compile` target are the same tool by any honest reading), and not fuzzy/substring
  (a `ruff` hook must never be satisfied by a `ruff-format` target -- two different tools in two
  different taxonomy categories).
- **D-P2 -- "single-tool Makefile target" is a SHAPE, not a name list.** The target→hook
  direction only considers *tool-shaped* targets, defined as: the target's recipe has at most 2
  real lines (non-blank, non-comment), AND at least one of
  (i) some real recipe line CONTAINS the token sequence `pre-commit run <hook-id>` -- anywhere on
  that line, not only as its first token. This repository's own delegating recipes are
  `uv run pre-commit run ruff --all-files` (`Makefile:85-86`, and seven more like it -- EIGHT
  delegating recipes in all, `Makefile:74-98`), so a
  first-token parse, a line-anchored regex, or a `startswith` check would miss EVERY real
  delegate in the very repository whose convention this clause is copied from. Match the token
  sequence with the same token-boundary semantics `recipe_mentions_target` uses, take the token
  immediately after `run` as the delegated hook id, and ignore any leading runner prefix
  (`uv run`, `poetry run`, `npx`, `env VAR=x`) rather than enumerating the prefixes.
  (ii) the target name matches one of the sibling skill's pinned `validate-<short-name>` alias
  names or its bare category short-names (`format`, `lint`, `security`, `duplicate`, `dead`).
  A target with prerequisites and an empty recipe is an AGGREGATE and is never tool-shaped, so
  `validate`, `test` and `dev` cannot be flagged. Rationale: an aggregate has no single hook it
  could correspond to, so demanding one would be a false positive by construction.
  Plan 11-02 extends this predicate with a clause (iii) over the shared catalog's real tool names
  once that catalog exists; this plan must therefore route the decision through ONE predicate
  function so 11-02 extends it in one place rather than forking it. **The ≤2-real-line cap is a
  global AND over every clause, including any clause a later plan adds.** A target whose recipe
  exceeds the cap is never tool-shaped no matter what it is named -- pin that structure now
  (evaluate the cap first, then OR the clauses) so 11-02's extension cannot be implemented as a
  fourth way to bypass it and quietly reclassify a long recipe as a single tool.
- **D-P2b -- the target→hook recommendation always states BOTH options, and this repository is
  the reason.** `format` (`Makefile:103-104`) is in clause (ii)'s pinned short-name list, has a
  one-line recipe, and has no matching hook -- deliberately, with a Makefile comment saying so
  ("dev-only, mutates files -- deliberately NOT wired into the validate/commit gate"). It is not
  alone: `security-scanner` and `duplicate-code` (`Makefile:109-117`) are deliberately non-gating
  in the same way, each with its own Makefile comment saying so. `security-scanner` additionally
  becomes tool-shaped once plan 11-02 adds clause (iii) over catalog tool names, because after the
  runner prefix its recipe names this ecosystem's dedicated security scanner, which the catalog
  indexes. `duplicate-code` does NOT: after the runner prefix its recipe names a general-purpose
  linter invoked with a rule-selector flag, and the design spec's duplicate-code cell for that
  stack carries the linter-plus-rule-id form rather than the bare binary name -- so the catalog
  cannot answer it, and plan 11-02 states explicitly that indexing the bare name to force a match
  would misclassify this repository's own lint hook. Do not pre-empt that here by adding the bare
  name to clause (ii)'s short-name list. So a recommendation that only ever says "add a hook" would
  tell this repository's maintainer to undo separately-considered decisions on the skill's first
  real run. The dual recommendation (add a matching hook, OR record in the Makefile that the target
  is deliberately non-gating) is MANDATORY finding text, not a stylistic preference, and the SUMMARY
  must record how each of those three real targets classified under the predicate as implemented --
  including, for the two that this plan's predicate does not yet reach, whether they are tool-shaped
  at all today.
- **D-P3 -- the overlap with the sibling skill is deliberate and is not suppressed.** The
  `ai-kit-project-rules-makefile` skill already unions pre-commit hook ids into its required
  Makefile target set, so a hook with no target produces a `makefile`-kind finding there AND a
  `precommit`-kind parity finding here. Both are correct in their own domain and they recommend
  different things (the sibling says "add this target"; this skill says "the two files disagree
  about the tool set"). Do NOT suppress either, do NOT reach into the sibling to deduplicate, and
  do NOT reuse the sibling's `issue` strings. Phase 15's orchestrator is the only component
  allowed to merge across domains (`.planning/intel/constraints.md`, cross-skill remediation
  merging ownership).
- **D-P4 -- finding vocabulary, pinned.** `category: "precommit-parity"` with
  `issue: "hook_without_target"` / `issue: "target_without_hook"`, both at `CRITICALITY_HIGH`.
  The inherited stage-split finding keeps the exact `category`/`issue`/criticality the shared
  function already returns -- it is not re-labelled on the way through. Plans 11-02/11-03 add
  further categories; none of them reuses `precommit-parity`.
