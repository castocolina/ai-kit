## Warnings

### WR-01: Grouped-only sort key still no-ops the table after returning to flat mode

**File:** `skills/ai-kit-usage-metrics/ai_kit_usage_metrics/dashboard.py:1787-1790`

**Issue:** `b9d8a52` added a `GROUPED_SORT_KEYS` fallback for the grouped
branch of `buildCurrentRowsFromFiltered()` (dashboard.py:1768-1786), but the
flat branch (the `else` immediately following it) still passes the raw
`sortKey` straight through with no equivalent validation:

```js
} else {
  currentRows = sortRows(currentFiltered, sortKey, sortDir);
  currentBuilder = flatRowBuilder;
}
```

`sortKey` is shared, mutable, module-level state (`dashboard.py:1122`) set by
the `<th>` click handler (`dashboard.py:1838-1849`) from whichever `<thead>`
row is currently visible — flat (`thead-flat`) or grouped (`thead-grouped`,
`dashboard.py:589-595`). `thead-grouped`'s `count` column has no counterpart
on a flat row (flat rows never carry a `count` field — verified against the
full column list in `refined_store.py` plus the runtime-only `subfamily`
field). Reproduced by walking the real shipped `sortRows()`/`groupBySession()`
functions through node:

1. Check "group by session".
2. Click the "count" column header (`sortKey` becomes `"count"`).
3. Uncheck "group by session" — `buildCurrentRowsFromFiltered()`'s flat
   branch runs `sortRows(currentFiltered, "count", sortDir)`.
4. Every flat row's `row["count"]` is `undefined`, so `sortRows`'s
   `av == null && bv == null` branch fires for every pair and the comparator
   returns `0` for the whole array — the table renders unsorted, silently,
   with no visual indication (same failure mode `b9d8a52`'s own commit
   message describes for the original grouped-mode direction).

This is the mirror image of the bug `b9d8a52` fixed, just triggered by the
opposite toggle direction and via a grouped-only sort key (`count`) instead
of a flat-only default (`date`).

**Fix:** Give the flat branch the same treatment — a `FLAT_SORT_KEYS` list
(the 13 flat-mode `data-sort-key` values) with an equivalent fallback, e.g.:

```js
var FLAT_SORT_KEYS = [
  "runtime", "model", "family", "subfamily", "command_text",
  "exec_duration_ms", "date", "tokens_input", "tokens_output", "price",
  "source_confidence", "execution_certain", "session_id"
];
...
} else {
  var flatKey = FLAT_SORT_KEYS.indexOf(sortKey) === -1 ? "date" : sortKey;
  currentRows = sortRows(currentFiltered, flatKey, sortDir);
  currentBuilder = flatRowBuilder;
}
```

(Or unify both lists into one `SORT_KEYS_BY_MODE` map and reset `sortKey` to
the mode's default whenever the group-by-session checkbox itself changes,
which would also fix the display staying on a stale/invisible active sort
column indicator — but that's a larger change than this narrow fix needs.)

### WR-02: `b9d8a52`'s grouped-mode sort fallback shipped with no regression test

**File:** `tests/test_ai_kit_usage_metrics.py`

**Issue:** `b9d8a52` (the WR-01-from-iteration-2 fix) added `GROUPED_SORT_KEYS`
and the `groupedKey` fallback to `dashboard.py` but added zero test coverage
— confirmed by diff (`git show b9d8a52` touches only `dashboard.py`) and by
grep: no test in the suite references `GROUPED_SORT_KEYS`, `groupedKey`, or
drives `buildCurrentRowsFromFiltered()` with the DOM's `group-by-session`
checkbox toggled. Its sibling fix in the very next commit (`310f020`,
WR-02-from-iteration-2) took the opposite, better approach: it shipped with a
dedicated node-executed test
(`test_virtualizer_fallback_timer_reversed_by_late_mount_via_node`) that
extracts and exercises the real shipped function bodies. The asymmetry means
this fix — and the closely-related flat-mode gap in WR-01 above — has no
regression protection: a future refactor of `buildCurrentRowsFromFiltered()`
could silently reintroduce either no-op-sort bug without failing CI.

**Fix:** Add a node-executed test analogous to the existing
`test_group_by_session_dedups_turn_tokens` / `test_turn_key_and_group_by_session_null_turn_via_node`
style, but driving `buildCurrentRowsFromFiltered()` (or `sortRows` +
`groupBySession` composed the same way the production code composes them)
with a `sortKey` outside the current mode's field set, asserting the row
order changes from the naive pass-through. Cover both directions (flat
default `"date"` fed into grouped rows, and a grouped-only key like
`"count"` fed into flat rows) so WR-01 above and this gap are closed by the
same test.
