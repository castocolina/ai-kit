# Phase 25.1: Configurable cross-AI retry ladder and upstream error propagation — Specification

**Created:** 2026-10-24
**Ambiguity score:** 0.15 (gate: ≤ 0.20)
**Requirements:** 10 locked *(R8–R10 added 2026-10-24, owner)*

## Goal

A failed cross-AI child run follows a ladder whose waits are configurable per project and per
user. Inside one runner call it does a soft exponential backoff, one session reset and a second
soft series. Outside the call, the caller owns the hard waits (10, 15, 30 minutes) and a user
notice. The runner passes the upstream error through verbatim instead of interpreting it, and
classifies it from an evidence-labelled catalog keyed by route, provider and body, never by
status code alone.

## Background

- **Source:** owner request 2026-10-24, after the Phase 25 plan reviews (conversation with uz,
  recorded in ROADMAP Phase 25.1 and QTA-07..QTA-11). Evidence: `25.1-EVIDENCE.md`.
- **What Phase 25 delivers (the base; contracts from 25-01..25-11, in execution 2026-10-24):**
  - one CLI per call, no automatic fallback (25-01, landed in a063759);
  - per-CLI pattern table in a marked JSON block of the runner template (25 D-02), route-aware
    classes (transient, router quota/rate limit, off-router quota, auth, billing, permission,
    bad model);
  - in-call rungs: 3 same-session retries, then 3 new sessions, waits from `CONFIG.backoffS`
    (template default `[30, 60]`, last value repeats);
  - a router quota that persists exits 75 with `retry_after_s=600 cycle=<n>`; a 0600 state file
    keyed by lane and model holds `first_seen`, `due_at`, `last_sid` and `task_digest`; the
    4-hour cap from `first_seen` exits 69 with `stopped=cap`;
  - the review orchestrator schedules one one-shot re-invoke of the same lane at
    `retry_after_s` (25-10); every stop prints `cross-ai: report ...` evidence before the
    `AIKIT-XAI` status line.
- **What is wrong with it for the owner:**
  - the waits are fixed and coarse: 30/60 s between same-session retries, then a flat 10-minute
    cooldown. A single 400 or a quota hiccup gets either a long sleep or a burst of retries;
  - nothing between "soft" and "10 minutes" is configurable, and the values are baked into each
    rendered copy;
  - a status code decides too much. Captured counter-examples: Kimi's 5-hour usage limit is a
    403; a router 402 "usage balance exhausted (reset after 2m)" was classified billing and
    stopped (exit 69) although it reset in 2 minutes; OmniRoute's `ALL_TARGETS_SKIPPED` 429
    carried `retry_after` 340954 (94 hours);
  - OmniRoute adds its own reason codes (`ALL_TARGETS_SKIPPED`, `all_targets_cooling_down`,
    model cooldown or "unavailable", `circuit_open`, `model_not_in_catalog`) on top of the
    provider bodies it passes through, and each connected provider's errors are handled
    differently inside OmniRoute (owner, 2026-10-24).
- **Producers of the runtime choice today:** `ai_kit_spec/runner_dispatch.py` passes
  `--prefer <runtime>`; GSD's `workflow.cross_ai_command` (`node .planning/scripts/cross-ai.mjs`)
  passes none, so the rendered `CONFIG.prefer` list decides; after 25-01 only its first entry
  runs.
- **Config the runner already reads:** `.planning[/$GSD_PROJECT][/workstreams/$GSD_WORKSTREAM]/
  config.json` `workflow.cross_ai_timeout` (the outer deadline), resolved by the runner itself.

## Requirements

1. **Soft ladder inside one call** (QTA-07).
   - Current: 3 same-session retries and 3 new sessions with `backoffS` waits of 30/60 s, for
     transient errors and router-lane quota or rate limits; other classes stop at once.
   - Target: for the same two classes (transient, router-lane quota or rate limit), the runner
     retries the same session with an exponential soft backoff — wait `base_s × factor^(k−1)`
     before retry k, with jitter of at most ±10%, up to `max_retries` retries — then resets the
     session (`session_resets` times, a fresh session id on the same lane and model), runs
     another soft series after each reset, and then exits with the evidence report and the
     retry hint for the caller. Defaults: `base_s` 1, `factor` 1.5, `max_retries` 5,
     `session_resets` 1 (waits 1, 1.5, 2.25, 3.4, 5.1 s). Every other class keeps Phase 25's
     single attempt and report. Every wait stays inside the call deadline and the cap headroom
     (25 cycle-3 clamp).
   - Acceptance: self-test cases with an injected clock show, for a transient fake that always
     fails: 5 same-session attempts at the default waits, one new session id, 5 more attempts,
     then exit 75 with the report; for an auth fake: one attempt and exit 69; no case sleeps
     longer than the configured soft waits.
   - *Amended 2026-10-24 (25.1 D-07, D-10):* the retry hint (`retry_after_s`/`cycle`) is emitted for
     both soft-ladder classes, so the caller's hard tier (R3) applies to transient exhaustion too
     (owner wording: a 400, a quota error "or another kind of error"; needs confirmation). A CLI
     with no session resume runs each soft retry as a new session under the dirty-tree rule, and
     `session_resets` has no effect there.

2. **Retry config and precedence** (QTA-07).
   - Current: `backoffS`, `sameSessionRetries`, `newSessionRetries`, `cooldownS` and `capS` are
     baked into the rendered CONFIG only.
   - Target: the runner reads `workflow.cross_ai_retry` (`base_s`, `factor`, `max_retries`,
     `session_resets`, `hard_waits_s`) from the same project config files it already reads for
     `workflow.cross_ai_timeout`, then a user-level ai-kit runner config, then the rendered
     defaults; each key falls back on its own. Bounds: `base_s` 0..60, `factor` 1.0..3.0,
     `max_retries` 0..10, `session_resets` 0..3, `hard_waits_s` 1..6 entries, each 0..`capS`.
     A value out of bounds or of the wrong type is refused: the runner prints which key and
     source, ignores that key and uses the next source. `capS` (14400) is not configurable
     upward.
   - Acceptance: self-tests for project-over-user-over-default precedence per key, each
     out-of-bounds key, a wrong type, a malformed config file, and `capS` refusing a value above
     14400.

3. **Caller-owned hard tier and user notice** (QTA-08).
   - Current: one cooldown value (`retry_after_s=600`); the review orchestrator re-invokes once
     (25-10); the execute skills have no re-invoke loop after the owner decision.
   - Target: when the runner exits 75 with `retry_after_s`/`cycle`, the caller (the
     `ai-kit-spec-review` and `ai-kit-spec-execute*` skills, and an orchestrating agent following
     the policy reference) re-invokes the same lane, same CLI and model, once per entry of
     `hard_waits_s` (default 600, 900, 1800 s), as one-shot waits. `retry_after_s` on cycle n is
     `hard_waits_s[n]`. After the last entry fails, or at the 4-hour cap, the caller notifies the
     user with the evidence report and stops that lane. Nothing switches harness, provider or
     model (owner rule, reconfirmed 2026-10-24: never, only notify).
   - Acceptance: self-tests show cycle 0, 1, 2 printing `retry_after_s=600`, `900`, `1800` and
     the next re-invoke exiting 69 with `stopped=hard-waits` (or `stopped=cap` when the cap
     comes first); the skills' text tests pin the re-invoke rule, the notice and the absence of
     any model or harness switch.

4. **Upstream error pass-through** (QTA-09).
   - Current: the report names the class, status, pattern and times; the upstream text is not
     carried as such.
   - Target: the evidence report carries the upstream error as received — the matched error
     line or JSON object, not the whole stderr — redacted (keys, tokens, account and connection
     ids removed) and capped at 2000 characters. Structured retry fields the upstream sent
     (`retry_after`, `reset_at`, `retry_after_seconds`, `resetsAt`) are copied as-is into the
     report, labelled `upstream`. The runner never parses free-text reset times and never
     changes its own waits from upstream fields; the waiting harness or agent may use them and
     flags its inference.
   - Acceptance: fixtures from `25.1-EVIDENCE.md` (the router 429 `ALL_TARGETS_SKIPPED`, the
     router 402 with `retry_after` 120, the Kimi 403, the GLM 1310 body) produce reports
     containing the redacted body and the upstream fields verbatim, with identical runner waits
     whether or not the fields are present; a sentinel key and a connection id in a fixture body
     never appear in the output.

5. **Evidence-labelled error catalog** (QTA-10).
   - Current: the Phase 25 pattern table has per-CLI rows for the bodies captured until
     2026-10-24 morning; OmniRoute reason codes and the evidence samples above are not rows.
   - Target: the catalog is data the owner can extend without code changes (pattern, route,
     provider, class, verified/unverified, source). It holds OmniRoute's reason codes as rows of
     their own, apart from the provider bodies passed through OmniRoute, and every sample in
     `25.1-EVIDENCE.md` as a fixture. A status code alone never decides a class: a bare-code row
     matches only after every body row (25 D-03 order kept).
   - Acceptance: each evidence fixture classifies to its expected class (the Kimi 403 5-hour
     limit is a quota-class row, not auth; the router 402 with a reset is router quota, not
     billing, on a confirmed router route — *amended 2026-10-24, D-15*: on a `router-inferred` route it
     stays billing, per the 25 cycle-1 ruling); a catalog row with an unknown class or a missing label is refused by the
     self-test; `--classify-only` reports the matched row id and its label.

6. **One runtime per call** (QTA-11).
   - Current: `--prefer a,b,c` and `CONFIG.prefer` are lists; only the first entry runs.
   - Target: the runner takes `--runtime <id>`; `--prefer` stays accepted and reads only its
     first entry (any further entries print a one-line notice that they are ignored);
     `CONFIG.runtime` replaces `CONFIG.prefer` in rendered copies, and old copies with
     `prefer` still run its first entry. `runner_dispatch.py`, the curated-config command
     builder and the skills pass `--runtime`. Changing the runtime is an edit of the config that
     calls the runner, done by the agent; the runner never chooses another one.
   - Acceptance: self-tests for `--runtime`, `--prefer a,b` (runs a, prints the notice, never
     starts b), a rendered copy with only `prefer`, and an unknown runtime (exit 2); the Python
     dispatch test asserts the `--runtime` argv.

## Boundaries

**In scope:**
- The runner template's ladder, config reading, catalog rows, report and runtime flag, with
  self-tests.
- The callers' hard-tier re-invoke and user notice in the review and execute skills and the
  policy reference.
- The producers of the runtime flag (`runner_dispatch.py`, the curated-config command builder).
- Re-rendering the dogfood runner; README and skill docs.
- The `ai-kit-cross-ai` skill and the pointers to it from the listed skills (R8).
- `--model`, `--tools-profile` and the per-runtime validation in the runner (R9).
- The `copilot` runtime rows, unverified, with fake-CLI tests (R10).

**Out of scope:**
- Parsing free-text reset times in the runner — owner decision 2026-10-24: pass the upstream
  error through; the waiting harness infers.
- Switching harness, provider or model on failure, or an allowlist for it — owner decision
  2026-10-24: never, only notify.
- The orchestrating session's own quota wake (reset + 60 s, surviving timers) — Phase 26
  (QTA-04, amended 2026-10-24).
- Changing OmniRoute's behavior or config (combo strategy, `context_cache_protection`) — owned
  by llm-env.
- A live Copilot run — no model call is made here (the CLI is installed since 2026-10-25, but a
  real capture is the owner's); the rows stay unverified until then.
- An idle watchdog — the runner's heartbeat logs progress; a stall is the caller's call (R8
  documents how to read it).
- Reading OmniRoute's database or credentials — they hold provider keys; evidence comes from
  logs and the CHANGELOG only.

## Constraints

- The runner stays a single Node file with no dependencies; the Python side stays stdlib-only.
- The runner self-test keeps running under 180 s; soft waits in self-tests use an injected
  clock.
- Config reads never follow a path outside the project's `.planning` tree or the user's
  ai-kit config dir; a config file never makes the runner run another command.
  *(Amended 2026-10-25: the `cross_ai_timeout` read keeps following a symlinked `.planning/config.json`,
  for parity with gsd-tools `config-get` and Phase 25 behavior; the retry config and the catalog
  overlay reads are confined.)*
- Every evidence body in tests is synthetic or redacted; sentinel keys are built at run time.
